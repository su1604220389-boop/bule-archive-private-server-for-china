# 92 — 洞状态迁移到 RW 段（修 `libil2cpp_hook.bin` 的写权限 bug）

> 交付物：`work\ba\runtimehook\libil2cpp_hook_v2data.bin`

> 源码目录 `work\ba\runtimehook\cave_m1\`（**另起目录**，没有改动 `cave/` 与 `build.py`，不覆盖别人正在改的东西）

## §1 根因

### 1.1 一句话

**洞把「跨调用状态」放进了自己所在的 RX 页**：`cave.ld` 里 `*(.data*)` 把 `g_skip / g_tick / g_orig /
g_argc / struct g` 全部并进了 `.cave`，而 `.cave` 链接在 `0xF2C2410` —— 那是 RX PT_LOAD #2 的最后一页。

### 1.2 现场三件套

| 证据 | 内容 |
|---|---|
| 链接脚本 | `cave\cave.ld:15-21`：`.cave : { *(.text.cave_entry) *(.text*) *(.rodata*) *(.data*) }`，`. = 0xf2c2410` |
| 真正写全局的地方 | `cave\hook.S:69` `str w17,[x16,:lo12:g_tick]`；`logic.c:61-64,119` 的 `g_skip/g_tick/g_orig/g_argc/g` |
| 真机崩溃 | `pc = 0x72cdd3c43c`、`fault addr = 0x72cdd3cf08`、`code 2 = SEGV_ACCERR (write)` |

复核结果（与任务书一致，且**补上了一个更强的推论**）：

* 洞页基址 `0x72cdd3c000` → `pc` 在页内 `+0x43C`；洞首在页内 `+0x410`，所以 `pc = 洞 + 0x2C`。
* 反汇编 v1 的 `cave/hook.bin`，`0xF2C2410+0x2C = 0xF2C243C` 正是
  `str w17, [x16, #0xf08]`，目标 `0xF2C2000+0xF08 = 0xF2C2F08 = g_tick`
  —— 和 tombstone 的 fault addr `0x72cdd3cf08`（页内 +0xF08）**逐字节对得上**。
* ★ **关键推论**：崩溃点在**触发器**里，而触发器只有在 `g_skip == 0` 时才会走到那条 `str`
  （`hook.S:64-69` 先 `ldr w16,[g_skip]; cbnz w16, replay`）。`g_skip = 0` 是 `cave_main`
  在 mprotect **成功**分支里写的（`logic.c:353`）。而真机日志里确实有 `B0` 行
  （`B0` 的第四参数 = `0x72cdd3c000` = 洞页基址），`B0` 只在 mprotect 成功分支里打。
  ⇒ **mprotect 当时是成功了的**：`DL_INIT` 期间洞页确实被写成了 RW，`g.base/g.fd/g_skip` 都写进去了；
  **可到了触发器执行时，这一页又变回 R-X 了**。
* 所以 v1 的 bug 不是「漏了 mprotect」，而是**「写权限不持久」**。谁在中间把权限改回去，
  静态手段查不到（ACE/libtprt 的页保护、或它重映射 RX 段——**未确定**）。
  这恰恰是「别再依赖改权限，把状态搬走」的理由。

### 1.3 结论

洞所在页的权限不由我们掌控；**任何依赖「这一页被我 mprotect 成可写」的设计都不成立**。
唯一稳的路是：让洞对「可写」的依赖只剩一次，且这次发生在**本来就可写**的段里。

## §2 空隙归属核实结果（决定方案可行性的一步）

### 2.1 实测的 program header（`work\ba\bapatch\libil2cpp.bin`，sha256 = `5ac1cbe0…`，原厂基线）

```
#   type      flg  p_offset     p_vaddr      p_filesz     p_memsz      align
1   LOAD      R    0x0          0x0          0x59b4e54    0x59b4e54    0x4000
2   LOAD      RX   0x59b8000    0x59b8000    0x990a410    0x990a410    0x4000   ← 洞在这里
3   LOAD      RW   0xf2c4000    0xf2c4000    0x8ec868     0x8ec868     0x4000   ← ★ 整段在 RELRO 里
4   LOAD      RW   0xfbb4000    0xfbb4000    0x6974f8     0x8ddd58     0x4000
6   GNU_RELRO R    0xf2c4000    0xf2c4000    0x8ec868     0x8f0000     0x1      ← [0xF2C4000, 0xFBB4000)
10  LOAD      RX   0x1024c000   0x10494000   0x3370       0x3370       0x4000
11  LOAD      RW   0x1024c000   0x10498000   0x3660       0x4000       0x4000
12  LOAD      RW   0x1024c000   0x1049c000   0x4470       0x447d       0x4000
13  LOAD      RW   0x10250000   0x104a4000   0xfe90       0xfe90       0x4000   ← 数据段最终落这里
```

`.dynamic` 里：`DT_INIT = 0x10496434`、`DT_FLAGS = 0x8`（**DF_BIND_NOW**）、`DT_FLAGS_1 = 0x1`（NOW）、
`DT_SYMTAB = 0x104a4470`（落在 #13 内）。

### 2.2 问题一：`[0xF2C2410, 0xF2C3FFF]` 到底归谁？

| 子区间 | 4 KB 页假设 | 16 KB 页假设 | 结论 |
|---|---|---|---|
| `[0xF2C2410, 0xF2C3000)` | RX 段映射的最后一页（filesz 只到 `0xF2C2410`，内核按页映射，整页仍是 R-X） | 同上（且整页属于 RX 段） | **R-X，只读** |
| `[0xF2C3000, 0xF2C4000)` | 这一页**不属任何 PT_LOAD** → **未映射**（`SEGV_MAPERR`） | 落在 RX 段映射的最后一页（`p_align=0x4000`，映射收在 `0xF2C4000`）→ **R-X** | **要么未映射、要么只读，永远不是 RW** |

文件侧：`[0xF2C2410, 0xF2C4000)` 共 **0x1BF0 = 7152 B，全部是 0x00**，且**不被任何 SHF_ALLOC 节覆盖**
（`.plt` 正好收在 `0xF2C2410`，`.data.rel.ro` 从 `0xF2C4000` 起）。它就是链接器给 16 KB 页对齐留的文件 padding。

⇒ **任务书里「如果 `0xF2C3000` 这一页也归 RW 段，那就很简单」这条路不成立**：
`0xF2C4000` 是 16 KB 对齐边界，`0xF2C3000` 既不是 RW 段的起点，也不在 RW 段的映射里。

### 2.3 问题二：任务书里说的「RW 段 `0xF2C4000`」运行时到底可不可写？——**不可写**

`GNU_RELRO`：`p_vaddr = 0xF2C4000`、`p_memsz = 0x8F0000` → 覆盖 `[0xF2C4000, 0xFBB4000)`。
而 `PT_LOAD #3` 恰好就是 `[0xF2C4000, 0xFBB0868)` —— **整段都在 RELRO 里**。
加载器在重定位完成后会对 RELRO 区域做 `mprotect(…, PROT_READ)`；本库 `DT_FLAGS=0x8`（BIND_NOW），
所以把 `.got.plt` 一起锁死是安全的，加载器会照做。

⇒ **把 `.cave_data` 放到 `0xF2C4000` 附近 = 又一次只读写崩**。
（旁证：report/10 的 C5 项「运行时 mprotect + 写 libil2cpp 自己的 GOT」也是 `SEGV_ACCERR (write)`，
与本条一致 —— 那条 GOT 在 RELRO 里。）

### 2.4 真正可写的窗口在哪

把三个 RW 段逐个查「有没有既在 `p_filesz` 内、又不被任何 SHF_ALLOC 节覆盖、又不在 RELRO 里」的空档：

| 候选 | VA 区间 | 长度 | 结论 |
|---|---|---|---|
| **PT_LOAD #13 尾部 padding** | `[0x104B3DD0, 0x104B3E90)` | **0xC0 = 192 B** | ★ 选中。#13 flags=6（RW）、不在 RELRO、`.dynsym` 正好结束在 `0x104B3DD0`、文件里这 192 B 全 0 |
| PT_LOAD #11 的 bss 尾 | `[0x1049B660, 0x1049C000)` | 0x9A0 | 备选（无文件字节，靠 bss 零填） |
| PT_LOAD #12 的 bss 尾 | `[0x104A0470, 0x104A047D)` | 0xD | 太小 |
| PT_LOAD #3 filesz 之后 | `[0xFBB0868, 0xFBB4000)` | 0x3798 | ✘ 不属任何段的 memsz（4 KB 下未映射），且在 RELRO 覆盖范围内 |
| RX 洞页尾部 | `[0xF2C2410, 0xF2C3000)` | 0xBF0 | ✘ R-X |

选 `#13` 的额外理由：`DT_SYMTAB = 0x104A4470` 就落在 `#13` 里，动态链接器**必须**映射它，
所以「#13 没有被映射」这种失败模式基本不可能；而且 `0x104B3DD0` 正好是 `.dynsym` 的结束地址
（`0x104A4470 + 0xF960`），也就是「被用过的东西之后的纯 padding」，语义上最干净。

## §3 采用的方案与理由

**方案 ①（把可写全局链接进 RW 段）**，落点是 `PT_LOAD #13` 的尾部 padding。

* `.cave`（代码 + 只读常量）仍然链接在 `0xF2C2410`，**保持 R-X，不再 mprotect 它**。
* 新增输出段 `.cave_data`，链接在 **`0x104B3DD0`**，运行时 = `base + 0x104B3DD0`，可写。
* 段间距 `0x104B3DD0 - 0xF2C2410 = 0x11F1 9C0`（≈18.8 MB），`adrp/add :lo12:` 的 ±4 GB 绰绰有余，
  且链接期算好立即数 ⇒ **零重定位、零 GOT**（见 §4.5）。
* 段内布局（120 B / 192 B）：

| 符号 | VA | 大小 | 含义 |
|---|---|---|---|
| `g_arm` | `0x104B3DD0` | 4 | **0 = 未武装**（极性反转，见下） |
| `g_tick` | `0x104B3DD8` | 4 | 触发器计数（asm 自增） |
| `g_orig[4]` | `0x104B3DE0` | 32 | 原 methodPointer |
| `g_magic` | `0x104B3E00` | 8 | M0/M1 的读写探针 |
| `g_argc[4]` | `0x104B3E08` | 16 | 目标的形参个数 |
| `g`（struct st） | `0x104B3E18` | 48 | base / t0 / fd / attempts / done / nclass / nmeth / found / in |

安全性设计（这是本版与 v1 最重要的行为差异）：

1. **看门狗极性反转**：`g_skip`（1=停）→ `g_arm`（**0=停**）。
   数据段的文件初值天然是全零 ⇒ 只要链接/加载有任何问题，触发器**自动落回「只回放、不写内存」**。
2. **不再 mprotect 洞页**：洞里已经没有跨调用状态，RX 页只读正合适。
   （`install()` 里对 game 侧 `MethodInfo` 槽的 mprotect 保留 —— 那是 game 数据，不是 `.text`。）
3. **数据段可写性只赌一次，而且这次会被记进日志**（M0/M1，见 §4.6）。

未被采用的方案：

* 方案 ②（运行时 mmap）：`MAP_FIXED` 到空档有价值，但（a）`0xF2C3000` 在 16 KB 页设备上会覆盖 RX 段最后一页，
  （b）`MAP_FIXED_NOREPLACE` 失败时「武装标志放哪」回到同一个鸡生蛋问题（只能放可写内存，而它正是没拿到的那块）。
* 方案 ③（mprotect 洞页）：v1 已经证明**权限会被环境改回去**，等于没修。

### 4.5 自包含性（这条抓出了一个**会毁掉整轮实验**的真 bug）

* 洞内 **108 处**指向本页的引用（`adr` / 分支 / 常量池读写）**全部落在 blob 之内** —— 没有一处指到页内 padding。
* 构建期硬性校验：链接产物只允许 `.cave` 与 `.cave_data` 两个可分配节。

  > 为什么加这条：本版第一稿（sha `543a29…`，**已作废**）里，`extern char __c_data_start[]` 与
  > `extern void hitX_entry(void)` 都是「外部符号」，clang 走了 **GOT**，lld 把 6 个 GOT 槽放在
  > `0xF2C2FC0..0xF2C2FF0`（**恰好在 `.cave` 之后、objcopy 带不走的页内 padding 里**）。
  > 成品里那 6 个槽全是 0 ⇒ 运行时 `&hitN_entry` 全读成 0，`*slot` 会被写成 NULL。
  > 修法：extern 声明加 `__attribute__((visibility("hidden")))`，数据段边界改用编译期常量
  > （不再引用链接脚本符号），并把「只剩两个可分配节」变成构建时的硬检查。
  > 同类坑在 v1 的 `hook.elf` 里没有（实测 v1 只有 `.cave` 一个节）。

### 4.6 新增诊断日志（M0 / M1）

`cave_main` 一进来（在**任何**「假设数据段可用」的访问之前）就按下面顺序打三行，
写入 `/data/data/com.RoamingStar.BlueArchive/files/probe.log`：

```
M0 D <数据段运行时地址> <写前读回值>      ← 读成功才打；读崩 = SEGV_MAPERR
M1 D <数据段运行时地址> <魔数读回值>      ← ★ 判定行：值 == 4d3144415441a5a5 即「数据段可写」
B0  <base> <fd> <CAVE_VA> <数据段地址>   ← 原有的 B 行，第四参数现在直接给数据段地址
```

* `M0/M1` 用**局部 fd** 直写，不经过 `g.fd`（数据段还没被证明可用之前不能碰它）。
* 魔数 `0x4d3144415441a5a5` = ASCII `M1DATA` + `0xA5A5`。
* 只有 `M1` 校验通过且日志 fd 有效，才会 `g_tick=1; g_orig=…; g_arm = 1`（武装）；
  否则 `g_arm` 保持 0，触发器只回放 —— **失败是「静默不观测」，不是「崩游戏」**。

### 5.2 M 行判读表（**先看 `M1`，再看 `B0`**）

| `probe.log` 里看到什么 | 含义 | 下一步 |
|---|---|---|
| `M1 D <addr> 4d3144415441a5a5` | ★ **机制生效**：数据段在 `base+0x104b3dd0` 上确实可写可读 | 看 `B0` 第四参数是否等于 `M1` 的 `<addr>`；再看后续 `S*/R*` 有没有扫描记录 |

| **连 `M0` 都没有** | 读数据段时就崩（`SEGV_MAPERR`：地址没映射） | 说明 #13 没被映射（§6-E3），改用 #11 bss 尾做备选落点 |
| `M0` 有、`M1` 的 `<addr>` 与 `B0` 第四参数不一致 | 两次取址不一致（几乎不可能） | 记录两个值，先别改代码 |
| `M1` 值 ≠ 魔数 | 内存是「洞」（写入不落盘/被清零） | 同上，取 tombstone |
| `M1` 正确但完全没有 `B0` | 说明在 `M1` 之后、`B0` 之前出错（`clock_gettime`/算术） | 取 tombstone |

## §6 若仍崩，下一个怀疑点

按「已经证伪过什么」排序，**先查 M1，再按下面顺序走**：

**E1. 触发器 16 字节跳板被 ACE 解密覆盖（最可能）**
洞本身不进 `.text` 的加密页，但 `0x63C77FC` 在 `il2cpp` 节里。若 ACE 在运行期解密/重写该页，
文件里那 16 字节跳板会被原始字节盖掉 ⇒ 触发器根本不进来（现象：`M1/B0` 正常、`S*` 一条没有）。
查法：真机上在 `0x63C77FC` 处 dump 16 字节，和成品文件比对。若被覆盖，就要换「只在数据侧生效」的触发时机
（例如不再 hook 函数入口，而是把扫描挂到 `DT_INIT` 之后某个必被调用的导出函数）。

**E2. `M1` 缺失（写数据段 `SEGV_ACCERR`）**
说明 #13 那页被映射成只读。备选落点已经探明：`PT_LOAD #11` 的 bss 尾 `[0x1049B660, 0x1049C000)`（0x9A0 B，
不在 RELRO、不被任何节覆盖）。改法是只改链接脚本里的 `0x104b3dd0` 常量和构建器的 `DATA_VA`。

**E3. `M0` 缺失（读数据段 `SEGV_MAPERR`）**
说明 #13 没被映射。理论上不该发生（`DT_SYMTAB` 就在里面），若真发生，
优先怀疑「加载器只映射了 #1~#4 这四条主段」——那就只能退到 #11 bss 尾（同 E2 的改法），
或者退到方案 ②（`MAP_FIXED_NOREPLACE` 到 `0xF2C3000`，但**必须先用 auxv 读 `AT_PAGESZ` 确认是 4 KB 页**）。

**E4. `M1` 正常但 `install()` 报 `!` 行（mprotect 失败）或 `*slot` 写崩**
`MethodInfo` 可能落在只读页（例如 `.data.rel.ro` / RELRO）。此时现象是 `R*` 行里 `found` 一直是 0。
下一步改成「不写 methodPointer，只读 metadata 内存」的纯观测版。

**E5. `S*` 有了、`R*` 里 `found` 恒 0**
说明 `il2cpp_class_for_each` / `il2cpp_class_get_methods` 的偏移或签名与本包不符（`nclass` 会给出线索：
`nclass=0` ⇒ `for_each` 没回调；`nclass>0 但 nmeth=0` ⇒ `get_methods` 不对）。
这两个偏移来自导出桩，换版本要重新核对。

**E6. 日志 fd 打不开**
`fd < 0` 时本版**不武装**（静默不观测），不会崩。此时 `probe.log` 是空的，需要先确认
`/data/data/com.RoamingStar.BlueArchive/files/` 可写、SELinux 上下文正确。
