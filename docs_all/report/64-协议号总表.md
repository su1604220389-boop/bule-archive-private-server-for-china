**结论：11 个锚点中 10 个逐位一致，1 个存在真实差异。**

| 差异项 | Shittim | 国服 | 差值 | 定性 |
|---|---|---|---|---|
| `Account_LoginSync` | 1019 | **1017** | **-2** | 国服 Account 段在 LoginSync 之前比 Shittim 少 2 条协议，其后同段协议整体前移 2 |

**这不是提取误差，是国服与 Shittim 的真实差异。** 依据：

1. 国服 `Protocol` 枚举在 Account 段内**完全连续**（1000,1001,…,1021 无跳号），解码结果里没有任何 +2 跳变；
2. 若国服有「缺 2 条但保留原号」的空洞，解码值会在 `Account_InvalidateToken`(1016) 之后跳到 1019，实测没有，说明国服这份枚举是从 1000 起重新连续编号的；
3. 其余 10 个锚点（含跨 5 个不同号段）全部精确命中，说明解码规则本身正确。

> 实务影响：**整数号不上线路**（HTTP 上的 `protocol` 字段是 base32 token，见 §1.3），所以 1017/1019 的差异不影响联调；但如果你按 Shittim 的号写服务端内部索引，Account 段会整体错位 2。

### 0.2 base32 token 的算法（3 组真值全中）

| 协议名 | 真实抓包 token | 本地推导 | 结果 |
|---|---|---|---|
| `Account_Auth` | `AHTQLQI65FWJGGGK4KL5AEF57A` | `AHTQLQI65FWJGGGK4KL5AEF57A` | ✅ |
| `Account_Nickname` | `GVDSNCHUMIOS44NDTZM6ZPDDVQ` | `GVDSNCHUMIOS44NDTZM6ZPDDVQ` | ✅ |
| `Account_LoginSync` | `P3OMQZD2FXV7XXEGA7ETCXIJ4Q` | `P3OMQZD2FXV7XXEGA7ETCXIJ4Q` | ✅ |

算法（已实证）：

```
token = base32( MD5( UTF-16LE(协议名字符串) ) )   # RFC4648 字母表 A-Z2-7，去掉尾部 "="
```

26 个字符 = 16 字节 MD5 的 base32 编码长度（128 bit → 26 字符，末字符带 2 bit 填充），长度自洽。

**号段规律（重要）**：

* 主体是 **1000 一段**，段基址 = 段序号 × 1000：Account 1000, Character 2000, …, Shop 10000, MemoryLobby 12000, CumulativeTimeReward 13000, OpenCondition 15000, …, PermanentRaid 54000。
* **14000 段空缺**（13000 CumulativeTimeReward 直接跳到 15000 OpenCondition）——国服没有 14000 段的协议，但服务端若按段号推断，14000 应视为已保留/已下线。
* **55000 – 89999 全空**，然后接 **90000 段**：这是后期补丁追加的「杂项/新功能块」（Log 测试协议、Management/Order/Battle/Survey/Web 通知、Clan 聊天、Shop 教学抽卡）。
* 因此：**新协议若在 1000–54000 内找不到号，一定在 90000 段**。

## §2 提取方法（可复现）

### 2.1 定位 `Protocol` 枚举（不依赖类型名解码）

```powershell
cd C:\Users\su\Desktop\大肥鱼项目\BAServer
python report\_tmp\proto\s1_locate_enum.py
python report\_tmp\proto\s2_dump_enum.py
```

* `s1`：从 `string` 堆 `0x22D902` 起按 NUL 切出连续协议名块（431 条），拿它们的 `nameIndex` 序列去 `fields` 表里找连续 run。
  **结果：`fields[48892 .. 49393)`，owner = type#10770 `MX.NetworkProtocol.Protocol`**，`fields_start=48891`（含 `value__`），成员 `typeIndex` 全为 56580。
* `s2`：把这 501 个 `fieldIndex` 拿去 `fieldDefaultValues` 表查 `(typeIndex, dataIndex)`，**501/501 全部命中**（说明枚举常量值确实在这张表里，而不是被裁掉）。

### 2.2 解码常量值（本次真正的难点）

```powershell
python report\_tmp\proto\s7_final_decode.py    # 输出 s7_decoded.json + 11 锚点自校验
```

`fieldAndParameterDefaultValueData`（偏移 `0x12CB1D8`）里，每个成员一条记录，**两种宽度**：

```
stride = 下一条.dataIndex - 本条.dataIndex
# stride == 2 ：记录 = u16 value（大端）                     —— Account..Mission 这 9 段
# stride == 4 ：记录 = [u16 tag(小端)] [u16 value(大端)]      —— 其余段

id = (value & 0x7FFF) / 2                        # stride==2
id = value / 2 + block * 32768                   # stride==4，block = (tag - 0x00C0) / 0x100
```

实证链路：

1. 4 字节记录里 `tag` 只有 3 个取值：`0x00C0`(block 0) / `0x01C0`(block 1) / `0x02C0`(block 2)，且切换点正好在第 32768 个号附近（MomoTalk 33000）和 90000 处；
2. 用 `tag` 定 block 后，`Cafe_Get`(block 0) = 20000、`Attachment_Get`(block 1) = 46000 **两个锚点同时命中**；
3. 2 字节记录里的 `0x8000` 位是标记位（该段 id 都 < 16384），剥掉后 Account..Mission 全部对齐 1000/2000/…/8000 段基址；
4. 全表 493 个号严格单调递增、无重复，且 66 个段基址全部落在整千上（唯一的 90000 段是追加块）。

### 2.3 反推 base32 token

```powershell
python report\_tmp\proto\s3_token.py       # 256 组变体暴力：3/3 命中 md5+base32
```

试过的变体：MD5/SHA1/SHA256/SHA512/BLAKE2/ SHA3 × {ASCII, UTF-16LE, UTF-16BE, 带 NUL, 小写, 大写, 加 `MX.NetworkProtocol.` 前缀, 下划线换 `/`/`.`/删掉} × 截断 {16,20,32} 字节。

## §3 不确定项与假阴性风险

### 3.1 已确证 vs 推断

| 项 | 置信度 | 依据 |
|---|---|---|
| 501 个成员名单、顺序 | **确证** | fields 表连续 run + `Protocol` 类型名/命名空间可读 |
| 493 个整数号 | **确证** | 10/11 锚点命中 + 全表单调连续 + 段基址整千 |
| 3.2 的 90000 段归属 | **推断（高）** | block tag 规则外推，见下 |
| token 算法 | **确证** | 3/3 真值逐字符一致，256 变体中唯一全中 |
| Request/Response DTO | **部分确证** | 433 条同名精确命中；62 条未命中（见 3.3） |

### 3.2 90000 段的两种可能（`TutorialGacha` 的号）

4 个 TutorialGacha 在枚举最末尾（成员 #497–#500），属于后期补丁追加。解码时存在两种自洽解：

| 解 | 4 个号 | 依据 |
|---|---|---|
| **A（本表采用）** | **90011 / 90012 / 90013 / 90014** | `tag=0x02C0` → block 2，id = value/2 + 2×32768；block 0/1 分别被 `Cafe_Get`=20000、`Attachment_Get`=46000 两个锚点证实 |
| B | 57243 / 57244 / 57245 / 57246 | 只按「单调递增、取最小可行解」解包 |

我选 A 的理由：`tag` 字段不是随机的，它随 id 跨 32768 边界**恰好**在 0x00C0/0x01C0/0x02C0 之间切换，且切换点与 33000、90000 对得上；B 解会让末尾 6 条（`Clan_Chat_Records`、`Clan_Send_Chat`、4 个 TutorialGacha）落在 57241–57246 这种非整千基址上，与其余 66 个段「一律整千」的规律不符。

> **联调时以 token 为准，不依赖这个号**：token 是唯一上线路的标识，4 个 TutorialGacha 的 token 见 §1.3（`QQAWTCO7TMCITQPOWS7PIBYLCQ` 等），与号无关。

### 3.3 DTO 命中率

62 条协议没有同名 `{Name}Request` / `{Name}Response`，原因是客户端里 DTO 命名不完全规则，例如：

* `Cafe_Get` → `CafeGetInfoRequest` / `CafeGetInfoResponse`（名字里多了 `Info`，本表已按前缀兜底命中）
* `Equipment_List` → 只有 `EquipmentItemListResponse`，Request 侧在客户端被裁掉/改名

本表的 DTO 列规则：先精确匹配 `{Name去掉下划线}Request`，不中则取「以该前缀开头、以 Request 结尾」的最短类型名。
`protocol_map.json` 里每条都带 `dto_match`（`exact` / `fuzzy` / `none`）可自查。**未命中的不要当不存在**，只是名字不同或被裁剪——用 `lookup.py find <关键字>` 或直接搜 `s9_typenames.json` 更快。

### 3.4 前 8 个「伪成员」没有整数号

`Common_Cheat` `Error` `None` `System_Version` `Session_Info` `NetworkTime_Sync` `NetworkTime_SyncReply` `Audit_GachaStatistics` 这 8 个用的是 1 字节记录（stride=1），编码形态与主表不同，本次**没有解出**，表中标 `—`。

从原始字节可读出它们的前缀值 `01 00 02 04 06 08 0a`（对应 Error=None… 顺序），按 `value/2` 推断 `None=0, System_Version=1, Session_Info=2, NetworkTime_Sync=3, NetworkTime_SyncReply=4, Audit_GachaStatistics=5`，但**这是推断不是提取**，所以没写进 JSON 的 `id` 字段。

### 3.5 假阴性风险

1. **`md_deob.bin` 只解了「头部 XOR 0x66 + 每 64KB 的 [0x1000,0x5000) 段 XOR 0x66」，没解逐串随机单字节 XOR。**本表所有类型名/字段名都是用「256 个 key 逐个试 + 结果必须是合法标识符」解出来的（35,105 个类型解出 34,849 个，**256 个仍失败**），所以 DTO 列存在少量假阴性。
2. 判「字符串不存在」时不要用 `md_deob.bin` 直接 find，要用反向搜索法（`s27_revsearch.py`）。
3. `Protocol` 枚举只有一份（`MX.NetworkProtocol.Protocol`，type#10770）；若后续版本新增枚举副本，需重跑 `s1`。
4. 号段表里 `Clan` 出现两次（28000 段与 90009 段）、`Shop` 出现两次（10000 段与 90011 段），这是枚举里**真实的重名段**（后期追加的 Clan 聊天 / 教学抽卡），不是解析错误。
