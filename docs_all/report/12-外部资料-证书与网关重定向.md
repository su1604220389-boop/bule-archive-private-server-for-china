## A. Android 14–17 上装系统 CA 的正确做法

### A.1 结论一句话
**往 tmpfs 里写文件「不够」；`mount -t tmpfs` 挂到 `/system/etc/security/cacerts` 只是准备一个可写源目录，真正生效的动作是「用 `nsenter` 进 zygote 和每个 app 的 mount ns，把该目录 bind mount 到 `/apex/com.android.conscrypt/cacerts`」。**

### A.2 为什么必须 nsenter（原文，这是原理但必须知道，否则会做错）

[HTTP Toolkit: New ways to inject system CA certificates in Android 14](https://httptoolkit.com/blog/android-14-install-system-ca-certificate/)（**2023-09-21**）【一手】原文：

> - In Android 14, system-trusted CA certificates will generally live in `/apex/com.android.conscrypt/cacerts`, and all of `/apex` is immutable.
> - That APEX cacerts path **cannot be remounted as rewritable** - remounts simply fail. In fact, **even if you unmount the entire path from a root shell, apps can still read your certificates just fine**.
> - **The alternative technique of mounting a tmpfs directory over the top also doesn't work** - even though this means that `ls /apex/com.android.conscrypt/cacerts` might return nothing (or anything else you like), **apps will still see the same original data**.

> The `/apex` mount is explicitly mounted with **PRIVATE propagation**, so that all changes to mounts inside the `/apex` path are never shared between processes.
>
> That's done by the `init` process ... which then launches the **Zygote** process (with a new mount namespace copied from the parent, so including its own private `/apex` mount), which then in turn starts each app process.

**⇒ 直接回答 Lead 的问题：**
| 问题 | 答案 |
|---|---|
| 往 `/apex/.../cacerts` 的 tmpfs 里写文件够不够？ | **不够**。app 走自己的 mount ns，看不到。 |
| 要不要 `stop`/`start` 服务？ | **不需要**。正常做法是 nsenter 到 zygote + 各 app ns 逐个 bind mount（并行，<1 秒）。 |
| 要不要重启？ | **不需要重启**，但要 **force-stop 目标 app 再启动**（让它从 zygote fork 出新 ns）。 |
| `update-ca-certificates` 等价物？ | **没有**。Android 不做 CA 索引重建，只认文件名 `<subject_hash_old>.0` + 权限 + SELinux label。 |
| 会不会影响已运行的 app？ | **会**。已运行的 app 必须逐个 nsenter 注入（或直接 force-stop 让它重开）。 |
| 掉电/重启后还在吗？ | **不在**，是内存态，重启即失效。开机脚本要重跑。 |

### A.3 可直接抄的完整命令序列（root，无 Magisk 模块，纯 shell）

核心脚本来自 HTTP Toolkit 同文，我把「只针对一个 app」的瘦身版整理如下（**这就是你们要的"只有 root、脚本化"版本**）：

```bash
#!/system/bin/sh
# ---- 0. 准备：cert 必须是 DER，文件名 <subject_hash_old>.0 ----
# 宿主机上：
#   openssl x509 -in ca.pem -inform PEM -subject_hash_old -noout      # 得到 8位hash
#   openssl x509 -in ca.pem -outform der -out <hash>.0
#   adb push <hash>.0 /data/local/tmp/
CERT=/data/local/tmp/你的HASH.0

# ---- 1. 先把现有证书拷出来（关键！挂上 tmpfs 后原目录就读不到了）----
mkdir -p -m 700 /data/local/tmp/tmp-ca-copy
cp /apex/com.android.conscrypt/cacerts/* /data/local/tmp/tmp-ca-copy/

# ---- 2. 在 /system/etc/security/cacerts 上建可写 tmpfs 作为「源」----
mount -t tmpfs tmpfs /system/etc/security/cacerts
mv /data/local/tmp/tmp-ca-copy/* /system/etc/security/cacerts/
cp "$CERT" /system/etc/security/cacerts/

# ---- 3. 权限 + SELinux label（缺一不可）----
chown root:root /system/etc/security/cacerts/*
chmod 644 /system/etc/security/cacerts/*
chcon u:object_r:system_file:s0 /system/etc/security/cacerts/*

# ---- 4. 注入 zygote（新启动的 app 会继承）----
ZYGOTE_PID=$(pidof zygote  || true)
ZYGOTE64_PID=$(pidof zygote64 || true)
for Z_PID in "$ZYGOTE_PID" "$ZYGOTE64_PID"; do
  [ -n "$Z_PID" ] && nsenter --mount=/proc/$Z_PID/ns/mnt -- \
      /bin/mount --bind /system/etc/security/cacerts /apex/com.android.conscrypt/cacerts
done

# ---- 5. 注入所有已在运行的 app（并行）----
APP_PIDS=$(echo "$ZYGOTE_PID $ZYGOTE64_PID" | xargs -n1 ps -o 'PID' -P | grep -v PID)
for PID in $APP_PIDS; do
  nsenter --mount=/proc/$PID/ns/mnt -- \
      /bin/mount --bind /system/etc/security/cacerts /apex/com.android.conscrypt/cacerts &
done
wait
echo "System certificate injected"
```

然后：`am force-stop com.RoamingStar.BlueArchive` → 重新启动游戏。

> ⚠️ 注意：第 5 步会动 **system_server** 所在的 ns 里的挂载，**部分机型会软重启（soft reboot）**。如果遇到，只做第 4 步（仅 zygote）+ force-stop 目标 app 即可。

### A.4 更稳的变体：只注 init + zygote（推荐给 KernelSU 环境）

[Karoliukas29/android14-trust-ca](https://github.com/Karoliukas29/android14-trust-ca)（README 提交 **2026-07-26**，实测 Pixel 7 / Android 16 / Magisk 30.7）【一手】：

> The script stages a fresh copy of the on-disk system certs **plus your CA** into a labelled `tmpfs` directory, then **bind-mounts that over the APEX `cacerts`** — but only inside the mount namespaces of **`init` (pid 1) and the `zygote`/`zygote64` processes**. Newly-launched apps fork from the zygote, so they inherit the injected store; the rest of the system is left untouched.
>
> **Injecting into _every_ process (including `system_server`) tends to soft-reboot the phone** — so this deliberately targets init + zygote only.
>
> * **In-memory.** The bind-mount does not survive a reboot. Re-run the script after each boot.
> * **Re-run safe (idempotent).** It first unmounts any previous overlay, and always sources the certs from the **stable** `/system/etc/security/cacerts` ... so a second run can't cannibalise its own overlay.
>
> After it runs, **force-stop and relaunch** the target app so it forks a fresh process that inherits the new store.

**⇒ 对我们是最优做法：注 init+zygote，然后 force-stop 游戏重开。不软重启、可重跑。**

### A.5 《TrustUserCertificates》里的 `inject_into_apex()`（同一手法的模块化实现）

[lupohan44/TrustUserCertificates / service.sh](https://github.com/lupohan44/TrustUserCertificates/blob/main/service.sh)【一手】源码：

```sh
function inject_into_apex() {
    if [ -d "/apex/com.android.conscrypt/cacerts" ]; then
        ZYGOTE_PID=$(pidof zygote || true)
        ZYGOTE64_PID=$(pidof zygote64 || true)
        Z_PIDS="$ZYGOTE_PID $ZYGOTE64_PID"
        for Z_PID in $Z_PIDS; do
            [ -n "$Z_PID" ] && nsenter --mount=/proc/$Z_PID/ns/mnt -- \
                /bin/mount --bind /system/etc/security/cacerts /apex/com.android.conscrypt/cacerts
        done
        APP_PIDS=$(echo $Z_PIDS | xargs -n1 ps -o 'PID' -P | grep -v PID)
        for PID in $APP_PIDS; do
            nsenter --mount=/proc/$PID/ns/mnt -- \
                /bin/mount --bind /system/etc/security/cacerts /apex/com.android.conscrypt/cacerts &
        done
        wait
    fi
}
```
（注释原文：「**We can't do this globally as APEX mounts are namespaced per process**, so we need to inject a bind mount for this directory into **every mount namespace**」）

## B. Unity（UnityWebRequest / BoringSSL）到底读不读系统信任区 ★决定性

### B.1 结论一句话
**读。而且比你想的更宽松：Unity Android 的 TLS 后端是自研 `UnityTLS`，它把设备证书库并成 `trusted_ca` 列表；从 `2021.3.48f1` 起，连「用户自己装在机器上的证书」也会被并进去。**
**⇒ 你们是 `2021.3.56f2`，理论上「设置 → 安全 → 安装证书（用户证书）」就够了，连 APEX 手术都可以跳过。**

### B.2 证据链（三步，全是一手）

**(1) Unity 官方文档：UnityWebRequest 对着「运行平台的根证书库」校验**
[UnityWebRequest 文档](https://docs.unity3d.com/7000.0/Documentation/ScriptReference/Networking.UnityWebRequest.html)【一手】原文：
> HTTPS is supported and the server certificate is validated against **the root certificate store available on the system the app runs on**. Validation can be disabled ... by assigning the `UnityWebRequest.certificateHandler` property.

[certificateHandler 文档](https://docs.unity.com/ja-jp/engine/6000.5/script-reference/unityengine/networking/unitywebrequest/certificatehandler)【一手】原文：
> Setting this property to `null` makes the platform use the default certificate validation, which will validate certificates against a root certificate authority store (**most commonly Operating System store**).

**(2) 官方 issue tracker（错误串）：Android 上用的就是 UnityTLS，且报「不受信 CA」**
Issue 标题本身即证据【一手】：
`[Android] error "Curl error 60 (CERT verify failed: Certificate is not correctly signed by a trusted CA), UnityTLS error code 7" when using UnityWebRequest to connect to the server with a self-signed certificate`
→ 说明：① 走 libcurl + **UnityTLS**；② 自签会被拒；③ 拒的理由是「不在 trusted CA 列表」。

**(3) ★关键：`UUM-73839` 修的就是「用户装的证书进不了 trusted_ca 列表」**
[Unity 2021.3.48f1 Release Notes](https://unityreleases.com/issues/UUM-73839?major=2021)（**2025-01-22**）【一手】原文：
> **2021.3.48f1 | Fixes | Android | Fix | Fixed issue where user installed certificates directly to an Android device wouldn't show up in the `trusted_ca` list.**

原始出处：[yusjoel.github.io Unity 2021.3.48f1 release notes](https://yusjoel.github.io/UnityReleaseNotes/2021/2021.3.48f1.md)【一手】同样原文，并直接链到上面那个 issue tracker 条目。
（同一修复也被 backport 到 `2022.3.55f1`、`6000.0.32f1`、`6000.1.0a6` 等）

**⇒ 这条 release note 的含义非常明确：Unity Android 的 `trusted_ca` 列表 = 系统库 ∪ 用户库。修复前漏了用户库，修复后补上。**
**⇒ 你们的 2021.3.56f2 > 48f1，修复已在。**

### B.3 但有三件事必须先排除（否则装什么都白搭）

| 风险 | 说明 | 怎么验 |
|---|---|---|
| **① 游戏可能不用 UnityWebRequest** | 如果 BA 国服自己用 `HttpClient`/原生 socket/BestHTTP，那 Unity 的 CA 逻辑不适用，要看它自己怎么验 | 静态看 `libil2cpp` 里有没有 `UnityWebRequest` 符号（`il2cpp` 导出表 / `dump.cs`）；或抓包看 TLS 指纹 |
| **② 可能有证书 pinning** | Unity 的 `CertificateHandler` 子类一旦被游戏设置，就绕过系统库 | 在 `dump.cs` 搜 `CertificateHandler` / `ValidateCertificate` 的实现类 |
| **③ 链条要完整** | **UnityTLS 不会自动补中间证书** | 见下 |

**(3) 的原文证据**（[Unity TlsException Handshake failed 解析](https://openillumi.com/unity-tls-exception-handshake-failed-fix/) **2025-10-16**【二手】）：
> Unity 独自の TLS 実装（**UnityTLS**）が、一般的な OS やブラウザとは異なる、より厳格な検証ルールを採用している
> **Unity の TLS スタックは、他の環境のように中間証明書を自動で補完しません**

**⇒ 操作含义：我们的服务器在 TLS 握手时必须下发「叶子证书 + 完整链」。最省事的做法是 **根 CA 直接签叶子（不要中间 CA）**，并在握手时同时下发 leaf 和 root。否则会得到 `UNITYTLS_X509VERIFY_FLAG_NOT_TRUSTED`，看起来像"CA 没装上"，其实是链不全。**

### B.4 就 B 节给一个 5 分钟判定实验（强烈建议先做这个）

```
1. 把我们的 CA 用「设置 → 安全 → 加密与凭据 → 安装证书 → CA 证书」装成【用户证书】（不碰系统、不用 root）
2. iptables DNAT state-api:443 → 我们服务器（你们已有）
3. am force-stop 游戏，重开
4. 看是否还报证书错
   ├─ 通了  → Unity 吃了用户证书（UUM-73839 生效）。系统 CA 那套可以全部不做，直接进业务
   └─ 还报错 → 再上 A.4 的 init+zygote 系统 CA 注入，重试
```
**为什么值得先做**：它把「证书信任」和「APEX 手术」两件事解耦。如果第 1 步就通，A 节全部工作量归零。

### B.5 顺带：关于 Android 17 的 Certificate Transparency（务必读，但**大概率与我们无关**）

[HTTP Toolkit: Android 17 enables certificate transparency, and breaks custom CAs](https://httptoolkit.com/blog/android-17-certificate-transparency/)（**2026-09-22**）【一手】：
> For all apps **targeting Android API 37** and running on Android 17 devices, all system-trusted certificates must now use certificate transparency (CT) or they won't be trusted by default

[SecureInSeconds: Android 17 Turned On Certificate Transparency](https://www.secureinseconds.com/blog/2026-09-27-android-17-certificate-transparency-internal-ca)（**2026-09-27**）【一手/二手混合】关键澄清：
> Google's own documentation states that **CT verification is not performed on connections that use custom trust anchors**
> CT applies to CAs that are **supported out of the box**, and that **manually installed CAs are not covered**

**⇒ 对我们的判定：**
- CT 的触发条件是 **`targetSdk ≥ 37`**。BA 国服包（2023–2024 年代码）几乎不可能 target 37 → **CT 不生效，我们安全**。
- **但请务必实测确认 `targetSdkVersion`**：`aapt dump badging base.apk | grep targetSdkVersion`。如果哪天真到 37，自签 CA 会被 `NOT_ENOUGH_SCTS` 直接拒，那时才需要 HTTP Toolkit 那套「自建 CT log」的重活。
- 额外风险：Android 17 同时默认开 **ECH** 和 **Local Network Protection**。ECH 对我们无害（我们按 IP DNAT，不靠 SNI）；但如果我们的服务器在**局域网 IP** 上，LNP 可能导致 app 连不上，建议服务器放公网或走 loopback。

## C. 同类项目怎么做（BA 以外也算）

### C.1 结论一句话
**BA 圈内没有人靠"装 CA"这条路——Steam 版走「客户端 RSA 公钥补丁」，日服走「mitmproxy + 系统 CA（root 改 /system）」。我们国服的处境（手机包 + 无 Magisk）在 BA 圈没有先例，但在通用 Unity 手游圈有成熟套路。**

### C.2 BA 私服的两个先例（结论复用自我上一份报告 03）

| 项目 | 做法 | 证书怎么处理 | 链接 |
|---|---|---|---|
| **Shittim-Server**（Steam） | 改 `global-metadata.dat` 的 RSA-4096 网关公钥 + mitmproxy 按 host/端口重写 | **PC 端**，装 mitmproxy CA 到 Windows「本地计算机」信任根 | [client-patching.md](https://github.com/Neoexm/Shittim-Server/blob/main/docs/docs/server/client-patching.md)【一手】 |
| **BaPs**（日服手机） | mitmproxy + WireGuard，纯 URL 重写，**不改客户端** | 把 `mitmproxy-ca-cert.cer` 改名 `c8750f0d.0` → `adb root` + `remount` → 推 `/system/etc/security/cacerts/` → `chmod 644` → 重启 | [Android_Mitmproxy_Readme_ZH.md](https://github.com/gucooing/BaPs/blob/main/Android_Mitmproxy_Readme_ZH.md)【一手】 |

⚠️ **BaPs 那套是 Android 13 及以前的写法（直接写 /system），在 Android 14+ 已经失效**——这正是为什么我们要看 A 节。

### C.3 通用 Unity 手游的落地套路（按"是否需要 root"排序）

| 方案 | 需要 root | 适用 | 现成工具 |
|---|---|---|---|
| **用户证书 + 重打包加 `networkSecurityConfig`** | 否（但要改包签名） | app 未 pin、且我们愿意重签 | 手改 manifest |
| **用户证书（裸装）** | 否 | **Unity 2021.3.48+ 可能直接吃**（见 B 节） | 系统设置 |
| **系统 CA（APEX 注入）** | 是 | 通用、最稳 | [Karoliukas29/android14-trust-ca](https://github.com/Karoliukas29/android14-trust-ca)【一手】/ [TrustUserCertificates](https://github.com/lupohan44/TrustUserCertificates)【一手】/ [ys1231/MoveCertificate](https://github.com/ys1231/MoveCertificate)【一手】 |
| **Frida unpinning** | 是 | 有 pin 时才需要 | [httptoolkit/frida-interception-and-unpinning](https://github.com/httptoolkit/frida-interception-and-unpinning)【一手】 |
| **重打包改 targetSdk / 打 patch** | 否 | 只想改一个 URL 时 | apktool + 重签 |

⭐ **[ys1231/MoveCertificate](https://github.com/ys1231/MoveCertificate) 值得单独说**（README 更新 **2026-11-01**）【一手】：
> 支持 `Android 7-17`，兼容 **magisk v20.4+ / kernelsu / APatch**
> 优先使用系统设置安装, 不需要处理编码问题：导出证书后直接 push 到手机，**使用系统设置正常安装证书，完了重启即可**

**⇒ 这是唯一一个 README 明确写「Android 17 + KernelSU」都支持的模块，和你们机况完全对得上。它内部也是「设置装用户证书 → 模块搬到系统 → 处理 APEX 挂载」这套。**
**⇒ 如果 B.4 的用户证书实验失败，直接用这个模块，比自己写脚本省事。**

## E. 不改客户端换网关的野路子

### E.1 结论一句话
**按「干净程度 × 可行性」排序：`settings put global http_proxy`（最简单，Unity 2019.3+ 支持）> per-app VPN（最干净，但工程量大）> iptables DNAT（你们已在用）> ip rule/network namespace（最底层，收益最低）。**
**但请注意：所有这些只解决"路由"，不解决"证书"。证书只有 B 节那几条路。**

### E.2 ① 全局 HTTP 代理（最省事，先试这个）

**Unity 支持吗？支持，但有版本条件。**
[Unity IssueTracker: \[Android\] UnityWebRequest doesn't work behind a proxy](https://issuetracker-mig.prd.it.unity3d.com/issues/android-unitywebrequest-doesnt-work-behind-a-proxy)【一手】：**Fixed in 2020.1.X / 2019.3.X**（2019-11-19）
[Unity IssueTracker: UnityWebRequest does not respect **auto** proxy settings](https://issuetracker-mig.prd.it.unity3d.com/issues/unitywebrequest-does-not-respect-auto-proxy-settings)【一手】：**Fixed in 2022.1.0a6** ← 即 **2021.3 不支持 PAC/自动代理**

**⇒ 判定：2021.3.56f2 支持「手动代理」，不支持 PAC。而 `settings put global http_proxy` 正好就是手动代理，所以应该能生效。**

```bash
# 设置全局手动代理（需要 root 或 shell）
settings put global http_proxy 10.0.0.2:8080
# 撤销
settings put global http_proxy :0
# 查看
settings get global http_proxy
```
⚠️ 注意事项：
- 这会让**全设备**流量走代理（包括系统更新），Android 会弹"网络可能被监控"通知。
- 代理是针对**当前默认网络**的；切 Wi-Fi/蜂窝可能失效，要重设。
- 只对读 `ProxySelector` 的 app 生效，**不保证所有 app**。
- **对我们的价值**：如果成功，我们连 DNAT 都不用，直接把 `state-api` 的 CONNECT 转到我们服务器。**但证书问题照旧。**

### E.3 ② per-app VPN（唯一真正"干净"的方案）★

**可行性：技术上完全成立，Android 原生能力，不需要 root。**
[Android 官方 VpnService 文档](https://developer.android.com/develop/connectivity/vpn)【一手】：`VpnService` 可创建 TUN、用 `Builder.addAllowedApplication()` 精确限定只接管某个 app 的流量。

现成可参考/可改的实现【二手】：

| 项目 | 说明 |
|---|---|
| [dabiaotouxiang/TunProxy](https://github.com/dabiaotouxiang/TunProxy) | 「Android VPN interceptor to send HTTP and HTTPS traffic to a proxy」，**Only the communication from the specified application can be acquired** —— 正是 per-app 场景 |
| [KingJem/FlowTrans](https://github.com/KingJem/FlowTrans) | VpnService TUN → 转发到上游 mitmproxy/mitmweb，专为抓包调试做 |
| [madeye/proxydroid](https://github.com/madeye/proxydroid) | 老牌 ProxyDroid，已现代化为 VPN-first 架构 |
| [xVanTuring/free-proxy](https://github.com/xVanTuring/free-proxy) | 把 HTTP/SOCKS5 代理变成 system-wide VPN |

**它能不能解决我们的问题？分两问回答：**
| 问题 | 答案 |
|---|---|
| 能把目标 app 的流量导到我们服务器吗？ | **能**，且比 DNAT 干净：不碰 iptables、不影响其他 app、不需要改 DNS/hosts，`addAllowedApplication` 精确圈定游戏包名。 |
| 证书怎么办？ | **一样要装 CA**。VPN 只改路由，不改 TLS 信任。除非 VPN app 自己内置 MITM（那就是把 mitmproxy 塞进 app），**仍然需要我们自己的 CA 被系统信任**。 |

**⇒ 结论：per-app VPN 是「换掉你们现在的 DNAT」的更优替代（更干净、可随时开关、不污染全局路由表），但它不是「CA 问题的替代品」。两者是正交的两件事。**
**⇒ 建议：如果 DNAT 已经 работа（能到我们服务器、只是证书报错），就不要换 VPN；只有当 DNAT 出现"影响其他 app / 路由冲突 / 难回滚"时才值得换。工程量大概是"写一个 TUN 循环 + 一个 TCP 转发"，1–2 天。**

### E.4 ③ `ip rule` / network namespace（不推荐）

用 `ip rule add uidrange <uid> lookup <table>` 把某 uid 的流量导到独立路由表，再在该表里 default via 我们的网关。
- **能实现**，但 Android 的 `netd` 会管理路由表与 fwmark，手工插 `ip rule` 容易与 netd 打架，重启即失效，且需要 hook `netd` 的重建流程。
- **收益**：与 DNAT 等价。
- **判定：除非 DNAT 走不通，否则不值得。**

### E.5 ④ 已被你们证伪的路，我在资料里找到了"为什么"

| 你们试过 | 为什么不行 | 出处 |
|---|---|---|
| 改 `files/Hosts` | 它是 Unity 自己的名字解析缓存，不是系统解析入口 | 【推断】 |
| 改 `/system/etc/hosts` | app 走 `netd`（DNS 在 netd 里做），且不同 mount ns | 【推断】+ netd 架构常识 |
| iptables 只断不导 | 只断不导 = 直接超时，客户端没有得到新地址 | 【推断】 |

**⇒ 你们的 DNAT 方向是对的。** 上游 BaPs/Shittim 也都是「在解析/连接层做重写」，而不是改 hosts。

## F. 如果让我现在选一条路

### F.1 我的排序（按「今天就能出结果」排）

**第 0 步（30 分钟，必做）：先确认 `targetSdkVersion`，并做一个"用户证书"实验。**
```bash
aapt dump badging base.apk | grep -E "targetSdkVersion|sdkVersion"
```
- 若 `targetSdkVersion < 37` → **Android 17 的 CT 与我们无关，放心装 CA**（大概率如此）。
- 然后把 CA 装成**用户证书**，force-stop 游戏重开，看证书错是否消失。
- **这一步成本几乎为零，却可能直接让 A 节的全部工作作废。**

**第 1 步：证书（两条腿走）**

| 若第 0 步的用户证书**生效** | 若**不生效** |
|---|---|
| 结束。直接进业务层，不用碰 APEX。 | 用 [MoveCertificate](https://github.com/ys1231/MoveCertificate)（支持 Android 7–17 + KernelSU）；或手跑 A.4 的 init+zygote 注入脚本。**关键是：注 zygote → force-stop 游戏 → 重开**，不要往 tmpfs 里傻写。 |

**第 2 步：路由（你们已经在做，保持 DNAT）**
DNAT `state-api.bluearchive-cn.com:443` → 我们服务器。这步没问题，别换。
只有当 DNAT 开始干扰其他 app 时，才考虑换 per-app VPN。

**第 3 步：TLS 服务端配置（很容易被忽略，但会伪装成"CA 没装上"）**
- 根 CA **直接签叶子**，不要中间 CA；
- 握手时**同时下发 leaf + root**（UnityTLS 不补链）；
- 证书里要有 `subjectAltName = state-api.bluearchive-cn.com`（以及 `gsqc-api.bluearchive-cn.com`，如果也要劫）；
- 有效期别超过 398 天（虽然自签无所谓，但有些校验器会看）。

### F.2 装 CA 这条路成算多大？

| 情形 | 概率（我的判断） | 依据 |
|---|---|---|
| Unity 吃**用户证书**，第 0 步就通 | **约 55%** | UUM-73839 修复已在 2021.3.56f2；Unity 文档明说对"系统根证书库"校验 |
| 需要**系统 CA**（APEX 注入）才通 | **约 35%** | 若游戏显式走 Java 的 `TrustManager`（只信系统库），或 Unity 版本分支行为不同 |
| **两条都不通**（游戏有自己的 pinning / 不用 UnityWebRequest） | **约 10%** | 需要在 `dump.cs` 里确认有没有 `CertificateHandler` 子类；BA 官方是否 pin 未知 |

**综合：装 CA 这条路整体成算 ~90%，但"必须动 APEX"的概率只有 ~35%。所以千万别一上来就做最重的那步。**

### F.3 如果 CA 彻底失败，替代方案是什么（按优先级）

1. **在 `libil2cpp.so` 里改 URL 字符串**（我们已验证 libil2cpp 无 hash pin、可改）。既然能改 `SDKConfigSettings.json`，改 il2cpp 里的 `https://state-api...` 常量是同一类操作，只是要处理 Unity 的字符串驻留（`il2cpp` string literal 在 metadata 里，改长度会破坏偏移 → **只能等长替换**，比如把域名换成等长的我们自己的域名）。
   - 💡 **这其实是个很实用的技巧**：注册一个**和 `state-api.bluearchive-cn.com` 等长**的域名（比如 `state-api.bluearchive-cnX.com` 长度一样不行……但可以注册 `xxxxx-api.bluearchive-cn.com` 这类子域？不行，得是同一个 TLD）。**更可行：等长替换成我们控制的、长度相同的域名**，例如 `state-api.baexample.com` 长度不同……需要精确等长。**所以更稳的是改 `libil2cpp` 里的指针而不是内容** —— 但这需要逆向。
2. **在 `libunity.so` 的 `getaddrinfo` 做 code cave**（报告 01 已列）。libunity 受 ACE 校验，风险高。
3. **重打包 + 改 manifest 的 `networkSecurityConfig`**，把我们的 CA 设为**app 级 trust-anchor**（这样连系统库都不用动）。
   - ⚠️ 但 B 节提到 Unity 论坛有"Unity 不理会 networkSecurityConfig"的说法（[Unity Discussions](https://discussions.unity.com/t/network-security-config-isnt-work-on-android/935199)【二手】）——因为 Unity 用自己的 TLS 栈。**所以这条路对 Unity 大概率无效，除非游戏走 Java 层。**

### F.4 一句话给 Lead

> **先把 CA 装成「用户证书」试一次（5 分钟），别直接上 APEX。**
> Unity 2021.3.48f1 起会把用户证书并进 `trusted_ca`，你们是 .56f2，很可能白捡。
> 如果不成，用 MoveCertificate（支持 Android 17 + KernelSU）或「注 zygote + force-stop 重开」的正确姿势，**关键是别指望往 tmpfs 里写文件就能生效**。
> Android 17 的 CT 只在 targetSdk ≥ 37 时才咬人，先 `aapt dump badging` 确认一下就能排除。
