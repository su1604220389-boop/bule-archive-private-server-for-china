## 一、本次被推翻的既往结论

| 编号 | 旧结论 | 实际 | 影响 |
|---|---|---|---|
| R1 | 三处 CA 都已安装、客户端仍拒绝 → 判定为 pinning | 三处写入**全部无效**，且各有不同原因 | 今晚「pinning」结论的前提不成立，必须重判 |
| R2 | 系统 CA 文件是 DER | AOSP `system/ca-certificates` 里 `files/*.0` 是 **PEM armor** | 格式不是失败主因（见 R3），但不能继续按 DER 铺 |
| R3 | 「装 DER 导致 App 读不到」 | **不成立**。`DirectoryCertificateSource.readCertificate()` → `CertificateFactory.generateCertificate()`，PEM/DER 通吃 | 不要在格式上再花时间 |
| R4 | `/system/etc/security/cacerts` 是一份有效副本 | A14+ `SystemCertificateSource.getDirectory()` 在 APEX 目录非空时**完全忽略** `/system` | 这一份是死代码 |
| R5 | 「nsenter 看 dev/ino 一致 ⇒ App 能看到我们的文件」 | `/apex` 是 **private propagation**：基础挂载全局可见，但**任一 ns 里新加的 mount 不传播** | 这正是今晚始终对不上的那个矛盾的解释 |

### 三处写入失效的确切原因（分列，不合并）

1. `/data/misc/user/0/cacerts-added/` → **用户库**，`targetSdk=33 ≥ 24` 默认不被信任。
2. `/system/etc/security/cacerts/` → **A14+ 被 APEX 目录遮蔽**，死代码。
3. `/apex/com.android.conscrypt/cacerts/` → **目录选对了**，但文件不在 App 进程的 mount namespace 里。

## 二、判据修正：`access_denied(49)` 不是标准链校验失败

标准证书链失败 alert 是 `46 certificate_unknown` / `42 bad_certificate` / `48 unknown_ca`。
`49 access_denied` 出现在握手阶段，更可能是 **App 自身的 TLS 包装层 / 自校验 / 自定义 verify 回调** 触发的。

⇒ 因此**不得**继续把「客户端拒绝」直接等同于「信任库不认证书」。必须先拿 logcat 证据分层。

---

## 三、分层探针（一条命令把问题定位到某一层）

`DirectoryCertificateSource.readCertificate()` 在解析失败或打不开时是 **`return null` 静默吞掉，只打一条 `Log.e`**。
这条特性既是「毫无报错但不信任」的成因，也是最好的探针：

```sh
logcat -d -b all | grep -i -E 'DirectoryCertificateSrc|Trust anchor|trust manager|certification path'
```

判读：

| logcat 现象 | 定位层 | 下一步 |
|---|---|---|
| 有 `DirectoryCertificateSrc` 相关 `Log.e` | 证书**读取层**（文件不可见/不可解析） | 做 mount ns 注入 |
| `Trust anchor for certification path not found` | 证书**链/信任层**（store 已生效） | 补证书链 |
| `certification path` 以外、trust 相关一片空白 | App **不走系统 store** | 转 Frida hook `X509TrustManager.checkServerTrusted` 并打调用栈 |
| 出现 `49 access_denied` 且无上述任何日志 | App **自校验 / pinning** | 同上，转运行时 hook |

## 四、正确做法（已下达给 phone-ops）

1. **建影子 store**：拷 APEX 全部原厂证书 + 我们的 CA，归一化 PEM、`root:root 644`、`chcon -R u:object_r:system_file:s0`，**目录本身也要 chcon**（否则 search 被拒，文件 label 再对也没用）。
2. **挂进 zygote64 的 ns**（fork 会复制 mount table，新 App 自动继承）：
   ```
   nsenter --mount=/proc/$(pidof zygote64)/ns/mnt -- /system/bin/mount --rbind $WORK /apex/com.android.conscrypt/cacerts
   ```
   同时挂 `/system/etc/security/cacerts`。
3. **已在跑的 App 各补挂一次**。
4. `kill -9` 后 `monkey` 拉起（`am` 在 `u:r:ksu:s0` 下被挡）。

### 两条硬约束
- **必须 `--rbind`，不能 `--bind`**：A15+ 每张证书可能是单文件挂载，`--bind` 会把 100+ 张证书覆盖成空。
- **不重启 zygote、不重启设备**：全程运行时可做，10 秒可回滚。

## 七、待确认的环境前提

- 现代 KSU 需要 **metamodule（meta-overlayfs）** 才能挂载模块；没装的话所有 `$MODDIR/system/` overlay 类模块都是死的。
- 确认游戏在 KSU 里**没有**被设成「卸载模块 / umount」——那会把证书层从该进程 ns 卸掉。

## 八、不变的红线（今晚已各坑一次的教训）

1. `access_log` 有记录 **≠** TLS 通过。
2. `error_log` 为空 **≠** TLS 通过。
3. 判 TLS 通过**只认 pcap**：ServerFlight 之后是否出现 `GET /` / `POST /` / `PRI * HTTP/2`。
4. tcpdump 过滤必须 `not src net`，不能 `not net`（后者会连入站流量一起滤掉，导致空抓）。
5. 不给 `.so` 用 `cat > dst`（会导致 0 字节 + `dlopen` 报 `file offset >= file size`）。
6. `UseCustomExcel=true` 会触发 `ResetDumped()` 删 316 MB 后崩溃，不得开启。
