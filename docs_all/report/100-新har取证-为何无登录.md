```

```

**统一解释（一条即可覆盖全部观测）：**

> **官方国服在这三次抓包的整个期间（11-11 20:34 至 11-14 19:40，横跨 3 天）都处于 `State=1` 状态。客户端在拿到 `State:1` 后按设计停止在标题页，不发出任何 `/api/*` 业务请求。因此三份 HAR 里都不可能存在 `account/auth` 与 `academy/getinfo`——它们从未被发出，与抓包工具、抓包时长、SDK 登录、手机 vs 虚拟机、DNAT 全都没有关系。**

|---|---|

### 7.4 ★ 但有一个新事实必须点出来

**`State:1` 跨了 3 天没变过。** 这比"抓包时机不对"严重：

- 正常的维护窗口是**小时级**的。11-11 20:34 → 11-14 19:40 是 **71 小时**。
- `Msg` 的原文是「请耐心等待**开服**」——用的是"开服"（service opening）而不是"维护结束"。
- 同一时间官方 CDN 是**活的**（`static.bluearchive-cn.com` 正常返回 78/10/11/9/32 B 的 manifest、`gs-api/api/health` 返回 `ok`）。

⇒ **两种可能，数据本身不足以区分：**

| 可能 | 支持 | 反对 |
|---|---|---|
| **(a) 官方真在做一次超长维护 / 版本升级期** | `State:1` + 维护文案是服务器主动给的；`gs-api/health`=ok 说明网关是活的（维护期常见：网关开着、业务关着） | 71 小时偏长；四份 state 的 4 个版本号里 3 个是同一批（`202611051844/1826/1836`），资源侧没有变化，不像大版本升级 |
| **(b) `State:1` 是这套 build / 这个账号 / 这个渠道的"未开服"常态门禁**（例如测试服、预下载期、或 `prod39` 不是线上服） | "等待开服"的措辞；`IsOpenPreDownload:true`；版本号停在同一批 | 无法证伪，也**无法证实** |

**处置建议：不要把"等维护结束"当成唯一计划。** 需要两条腿走：
1. **加一个轻量探针**（每天几次 `GET /api/state` 带 4 个业务头，只看 `State` 是否变 0）。一旦变 0，立刻按 §8 抓。探针脚本 report/96 已有，可直接复用。
2. **并行推进非抓包路线**（report/55、report/59 的静态反编译已能把 `AccountAuthStart` 协程解出来）——因为如果 (b) 成立，"等开服"可能永远等不到。
