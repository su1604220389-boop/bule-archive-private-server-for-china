## 2. 尚未排除的假设（按可能性排序）

> 排序依据：**与"解密成功 + 无弹窗 + 无第二条请求 + 无异常上报"四件事同时相容**，
> 且**在历史实验里从未被单独改过**。

### H1 ★★★ `protocol` 取的是"名字"，而客户端可能按"token"认领会话

- **为什么没被排除**：外层 `protocol` 在**所有历史实验里一直是 `"Account_Auth"`，一次都没变过**。
  而客户端**发请求**时写的确实是 token：`AHTQLQI65FWJGGGK4KL5AEF57A`（`report\48:364-370` §A.4，实测）。
- **文档怎么说的**：`report\48:516-524`（§B.6）——"客户端读什么，`ParseProtocol` 无函数体，不可知"；
  `report\48:262-269`（§9 实验 1/2）把"回显 token"列为**第一优先**最小实验；
  `report\41:315`（检查项 1）与 `41:532`（L1 枪）同样把它列为"极低成本、二值判据"。
- **反证据（必须记）**：真服 Error 响应用的**是名字** `"Error"`，且客户端正确弹了专属文案。
  ⇒ 名字**能**被解析。**但** `"Error"` 极可能是特例（走 `IsSpecificErrorJson` / 全局错误分支，不需要匹配任何 pending 会话），
  **它不能证明 `"Account_Auth"` 这个名字也能匹配到 pending 会话**。
- **文档给出的静默机制**：`report\48:222-241`（§7）——
  `ParseProtocol` 取出的东西匹配不上任何待完成会话 ⇒ 这一步**静默跳过** ⇒ `ResponseHandler`/`NetworkErrorHandler` 都不调
  ⇒ `IsFinished` 永不置位 ⇒ `WaitForRequest` 永远 `yield`。

### H2 ★★★ `requestid` 缺失（历史文档从未出现过这个字段）

- **文档覆盖情况**：`report\` 全目录检索 `requestid`，只有两处命中：
  ① `report\22:321` 一个无关的 XML `<RequestId>`；② `report\49:17` 我自己写的**用法注释**。
  ⇒ **我们所有历史构造里都没有这个键**，而真服响应里**有**。
- **它可能是什么**：真服三个键 `protocol` / `packet` / `requestid` 里，前两个我们都有，**只有它没有**。
  若客户端用它做"这一包属于哪次请求"的关联键，缺它 = 永远匹配不上 = 症状完全吻合。
- **反证据**：客户端**发请求**时既没有 multipart 字段、内层 11 键里也没有它
  （`report\35` §三 的明文、`report\32` §0 的三字段）⇒ 服务端无从"回显"。
  **除非**它是客户端本地生成、只用于日志/去重，那它就不影响匹配。
- **判定**：逻辑上存疑，但**成本为零**，且是"我们与真服信封唯一的已知结构差"。

### H3 ★★ 分发到 `Account_Auth` 之后，客户端走进了**沉默分支**（S2–S5）

- `report\48:170-184`（§5）列了 5 条沉默分支，S1 是"没认领"，**S2–S5 是"认领了但没走完"**：
  - **S2** `co_RelayPacketsProcess` 队列停住（`taskQueue`/`queueState`/`errorExist` 三件套，`48:136-154`）；
  - **S3** `AccountAuthStart` 的两个回调都没被调（`<AccountAuthStart>b__20_0/1`，`48:176`）；
  - **S4** `SkipAccountCallname` 里的局部函数 **`g__TTSSaveAndRequestAccountAuth`**——**先存 TTS 再发 Auth**，
    若 TTS 存档失败可能既不前进也不报错（`48:177`；`TTSCdnUri` 指向 Nexon 国际 CDN，见 `report\41:143`）；
  - **S5** `OnLoginFinish` 里的 `g__CompletePatch` / `g__ContinuedContentProcess`（`48:178`）。
- **为什么没被排除**：这些分支**都不产生弹窗、不产生异常上报、不产生新请求**——与四件事全部相容。
- **但**它们都发生在"认领成功之后"，所以**优先级低于 H1/H2**（先得让 H1/H2 过）。

### H4 ★★ 内层字段的**类型/取值**让反序列化在中途失败

- `report\41:152`（`StaticOpenConditions` dict vs list 未证）、`report\47:26`（无 ResultState）、
  `report\49` §5（`FunctionClose` 类型未知、故意不写）。
- **为什么没被排除**：canary 只证明"解密出明文"，**不证明 DTO 反序列化成功**。
  若某个已知属性的类型不符（最可能：`StaticOpenConditions` 的 dict/list），Newtonsoft 会抛
  `JsonSerializationException`，而该异常**被 catch**（`report\41:206` 的论证）⇒ 无弹窗、无日志、无后续请求。
- **压制它的证据**：今天 Error 响应能被正常解析 ⇒ 解析器本身可用；但错误包是**另一个 DTO**，不能证明 Auth DTO 的字段表能过。

### H5 ★ `CurrentVersion` / 版本分支

- `report\42:630-642`（§4.4）：Shittim 源码实测"服务端对版本不做任何拒绝"，`CurrentVersion` 是**告知**不是**校验**，
  且 `AccountHandler.cs:121` 注释明说"客户端这里永远发 `Version: 0`，官方回自己的 build 号"。
- ⇒ **文档判定：版本不匹配不会造成静默停住**。保留为低概率项（因为国服客户端是否照搬这套未知）。

### H6 ☆ `ServerTimeTicks` 时区偏移（8 小时）

- 从未有任何文档验证过客户端用 `DateTime.Now` 还是 `UtcNow` 比对。
- **弱点**：即便偏移，最可能的表现是时间显示错，而不是登录卡死。列为最低优先级。

### H7 ☆ REST 传输的完成回调不走 `WaitForRequest`

- `report\48:310-344`（附录 A.2）："静态不可判定，正反各有一条硬证据"。
  若 REST 路径有自己的完成判定，那 H1/H2 的推断链可能要改写。
- **但**：48 号同时给出正向证据（API 类自己管会话）⇒ 暂按"走同一套"处理。

## 3. 文档内部矛盾（四处，必须记）

### C1 ★ 41 号说"响应不需要加密"，48 号说"明文已被 6 轮反证"

| 位置 | 原话 |
|---|---|
| `report\41:67`、`41:429` | "客户端**没有**「编码响应」的代码路径……**加密响应这条线可以整条撤掉**，明文 JSON 是对的方向" |
| `report\48:502-514` | "如果 `DecryptOrReturnOriginal` 真的会在解密失败时把原串交给下游，那'真实明文 JSON'那一轮就**必须**前进。它没有 ⇒ 明文路线不成立 ⇒ 按真服封装复刻加密是唯一有现场支持的一条" |
| 今天现场 | 加密复刻 → 解密成功（canary 命中）⇒ **48 号正确，41 号错** |

钥匙从来不是问题。**这是典型的"从一个正确的事实（无 EncryptResponse）推出一个错误的结论（无需加密）"。**
⇒ **处置：`report\41` §8-1 与 §9.A 的结论作废，不要再引用。**

### C2 ★ `report\32:380-384` 的判据与 D-44①② 直接冲突

| 位置 | 原话 |
|---|---|
| `report\32:382-384` | "回明文 JSON → 报「服务器处理请求失败」→ **说明它在解密响应时失败（响应必须加密）**" |

### C3 ★ 48 号 §9 的"回显 token"实验 vs 今天"真服用名字"

- **不必然矛盾**（Error 可能是特例），但**必须用实验分开**，不能直接采信任一方。见 §5-E1。

### C4 ★ `DEADENDS D-46` 表格"4491 B 加密 = 3740 B 明文，完全一致" vs `report\41:376-416` 的算术证伪

- D-46 用那轮结果推出"加密与否都不影响"。

## 4. 五个子问题逐一回答（只答文档里有的）

### Q1. `packet` 里必须有哪些字段才能让客户端往下走？

**文档从没指出过任何一个"缺了就静默"的具体业务字段。** 唯一被指认过的是**信封字段**，而它今天已被排除：

| 文档给的候选 | 依据 | 现状 |
|---|---|---|
| `MissionProgressDBs` / `EventMissionProgressDBDict` / `BattlePassMissionProgressDBDict` | `report\47:270-303`（H1）、`report\47:386` 自评"纯假设，未证实" | **今天已排除**（49 号 26 键已含） |
| `DailyRecordDBs` | `report\47:296-303`（§7.3，集合，null 会 NRE） | 同上，已含 |
| `SessionKey` / `MxToken` / `EncryptedUID` | 42 号 §3.6 曾担心 | **47 号 §0.1 已否**：DTO 里没有；`SessionKey` 四层 0 命中 |
| `StaticOpenConditions` | `report\41:152`（类型未证） | **未排除**（H4） |

**文档真正给出的答案是"不是字段问题"**：
> `report\48:224`「缺的不是推送，也不是字段：缺的是**让客户端把这个响应认领给它正在等待的那个会话**」

⇒ **Q1 的答案：没有"某个业务字段缺了就静默"的记载；47 号给的那一组已被 49 号+今天现场排除。剩下的是"认领"而非"内容"。**

### Q2. 外层 `protocol` 到底该是名字还是 token？

| 事实 | 出处 | 强度 |
|---|---|---|
| 客户端**发请求**写的是 token（26 字符 base32） | `report\48:364-370`（§A.4）、`report\35` §二 | **实测** |
| 客户端**读响应**读什么：`ParseProtocol` 无函数体 ⇒ **不可知** | `report\48:372-377`（§A.4）、`48:516-524`（§B.6） | —— |
| `Protocol` 在客户端是**枚举**（`HttpMessage.<Protocol>k__BackingField`） | `report\48:520` | 实测（字段存在） |
| 若 `ParseProtocol` 解析失败，最省事的写法是 `default(Protocol)`；若 `Common_Cheat` 恰为 0 号 ⇒ 静默错配 | `report\48:521-524` | **假设，自称不可验证** |
| **成功响应用什么：文档从未有过实测** | —— | **[文档未覆盖]** |

**唯一新增证据（今天，非文档）**：真服 Error 响应用**名字** `"Error"`。
**但它只证明"名字能被解析成 Error"**，不证明"名字能被匹配到 Account_Auth 的 pending 会话"——
因为 Error 很可能走全局错误分支（`report\48:236` 的 `IsSpecificErrorJson`、`report\34` §六）。

⇒ **结论：文档未覆盖，今天也只答了一半 ⇒ 这是当前第一号未知量。**

### Q3. `requestid` 历史文档里出现过吗？

**没有。** 全目录只有两处命中：
- `report\22:321`：一段无关 XML 的 `<RequestId>`（真实上游接口取证里的阿里云响应头）；
- `report\49:17`：我上一轮按 lead 描述写的用法注释。

`report\36`（24 键）、`report\42`（Shittim 全流程）、`report\47`（DTO）、`report\32/35`（信封）**全部没有它**。
Shittim 的外层信封只有 `protocol` + `packet` 两个键（`report\42:224`、`report\28` §2.5）。

⇒ **它是我们一直漏掉的东西，而且是"我们与真服信封唯一的已知结构差"。**
但**是否影响匹配存疑**：客户端请求里没有携带它，服务端无从回显（详见 H2）。

### Q4. `ErrorCode` / `Protocol:-1` 这类错误内层，能不能借鉴？

**能，而且文档里已经有"用错误字段做探针"的做法：**

### 8.3 关键几阶的详细判读

#### R00 —— 为什么它排在所有字段实验前面

- 若 E0 阳性是**读法 A**（全局错误扫描），那么"E0 弹框"根本不代表 `Account_Auth` 被分发；
  此时去调字段是**在错误的层级上做实验**，跑满 13 阶也只会得到一列"静默"。
- R00 只改**一个字符级变量**：同一个错误 JSON，`-1` → `1002`。
  - **仍弹** ⇒ 错误识别与 `Protocol` 值无关 ⇒ 读法 A ⇒ **E0 的阳性不能作为"分发到达"的证据**，应先回去做 H1（外层 token）；
  - **静默** ⇒ 路由键 = 内层 `Protocol` ⇒ 读法 B ⇒ 我们的 `1002` 是对的，字段才是嫌疑 ⇒ §8 全部有效。
- **这一阶的阳性与阴性长得完全不一样**（弹框 vs 静默），不是废实验。

#### R01 —— 全阶梯的"观测通道自检"

- `UpdateRequired` 是 26 键里**唯一一个语义明确、且必然触发 UI 分支**的布尔位
  （`report\36` §1：官方 `UpdateRequired` 为 true 时下发，客户端据此走更新流程；`report\42:630-642` §4.4）。
- **静默的后果很重**：如果连"置 true 都不弹框"，说明我们的**成功 DTO 根本没有被消费**——
  那么 R02–R13 全部只能产出静默，**§8 应当整体作废**，问题回到 H1/H3（认领/分发），而不是字段。
- 所以 R01 的价值不在"它是不是答案"，而在"它决定 §8 要不要继续"。

#### R09 —— 为什么用 `State=0` 当第二校准

- `AccountDB.State` 在 `report\36` §2 的实测值是 `1`（正常）。客户端有 `IsStateMatch`（`report\47` §5.2 提到 `MX-GameLogic-DBModel-AccountDB-IsLevelOrExpHigherThan`），
  说明**状态是被业务逻辑读取的**。
- 若 `0` 能触发"账号状态异常"类弹窗，就等于**正面证明 AccountDB 子对象被成功反序列化并被消费**。
  这是对 R01 的独立复核（R01 验的是顶层 bool，R09 验的是嵌套对象）。

#### R12 —— 为什么是"条件阶"而不是常规阶

- `report\48:190-201`（§6.1）：昵称框是**客户端主动弹**，触发条件是 `Nickname` 为空；用户输入后才发 `Account_Nickname`。
- ⇒ **空串本身就是一个免费探针**：只要流程走到 `HandleAccountAuthResponseMessage` 之后，就应当看到框。
  **把 Nickname 改成非空，是在"抹掉"这个信号，而不是增加信号。**
- 只有在"昵称框出现但点了没反应/被卡住"的情况下，改成非空（跳过改名）才是有意义的推进。

```
  └─ 静默    ⇒  §8 停，回 H1/H3（认领/分发），字段不是变量
R02  →  判"26 个键是不是变量"
  ├─ 有反应  ⇒  用 R03–R05 定位是哪一组
  └─ 静默    ⇒  与 R01 阴性同解
```

**这 4 阶的共同点：每一阶的两种结果都指向一条明确的下一步**，没有一阶是"跑了也不知道该怎么办"。
