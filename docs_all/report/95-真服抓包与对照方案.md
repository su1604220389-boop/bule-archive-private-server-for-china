## §1 目的：为什么要抓真服

### §1.1 先纠正一个目标表述

任务书说"如果能看到真服的响应，以及客户端在 24000 之后发了什么，就不用猜了"。
这两件事的**依赖关系是单向的**，必须拆开：

```
想看到「24000 之后客户端发什么」
        ↑  只需要
我方服务器成功回一次「客户端能接受的 24000」  ← 关键在这里
        ↑  有两种拿法
   ┌────┴─────────────────────────────┐
   (a) 抓真服，抄它的值               (b) hook 客户端，问它为什么不接受
```

也就是说：**"客户端在 24000 之后发什么"根本不是真服才能回答的问题** —— 只要我们回一次对的 24000，客户端自己就会发下一条，我们的 nginx 日志会直接记下来。`report/67` 已经证明了这一点（`REQUEST-ID` 链在 getinfo 之后断掉，是因为我们回了假包，不是因为客户端不想继续）。

**所以抓真服唯一真正要买的东西是：一份确定可用的 24000 响应样本，用来终结"字段该是什么值"的猜测。**

### §1.2 为什么现在必须要一份真样本（三条路都断了）

| 层 | 现在有什么 | 缺什么 | 缺口能不能本地补 |
|---|---|---|---|
| **DTO 字段名/顺序** | `report/72` 全量 821 个 DTO；`dto_schema_academy.json` 有 `AcademyGetInfoResponse` 9 个 wire 字段 | 不缺 | 已补齐 |
| **字段类型** | metadata + Shittim 投票，`conf: high/mid/low/guess/vote` | `ZoneVisitCharacterDBs` 仍是 **`unknown / guess`** | 部分能补（metadata 在本地） |
| **字段取值** | 只有 Shittim 的实值（国际服口径）+ 我们编的默认值 | 国服 3.0.2 的真实值 | **不能** ← 这是真服唯一的独家价值 |
| **账号态数据** | `ExcelDB.db` 有 `AcademyLocationDBSchema` 11 行 / `AcademyZoneDBSchema` 95 行 / `AcademyFavorScheduleDBSchema` 1053 行 | `ZoneScheduleGroupRecords` 是**每个账号自己的进度**，Excel 里根本没有 | **不能** |

### §2.7 ★ 第二个不需要真服就能改的问题：`protocol_map.json` 的 id 列和线上不一致

审计过程中撞出来的，顺手记一下，因为它会**直接污染抓包结果**：

| 事实 | 证据 |
|---|---|
| `protocol_map.json` 里 `Account_LoginSync.id = 1017`，`Account_RequestBirthdayMail.id = 1019` | `python -c "json.load(open('work/ba/proto/protocol_map.json'))"` |
| 但客户端实际发出的包里，**token `P3OMQZD2FXV7XXEGA7ETCXIJ4Q` 的 `Hash>>32 = 1019`** | `report/67 §2.1`：`Hash:4376571674624` → `4376571674624>>32 = 1019` |
| 而 `name_to_token("Account_LoginSync") == "P3OMQZD2FXV7XXEGA7ETCXIJ4Q"` | 本轮实算，与 map 的 `token` 列一致 |
| `report/67` D7 已明写"`1017` 是误传；国服 `Account_LoginSync = 1019`" | 同上 |

⇒ **`protocol_map.json` 的名字↔token 列是对的，`id` 列对 `Account_LoginSync` 是错的**（1017 是国际服枚举值）。
⇒ 危害：任何"按 id 反查名字"的代码都会把 1019 那条包标成 `Account_RequestBirthdayMail`。抓包器要是也这么干，整份 capture 的头字段就是错的。

**权威性规则（已写进 `passthrough_capture.py`）**：

1. **名字**以 **form `protocol` token** 为准 —— `token = base32(MD5(UTF-16LE(名字)))`，它是名字的密码学函数，**不会说谎**；
2. **数字**以 **包内 `Hash >> 32`** 为准 —— 那是客户端实际写进包里的；
3. `protocol_map.json` 的 `id` 列只作兜底，且必须在结果里标注 `protocol_name_source = "map(id) [非权威]"`。

`passthrough_capture.py` 现在会在 capture 里显式写 `id_name_conflict` 与 `packet_vs_token_mismatch`，实测输出：

```
protocol_id             1019
protocol_name           Account_LoginSync
protocol_name_source    form token
id_name_conflict        Hash>>32=1019 → protocol_map 说它是 Account_RequestBirthdayMail；
                        但 form token 指向 Account_LoginSync。以 token 为准（report/67 D7 已定案）
packet_vs_token_mismatch packet Hash>>32 = 1019 但 protocol_map 给 token Account_LoginSync 的 id 是 1017
```

**建议**：把 `protocol_map.json` 里 `Account_LoginSync` 的 `id` 改成 1019，并给它一条"名字↔id 可能分叉"的一般性说明。这是别人的产物，我**没有改**。

### §3.1 它到底是什么 —— MITM 双向终结，**不是 TCP 代理**

这一节必须读，否则部署方向会错。

```
  ┌──────────┐   ①TLS：我们签的证书      ┌──────────────────┐   ②TLS：真服真证书   ┌──────────┐
  │ 客户端   │ ───────────────────────→ │ passthrough_      │ ──────────────────→ │ 真服     │
  │(BA 3.0.2)│ ←─────────────────────── │ capture.py        │ ←────────────────── │ gsqc-api │
  └──────────┘   ④TLS 加密的真服回包    └──────────────────┘   ③真服原始响应字节  └──────────┘
                     （原样，不解密）       │                            │
                                            └── 解密两侧明文件落盘 ──────┘
```

**为什么不能做 TCP 层透传（iptables/hosts 直连真服 IP）**：
客户端的 TLS 是拿**我们自己的 CA** 校验的（自签 CA 在 `work\ba\ba_test_root_ca.crt`，链路见 `report\20`，`report/evidence/22/*.pem` 是我们自签链）。如果直接把真服 IP 指过去，客户端会拿到**真服的证书**，而签发者不是我们的 CA → **握手直接失败**。
⇒ 必须我们终结入站 TLS（用我们的证书），再用**一条完全独立的出站 TLS 连接**冒充客户端连真服。这就是"二次连接"。

**为什么请求字节可以原样转发**：国服信封把 key 附在密文尾部一起传（请求 `IV16+CT+KEY32`，响应 `CT+KEY32`+固定 IV），**真服自己就能解**，不依赖会话共享密钥。所以逐字节转发是可行的。

### §3.5 ⚠ 透传能不能成功，只取决于这一件事

**请求字节可以原样转发，不代表真服会接受它。**

已有硬证据：`scripts/cn_real_capture.py` 当年把客户端**真实发出的 1138 B multipart 体原样** POST 到真服，得到的是：

```
{"protocol":"Error","packet":"{\"Protocol\":-1,\"Reason\":\"sdk check failed,code: 100403\",\"ErrorCode\":1018}",…}
```

`100403` 在官方 SDK 错误码表里是 **"登录已过期，请重新登录"**（`sdk_resp/common_client-code.json`）。

⇒ 推论（**这决定了整个 B 阶段的价值上限**）：

| 情形 | `Account_Auth` 结果 | 能否拿到 24000 |
|---|---|---|
| 离线重放旧的请求体 | `100403` | ❌ 永远到不了 |
| 客户端此刻真在登录，但 **SDK 域没劫持**（走真 SDK 还行？） | 见下 | 视情况 |
| 客户端此刻真在登录，**SDK 域也透传**，新 token 有效 | 可能通过 | ✅ |
| 客户端此刻真在登录，但我们用了别人的/过期的 token | `100403` | ❌ |

**部署时必须同时劫持 `example.com`**，让 SDK 侧真的走一次真登录签出新 token，否则 `Account_Auth` 必定被拒，`24000` 根本不会被真服处理，抓到的会是一片 Error 信封 —— 这仍然有用（它告诉我们真服的拒绝语义），但**回答不了 24000**。

### §3.6 推荐参数

| 参数 | 建议值 | 理由 |
|---|---|---|
| `--listen` | `127.0.0.1:8443`（前面挂 nginx） | 不当 root，端口冲突少 |
| `--upstream` | 真服 `HOST:PORT`，**每次现场解析后传入** | 不写死（任务要求），IP 会变 |
| `--capture-dir` | `/opt/bacap/captures`（`chmod 700`） | 见 §6.3 |
| `--proto-map` | 仓库的 `work/ba/proto/protocol_map.json` | 821 条，用于 token↔id↔name |
| `--timeout` | 30 | 真服偶发慢，给足余量 |
| `--max-decrypt-bytes` | 8 MiB | 24000 首次可能带全量数据；超了就只记长度，不中断 |
| `--insecure` | **默认不要加** | 校验真服证书；只有排查证书链时才临时加 |
| `--dump-dir` | 可选 `/opt/bacap/raw` | 额外落"发给真服的原样请求"，用于复现 |

### §5.1 一条命令 —— 先说文件名

>
> | | 扁平版 `diff_vs_official.py`（他人） | 本版 `diff_vs_official_at95.py` |
> |---|---|---|
> | 做法 | 把嵌套**拍平**成 `a.b.c` 路径再比 | **先比类型，再递归** |
> | 输出分类 | 只在A / 只在B / 类型 / 值 / 数组长度 | 类型不一致 / 空非空★ / 列表长度 / 只在真服 / 只在我们 / 值 |

> | 实测同一对样本 | `差异：仅A=59 仅B=1 类型=0 值=1` | `类型不一致 1（dict/list 1 ← 最高危）/ 只有真服有 3 / 值不同 1` |
> | 适配 | 自己造的四类口径 | 直接吃 `passthrough_capture` 的 capture 产物 |
>

        /opt/bacap/captures/20261114-153012_0007_24000_Academy_GetInfo.json \

`diff_vs_official_at95.py` 会自动剥壳：真服那份是 `passthrough_capture` 的产物（`{"_meta","request","response"}`）时取 `response.inner`；我们那份是裸内层或外层信封也能认。输出分桶，**按"先看什么"排序**：

| 桶 | 含义 | 为什么排这个位置 |
|---|---|---|
| **类型不一致** | 同一键两边类型不同；`dict ↔ list` 标 `风险=HIGH` | 反序列化**直接抛异常**，是弹窗的典型成因。第一优先 |
| **空/非空不一致 ★** | 一边 `[]`/`{}`，一边有内容 | 我们构造器的通病，本次最可能命中的就是这条 |
| **列表长度不同** | 都非空但条数不同 | 长度错一般是显示问题，不一定崩 |
| **只有真服有** | 我们缺键 | C# 落默认值，`long`→0、`DateTime`→`0001-01-01` 可能引发下游错误 |
| **只有我们有** | 真服不发这个键 | 若为默认值应删掉，减少噪音 |
| **值不同** | 同类型不同值 | 只关心 `ServerTimeTicks` 这类时间值 |

### §5.3 三个必须手看的点（自动 diff 看不出来）

1. **`ZoneScheduleGroupRecords` 的 key 类型**

## §6 风险与边界

### §6.1 证书与信任链 —— 为什么"TCP 代理"是不行的

再强调一次（这是本文档最容易被误读的一点）：

- 客户端信任的是**我们的 CA**（`work/ba/ba_test_root_ca.crt`），不是公共 CA。
- 真服的证书由公共 CA 签发，**不在我们的信任链里**。
- 因此"把域名指向真服 IP / iptables 端口转发"会让客户端**看到真服的证书** → 校验失败 → 握手失败 → 一个字节都抓不到。
- **唯一可行形态：我们终结入站 TLS（我们的证书）→ 我们作为客户端另开一条出站 TLS（真服的真证书）→ 在应用层转发字节。** 这是 **MITM 双向终结**，必须这么描述，不能叫"透传代理"。

### §6.2 带宽

- 单次登录链路：`Auth(1138 B 请求 / ~1 KB 响应)` → `Nickname(632/~900 B)` → `CallName` → `LoginSync` → **`24000`（首次可能几 MB，带全量 Academy / Mission 数据）**。
- 透传要**缓冲完整响应**才能解密落盘（不流式），所以单次 24000 的峰值内存 ≈ 响应体大小 + 一份明文。`--max-decrypt-bytes 8MiB` 是保护阀门：超了只记长度、仍然转发。
- 每条请求**新建一条 TLS 连接**（为了简单和可复现，故意不发 keep-alive）。代价是 TLS 握手开销，收益是绝不会因为连接复用把两条请求的字节混在一起。如果真服打了 24000 又连发多条，这会变成明显的开销 —— 属于可接受的设计取舍。

### §6.3 账号安全（**这条最容易出事**）

- `captures/` 里会有 **`SessionKey` / `MxToken` / 完整 `AccountDB`** 的明文（这正是我们的目的）。
- 更严重：`work\ba\bapatch\sdk_resp\user_detail.json` 里是**一个真实悠星账号的活凭据**（`Data.User.Token`、`Data.User.ID`、`Data.Pass.ID`，`RegChannel: android_official`，`IsTestAccount: false`）。本文**不抄写这些值**，只指路径 —— 谁需要谁自己看。
- 要求：
  - `captures/` 与 `sdk_resp/` 一律 `chmod 700`，**绝不进 git**，绝不贴群、绝不过公网。
  - 抓包机下机前 `tar` 加密留存，明文目录清掉。
  - 用**小号**，不要用主号。1xx 开头的 ID 一旦被判异常，损失是账号本身。
  - 抓完立刻在官方客户端上改一次密码/踢下线，让抓到的 token 失效。

### §6.4 频率限制 / WAF

- 既有脚本每次真连之前都要先查 `drop_ip.log` 里 `127.0.0.1` 的封禁年龄（`scripts/167_realcapture.sh`、`182_realcap.sh`），`report/23` 还专门写了"手动关闭宝塔 WAF"的指引 —— 说明这条路上确实被 WAF 拦过。透传时**每秒可能发十几条**，比手动点击密得多。
- 建议：`--listen` 挂 nginx 时给个 `limit_req`；**一次登录一轮就停**，不要循环点。
- 真服侧也可能限频：`429`/空 `200` 都可能在 `index.jsonl` 的 `status` 里看到。`passthrough_capture.py` 会把它们原样转发并记录，不会吞掉。

### §6.5 边界（事实陈述，不展开）

只抓**自己账号、自己设备**在自己这次登录中产生的那几条包；不批量、不并发压测、不外传、不用于任何分发。抓到的东西只服务于"把私服做对"这一个目的。

### §6.6 三种会让方案直接失效的情况（提前想好退路）

| 情况 | 表现 | 退路 |
|---|---|---|
| 真服在 `Account_Auth` 就拒（100403） | `index.jsonl` 全是 `protocol_id=1002` 且 `status=200` 但内层 `Protocol=-1` | 回到 §3.5：检查 SDK 域是否也劫持、token 是否新鲜 |
| 真服返回 `24000` 但 `resp_decrypt=failed` | 说明真服换了容器格式（比如响应也加号了长度前缀） | 用 `--dry-run --decrypt <那个body>` 单独试；`passthrough_capture.py` 的多布局扫描会打出每种布局的得分 |
| 客户端在 24000 之前就崩/弹窗 | 抓不到 24000 | 说明问题在更前面，与本次行动无关，回 §2.6 |

## §7 真服有 ACE 会不会检测到？—— 诚实说：**不知道**

能确定的和不能确定的，分开写：

**能确定（有依据）**

1. 客户端侧 ACE（腾讯 ACE）主要做**进程 / 内存 / 模块 / 调试器**扫描。本方案**不改客户端任何字节**（用的仍是既有 patch 版本），只改变网络路径 —— 从 ACE 的检测面看，网络路径不在它的常规扫描范围。
2. **但我们的 TLS 指纹一定不像官方客户端。** 官方客户端是 Unity `BestHTTP/2 v2.4.0`（`scripts/cn_real_capture.py` 的请求头里写着），Python `ssl` 的 ClientHello（密码套件顺序、扩展、ALPN、GREASE）与它差异明显。**JA3/JA4 一算就知道不是官方客户端。** 这一点我们无法完整伪装（要伪装到一致，得用真客户端库或自写 ClientHello）。
3. 服务端侧更现实的风险不是 ACE，而是**风控**：同账号短时间多 IP/多设备登录、请求时序过快、版本头不匹配。

**不能确定（必须当作未知）**

4. 真服会不会因为 TLS 指纹异常而降级/拒绝，我们没有证据。
5. 会不会因为"同一账号在我们这种环境下反复 100403"而标记账号，我们也没有证据。
6. 客户端侧 ACE 是否会因为**网络层延迟/往返特征**（我们缓冲完整响应，会比真服慢几十毫秒）而告警 —— 未知。

**⇒ 结论：把"可能被识别"当成既定成本。用小号、只跑一轮、跑完改密。**
