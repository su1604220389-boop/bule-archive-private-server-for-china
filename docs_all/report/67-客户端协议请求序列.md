## 关键发现

**D1 · 报错点已定位到具体协议：`Academy_GetInfo` = 24000。**
05:46:12 那条 `getinfo` 解密后是 `"Hash":103079215104015 → 24000`，客户端确实在要课程表/日程模块数据；我们回的内层**只有一个键** `{"Protocol":24000}`（`gen_kind="min"`），凑了个 192 B 信封。客户端拿不到任何字段，8 秒后弹「同步账号信息时发生错误。将返回标题画面」。这与 05:40:27（回 0 B）后 32 秒同样弹窗、05:50:33（回 0 B）后的表现一致 —— **同一个失败面，三种回法，全部失败**。

**D2 · `SyncProtocols` 是空的，别再等它点名。**
LoginSync 请求明文 `{"Protocol":"Account_LoginSync","SyncProtocols":[],...}`。也就是说客户端登录同步时**没有指定子系统**，我们必须自己决定 `AccountLoginSyncResponse.Responses` 里放什么（或直接放 30 个子回包）。`report/65` 里「Responses 由 SyncProtocols 决定」的中置信度假设，**证据不支持**：它在这台客户端上是空表。

**D3 · 失败顺序是 LoginSync → Academy_GetInfo，且 Academy_GetInfo 是最后一个。**
05:50:33 一轮里，客户端拿到 1019 的 492 B 桩回包后**立刻**（同一秒）去要 24000。所以：即使把 1019 做成完整版，只要 24000 不实现，客户端仍会在同步步报错。**优先级：24000 > 1019**。

**D4 · 「跳过发音」不产生协议请求。**
05:46 那轮完全没有 `callname` 记录，界面却从「您的姓名如何发音」走到了同步错误。⇒ 不需要为「跳过」实现任何协议；`1010` 只在用户真的提交发音时才会来。

**D5 · 客户端会重放同一个包。**
05:50:33 的 1019 包与 05:45:03 的 **字节完全一致**（同 `req_key`、同 `req_iv`、同 `Hash` 计数器 0），05:50:33 的 getinfo 包也与 05:45:03 的完全一致。⇒ 客户端在同步失败后会把**缓存的原包原样重发**，不重新加密。服务端实现可以按「幂等」处理，不能假设每次都是新包。

**D6 · 同一条 getinfo 有时能解、有时 CRC 失败（工程注意点）。**
05:40:27 与 05:46:12 的包能正常 gunzip；05:45:03 与 05:50:33 的包 `BadGzipFile(CRC check failed)`，且这**两个坏包彼此字节完全相同**、与好包差 1 个 base64 字符（尾部 `VE00` vs `VE04`）。这三条 body 里都有 3 个裸 `+` 号（form 编码里裸 `+` 会被 `parse_qs` 解成空格）。⇒ 我们的 form 解析对 `+` 的处理可疑，**建议改用 `urllib.parse.parse_qsl(body, keep_blank_values=True)` 前先做 `body.replace(b'+', b'%2B')` 或 `unquote_plus` 关闭**，否则 `Academy_GetInfo` 会有约一半请求在解包阶段就丢（这也解释了为什么同一协议时而 0 B、时而 192 B）。

**D7 · 协议号 1017 是误传。**
`1017 = Account_DismissRepurchasablePopup`；国服 `Account_LoginSync = 1019`，已由解密明文的 `Hash>>32` 钉死（`4376571674624 >> 32 = 1019`）。
