# 35 — 国服网关信封加密破解

> 时间：2026-11-14 03:10 前后
> 结论等级：**已破解，实测 100% 命中已知明文**

---

## 一、一句话结论

**国服客户端发往网关的 `packet` 不是 passphrase 派生的强加密，而是把 AES-256 密钥明文附在包尾的"混淆"：**

```
packet (base64) → [u32 LE 明文长度][gzip( 432 字节内层 )]
内层 432 字节  → [ iv : 16 ][ AES-256-CBC 密文 : 384 ][ key : 32 (ASCII) ]
                 key = 最后 32 字节的 ASCII 原文本身（base64 文本形态）
明文           → PKCS7 去填充后的 373 字节 JSON 片段（以 ',' 开头）
```

`16 + 384 + 32 = 432` ✓，三个区段边界干净，没有任何隐藏头。

---

## 二、完整解密算法（可直接照抄）

```python
inner = gzip.decompress(base64.b64decode(packet_b64)[4:])   # 432 字节
iv    = inner[0:16]
ct    = inner[16:len(inner)-32]      # 384 = 24 块
key   = inner[len(inner)-32:]        # 32 字节 ASCII，例如 b"MjRlMmQ1MmNiZDg0Mzc2MjBjZTgwOTI3"
pt    = AES_256_CBC_decrypt(key, iv, ct)
pt    = pkcs7_unpad(pt)              # 373 字节
json_ = '{"Protocol":"<名字>"' + pt.decode()   # 拼成完整 JSON
```

**没有任何 passphrase、没有 PBKDF2、没有 RSA。** 密钥就是包尾那串文本。

（严格说这是"客户端每包随机生成一把 32 字节密钥、用同一把密钥做 AES-256-CBC、再把密钥明文附在密文后面"。按密码学不提供任何保密性，只能挡住随手抓包的人。）

## 四、三条结构性发现

### 1. `{"Protocol":"<名字>"` 这一段**在密文之外**
密文只装参数部分，所以解密结果以 `,` 开头。协议名由表单字段 `protocol` 标识。

### 2. `protocol` 表单字段是 **base32**（不是 base64）
```
AHTQLQI65FWJGGGK4KL5AEF57A   (26 字符)
  → base32 去 padding（补 6 个 '='）→ 16 字节
  → 01 e7 05 c1 1e e9 6c 93 18 ca e2 97 d0 10 bd f8
```
- 26 字符正好是 base32 编码 16 字节的长度（26 = ceil(128/5)），而**不是** 4 的倍数，所以先前"base64 解出 19 字节"的判断是错的
- 该值**跨请求固定**（02:39:38 与 02:42:51 两份样本完全相同），与每包随机的 key 无关 ⇒ 它是协议名的确定性映射键，可用来建表

### 3. 明文里有 `"Hash": 4303557230595`
疑似防篡改校验。接网关时要观察服务端是否校验它（Shittim 的 `Account_CheckYostar` 不校验任何东西，所以可能无所谓）。

## 五、桥接方案（可直接实施）

```
客户端 POST /api/account/auth  (multipart: protocol / encode / packet)
   │
   ├─ packet b64 → 去 4 字节长度头 → gunzip → 432 B
   ├─ key = b[-32:], iv = b[0:16], ct = b[16:-32]
   ├─ AES-256-CBC 解密 → PKCS7 unpad → 373 B 片段
   ├─ '{"Protocol":"<名字>"' + 片段                ← 完整 JSON
   ├─ 打包 Shittim 的 .mx：
   │     [crc u32=0][typeConversion i32=0][keyLen=0][ivLen=0]
   │     + XOR(0xD9)( [u32 明文长度][gzip(JSON)] )
   └─ POST http://127.0.0.1:5000/api/gateway
          ↓
      客户端 ← 响应（格式待定，见第六节）
```

`.mx` 打包这一半 `srv-ops` 已经验证过能往返（造出的 `.mx` 被 Shittim 正常处理，`WireDump` 写出了明文交换，并且拿到了 `Account_Auth`=1002、`NetworkTime_Sync`=3 两个真协议号）。

**实测已产出**：`out.mx`（334 字节），内容就是上面那份 `Account_Auth` JSON。

## 七、走过的弯路（诚实记录，避免别人重走）

| 尝试 | 结果 |
|---|---|
| `key = MD5/SHA1/SHA256(passphrase)` × 590,858 条客户端字符串 × 5 种布局 | **零命中**（全量跑完，13 次进程崩溃后靠断点续跑） |
| `key = PBKDF2(passphrase, salt, iters∈{1,10,100,1000})` × SHA1/SHA256 × dklen{16,32} | 跑到 47k/115k 无命中后放弃 |
| `key = tail24 / proto16 / 各种 MD5 组合` | 无命中 |
| `protocol` 字段 base64 解码（19 字节） | **方向从一开始就错了**，那是 base32 |
| 432 字节按 protobuf / flatbuffers / CRC 头解析 | 全部不成立 |
| **`key = 尾部 32 字节 ASCII`** | **一次命中** |

**突破点是两个数字巧合**：①尾部那串恰好 32 字节（= AES-256 密钥长度）②`16 + 384 + 32 = 432`。把尾部直接当 key 试一次就中。

更早那条"尾部有明文 base64 ⇒ 不是整段加密"的直觉是对的，但理由想错了 —— **那是密钥本身，不是 token**。
