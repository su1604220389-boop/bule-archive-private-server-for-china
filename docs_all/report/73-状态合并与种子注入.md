## §2 每个注入项的依据

### 2.1 `currencies` 28 条

**形状是查代码定的，不是猜的。** `build_response.py:400-413`（`StateView._account_currency()`）在渲染时把
`state['currencies']` 合成 `AccountCurrencyDB.CurrencyDict` / `UpdateTimeDict`：

```python
for row in (self.d.get('currencies') or []):
    k = str(row['type'])                       # ← 键是 type 转字符串
    cur[k] = int(row.get('amount', 0) or 0)
    if row.get('updateTime'):
        upd[k] = row['updateTime']
```

所以喂进去的只能是列表、元素形如 `{"type": <int>, "amount": <int>, "updateTime": <19 字符 ISO>}`，
**不是字典**。成品里 1003 的 `CurrencyDict` 有 28 个数字串键，就是这个函数的输出（§5.2 有实物）。

**ID 从哪来**：`ids.json.currencies`（原表第 5481–5514 行），28 条，`id` 恰好是 `1..26 + 28 + 29`。
这不是推断 —— 货币段 ID 列本身就是 `CurrencyTypes` 的枚举值，这是 report/69 §5.2 的结论，也是 report/68 G3 的正解。
脚本对每条 `type` 做 **查表断言**：`ids.json.currencies` 里没有的编号一律 `die()` 拒绝写入。

### 2.2 `characters` 3 条

**结构**：`CharacterDB` 在 `dto_schema.json` 里 **15 个字段全齐**（`ServerId`/`UniqueId`/`StarGrade`/`Level`/`Exp`/
`FavorRank`/`FavorExp`/`PublicSkillLevel`/`ExSkillLevel`/`PassiveSkillLevel`/`ExtraPassiveSkillLevel`/
`LeaderSkillLevel`/`IsFavorite`/`EquipmentServerIds`/`PotentialStats`，conf 全 high）。
脚本对模板做**双向断言**：少了 DTO 字段、或多了 DTO 没有的键，都直接 `die()`。

| ServerId | UniqueId | 名称 | 选它的依据 |
|---|---|---|---|
| 1000001 | **10010** | 白子 | 任务指定；report/69 §3.4 四条论证：基础形态（无换装后缀）、序章/主线核心、落在首发批次 10000–10099、可覆盖 |
| 1000002 | **10000** | 爱露 | `students` 段**顺序补足**的第一条（基础形态） |
| 1000003 | **10001** | 艾米 | 同上第二条 |

**为什么给 3 个而不是 1 个**：`CharacterListResponse.CharacterDBs` 是 `List<CharacterDB>`，多角色与单角色
结构完全相同、校验路径完全相同，不引入新风险；而多角色能让客户端"队伍/编成/图鉴"界面有东西可显示。
补足规则是**机械的**（`students` 段顺序取，跳过名称含全角括号 `（` 或 `＊` 的换装/异格条目）——
不按喜好挑 ID，换一份 `ids.json` 规则依然成立。想只要白子：`--characters 1`。

**ServerId 怎么定的**：沿用 seed 分配器发给白子的 `1000001`（与 report/69 §3.4 的记录逐字一致），
后两条顺延。它**不和** `account.ServerId=1` 同段 —— 这两者是不同实体序列的号，客户端只用 `ServerId`
当不透明主键、不做交叉校验；而 `EchelonDB.AccountServerId` 指向的是真账号号（变体里已改成 `1`，不是 `1000000`）。

**哪些是推断**（ID 表只有 ID 和名称，**没有任何属性**）：

| 字段 | 值 | 依据 | 性质 |
|---|---|---|---|
| `UniqueId` | 10010 / 10000 / 10001 | `ids.json.students` 逐字 | **硬事实** |
| `ServerId` | 1000001–1000003 | 沿用 seed 分配器，确定性发号 | 自定主键（非推断实体属性） |
| `StarGrade` | 3 | 3★ 是常见初始稀有度、也是资源最齐的档位（立绘/EX 演出/专武数据都有） | **推断** |
| `Level` / `Exp` | 1 / 0 | 新号最低等级 | **推断** |
| `FavorRank` / `FavorExp` | 1 / 0 | 羁绊未升；1 是最小合法档（0 可能被判非法） | **推断** |
| 五个技能等级 | 1 | **不能给 0** —— 0 会被客户端当"未解锁/非法"，1 是不越界的最小合法值 | **推断** |
| `IsFavorite` | false | 未收藏 | 语义安全 |
| `EquipmentServerIds` | `[]` | 新号没装备；且 `EquipmentDB` 缺身份字段（§3.2） | 结构合法 |
| `PotentialStats` | `{}` | 潜能未解锁 | 结构合法 |

### 2.3 `account.RepresentCharacterServerId` 0 → 1000001（唯一改动 account 的字段）

三个理由：
1. `build_response.py` 的 `--check-state` 有一条显式不变量：`RepresentCharacterServerId` 必须是 0 或
   `characters` 里某个 `ServerId`。现在有角色了，指向白子才自洽；
2. report/68 §4 R2 明确要求「有学生之后**必须**同时改」；
3. 不改的话，`characters` 非空但大厅看板是空的 —— 数据进了、观感没进。

**它不是哨兵**：任务列的四个哨兵是 `State=1` / `LobbyMode=1` / `ServerId=1` / `BirthDay=1970-01-01`，
这三个 + `PublisherAccountId=314816420` / `DevId="baserver"` / `Nickname="111"` / `CallName="111"` 全部原值保留（§1.3 断言）。
**回退办法**：`python merge_seed_into_state.py --no-represent`（重新生成一份不带代表角色的状态）；
注意 `build_response.py --set` 只改**本次生成**的内存视图、不落盘，不能用来改状态文件。

顺带核对过的联动项：`clan.member.AccountNickName="111"` 与 `account.Nickname` 一致（没改名，不需要同步，report/69 §5.4 的担心不触发）；
`clan.member.RepresentCharacterUniqueId` 仍是 0 —— 未进公会（`clan.accountClan=null`），当前不进任何回包，
将来进公会时再同步（见 §3.6）。

### 2.4 `echelons`：默认空，另给一份可选变体

**默认留空的理由不是"结构不全"** —— `EchelonDB` 11 个字段在 schema 里全齐（脚本同样做了双向断言）。
留空的原因是**枚举数值取不到**（report/68 G3）：

- `EchelonType`（`EchelonType` 枚举）、`ExtensionType`（`EchelonExtensionType`）、
  `UsingFlag`（`EchelonStatusFlag`）三个字段都是 `kind: enum`，而 `dto_schema.json` 只标了类型名、**没有取值表**；
- 从 metadata 的 `fieldDefaultValues` 段读出来的是加密分页的乱值（report/68 §4 G3 已证），
  硬塞 `0` 等于拿"未知"冒充"合法"；
- 编队是**需要枚举语义**的实体（report/68 G6 的原则：需要枚举语义的实体，我们就不发，而不是发一条 0 值记录去蒙）。

**可选变体怎么用**：`--with-echelon` 会把 seed 那条编队接上，并且把
`AccountServerId` 从 seed 的 `1000000` 改成真账号的 `1`、`LeaderServerId`/`MainSlotServerIds`
指向新发的角色号：

```
account_state.seeded.withechelon.json  →  1 条编队（1 号队，队长=白子，主槽 1000001/2/3）
out\seeded\optional\5000_Echelon_List.withechelon.json  →  对应成品包
```

它的 `EchelonType=0 / ExtensionType=0 / UsingFlag=0` 是**推断值**（可能是 `None`/`Invalid`）。
**判据**：默认那份（空编队）先上线；若客户端在大厅/编成界面报"没有队伍"或 NRE，再切这份变体 A/B。
两份状态的 `--check-state` / `--check-all` 都通过（`16 实体 0 问题` / `33 通过 0 失败`）。

### 2.5 时间与确定性

- 所有时间字段 = `_meta.frozenTime` = `"2026-11-14T00:00:00"`（与 `gen_default.DT_DEFAULT`、`account_state.json`
  的 `frozenTime` 同一个值），`ServerTimeTicks` = `639302112000000000`；
- **代码里没有 `now()`**：`--check-state` 会扫全文件，任何不在这两个白名单里的 19 字符 ISO 时间都报错 —— 它 0 问题；
- **确定性**：同一输入连跑两次，`account_state.seeded.json` 的 sha256 均为
  `686B9A9CA85227C74387C3ACDD8830FFF4C66AA03018D9F426E20736608A77D7`；可变项一律不写进产物
  （`_meta.seedMerge` 只记输入文件的 sha256，不记生成时刻）。

## §3 仍然为空或缺失的（诚实清单）

### 3.1 G2 — `ItemDB` 结构不全，`items` 只能留空（**最硬的一条**）

`dto_schema.json` 里 `ItemDB` 的**全部字段只有一个**：

```json
"ItemDB": {"fields": [{"name": "Expires", "type": "Nullable<DateTime>", "kind": "nullable", "conf": "high"}]}
```

真实 proto 的 `ItemDB` 继承自 `AbstractItemDB`，`ServerId` / `UniqueId` / `StackCount`（或 `Amount`）是

### 4.2 为什么通过数不变，以及"没变差"的证明

`--check-all` 校验的是**结构完整性**（字段齐全 / 无多余键 / 类型 / 子回包递归），不是"数据有多满"。

### 5.2 两种接入方式

**方式 A：直接发成品（最省事）**

```
读 out\seeded\<协议号>_<名字>.json → 补网关信封（AES/信封头）→ 发
```

每份都是完整 `ResponsePacket`：顶层带**整数** `Protocol`，加上响应 DTO 的全部字段（含 6 个基类字段）。
唯一要按链路补的是网关信封（加密/`Hash`/序列号），本报告不涉及。

**方式 B：进程内用引擎（可多账号、可改状态）**

```python
import build_response as br
schema = br.Schema(br.load_json('dto_schema.json'))
pmap   = br.load_json('protocol_map.json')
state  = br.load_json('account_state.seeded.json')     # 启动时读一次
b = br.Builder(schema, pmap, state)
pkt = {'Protocol': 2000}; pkt.update(b.build_body('CharacterListResponse'))
# 登录同步：
pkt = b.build_login_sync(1017, sync_protocols=None, mode='list')
```

`--check-state` 建议放在服务启动时跑一遍，坏了直接拒绝启动，比半路报错好（report/68 R6）。

### 5.3 四个现成的切换开关

| 想变什么 | 怎么切 | 影响 |
|---|---|---|
| 只发白子一个角色 | `python merge_seed_into_state.py --characters 1` | `characters` 1 条，2000/1017 同步变 |
| 大厅不挂代表角色 | 加 `--no-represent` | `RepresentCharacterServerId` 回到 `0`，仍是合法状态（0 或自己的 ServerId 都过校验） |
| 想要有编队 | 用 `account_state.seeded.withechelon.json` + `out\seeded\optional\5000_...` | 1 条 1 号队（队长=白子），枚举值属推断 |
| `Responses` 形态不确定 | 三份 1017 直接换 | 只有 `Responses` 一个键不同 |

### 5.4 关于 `24000_Academy_GetInfo.json` 的一个**有意偏离**

`gen_academy.py` 的默认输出是 `StaticOpenConditions: []`（`dto_schema_academy.json` 判成
`List<OpenConditionDB>`）。但 `build_response.py` 有一条 `TYPE_OVERRIDES`：CN 客户端实测接受
`dict<string,int>`（report/68 §4 G1 / report/49 的生产 payload 已过 `Account_Auth`）。
`AcademyGetInfoResponse` 继承的是**同一个 `ResponsePacket` 基类**，所以成品里这一项按实测形态绑定成
**55 键全 0 的字典**，和 1017 / 2000 里那份**逐键一致**。

具体偏离只有 5 个基类字段（`ServerTimeTicks`=639302112000000000、`StaticOpenConditions`=dict、
三个 mission 块 = 状态里的 `[]`/`{}`），`AcademyDB` / `AcademyLocationDBs` 完全是 `gen_academy.build()` 的原样输出。
若手机侧证明 `Academy_GetInfo` 要数组形态，直接把这一项换回 `[]` 即可（一行改动，不用碰 `gen_academy.py`）。
