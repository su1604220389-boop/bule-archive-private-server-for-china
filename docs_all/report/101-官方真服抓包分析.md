### 4.2 但本轮发现了一条关于 24000 的**坏消息**（很重要）

查 `work\ba\proto\observed_sequence.json`（2026-11-14 那轮私服日志取证），`last_request_before_sync_error.our_reply` 记录的**我们上一轮的 24000 响应**是：

> **也就是说：我们最近一次真实失败的那一轮，24000 回给客户端的其实是 `min` 兜底 —— `{"Protocol":24000}`，只有 1 个 key、192 字节，根本没跑 Academy 模板。**

### 7.3 下一步（按性价比排序）

**⓪ 先做这个（10 分钟，可能当场解决「同步账号信息」错误）**

**③ 拿到含 RPC 的 HAR 后**
```powershell

```

## 附录 B：`_id=5` 那条被删的到底是什么

`_id` 是 Reqable 的到达序号，88 条覆盖 `1..89`，**唯一缺号是 5**。缺口邻居：

```
_id=4   2026-11-15T19:59:29.432Z  GET  yostar-cn-netsdk-logging.cn-shanghai.log.aliyuncs.com /servertime
        <===============  _id=5 被删  ===============>
_id=6   2026-11-15T19:59:29.662Z  GET  static.bluearchive-cn.com /checkhealth.html
```

**判定：它不可能是游戏 RPC。** 两条独立理由：

1. **位置**：夹在 `03:59:29.432` 与 `03:59:29.662` 之间，即 **app 启动后第 0.5 秒**。此时 SDK 还没登录（登录发生在 `04:00:05`），游戏不可能发 RPC。该位置的请求全是启动期探活/埋点（`servertime`、`er.ns.aliyuncs/policy`、`checkhealth.html`、`sdk-api` 根路径）。
2. **数量**：全文**一条 RPC 都没有**。若删掉的那条是 RPC，那至少还得有 `account/auth` 等其余 RPC 在场——它们全都不在。**1 条删除无法解释 0 条 RPC。**

**最可能是**：与 `_id=2`（`client-logging/servertime`）、`_id=4`（`netsdk-logging/servertime`）同批的第三个启动埋点，例如 `er.ns.aliyuncs.com` 的第二次 `policy`、或上一轮 `baba.har` 里出现过而本轮缺失的 `cbsipv4.shuzilm.cn`（IP 归属查询）。**属无害信息，不影响任何结论。**
