## §2 每个地址是怎么核实出来的

### 2.1 代码洞 `0x0f2c2410` —— RX 段 `p_filesz` 的终点

```
$ readelf -lW libil2cpp.bin        （本机脚本解析 program header）
[2] LOAD  off=0x59b8000 va=0x59b8000 filesz=0x990a410 memsz=0x990a410 flags=5(R+X) align=0x4000
          off+filesz = 0xf2c2410
[3] LOAD  off=0xf2c4000 va=0xf2c4000 filesz=0x8ec868           flags=6(RW)
```

依据链：

1. RX 段 `p_vaddr == p_offset`（都是 `0x59b8000`）⇒ 本段内 **文件偏移 == 运行期 VA 的模块内偏移**。
2. `p_filesz` 正好结束在 `0x0f2c2410`，而 `p_memsz == p_filesz`（没有 BSS 尾巴）。
3. 加载器按页映射：最后一张页 `[0xf2c2000, 0xf2c3000)`（4 KB 页）被 `mmap` 整页映射，
   页尾 `[0xf2c2410, 0xf2c3000)` 的内容来自文件里那一段"不属于任何 LOAD"的字节。
   ⇒ **既可读可执行，又没人用**。容量 `0xBF0 = 3056 B`（16 KB 页的机器上是 `0x1BF0 = 7152 B`，本项目按保守值卡）。
4. `build.py` 每次构建都重新断言 `off+filesz == 0xf2c2410`，一旦上游换包立刻报错退出。

本次只用了 **2936 B / 3056 B**，余量 120 B。

### 2.2 `DT_INIT` 在 `0x0fa2fc50`

```
$ .dynamic @ 0x0fa2fad8 (size 0x200)
  DT_INIT 条目 @ 0x0fa2fc48, d_val = 0x0010496434
```

* `DT_INIT` 的 **`d_val` 落在 `0x0fa2fc50`**（条目本身是 `0x0fa2fc48`，`d_tag` 在低 8 字节）。
  这与任务书写的"文件偏移 `0xfa2fc50`"一致，我这边独立扫 `.dynamic` 得到的也是同一条。
* 原厂值 `0x0010496434` 指向 `PT_LOAD[10]`（`va=0x10494000, filesz=0x3370, flags=R+X`）里的真实代码，
  反汇编为 `mov w0,#1; b …` 之类的初始化桩链 —— 是**真的 C++ 静态初始化**，不是跳洞桩。
* `build.py` 断言 `d_val == 0x10496434`，否则拒绝构建（防止拿 `libil2cpp_patched.bin` 之类当基线）。

### 2.3 ⚠️ `0x13FACF` 不是代码地址（必须更正的前情）

```
$ python: 读 global-metadata.dat @0x13FACF
  b'Dungeon\x00HandleAccountAuthResponseMessage\x00OnLoginFinish\x00d'

$ python: 读 libil2cpp.bin @0x13FACF (48B)
  00 30 5e 32 0f 00 00 00 00 03 04 00 00 00 00 00
  00 dc 8c 02 06 00 00 00 00 38 5e 32 0f 00 00 00
  ascii:  .0^2.....................8^2....................
```

* `global-metadata.dat` 是**方法名表**，40 个 `LoginTask` 成员名在 `0x13F654`–`0x13FD9B` 连续排布
  （`report\39` §4.3 那张表就是按这个顺序列出来的）——**一眼可知那不是代码，是字符串区**。
* `.so` 里同一偏移是普通只读数据，没有任何函数序言（`stp/sub sp/paciasp`）。
* 附带确认：本包的方法名表**是明文**，所以"按名字找方法"这条路在运行期完全可行（§2.6）。

⇒ **结论：想钩 `HandleAccountAuthResponseMessage`，静态改代码需要的是 `methodPointers` 里的那个代码 VA，
而那个 VA 必须靠 `global-metadata.dat` 的 `methods` 表 + `Il2CppCodeGenModule` 才能算出来。
本包 metadata 头被混淆（magic `0x12724394`，标准 sanity 全文件 0 命中），静态这条路还在攻坚中
（`report\_tmp\meta\h*.py` 那条线）。本版不等它——改用运行期按名字找（§2.6）。**

### 2.4 触发器 `0x063c77fc` —— 全模块「被调用次数最多」的函数

做法：把 `.text`+`il2cpp` 段里**每一条 `BL`**（opcode `100101`）的目标统计一遍（3,465,919 条 BL，92,241 个不同目标）：

```
rank  target       bl_count   前 4 条指令
   0  0x063c77fc     413726   a9bf7bf3 aa0003f3 94010c8e b940da60
   1  0x063c72ac     362096   f81f0ffe 94012597 d5033bbf f84107fe
   2  0x063c73d0     272077   f81f0ffe 9401ae05 f81f0ffe 9401ae16
   ...
```

反汇编 `0x063c77fc`：

```asm
63c77fc: a9bf7bf3   stp  x19, x30, [sp, #-0x10]!
63c7800: aa0003f3   mov  x19, x0
63c7804: 94010c8e   bl   0x640aa3c            ; Class::Init 一类
63c7808: b940da60   ldr  w0, [x19, #0xd8]     ; klass->initialized 之类
63c780c: 35000080   cbnz w0, 0x63c781c        ; 没初始化就走慢路（0x63c781c 起还有一大段）
63c7810: aa1303e0   mov  x0, x19
63c7814: a8c17bf3   ldp  x19, x30, [sp], #0x10
63c7818: d65f03c0   ret
```

从反汇编看，这是 Unity 生成代码在方法入口会调的那个"类型是否已初始化"检查助手（读 klass->+0xd8，为 0 就往下走初始化）。
**413,726 个调用点**意味着：只要游戏在跑，它每秒都在被调几千次 —— 这正是我们要的
"延迟到 il2cpp 完全初始化之后再干活的时机"，而且**不需要线程**。

前 4 条能否无损回放（`build.py` 第 7 步自动判定并打印）：

| # | 指令 | 判定 |
|---|---|---|
| +0 | `stp x19,x30,[sp,#-0x10]!` | PC 无关，原样 |
| +4 | `mov x19,x0` | PC 无关，原样 |
| +8 | `bl 0x640aa3c` | 距洞 147 MB > ±128 MB ⇒ 生成 6 字跳板（`ldr x16,#16 / blr / b / nop / imm64`） |
| +12 | `ldr w0,[x19,#0xd8]` | PC 无关，原样 |

回放语义等价性：`stp` 压入的 `x30` 是**调用者返回地址**（我们的 trampoline 在进洞前已把它从栈上恢复），
所以被钩函数结尾 `ldp x19,x30,[sp],#0x10` 拿到的还是原值，`ret` 照常回到调用者；
跳板里的 `blr` 把 `x30` 写成洞内地址，与原始 `bl` 写成 `0x63c7808` 一样都只是"下一条"，同样会被上述 `ldp` 覆盖。

### 2.5 为什么不改 game 代码 —— ACE 加密页

`bapatch\encrypted_pages.txt` 记了 183 段 `.text` 可疑加密页（16 KB / 64 KB 一档）。
实测吻合：`il2cpp_class_get_method_from_name` 的真身 `0x640b1e8` 落在 `0x640a000-0x640e000` 里，
文件里是

```
640b1e8: e3d6ca2a 63d6ca2d ddc9c9ca 63d6ca2d …   ← 不是合法 ARM64
```

而同族的导出桩（`0x63c2eac: 140120cf b 0x640b1e8`）却是明文。
⇒ **这些页在文件里是密文，运行期由 ACE 解密**。往这些偏移写补丁会被解密覆盖；
运行期改又要处理指令重定位。

所以本版的目标方法**一个字节都不碰**：
只把 `MethodInfo.methodPointer`（`.data.rel.ro` 里一个 8 字节数据槽）换成洞里的 detour，
detour 记完日志再把 `br` 回原指针。返回值、异常、栈帧全部原样。

### 2.6 运行期按名字找方法：用到的 3 个 il2cpp API（都是导出符号，地址已实证）

来源于 `report\_frida\_out\il2cpp_syms.json`（1201 个恢复出的具名导出，`.gnu.hash` 链反推），
并用 `llvm-objdump` 复核了真身：

| 用途 | 导出桩 | 真身 | 复核 |
|---|---|---|---|
| 遍历所有类 | `il2cpp_class_for_each` @ `0x063c3b50` | `0x06391eb0` | 反汇编见下 |
| 遍历类的所有方法 | `il2cpp_class_get_methods` @ `0x063c2ea8` | `0x0640b084`（加密页，运行期可控） | 导出桩是 `b` |
| 取方法名 | `il2cpp_method_get_name` @ `0x063c37bc` | `0x063926a8` | `ldr x0,[x0,#0x18]; ret` ← 明文实证 |

`il2cpp_class_for_each` 真身（明文，`0x06391eb0`）：

```asm
6391eb0: f81c0ff8   str  x24, [sp, #-0x40]!
6391eb4: a9015bf7   stp  x23, x22, [sp, #0x10]
6391eb8: a90253f5   stp  x21, x20, [sp, #0x20]
6391ebc: a9037bf3   stp  x19, x30, [sp, #0x30]
6391ec0: aa0103f3   mov  x19, x1          ; x19 = userData
6391ec4: aa0003f4   mov  x20, x0          ; x20 = callback
6391ec8: 9401130b   bl   0x63d6af4
6391ecc: a9402018   ldp  x24, x8, [x0]
...
6391f00: 3944c808   ldrb w8, [x0, #0x132] ; 一个过滤位
6391f04: 36080068   tbz  w8, #0x1, 0x6391f10
6391f08: aa1303e1   mov  x1, x19
6391f0c: d63f0280   blr  x20             ; callback(klass, userData)  ← 签名实证
```

⇒ 回调是 `void (*)(Il2CppClass*, void*)`，`x0 = klass`、`x1 = userData`，与 Unity `il2cpp-api.h` 一致。

`il2cpp_method_get_name` 取的是 `MethodInfo+0x18`（不是 `+0x10`）——说明本包 `MethodInfo` 前面
多了一个 `virtualMethodPointer`（Unity 2022+ 的排布）。**这正是我只改 `+0` 那个 qword 的原因**：
`methodPointer`（直接调用用的那个）在 `+0`；detour 里 `br` 回它即可。
为了留证据，装钩时会额外打一行 `Q<tag>` 把 `MethodInfo[0..3]` 原样写进日志。

**为什么不用 `il2cpp_class_get_method_from_name`**：它的真身在加密页，无法离线确认它是否内部
调 `Class::Init(klass)`。若调，那就是对**每一个类**执行静态构造 —— 灾难。
用 `get_methods`+`get_name` 纯读，绝不触发 `.cctor`。

## §3 日志形态与判读

日志：`/data/data/com.RoamingStar.BlueArchive/files/probe.log`（**不能写 `/sdcard`，会静默失败**）

### 3.1 行格式

```
<tag><一位十进制> <hex16> <hex16> <hex16> <hex16>
```

| tag | 含义 | 字段 |
|---|---|---|
| `B` | DT_INIT 钩子跑起来了 | `base` `logfd` `caveVA(0xf2c2410)` `mprotect页` |
| `C` | 常量自检 | `class_for_each` `get_methods` `orig_dt_init` `0` |
| `S` | 开始一次扫描 | — |
| `R` | 扫描结束 | `第几次` `命中位图` `扫过的类数` `看过的方法数` `base` |
| `P` | **已把某个目标改成 detour** | `原methodPointer` `被改的槽地址` `klass` `MethodInfo` |
| `Q` | MethodInfo 现场 + 形参个数 | `MI[0]` `MI[8]` `MI[16]` `形参个数` |
| `U` | 收工，触发器之后只回放 | `命中位图` `第几次` `类数` `方法数` |
| `A` | **detour 被调用到！** | `x0` `x1` `x2` `x3` |
| `Y` | `x0`／`x1` 看起来是 C# 字符串 | 紧随其后是最多 48 个可见字符（**只有 `Q` 里形参个数 ≥1 时才会去碰 `x1`**） |
| `Z` | `HandleAccountAuthResponseMessage` 的 `x1+0x10` 起 4 个 qword | 响应对象字段的原始值 |
| `!` | mprotect 失败等 | — |
| `Z1` | **洞页没能改成可写 → mprotect 失败** | 后面跟 `mprotect_fail` |

`tag` 的数字 = 目标编号：**0 = `HandleAccountAuthResponseMessage`**、**1 = `ErrorAccountAuth`**、
**2 = `OnLoginFail`**、**3 = `OnLoginFinish`**。

### 3.2 判读表（一次观察就能定案）

| 日志里看到 | 结论 | 下一步 |
|---|---|---|
| 文件不存在 | DT_INIT 没执行 / 洞没被映射 / 被 ACE 拦了 | 先确认 `sha256sum` 装进去的是不是成品；再退到"只改 PLT"方案 |
| 只有 `Z1 mprotect_fail` | 洞跑到了，但**页权限改不动**（ACE 或 SELinux 拦 mprotect） | 放弃运行期改数据，转静态改代码（要等 metadata 攻坚） |
| `B0 …` | DT_INIT 钩子通了，`base`/`fd` 都在里面 | 看是否有 `S`/`R` |
| `B0` 但**一直没有** `S` | 10 秒内触发器没跑到（或 `g_skip` 没武装） | 检查 `B0` 第 1 字段（mprotect 返回）；再看 `R` 的 `第几次` |
| 有 `S`/`R`，`扫过的类数` 很小（<100） | 扫太早了，il2cpp 还没把类建出来 | 等下一次 `R`（8/10/12…秒各一次，共 40 次） |
| 有 `R`，`命中位图` = 0 | **4 个名字一个都没匹配到** ⇒ 要么方法名不在这套字符串里，要么 `get_methods` 的用法不对 | 看 `Q0` 是否出现过；把 `R` 的"看过的方法数"贴出来（正常应是 50 万量级） |
| 出现 `P0` | **钩子已装上 `HandleAccountAuthResponseMessage`** | 等 `A0` |
| **出现 `A0`** | ★ **客户端确实走到了这个处理器** —— 这一条就把"响应有没有到处理器"定案了 | 解读 `x0`/`x1`/`Y0`/`Z0` |
| 有 `P0` 但**始终没有** `A0`，而 `P1`(ErrorAccountAuth)/`P2`(OnLoginFail) 有 `A1`/`A2` | **响应到了、但被判失败** —— 走的是错误分支 | `A1`/`A2` 的 `x0` 就是失败上下文 |
| `P0/P1/P2` 都有，`A*` **一个都没有** | 登录流程根本没跑到 `Account_Auth` 之后 | 问题更靠前（请求没发出/被 SDK 拦），不在解析层 |
| 有 `Y0 xxxx` | `x0` 或 `x1` 直接就是 C# 字符串，内容就是**客户端实际收到的东西** | 直接读 |
| 有 `Z0 q0 q1 q2 q3` | 响应对象前 4 个字段（`klass*` 之后） | 指向 libil2cpp 内（`base+0x5…`）的多半是 `MethodInfo`/类指针；指向堆（`0x7f…`/`0x74…`）的多半是子对象或字符串，可进一步解 |

> 说明：`A0` 的 `x0` 是 `this`（`LoginTask*`），`x1` 才是响应消息对象（实例方法的第一个参数在 `x1`）。
> `Y`/`Z` 两行就是按这个假设打的。

## §4 上机手册（给 lead）

> 前提：游戏**已杀死**（这是安全写入窗口）。上一版把 so 写成 0 字节，就是在游戏跑着的时候用 `>`
> 重定向写的。**全程禁止 `>`，只用 `cp` + `mv -f`。**

```sh
# 0) 拿到包路径（不同设备后缀不同）
adb shell pm path com.RoamingStar.BlueArchive
#   → package:/data/app/~~xxxx==/com.RoamingStar.BlueArchive-yyyy==/base.apk
#   LIB 目录 = 上面路径把 base.apk 换成 lib/arm64
#   下面统一用 $LIB 代替，先自己 export 好：
adb shell "LIB=\$(dirname \$(pm path com.RoamingStar.BlueArchive | sed 's/package://'))/lib/arm64; echo \$LIB"
```

### 4.1 上机

```sh
# 1) 确认游戏真的没在跑（有输出就说明还在跑，先强杀）
adb shell "su -c 'pidof com.RoamingStar.BlueArchive'"

# 2) 备份（若 /data/local/tmp/il2cpp.factory.so 已是 5ac1cbe0… 可跳过）
adb shell "su -c 'sha256sum \$LIB/libil2cpp.so'"
adb shell "su -c 'cp \$LIB/libil2cpp.so /data/local/tmp/il2cpp.baseline.\$(date +%s).so'"

# 3) 推成品
adb push work/ba/runtimehook/libil2cpp_hook.bin /data/local/tmp/il2cpp_hook.so

# 4) 本地先算好期望值，再在手机上核对（大小 + sha256 两项都要对）
#    期望：270927056 B
#    sha256：11cefd6d5b89536ad588af581c7d19b85e03212a3f01319de4ed872745147b6f
adb shell "su -c 'stat -c %s /data/local/tmp/il2cpp_hook.so'"
adb shell "su -c 'sha256sum /data/local/tmp/il2cpp_hook.so'"

# 5) 原子替换：先 cp 到目标目录里的临时文件，校验，restorecon，最后 mv -f（rename 是原子的）
adb shell "su -c 'cp /data/local/tmp/il2cpp_hook.so \$LIB/.new_libil2cpp.so'"
adb shell "su -c 'sha256sum \$LIB/.new_libil2cpp.so'"          # 必须等于上面那个 sha256
adb shell "su -c 'chown system:system \$LIB/.new_libil2cpp.so'"
adb shell "su -c 'chmod 644 \$LIB/.new_libil2cpp.so'"
adb shell "su -c 'restorecon -v \$LIB/.new_libil2cpp.so'"       # 打印 applied，不是 failed
adb shell "su -c 'mv -f \$LIB/.new_libil2cpp.so \$LIB/libil2cpp.so'"
adb shell "su -c 'sha256sum \$LIB/libil2cpp.so'"                # 再核一次

# 6) 清日志 → 启动 → 等登录流程走完（30~60 秒）
adb shell "su -c 'rm -f /data/data/com.RoamingStar.BlueArchive/files/probe.log'"
adb shell monkey -p com.RoamingStar.BlueArchive -c android.intent.category.LAUNCHER 1

# 7) 读日志
adb shell "su -c 'cat /data/data/com.RoamingStar.BlueArchive/files/probe.log'"
adb shell "su -c 'ls -l /data/data/com.RoamingStar.BlueArchive/files/probe.log'"
```

> `LIB` 里带 `~~xxxx==` 这种随机后缀，**别手打**，用第 0 步那条命令展开。
> 若 `restorecon` 不认（旧 toybox），用 `chcon u:object_r:apk_data_file:s0`；`mv -f` 之后
> 再用 `ls -Z` 看一眼 label 是不是 `apk_data_file`。

### 4.2 回滚（10 秒内完成）

```sh
adb shell "su -c 'cp /data/local/tmp/libil2cpp.factory.so \$LIB/.rb.so'"

```

## §5 风险与回滚

| 风险 | 概率 | 后果 | 兜底 |
|---|---|---|---|
| 触发器挑错函数（不是"每方法进入都调"的那个） | 低 | 只是不扫描、不崩：`g_skip` 一直是 1，触发器只做 4 条指令回放 | 回滚；换直方图 rank 1/2 |
| `mprotect` 被 ACE 拦 | 中 | 只写 `Z1 mprotect_fail`，游戏照常启动 | 转静态改代码路线（要等 metadata） |
| 类枚举扫太早 / 过滤位跳过目标类 | 中 | `R` 里命中位图 0，多试几次 | 本版自动重试 40 次（8/10/12/…86 秒） |
| 改 `MethodInfo.methodPointer` 让 ACE 起疑 | 低 | ——（只改数据页，页权限短暂 RWX→RW） | 回滚 |
| 触发器常驻带来固定开销 | 确定 | 每次该助手调用多 5 条指令（`adrp/ldr/cbnz`） | 本版**故意不做运行期卸载**：卸载要写代码页，与正在执行的线程有竞态；5 条指令的开销远小于一个竞态 |
| 洞被别的补丁覆盖 | 低 | —— | 本版从原厂 `libil2cpp.bin` 构建，且 `build.py` 强校验 sha256 |

**可用备份（手机上现成的）**

| 路径 | sha256 | 说明 |
|---|---|---|
| `/data/local/tmp/il2cpp_orig.so` | `6e2edf5a…` | 早期备份（可能是已被改过的版本，**用它回滚前先比 sha**） |
| `/data/local/tmp/libil2cpp.factory.so` | `5ac1cbe0…` | **原厂纯净版，优先用这个回滚** |

**本地基线**：`work\ba\bapatch\libil2cpp.bin` = `5ac1cbe0fb8f730ffd22b93624a70ae9c90b0a1f3f3fbeb18c5d6af3c73882c3`（270,927,056 B）

**⚠️ 不要用的文件**

| 文件 | sha256 前缀 | 为什么不能用 |
|---|---|---|
| `work\ba\bapatch\libil2cpp_patched.bin` | `a473ba16` | g20 探针，洞里是坏的旧桩 |
| `work\ba\bapatch\libil2cpp_probe.bin` | `16fd1eba` | 只打出过 `START`，崩在 `pthread_create` |
| `work\ba\runtimehook\cave\libil2cpp_hook.bin` | `4ea00986` | **上一轮 pthread 版**（`cave\hook.c` + `mk_hook.py`）的产物，本版已取代它 |

## §6 边界与没做的事

* **没有**连接手机 / 服务器；没有 adb、没有 ssh、没有 Operit API、没有 push 任何文件。
* **没有**碰 `libtprt.so`；**没有**用 `pthread_create`；**没有**起任何线程。
* **没有**改动 game 的代码（只改 2 处代码：洞 + 触发器；1 处数据：`DT_INIT`）。
* **没有**解决"静态算出 `HandleAccountAuthResponseMessage` 的代码 VA"——那需要解 `global-metadata.dat`
  的头部（magic `0x12724394`，被混淆）或从 `Il2CppCodeGenModule.methodPointers` 按 token RID 反查。
  这一版**绕过**它：运行期按方法名找。如果以后静态地址拿到了，`build.py` 加一个
  `--hook NAME=VA` 直接走静态 trampoline 即可（回放槽和跳板逻辑现成能用）。
* 本版**不能**回答"响应体原文是什么"，只能回答"处理器有没有被调用到、`x0/x1` 是什么"。
  要拿原文，下一步应当钩网络层的 `HttpGameMessage.DecryptOrReturnOriginal` 一类函数（同样是"按名字找"，
  同一套机制可以直接复用）。
