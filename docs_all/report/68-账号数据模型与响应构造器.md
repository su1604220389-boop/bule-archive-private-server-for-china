# 68 · 账号数据模型与响应构造器（国服《蔚蓝档案》私服）

> 目标：把"一条条手写 JSON、缺口返回空壳"换成**一份账号状态 + 按协议自动构造完整响应**。
> 交付物：`work\ba\proto\account_state.json`（状态）、`work\ba\proto\build_response.py`（引擎）、
> `work\ba\proto\out\1001_Account_Nickname.json`、`work\ba\proto\out\1017_Account_LoginSync.json`（成品）。
> 只读引用、**未修改**：`dto_schema.json`(91,469B) / `protocol_map.json`(127,725B) / `gen_default.py`(12,764B)。
> 全程不连手机、不连服务器、不碰 `libtprt.so`。

---

## §0 一句话结论

`Account_LoginSync`(1017) 现在可以**从一份状态生成结构完整、语义自洽的响应**：

```bash
python build_response.py --protocol 1017 --request req.json --out out\1017_Account_LoginSync.json
```

- 响应体 **37 个字段全齐**（`ResponsePacket` 6 个 base + `AccountLoginSyncResponse` 31 个自有），
  26 个对象子回包**逐个递归校验**通过，`--check-all` **33 条可生成协议 33 条通过 0 失败**，
  `--check-state` **12 个实例化实体 0 问题**。
- `Responses` 按请求里的 `SyncProtocols` **只发客户端点名的子回包**；拿不到 `SyncProtocols` 时保守发全部 26 个（产物里已标注原因）。
- 每个子回包**同时**出现在命名字段和 `Responses` 里，且**逐字节一致**（同一份状态、同一次构造、缓存复用），所以客户端走哪条路读都一样。

### 2.3 三条语义规则（engine 与 data 都遵守）

1. **"给默认值" ≡ "官方省略该字段"**。
   `Shittim` 的序列化用 `DefaultValueHandling.Ignore`（见 `report\_tmp\shittim\src\...Packet.cs` 注释），
   官方回包大量字段根本不出现；客户端反序列化后拿到的是 CLR 默认值。所以对 `enum=0 / bool=false / int=0 / ""`
   这些取值，"显式写 0" 与 "官方省略" 对客户端**完全等价**。这是我们敢用 0 填枚举、而不用猜枚举编号的依据。
2. **`null` 对象 = 该实体不存在，不是"空壳占位"**。
   `EchelonListResponse.ArenaEchelonDB`、`ClanLoginResponse.AccountClanDB`、
   `TimeAttackDungeonLoginResponse.PreviousRoomDB` 三处是 `null`：新账号没有竞技场防守队 / 不在公会 / 没有历史房间。
   编一个全 0 的对象反而会让客户端以为"存在一条记录"。
3. **空列表是合法数据，`{}`/`null` 顶替列表不是**。
   `Item_List` → `ItemDBs: []` + `ExpiryItemDBs: []`；`Character_List` → 4 个空列表。
   顶层 13 个集合块全部是"结构完整、内容为空"，不是缺字段。

### 2.4 时间可复现

`_meta.frozenTime = "2026-11-14T00:00:00"`（无时区 ISO）。所有 `DateTime` 字段、以及 `ServerTimeTicks`
（`=_ticks_of(frozenTime)`，整秒精度，口径同官方 "…0000000"）都由它推导，**代码里没有 `now()`**。
`_meta.extraFixedTimes` 单独登记 `1970-01-01T00:00:00` 这个哨兵，`--check-state` 会扫描整份状态，
任何不在这两个白名单里的 19 字符 ISO 时间都会报错（防止有人偷偷塞 `now()`）。

## §3 `build_response.py`：用法与内部映射规则

### 3.1 命令

```bash
# 单条：按协议整数号
python build_response.py --protocol 1017
python build_response.py --protocol 1001 --out out\1001_Account_Nickname.json

# 按协议名
python build_response.py --protocol Account_LoginSync

# 带请求明文（读 SyncProtocols；1001/1010 还会回显 Nickname/CallName）
python build_response.py --protocol 1017 --request out\_req_2000_4000.json

# 改状态再出包（裸字段名自动落到 account；也接受 account.Nickname / AccountDB.Nickname）
python build_response.py --protocol 1001 --set Nickname=111
python build_response.py --protocol 1017 --set Level=2

# 1017 的 Responses 形态
python build_response.py --protocol 1017 --responses-mode single   # ResponsePacket 单值
python build_response.py --protocol 1017 --responses-mode none     # 完全不发 Responses

# 自检
python build_response.py --check-state       # 只校验 account_state.json（含不变量）
python build_response.py --check-all         # 遍历全部可生成协议，报告通过/失败/原因
python build_response.py --list-protocols    # 列出 33 条可生成协议
```

退出码：`0` 成功 / `2` 参数或协议不支持 / `3` 生成后自检失败（CI 可直接用）。
产物写盘时用 `utf-8-sig` 读输入（容 BOM）、`utf-8` 写输出、2 空格缩进、`ensure_ascii=False`。

### 3.2 协议号 → 响应 DTO 的解析链

```
--protocol 1017
  └→ protocol_map.json["Account_LoginSync"] = {id:1017, resp:"AccountLoginSyncResponse"}   # 主源
  └→ dto_schema.json["AccountLoginSyncResponse"] = 31 字段 + base=ResponsePacket          # 兜底源
```

反查索引（`Builder._index_pid`）先建 `resp DTO → 协议号`：**protocol_map 优先**，
protocol_map 里 `resp` 为空的（例如 `Equipment_List`(3000)，该条 `dto_match=none/none`）
才用 `dto_schema.json` 自己登记的 `protocol` 兜底。
**protocol_map 有 resp 但 DTO 未收录的，不算可生成** —— 那正是上游缺口，必须如实报出来，不能被 schema 的旧号糊过去
（典型：schema 里 `AccountLoginSyncResponse.protocol=1019`，若拿它兜底会把 1019 错当成 LoginSync）。

### 3.3 字段绑定优先级（`build_body` 四步）

1. **`GLOBAL_SOURCES`**：每个 `ResponsePacket` 都有的 base 字段 ——
   `StaticOpenConditions ← settings.openConditions`、`MissionProgressDBs ← missionProgress`、
   两个 `*MissionProgressDBDict` ← `eventMissionProgress` / `battlePassMissionProgress`，
   以及 `ServerTimeTicks ← _ticks_of(frozenTime)`。
2. **`SOURCES[dto][字段]`**：显式声明式映射表（`build_response.py` 顶部，逐条对应 `account_state.json` 的点路径，
   支持 `cafe.cafes[0]` 这种下标）。**这条路找得到就用状态值**；路径不存在则跳过（走默认值），
   路径存在但值为 `null` 则**照抄 null**（= 实体不存在，见 §2.3 规则 2）。
3. **嵌套响应自动构造**：字段 `kind=object` 且其类型本身是一个响应包（`base` 链能走到 `ResponsePacket`）时，
   没有显式映射就**递归构造子回包**。1017 的 26 个命名字段全走这条 —— 所以引擎不需要为每个子回包写一次代码。
4. **`default_for`**：剩下没人认领的字段按 §2.3 规则 1 给默认值。

规范化（`norm_object` / `norm_value`）做三件事：**补齐缺字段 / 丢掉 schema 不认识的多余键 / 按 kind 做类型收敛**
（`string→str`、`bool→bool`、整型→int、`DateTime→str`、`enum→int`、`List<X>` 逐元素、`Dictionary<K,V>` 按键值类型、
`Nullable<T>` 保留 null）。这样即使状态文件里手写了一个 `"Level": "1"`（字符串），产物里也会是 `1`（int）。

### 3.4 `Account_LoginSync`(1017) 的特化

```
响应 = { "Protocol": 1017 } ∪ AccountLoginSyncResponse 的 37 个字段
        ├─ 6 个 base：ServerTimeTicks / ServerNotification / MissionProgressDBs /
        │              EventMissionProgressDBDict / BattlePassMissionProgressDBDict / StaticOpenConditions
        ├─ Responses : 客户端在 SyncProtocols 里点名的每个协议 → 一个完整子回包包体
        ├─ 26 个命名字段：全部完整（同一份状态构造，与 Responses 里的同一子回包逐字节一致）
        └─ 4 个标量：FriendCount=0 / FriendCode="BASERVER" / PickupFirstGetHistoryDBs=[] / AccountLevelRewardIds=[]
```

- `Responses` 元素形态：`{"Protocol": <子协议号>, ...该 DTO 的全部字段}`，
  子包 `ServerTimeTicks` 固定 0（官方子回包不带时间戳；`Shittim` 生产代码同样把它清零，依据见 `AccountHandler.cs:627`）。
- **只发点名的**：`--request` 给了 `SyncProtocols` 就按顺序去重生成（例：`[2000,4000]` → 只有 2 个元素，
  见 `out\variants\1017_Account_LoginSync.sync-2000-4000.json`）。
- **拿不到 `SyncProtocols`**（请求解密失败 / 没给 `--request`）→ 保守发全部 26 个，并在 stderr 的 `[note]` 与报告里标注来源。
- 客户端点名了 1017 里不存在的协议号 → 不静默吞掉，汇总成 `未识别协议号 [...]` 打进 note。
- `SyncProtocols` 里既接受整数（`[2000,4000]`）也接受协议名（`["Character_List","Item_List"]`）。

### 3.5 两套自检

| 命令 | 检查什么 | 本次结果 |
|---|---|---|
| `--check-state` | ① `DB_STATE_MAP` 里 47 条"状态块→DTO"逐字段核对（齐全/无多余键/类型），**递归进嵌套对象与集合元素**；② 时间字段白名单；③ 不变量：`RepresentCharacterServerId` 必须是 0 或自己 `characters` 里的 `ServerId`、`MemoryLobbyUniqueId` 非 0 时 `memoryLobby` 不能空 | **12 实体 / 0 问题** |

`--check-all` 通过时 `--verbose` 会打印 `null=数量 warn=数量`，便于盯住"是不是又靠 null 混过去了"。

### 4.3 数据/结构缺口 G1–G9（按严重度）

**G1 `Responses` 是 `List<ResponsePacket>` 还是单值 `ResponsePacket`？——三份证据二比一。**
- `dto_schema.json`：`List<ResponsePacket>`，**`conf: mid`**，来源是 `build_schema.py` 的
  `MANUAL[57877] = ('List<ResponsePacket>', 'mid')` —— 手工裁定，因为 metadata 没有泛型实例表。
- `type_index_map.json`：`57877 → {"full":"MX.NetworkProtocol.ResponsePacket","kind":"type","name":"ResponsePacket","td":10776}`
  —— 这个 typeIndex 直接指向 `ResponsePacket` **类本身**，而不是泛型实例
  （对比 `List<long>` 的 `22246` 在表里根本没有条目）。
- `shittim_types.json`（国际服 DTO 交叉校验源）：`["Responses","ResponsePacket?"]` —— **单值可空对象**。
- `Shittim` 生产实现 `AccountHandler.LoginSync`（`report\_tmp\shittim\src\...AccountHandler.cs:288-643`）
  从头到尾没给 `Responses` 赋值，26 个子回包全走命名字段；其注释明确写"官方子回包只带自己的 payload + Protocol"。

→ 结论：`List` 这一侧只有"手工裁定 + 字段名复数"，`ResponsePacket` 单值这一侧有类型索引 + 国际服 DTO 两份硬证据。
**引擎默认按本任务规格出 `list`**，但同一份状态可立刻切另外两种形态，三个产物都已生成：

| 形态 | 命令 | 产物 | 什么时候用 |
|---|---|---|---|
| `list`（默认） | `--responses-mode list` | `out\1017_Account_LoginSync.json` | 本任务规格；客户端遍历子回包 |
| `single` | `--responses-mode single` | `out\variants\...responses-single.json` | 若 list 让客户端抛反序列化异常 |
| `none` | `--responses-mode none` | `out\variants\...responses-none.json` | = Shittim 生产做法（只发 26 个命名字段） |

三种形态的**子回包内容完全相同**，只有 `Responses` 一个键的形态不同 → 手机侧一次 A/B 就能定论。
若 `list` 下报 `同步账号信息时发生错误`，优先怀疑这里（而不是数据）。

**G2 `ItemDB` 只有 1 个字段。**
`dto_schema.json` 里 `ItemDB` = `{ Expires: Nullable<DateTime> }`，**没有 `UniqueId`/`Amount`**。
一个"只有过期时间"的道具无法表达"我有什么道具"，所以 `items` 只能为空。
这不是我们偷懒：`Shittim` 的 `ItemListResponse.ItemDBs` 是 `List<ItemDB>`、其 `ItemDB` 有身份字段，
而国服 metadata 里只解出 1 个 → 属于**提取缺口**，回补方法见 §5 R4。**在补齐前不编造 `UniqueId`。**

**G3 枚举常量值取不到（`CurrencyTypes` / `EchelonType` / `OpenConditionContent` / `FurnitureLocation` …）。**
试过从 `report\_tmp\patch\md_deob.bin` 的 `fieldDefaultValues` 段直接读（`mdlib.MD()`）：
- `AccountState` 读出 `WaitingSignIn=0x00, Normal=0x02, Dormant=0x04 …`（步进 2 的字节流）；
- `CurrencyTypes` 读出 `Invalid=0x00, Gold=0x02, GemPaid=0x04 …`（同一模式）；
- `Protocol` 同样读出乱值（而 `protocol_map.json` 的真值来自 `shittim_enum_numbers.json` + SDK 表，不是从这里读的）。
该段仍是分页加密状态（`report\_tmp\patch\enc_pages.json` / `codepage_bits.bin` 即为此存在），
**读出来的是邻近成员的字节窗口，不是真值**。所以：`currencies` 空 → `CurrencyDict={}`，绝不拿猜的编号当键
（编错的货币 id 会让客户端在"未知货币"处炸，比缺更糟）。
替代依据只有一条：官方会省略大量字段（`DefaultValueHandling.Ignore`），省略后客户端就是 CLR 默认 `0`，
所以 `enum=0` 与"官方没发这个字段"等价 —— 这条只救得了"0 是安全值"的字段（`CafeAllowCopy`、`RaidSeasonType` 等）。

**G4 `characters` 为空 —— 初始学生的 `UniqueId` 拿不到。**
需要 FlatData 的 `CharacterExcel.UniqueId`，本地没有该表（`report\_tmp\cn_proto` 只有协议表）。
`Shittim` 的生产代码里有专门的反向证据：
> "Item_SelectTicket used to record furniture box picks as characters… **The client aborts loading on a character id with no excel entry**" (`AccountHandler.cs:379-390`)

即：乱填 `UniqueId` 会让客户端**卡在加载**，比空列表更糟。所以选择 `characters: []` +
`RepresentCharacterServerId: 0`（语义=尚未发放），并在 `_meta.gaps` 里写清。补法见 §5 R2。

**G5 `CafeId=1` / `CafeRank=1` 是假设值。**
新账号一定有咖啡馆（`Shittim` 每次都发 `CafeGetInfoResponse`），但 `CafeId` 要能对上 `CafeExcel` 行、
`CafeRank` 要能对上咖啡馆等级表。选 1/1 是最小合法猜测，**未实测**。若客户端在咖啡馆界面报错，先查这里（§5 R1）。

**G6 其余枚举字段一律 0。**
`EchelonDB.EchelonType`、`FurnitureDB.Location`、`PurchaseOrderDB.StatusCode`、`ClanMemberDB.ClanSocialGrade`。
因为对应实体我们都**没有实例化**（`echelons`/`furniture`/`billing.orders` 全空），所以这些 0 不会出现在产物里 ——
这是有意的：**需要枚举语义的实体，我们就不发**，而不是发一条 0 值记录去蒙。

**G7 1017 vs 1019 的记录冲突（必须知道）。**
`protocol_map.json`：`1017 = Account_LoginSync`、`1019 = Account_RequestBirthdayMail`（本任务已确证 1017，产物按 1017 出）。
`dto_schema.json`：`AccountLoginSyncResponse.protocol = 1019`（`protocolSource: cn_sdk`）；
外部 SDK 表 `headless__data__protocols.json` 也写 1019（该行置信度"低"）。
服务端应**回显请求 `Hash>>32` 里的协议号**；若手机侧实测发的是 1019，用
`--protocol 1019` 重出同一份（数据不变，只变回包号）。

**G8 三处 `null` 对象**（不是缺口，是语义）：`EchelonListResponse.ArenaEchelonDB`、
`ClanLoginResponse.AccountClanDB`、`TimeAttackDungeonLoginResponse.PreviousRoomDB`。
如果客户端在这三处 NRE（说明它没做判空），**先改成发全 0 对象**，改法是一行状态补丁：
在 `account_state.json` 里把 `arenaEchelon` 从 `null` 换成 11 个 0 的 `EchelonDB`，引擎会自动接上。

**G9 `ItemListResponse` 子回包发不发？（一处已知分歧）**
国服 schema 里 `AccountLoginSyncResponse` 第 7 个字段就是 `ItemListResponse`（`conf: high`），所以我们发它（结构完整、两个列表为空）。
但 Shittim（国际服）生产代码有一句明确的实测注释：
> "Official Account_LoginSync has NO ItemListResponse child (the client fetches Item_List separately right after login)" (`AccountHandler.cs:445`)

两种可能：国服这个版本加了该字段（schema 是国服 metadata 解出来的，可信），或字段存在但官方实际留 null。
我们按 schema 发，理由是"结构 100% 完整"优先。
**若怀疑它，怎么排除**：`--responses-mode` / `--set` 都改不了它 —— schema 里它是非空对象字段，
引擎总会补默认值（`--set items=null` 会被回落成 `"ItemDBs": []`）。
排除办法是**从产物 JSON 里手工删掉 `ItemListResponse` 这一个键**（客户端反序列化后拿到 null）再试一次，
若这一改就过，说明国服客户端也期望它是 null，届时在 `build_response.py` 的 `SOURCES` 之外加一条
`OMIT_FIELDS = {'AccountLoginSyncResponse': {'ItemListResponse'}}` 由引擎负责剔除（别手改 `dto_schema.json`）。

## §5 后续怎么把数据填满（R1–R5）

> 原则：**先有数据再加字段/实体**，不要反过来用 `{}` 或 0 去糊。
> 每次改完状态：`python build_response.py --check-state && python build_response.py --check-all`，再 diff `out\`。

### R1 对齐 `CafeExcel`（解决 G5）
从客户端 FlatData 取 `CafeExcel` 的第一行：`CafeId`、`CafeRank` 上限、`ComfortLimit`。
改 `account_state.json → cafe.cafes[0]` 的 `CafeId`/`CafeRank`/`ProductionDB.ComfortValue`。
`CafeDBId` 用我们自己的自增 id（客户端只当主键用，不回表）。

### R2 填初始学生（解决 G4）
需要 `CharacterExcel`：取教学目标学生的 `UniqueId`（1★）、`StarGrade` 与初始技能等级。
在 `account_state.json` 追加一条 `characters[]`：

```json
{
  "ServerId": 1, "UniqueId": <CharacterExcel.UniqueId>, "StarGrade": 1, "Level": 1, "Exp": 0,
  "FavorRank": 0, "FavorExp": 0,
  "PublicSkillLevel": 1, "ExSkillLevel": 1, "PassiveSkillLevel": 1,
  "ExtraPassiveSkillLevel": 1, "LeaderSkillLevel": 1,
  "IsFavorite": false, "EquipmentServerIds": [], "PotentialStats": {}
}
```

然后**必须**同时把 `account.RepresentCharacterServerId` 改成同一个 `ServerId`（引擎的 `--check-state` 会拦住忘了改的情况）。
有学生之后，`echelons` 才能填（`EchelonDB.AccountServerId`=1、`MainSlotServerIds` 指向角色 `ServerId`），
编队需要 `EchelonType` 的枚举值 —— 见 R5。

### R3 填货币（解决 G3）
`CurrencyExcel` 里每行给出 `CurrencyType`（就是 `CurrencyTypes` 的编号）、`ChargeLimit`、`OverChargeLimit`。
在 `currencies[]` 追加行，引擎会自动合成 `AccountCurrencyDB.CurrencyDict` 与 `UpdateTimeDict`：

```json
"currencies": [
  { "type": <CurrencyTypes.Gold>,        "amount": 10000, "updateTime": "2026-11-14T00:00:00" },
  { "type": <CurrencyTypes.ActionPoint>, "amount": 120,   "updateTime": "2026-11-14T00:00:00" }
]
```

### R4 回补 `ItemDB` 字段（解决 G2）
两条路，任选其一：
1. **重解 metadata**：`report\_tmp\patch\md_parse.py` / `md_types.py` 已能列 `ItemDB` 的 `fields` 段；
   若字段确实存在但被 `SKIP_FIELDS` 或 `conf` 过滤掉了，改 `build_schema.py` 的重建流程（**不要手改 `dto_schema.json`**）。
2. **抓真实响应**：拿一次官方 `Item_List` 的回包 JSON，直接看 `ItemDBs[0]` 的键名与类型
   （`report\_tmp\packet_bin\*` 有历史报文与解析脚本可复用）。
有了字段后，`items[]` 就能填；在此之前保持 `[]`。

### R5 扩协议覆盖（从 33 到 400+）
`build_schema.py` 的 `TARGETS` 现在是 16 组（`('协议名', 'DTO前缀')`）。每加一组，`dto_schema.json` 就会自动
把该协议的 Request/Response 及其递归引用全部带出来，`--check-all` 立刻多一条。
按"进大厅之后的顺序"排优先级：

1. **角色养成**：`Character_ExpGrowth`(2001) / `Character_UpdateSkillLevel` / `Character_Transcendence`
2. **任务与邮件**：`Mission_List` / `Mission_Sync` / `Mail_List` / `Mail_Receive`
3. **商店与抽卡**：`Shop_List` / `Shop_BuyGacha` / `Shop_GachaRecruitList`（这条已有）
4. **课程表/学院**：`Academy_GetInfo` / `Academy_AttendSchedule`
5. **签到**：`Attendance_List` / `Attendance_Check` / `Attendance_Reward`

对新扩的 DTO，状态层只需要在 `SOURCES` 里加一行映射 + 在 `DB_STATE_MAP` 里加一条校验，
剩下的补齐/丢键/类型收敛由引擎负责。**不要**为新协议写第二套手写 JSON。

### R6（可选）把引擎接进服务端
服务端只需三步：`Builder(schema, pmap, state)` → `builder.packet(pid, dto)`（或 `build_login_sync(pid, sync_protocols)`）
→ `json.dumps`。状态文件在进程内只读一次即可（`--check-state` 放在服务启动时跑，坏了直接拒绝启动比半路报错好）。
若将来要做"多账号"，把 `account_state.json` 变成 per-account 目录 + `Builder` 按账号实例化即可，映射表不用动。
