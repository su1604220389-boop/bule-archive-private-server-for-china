
### 职责边界（一排就够，不要越界）

| 层 | 应该做 | **不应该做** |
|---|---|---|
| **bridge** | 传输、加解密、外层信封、实验开关、日志 | 任何字段名、任何 DTO 名、任何"这条协议要补什么键" |
| **router** | 协议号/名解析、DTO 查表、Error 信封、冲突告警 | 生成字段值、算业务规则、写库 |
| **factory** | schema 驱动的结构生成、账号状态绑定、类型映射 | 认协议号做特判、决定返回哪条协议 |
| **account_service** | 身份、会话、状态持久化、`build_account_db_for` | 拼响应包、决定某个协议发哪些键 |

**为什么这样切**：协议的"形状"来自 metadata（`dto_schema_full_v2.json`，709 个类型），
协议的"数据"来自账号状态（41 键），协议的"编号"来自 metadata（`protocol_map.json`）。
三件事各有唯一事实源，**没有任何一件需要按协议写代码**。以前每加一条协议要写一段
`if name == ...`，是因为把"形状"和"数据"混在了分支里。

## 2. 协议号确定规则

### 2.1 两级解析，各按优先级降级

```
协议号 pid（决定 "Protocol": ?）
   1. request_ctx['protocol_id']           显式传入（最可信）
   2. request_ctx['hash'] >> 32            客户端真实协议号所在（Hash = (proto<<32)|counter）
   3. 都没有                                → pid = None（继续靠名字路由，Protocol 由 DTO 常量兜）

协议名 name（决定查哪张 DTO 表）
   1. request_ctx['protocol_name']         从 base32 token 解出来的名字
   2. request_ctx['protocol_token'] → 反查   base32(MD5(UTF-16LE(name)))；501 条 token 全表索引
   3. pid → 反查                              protocol_map 的 id→name 索引（493 个数字号）
   4. request_ctx['path'] → 反查             仅当上面全落空（最弱，标 warning）
```

### 2.2 为什么"协议号 > token > path"

- **协议号是客户端的真值**：`Hash` 在请求体里，实测 `4299262263303 >> 32 = 1001`；
  `1002/1001/1010/1019/24000` 全部对上（report/83 §6.3）。
- **token 是协议名的真值**：`base32(MD5(UTF-16LE(协议名)))`，`token('Account_Auth')
  = AHTQLQI65FWJGGGK4KL5AEF57A` 逐字符命中；`token('Account_Nickname')
  = GVDSNCHUMIOS44NDTZM6ZPDDVQ` 同样命中（`test_router.py` 每次跑都验一遍）。
- **path 只作交叉校验**，因为**路径与协议名不是一一绑定**（`/api/academy/getinfo` →
  `Academy_GetInfo`，但同一个 handler 可能吃多条协议）。path 能反查出来的路径键由协议名
  机械派生：`Account_Auth → account/auth`，`Academy_GetInfo → academy/getinfo`。
  499 条协议能派生出路径键（`Error` / `None` 这类没有下划线的不行）。

### 2.3 冲突处理（全部"记 warning 但不出错"）

| 冲突 | 处理 | warning 文案 |
|---|---|---|
| `protocol_id` 与 `hash>>32` 不一致 | 用 `protocol_id` | `protocol_id=X 与 hash>>32=Y 不一致，采用 protocol_id` |
| id 反查出的名字 ≠ 显式 name | **用 name**（token 是更强的证据） | `id/name 冲突: id=N 期望 A，实际 B（采用 name）` |
| path 反查出的名字 ≠ 协议 | **用协议号/名**，path 只报警 | `path 与协议名不一致: path=... → A，实际 B（按协议名/协议号走）` |
| 只有 path | 用它反查（最弱兜底） | `协议名由 path 补出: X` |
| 名字存在但无数字号（`Error`/`None`/`Session_Info`/`Common_Cheat`/`NetworkTime_Sync` 等 6 条） | 正常查 DTO；查不到 → Error | `X 在 protocol_map 里没有协议号` |
| 什么都解不出 | **Error 信封** | `既无协议号也无协议名，无法路由` |

### 2.4 ⚠ 已发现的真问题：国服与 Shittim 编号在 Account 段有偏移

`protocol_map.json` 记的是 **Shittim 口径**：

| 协议 | Shittim（protocol_map） | 国服实测 | 出处 |
|---|---|---|---|
| `Account_LoginSync` | **1017** | **1019** | report/64 §1（"国服 Account 段在 LoginSync 之前比 Shittim 少 2 条协议，其后同段协议整体前移 2"） |

于是**只按协议号路由**时：国服发来 `1019` → 查成 `Account_RequestBirthdayMail`
（`AccountRequestBirthdayMailResponse`）；国服发来 `1017` → 才查到 `AccountLoginSyncResponse`。

**本层的处理（不猜，只留显式入口）**：

```python
protocol_router.set_id_aliases({1019: 'Account_LoginSync'})          # 进程级
# 或按次
route({'protocol_id': 1019, 'protocol_id_aliases': {1019: 'Account_LoginSync'}})
# 或最直接：把一个 DTO 硬钉死
route({'protocol_id': 1019, 'dto_override': 'AccountLoginSyncResponse'})
```

**但注意**：线上 bridge 手里有 token（base32），token 反查出来的名字是**国服真实协议名**，
按 §2.1 名字优先 → 1019 会走 `Account_LoginSync` 分支，**不受这个偏移影响**，只是会多一条
`id/name 冲突` 的 warning（提醒你 `protocol_map` 与真机编号不一致）。填了别名表这条 warning 就消失。

`test_router.py` 里专门有 5 条断言覆盖这个场景（见附录 A「路由规则专项」）。

## 3. 响应生成规则

### 3.1 一条响应包的键顺序与层级

```
$ Protocol          ← BasePacket.derivedMembers[emit=envelope] / 根层=DTO 自己的常量
  $ SessionKey      ← BasePacket.fields[0]（对象）  ★仅根层 ★仅白名单协议（见 3.4）
  $ OSType         ← BasePacket.fields[1]（默认不发，见 3.5）         ★仅根层
  $ AccountId      ← BasePacket.derivedMembers[emit=derived]         ★仅根层
                      formula: SessionKey?.AccountServerId ?? 0 → 只有 SessionKey 是对象时才发
  $ ServerTimeTicks                    ┐
  $ ServerNotification                 │
  $ MissionProgressDBs                 │ ResponsePacket.fields 6 个
  $ EventMissionProgressDBDict         │ ★根层默认必发；嵌套子响应用 base_fields 控制（3.9）
  $ BattlePassMissionProgressDBDict    │
  $ StaticOpenConditions               ┘ ← 55 键字典（不是数组！）
  $ <DTO 自有字段…>                    ← 沿 baseChain 逐层，v2 自带 baseChain
```

**为什么 `AccountId` 是"有条件"发**：它不是字段，是 `BasePacket` 上的只读派生属性
`SessionKey?.AccountServerId ?? 0`（report/76 §1.1 §1.4）。没有 SessionKey 时它就是 0，
而官方序列化器用 `DefaultValueHandling.Ignore` 会把 0 丢掉 —— 所以**没有 SessionKey 就不发
AccountId**，语义完全一致。有 identity 时发，且值一律取 identity 的号（见 3.7）。

**实测键数对照**（`state=account_state.seeded.json` + identity）：

| 协议 | 键数 | 说明 |
|---|---:|---|
| `Account_Auth` 1002 | **36** | Protocol + SessionKey + AccountId + 6 基类 + 27 自有 |
| `Account_LoginSync` 1017 | **37** | 无身份键（不在白名单）+ 6 基类 + 30 自有（`Responses` 已剔除） |
| `Academy_GetInfo` 24000 | **9** | 6 基类 + `AcademyDB` + `AcademyLocationDBs` = **与 report/83 里那个"唯一被证明客户端接受"的手写包同结构** |
| `Management_Data` 90004 | **8** | 6 基类 + `Data` |

### 3.2 `StaticOpenConditions` 必须是 55 键字典

取值优先级：`state['settings']['openConditions']`（account_service 从 `social` blob 取）
→ 模块内置常量（与 `gen_full.py` 的 55 键一致）。
`test_router.py` 的 G4 在全量 457 条上断言"恒为 55 键字典"，0 违反。

> 老代码里 `24000/1019` 用过 `"StaticOpenConditions": []` —— 那是**类型错**
> （`Dictionary<OpenConditionContent,OpenConditionLockReason>`，不是 List）。本层已消灭。

### 3.3 `emit:false` 的字段一律不生成（任何层级）

`AccountLoginSyncResponse.Responses` 的类型是 `ResponsePacket?`（**单个可空引用**，
且 `ResponsePacket` 是抽象类），Shittim 全仓库从不给它赋值（report/76 §1.5）。
本层两条防线：

1. `schema` 里的 `"emit": false` → 跳过；
2. `NEVER_EMIT = {'Responses'}` 常量兜底（schema 换版本也不至于漏）。

G2 断言"**任何层级**都不出现 `Responses`"，457 条 × 递归全树，0 违反。
这就是 1019 从"492 B 的 `{"Responses":[]}`"变成"37 键 / 7758 B 的 26 个具名兄弟子响应"的原因 ——
它**不需要为 1019 写一行代码**：26 个子响应的字段表本来就在 schema 里。

### 3.4 `SessionKey` 只在**白名单协议**上回显（照抄官方网关策略）

官方的 `ShouldEchoSessionKey()`（report/76 §1.4，`GatewayController.cs:317-322`）写得很死：

```csharp
// Protocols whose responses officially carry SessionKey/AccountId, from live captures:
// Account_CheckNexon, Account_Auth, ProofToken_RequestQuestion, ProofToken_Submit.
private static bool ShouldEchoSessionKey(Protocol protocol) => protocol
    is Protocol.Account_Auth or Protocol.Account_Auth2
    or Protocol.ProofToken_RequestQuestion or Protocol.ProofToken_Submit;
// 注释原话：every other response omits both.
```

本层的 `SESSION_KEY_ECHO_PROTOCOLS`（= 官方 4 条 + 自己签发会话的 3 条）：

```
1000 Account_Create   1002 Account_Auth   1009 Account_CheckYostar
1012 Account_Auth2    1014 Account_CheckNexon
37000 ProofToken_RequestQuestion   37001 ProofToken_Submit
```

- 在名单里 → 发 `SessionKey` + 派生 `AccountId`（`Account_Auth` 的 36 键就是这样来的）；
- 不在名单但**有**会话 → **不发**，并记一条 warning（`X 不在 SessionKey 回显白名单，已省略`）；
- 都不在 → 什么都不发。
- 想退回"所有响应都发"：`context['session_key_scope'] = 'all'`（`test_router.py` 里有一条断言守这个开关）。

> 这个策略不是我拍的：同事的 `example_auth_flow.py` 也按同一份白名单把 `SessionKey`
> 从 1017 里剥掉（他们的注释：「1017 之类的业务响应带上它与官方形态不符」）。
> 加了白名单之后，1017 正好 **37 键**，与他们的期望值完全对上。

### 3.5 `OSType` 默认**不发**（与真服字节一致）

- 真服 1002 的 24 键里**没有** `OSType`（report/36 §1）；
- `OSType` 是**请求侧**字段（客户端→服务端），服务端回显它没有意义；
- 同事的 `example_auth_flow.py::inject_session()` 也显式 `packet.pop('OSType')`。

所以默认 `ostype_mode='omit'`；要发就 `context['ostype_mode']='emit'`（值取 `ctx.os_type`，默认 0）。
> 这是本层**唯一**故意"不把 schema 声明的字段全发出来"的地方，理由是"真服实测没有"，已在
> 测试里用集成结果（36 键）反向确认。

### 3.6 类型映射表

| schema `kind` | 生成值 | 备注 |
|---|---|---|
| `scalar` string | `""` | `Guid` → `"00000000-0000-0000-0000-000000000000"` |
| `scalar` bool | `false` | |
| `scalar` int/long/byte/…/decimal/TimeSpan | `0` | |
| `scalar` float/double | `0.0` | 保持 float，不写 0 |
| `datetime` | `state['_meta'].frozenTime`（无时区 ISO） | 离线=冻结值，线上=now（account_service 写） |
| `enum` | `0` | 枚举值表未定，一律 0 |
| `list` | `[]` | **有账号数据时**按元素类型绑定（见 3.8） |
| `dict` | `{}` | 同上（`eventMissionProgress` 等） |
| `nullable` | `null` | |
| `object` | 递归（深度 8，带环保护） | 类型不在 schema → `{}` 并计数 |
| `unknown` | 名字启发式（见 3.10） | 全库 264 个，见 §4.4 |

### 3.7 身份一致性收口（`_identity_fixups`）

`SessionKey.AccountServerId`、派生 `AccountId`、`AccountDB.ServerId` **必须是同一个号**，
否则等于发出一份自相矛盾的凭据。生成后做一次全树扫描：凡 `AccountDB.ServerId ≠ identity 的号`
→ 改成 identity 的号 + 记 warning + `stats.identity_fixups += 1`。

实测效果（集成跑）：state 里 `account.ServerId = 10000000000`，identity 同号 → 0 次修正；
若 state 是"老账号 1 号"而 identity 是新号，就会自动收口并告警。

### 3.8 账号状态绑定：**类型名 → 状态路径**，不是协议 → 响应

这是"通用"的关键。绑定表全部按 **schema 类型名** 索引（4 张表 + 可被 context 追加）：

| 表 | 形状 | 例 |
|---|---|---|
| `OBJECT_BINDINGS` | 类型名 → 状态路径 | `AccountDB → account`、`CafeDB → cafe.cafes[0]`、`ArenaPlayerInfoDB → arena.playerInfo` |
| `LIST_BINDINGS` | 元素类型名 → 状态列表 | `CharacterDB → characters`、`ItemDB → items`、`EchelonDB → echelons` |
| `DICT_BINDINGS` | 字段名 → 状态 dict | `EventMissionProgressDBDict → eventMissionProgress` |
| `SCALAR_BINDINGS` | 字段名 → 状态路径（只收全局语义唯一的） | `CurrentVersion → auth.CurrentVersion` |

**加一行 = 支持一个新 DB 类型，永不需要碰协议。** 调用方还能不改文件地追加：
`context['object_bindings'] = {'MyNewDB': 'someBlob.myNewDB'}`。

**取值优先级（高→低，这是 `values` 覆盖能生效的保证）**：

```
1. context['values']['AccountDB.Nickname']   精确路径覆盖（或裸字段名）
2. context['hooks']                          回调 fn(where, name, default) -> (handled, value)
3. 账号状态绑定                                OBJECT/LIST/DICT/SCALAR + 同名对象
4. 类型默认值                                  见 3.6
```

> 这一版修过一个真 bug：早先绑定在覆盖**之后**做，导致 `values` 被状态值盖掉。
> 现在绑定被折进"默认值"里算，`values`/`hooks` 永远赢（`test_router.py` 用
> `Account_Nickname + values={'AccountDB.Nickname':'Sensei'}` 验证）。

**合并语义**：状态对象按"**同名键**"逐字段喂给 DTO；DTO 没声明的键**丢弃并计数**
（`stats.extra_keys_dropped`），不让脏键上线；类型不符的键**保留默认并告警**
（`stats.type_mismatch_skipped`）。

### 3.9 嵌套子响应：`base_fields='root'`（默认）

`Account_LoginSyncResponse` 有 26 个**同为 Response 根**的嵌套字段。默认只在**根层**发
ResponsePacket 的 6 个字段，嵌套子响应只发 `Protocol`（它自己的常量）+ 自有字段。

依据：Shittim 的 handler 从不给嵌套子响应赋 `ServerTimeTicks` / `StaticOpenConditions`，
`DefaultValueHandling.Ignore` 会把这些默认值丢掉。设 `base_fields='all'` 可以把 6 字段塞到
每一层，代价是 1019 从 ~7.8 KB 涨到 ~37 KB（26 × 55 个 `StaticOpenConditions` 键）。

### 3.10 `unknown`（类型推断不出来）的兜底

全库 **264 个字段** `kind=unknown`（占 264/2833 = 9.3%）。一律 `null` 是危险的：C# 非可空值类型
遇到 `null` 会抛 `JsonSerializationException`，**整个响应解析失败** —— 比给错值更糟。
所以按**字段名**做通用启发（不含任何协议知识）：

```
^(Is|Has|Can|Enable|Allow|Use|Show|Need|Should|Contains)(?=[A-Z_])   → false
(Display|Enabled|Disabled|Visible|Flag|Flags|Lock|Locked|Closed|Open|New)$  → false
(Date|DateTime|Time|Ticks|Timestamp|At)$                            → frozen ISO
```

### 4.6 诚实声明：**结构完整 ≠ 客户端会接受**

这一节是本报告最重要的部分，必须写清楚：

**本层保证的**（每条都有全量断言，457 × 6 条不变量）：
1. 非 Error 的包一定非空，且含 `Protocol` + 基类 6 字段；
2. 任何层级都不出现 `emit:false` 的字段（`Responses`）；
3. `json.loads(json.dumps(x))` 往返一致；
4. `StaticOpenConditions` 恒为 55 键字典；
5. `route()` 对任意垃圾输入都不抛异常、不返回 None；
6. 不出现 schema 未声明的键（G6）。
7. 每个 DTO 的**每一个声明字段都出现**（`emit:false` 除外），嵌套对象递归到叶子。

**本层不保证的**：
- ❌ **字段取值是否正确**。1 262 处 `unknown` 类型是按字段名猜的；`0`/`false`/`""` 是类型默认值，
  不是游戏数值（例如 `Currency` 的数量没有从 `ExcelDB.db` 取，`ServerNotification` 恒 0
  而不是真服那样的 `8 = HasUnreadMail`）。
- ❌ **客户端的业务校验**。客户端可能读某个字段做一致性校验（例如拿 `AccountDB.ServerId`
  去比 `SessionKey.AccountServerId`——这一条我们做了收口，但别的校验我们不知道）。
- ❌ **客户端会走多远**。report/83 的结论是"`Academy_GetInfo` 换成真结构后客户端表现与假包
  完全相同 ⇒ 卡点不在这条"。**本层让"假包"不再假，但并没有证明客户端会前进**。
- ❌ **一次响应能替代一个 handler**。有副作用的协议（改名、领取、购买）必须先由
  `account_service.update_account()` / `save_blob()` **落库**，再让本层从新状态渲染 ——
  本层是**只读渲染器**，不写任何东西。

一句话：**这一层解决的是"每条协议都有结构完整的包"，不是"每条协议的行为都对"。**

### 6.2 第 2 处：加一个薄适配方法（放在 `_cn_send_envelope` 之前）

```python
    def _router_response(self, proto_str, packet_b64, rec, name=None):
        """任何协议 → protocol_router → ResponseSpec → 现有信封。

        这里只做 4 件事：取协议号、解请求明文、要账号状态、交给 router。
        不判断协议、不拼字段 —— 那是下面两层的事。
        """
        # (1) 协议号：Hash>>32（rec['req_Hash'] 在 path A 里已经填过）
        pid = None
        h = rec.get('req_Hash')
        if isinstance(h, int) and h > 0:
            pid = h >> 32
        elif isinstance(h, str) and h.isdigit():
            pid = int(h) >> 32

        # (2) 请求明文（能解就解；解不了不影响路由，只是 hook 看不到 payload）
        req_payload = None
        try:
            r = cn_cipher.decode_packet(packet_b64, proto_str)
            if isinstance(r.get('json'), dict):
                req_payload = r['json']
        except Exception:
            pass

        # (3) 账号侧：拿不到就降级成骨架（router 不要求它必须存在）
        state = ident = sk = None
        try:
            ident_obj = ACCOUNT.identify(req_payload) if req_payload else None
            if ident_obj is not None:
                acct = ACCOUNT.get_or_create_account(ident_obj)          # 首登自动建号
                sk = ACCOUNT.issue_session_key(acct).to_dict()           # {AccountServerId, MxToken}
                state = ACCOUNT.build_state_for(acct)                    # 41 键，含 _meta.frozenTime
                ident = {'account_server_id': acct.server_id,
                         'mx_token': sk['MxToken']}
        except account_service.AuthRejected as e:
            rec['account_auth_rejected'] = str(e)
            # 身份不成立 → 直接 Error(3)，让客户端回标题重登
            spec = protocol_router.route({'protocol_name': name, 'protocol_id': pid})
            spec.payload = _rf.build_error_packet(
                error_code=protocol_router.ERROR_CODE_INVALID_SESSION)
            rec['router'] = spec.as_dict()
            return self._cn_send_envelope('Error', spec.payload, rec)
        except Exception as e:                    # noqa: BLE001
            rec['account_err'] = repr(e)

        # (4) 路由 + 渲染
        ctx = protocol_router.make_request_ctx(
            protocol_name=name, protocol_id=pid, protocol_token=proto_str,
            path=self.path, request_payload=req_payload,
            identity=ident, state=state, session_key=sk)
        spec = protocol_router.route(ctx)
        rec['router'] = spec.as_dict()             # 观测：dto/source/is_error/warnings 全进日志
        return self._cn_send_envelope(spec.envelope_name, spec.payload, rec)
```

1. **接 `ExcelDB.db`（解 L6）** —— 这是"客户端会不会往下走"最可能的真因。路径：写一个
