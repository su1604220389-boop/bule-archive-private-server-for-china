## 1. Q1 — Shittim 的 `.mx` 到底是什么格式（源码实测）

### 1.1 入口

`Shittim-Server__Controllers__Api__GatewayController.cs:157-166`：

```csharp
[HttpPost("gateway")]
public async Task GatewayRequest()
{
    var formFile = Request.Form.Files.GetFile("mx");
    if (formFile is null)
    {
        Response.StatusCode = 400;
        await Response.WriteAsync("Expecting an mx file");
        return;
    }
```

⇒ **必须是 `multipart/form-data` 里一个 name=`mx` 的「文件」字段**（`IFormFile`）。文本字段（`protocol`/`encode`/`packet`）它完全不看。

### 1.2 二进制布局（`DecodeGatewayPayload`，`:360-409`）

```csharp
var crc             = reader.ReadUInt32();   // u32 LE
var typeConversion  = reader.ReadInt32();    // i32 LE
var keyLength       = reader.ReadByte();     // u8
var ivLength        = reader.ReadByte();     // u8
var headerKey       = ReadExact(reader, keyLength, "AES key");
var headerIv        = ReadExact(reader, ivLength, "AES IV");
var rawPayload      = ReadExact(reader, rest, "payload");
```

即：

```
+0   u32  crc
+4   i32  typeConversion
+8   u8   keyLength
+9   u8   ivLength
+10  u8[keyLength]   headerKey
+..  u8[ivLength]    headerIv
+..  u8[rest]        rawPayload
```

`rawPayload` 最少 4 字节，否则 `Gateway payload is too short`。

### 1.3 `RequestXorKey` —— 单字节 0xD9（`:107`）

```csharp
private static readonly byte[] RequestXorKey = { 0xD9 };
```

`XOR.Crypt` 就是拿这个 1 字节循环 XOR 整段。

### 1.4 `rawPayload` 的三种解包变体（`DecodeGatewayPayloadBodies`，`:462-493`）

| 变体 | 做法 |
|---|---|
| `xor-length-prefix` | 整段 XOR 0xD9 → 前 4 字节当 `u32 len`，`[4..]` 做 gzip |
| `clear-length-prefix` | **前 4 字节明文**当 `u32 len`；`[4..]` 先 XOR 0xD9 再 gzip |
| `xor-no-length` | 整段 XOR 0xD9 → 从头 gzip（无长度前缀） |

三个都试，任一成功即用。

### 1.5 解出来的东西怎么判、怎么二次解密（`TryBuildGatewayPayload`，`:495-596`）

1. `TryReadJson` —— 首个非空白字符必须是 `{` 且能被 `JObject.Parse` 吃掉 → 明文 JSON，直接用
2. 否则若 `headerKey` 长度 ∈ {16,24,32} 且 `headerIv` 长度 == 16 → `HybridCryptor.DecryptTextAES(payload, headerKey, headerIv)`（**AES-CBC**）
3. 否则遍历内存里记住的历史会话 key（`GatewaySessionCryptoBuilder.GetAesCandidates()`）
4. 否则 `TryDecryptRsaPayload` —— 用网关私钥 RSA 解，**依次试 OAEP-SHA1 / PKCS1 / OAEP-SHA256 / OAEP-SHA384 / OAEP-SHA512**
5. 全失败 → 抛 `Gateway payload could not be decoded`

### 1.6 `encode` 字段在 Shittim 里**没有对应物**

`strings` 能搜到 `encode`，但 `GatewayController` 里没有任何地方读它。**在 Shittim 的语义里，要不要解密完全由 `keyLength/ivLength` 是否为 0 决定**，不是一个显式开关。

### 1.7 `PROTOCOL_HEAD_RESERVE` 在 Shittim 里也**没有对应物**

这是**国服客户端独有**的常量名（见 §3.4）。

## 2. Q2 — `protocol` 字段（26 字符 → 19 字节）

### 2.1 实测数据

```
b64 : AHTQLQI65FWJGGGK4KL5AEF57A        (26 字符，无 padding)
raw : 00 74 d0 2d 02 3a e4 55 89 18 61 8a e0 a2 f9 00 41 79 ec
len : 19
```

- 26×6 = 156 bit = 19.5 byte ⇒ 19 字节无 padding 的 base64 **长度自洽**
- Shannon 熵 **4.143 bit/byte**，19 字节里 18 个互不相同 —— **对 19 个样本来说已是理论最大值（log2 19 = 4.25）**，符合随机/密文
- 单字节 XOR / 加减，扫 256×3 种，**没有一种能得到全可打印** ⇒ **不是单字节混淆**
- `byte[0] = 0x00`、`byte[15] = 0x00` —— 两个 0 字节，在真随机 19 字节里的概率约 1.3%，不算罕见但值得注意

### 2.2 一个很扎眼的巧合

客户端真正的协议名（`global-metadata.dat` @`0x22D9xx` 实测的枚举名）里，**长度正好是 19 的有三个**：

```
Account_CheckYostar     19
Account_GetTutorial     19
Account_SetTutorial     19
```

**`protocol` 字段长度 = 19 = 明文协议名长度。**

⇒ 这说明 `protocol` 很可能用的是**保长加密**（流密码 / CTR / CFB / OFB / RC4 / 定长 XOR），而不是 AES-CBC（CBC 会补齐到 16 的倍数，`Account_Auth` 12 字符会变成 16 或 32）。

### 2.3 但它也可能根本不是一个"加密后的名字"

客户端类簇里有 `ProtocolHashHelper`（`GetHash`）和 `MD5HashService`（`ComputeDigest` / `ComputeDigest64` / `ComputeHead`）。

⇒ 另一种同样自洽的解释：**`protocol` 是一个"协议标签/校验码"，真正的协议名在 `packet` 解密后的 JSON 里**（就像 Shittim 从 `jsonNode["Protocol"]` 读一样）。

**这两种解释无法只靠静态数据区分，判据见 §6「决定性实验 2」。**

### 2.4 已经排除的

| 猜测 | 排除依据 |
|---|---|
| `protocol` 是明文协议名 | 19 字节里 8 个不可打印，且无任何命名像 |
| 单字节 XOR / 减法 | 256×3 全扫，无可打印解 |
| AES-CBC（补齐到 16/32） | 19 不是 16 的倍数 |
| 与 `PackertCryptManager` 的 `ping` 之类无关 | `protocol` 字段由 `EncryptRequest` 统一产出（见 §3.4 类簇顺序） |

## 3. Q3 — `packet` 的 432 字节是什么

### 3.1 外层已 100% 确认

```
packet b64 (612 字符) → 459 字节
  [0..4]  b0 01 00 00   = u32 LE = 432
  [4.. ]  1f 8b 08 00 …  gzip magic
  gunzip → 432 字节      与 u32 头声明的 432 完全一致
```

612×6/8 = 459，`ceil(459/3)*4 = 612` —— 长度自洽。

⇒ **外层 = `[u32 LE 明文长度][gzip(内层)]`，无 XOR、无 header。**

**这一条直接否掉了 Shittim 的三种变体**：Shittim 的三种变体里，`rawPayload` 前 4 字节要么是明文长度、后面的 gzip 被 XOR 过（变体 2），要么整段被 XOR（变体 1/3）。**我们的样本 gzip magic `1f 8b` 明晃晃地在明文位置**，说明外层没被 XOR。

### 3.2 内层 432 字节

```
9c 46 0e 7d e0 df 62 a2 58 07 70 8e 00 0d b0 ba …
```

- 当 flatbuffers root offset 读 = **2098087580**，远超 432 ⇒ **不是 flatbuffers**（题面已判，此处复核成立）
- 432 = **27 × 16**，432 % 32 = 16 ⇒ **AES-128 块长的整数倍**
- 前 16 字节无重复字节，分布像随机

### 3.3 三种布局及其推出的明文长度

| 布局 | ct 长度 | 块数 | PKCS7 还原后的明文长度区间 |
|---|---|---|---|
| `salt(16) + iv(16) + ct` | 400 | 25 | **384 – 399** |
| `iv(16) + ct` | 416 | 26 | 400 – 415 |
| 裸 `ct` | 432 | 27 | 416 – 431 |

**`salt(16)+iv(16)+ct` 是最符合的**：明文 384–399 字节，正好是一个 `Account_Auth` 短 JSON 的量级（字段少、无 DB 回灌）。而且——

> 客户端类簇里精确存在 **`StringCipher.EncryptStringWithPassphrase` → `cipherTextWithSalt` → `DecryptStringWithPassphrase`**，以及 **`EncryptBytesWithPassphrase` → `cipherTextWithSaltBytes`**。

**"带 salt 的 ciphertext" 这个命名，和 `salt||iv||ct` 这个布局是逐字对应的。**

### 3.4 客户端侧的类簇（`global-metadata.dat` 实测，@`0x25E1BE`–`0x25E580`）

按 metadata 里名称表的**物理顺序**原样抄下来（顺序本身反映声明顺序）：

```
HybridCryptor
  EncryptTextAES / DecryptTextAES / GenerateKeyAndIV / LoadPublicKeyFromPem
  EncryptKeyAndIVWithRSA / VerifySignatureKeyAndIVWithRSA / EncryptJsonWithRSA / VerifySignatureKeyWithRSA
AESKeyHolder (part1 / part2 / part3)
CipherKeyHolder
RSAPublicKeyHolder
AesKeyIV (IV / EncryptedKeyIV / encryptedBase64Key / encryptedBase64IV)
MD5HashService
  ToHexString / ComputeHash / ComputeHashAsString / ComputeDigest / ComputeDigest64
  ComputeHead / dbUrl / GenerateKey / ExtractDBFileNameFromURL / ExtractReservedWordFileNameFromURL
PacketCryptManager
  requestBytes / EncryptRequest / PROTOCOL_HEAD_RESERVE / _cryptor / _checker
StringCipher
  EncryptString / DecryptString / passphrase
  EncryptStringWithPassphrase / cipherTextWithSalt
  DecryptStringWithPassphrase
  EncryptBytes / DecryptBytes
  EncryptBytesWithPassphrase / cipherTextWithSaltBytes
  DecryptBytesWithPassphrase
XORCryptor
  ENCRYPTION_KEY
ProofToken / MD5ProofHash / ProofTokenHelper
ProtocolHashHelper / GetHash
```

**这张表基本把国服信封的构造流程写出来了：**

```
PacketCryptManager.EncryptRequest(...)
  ├─ _checker   -> 算一个校验值（对应 Shittim 信封里的 crc / 或 protocol 字段）
  ├─ _cryptor   -> XORCryptor(ENCRYPTION_KEY) 做外层 XOR
  ├─ StringCipher.EncryptStringWithPassphrase(protocolName, passphrase) -> protocol 字段
  └─ StringCipher.EncryptBytesWithPassphrase(json, passphrase)          -> packet 内层（cipherTextWithSalt）
  外层再 [u32 len][gzip] 包一层（PROTOCOL_HEAD_RESERVE 可能与此有关）
```

另外 `MX.Core.Crypto` 这个命名空间与 Shittim 的 `Schale.MX.*` 同源 —— **两边的类设计是同一套**，只是国服在 `GatewayController` 那一层换了包装。

### 3.5 一个必须点出来的结构差异

| | Steam / Nexon（Shittim 吃） | 国服（我们抓到的） |
|---|---|---|
| 载体 | `multipart` 里一个 **文件** `mx` | `multipart` 里三个 **文本字段** |
| 头 | `[crc][typeConv][keyLen][ivLen][headerKey][headerIv]` | 无；长度前缀在 `packet` 里 |
| 外层混淆 | XOR 0xD9 + gzip，3 种变体 | **无 XOR**，直接 `[u32 len][gzip]` |
| 内层 | 明文 JSON 或 AES-CBC（key 来自 header） | **AES + passphrase + salt**（key 不随包传） |
| 协议标识 | JSON 里的 `Protocol` 字段 | 独立的 `protocol` 文本字段 |

**⇒ 两边信封不兼容，这是实测结论，不是推断。**

## 4. Q4 — 密钥从哪来（最关键，也最诚实）

### 4.1 已经确定的

| 事实 | 等级 |
|---|---|
| 国服客户端有 `XORCryptor.ENCRYPTION_KEY` 这个静态成员 | 实测（metadata 名称表） |
| 国服客户端有 `StringCipher.passphrase` 这个参数/字段 | 实测 |
| `StringCipher` 的加密函数叫 `EncryptStringWithPassphrase` / `EncryptBytesWithPassphrase`，输出叫 `cipherTextWithSalt` | 实测 |
| metadata 里 `Rfc2898` 命中 1 次（@`0x22D9E48`），`PBKDF2` 命中 1 次（@`0x60F708`） | 实测 |
| **密钥不随包传输**：`packet` 里没有 Shittim 那种 `headerKey/headerIv` 字段 | 实测（外层结构已证） |
| **这是本次会话的第一条网关请求**（`/api/account/auth` 之前没有任何网关交互），所以**不可能是"会话协商出来的 key"** | 实测（`ba_raw.log` 时间线） |

**⇒ 结论：这把钥匙是编译进客户端的固定常量（或由固定 passphrase 经 PBKDF2 派生）。**

这一条很重要，它**排除了"必须先做 RSA 握手才有 key"** 的可能 —— 也就是说 `Account_Auth` 这个首包用的是**内置密钥**，与 metadata 里那把 RSA 公钥（网关握手用，见 `report\30-网关RSA公钥定位与替换.md`）是**两套机制**。

### 4.2 没做到的（诚实标注）

**本次没有取得 `passphrase` / `ENCRYPTION_KEY` 的具体值。** 原因：

- metadata 的名称表里只有**标识符名**，**没有它们的值**；值在 `stringLiteralData` / `fieldDefaultValues` 区段，而 metadata 头部是加密的（magic `0x12724394` ≠ `0xFAB11BAF`，见 `report\24-state接口schema反推.md` 的独立复现），**拿不到区段 offset**
- `libil2cpp.so` 里 C# 字面量**不在 .so**（已实测：`multipart/form-data`、`Account_CheckYostar` 等在 `.so` 里 0 命中，在 metadata 里才有）⇒ 需要反汇编 `.text` 才能读到静态构造器里的常量，而本项目 `.text` 有 26.2% 页面在磁盘上是 ACE 加密的（`report\11`）

**没有硬耗下去**：按任务要求，20 分钟内 Q4 无明确答案就优先给 Q1 和 Q5。

### 4.3 但是破解这件事是可行的，而且有捷径

**已知明文攻击**：这条请求是 `Account_Auth`，客户端会把我们 SDK 下发的登录态塞进包里。我们知道：

```
uid   = 314816420                                    (9 字节 ASCII)
token = 61de1d1b7519ab1231866f74c11fcfdd1f80b210     (40 字节 ASCII)
```

**40 字节的已知明文，足以在候选 passphrase 字典上做离线校验 —— 命中即 100% 确定，不存在误判。**

流程：

```
for pass in 字典:
    key = PBKDF2(pass, salt=payload[0:16], iters, 32)
    pt  = AES-CBC-decrypt(key, iv=payload[16:32], ct=payload[32:])
    if b"61de1d1b7519ab1231866f74c11fcfdd1f80b210" in pt: 命中
```

`iters` 只需要扫 `{1, 1000, 10000, 100000}` 四档（.NET 的 `Rfc2898DeriveBytes` 默认 1000，但很多实现显式指定）。

### 4.4 如果字典刷不出来，还有三条路

| 路径 | 做法 | 成本 |
|---|---|---|
| **反汇编静态构造器** | 在 `libil2cpp.so` 里定位 `MX.Core.Crypto.StringCipher` / `XORCryptor` 的 `.cctor`，读被 `ldr` 进的常量池 / `adrp+add` 指向的字面量 | 中（需要 ig5/Ghidra + 符号恢复，本项目已有 1201 个恢复符号） |
| **动态取常量** | 在进程内 hook `StringCipher.EncryptStringWithPassphrase` 拿入参 —— 但本项目已确认 Frida 与 ACE 共存风险高（`report\18`） | 高 |
| **绕过而非破解** | 不去解国服信封，而是**让客户端改发 Steam 信封**——若 nginx 侧能做到「收到三字段 → 直接回一个客户端能接受的响应」，就不需要解密 | 见 §5 路径 C |

## 5. Q5 — 最短可行路径

### 路径 A：写转换器（CN 三字段 → Shittim `.mx`）

```
客户端 POST /api/account/auth（三字段）
   → [转换器] 解 packet（AES + passphrase + salt）
   → 重新打包成 Shittim 的 .mx（[crc][typeConv][keyLen=0][ivLen=0][u32 len][gzip(json)]）
   → POST http://127.0.0.1:5000/api/gateway
   → Shittim 响应（明文 JSON）
   → [转换器] 按国服的响应格式回给客户端
```

- **前置**：拿到 passphrase（§4.3 或 §4.4）
- **工作量**：转换器本身约 150 行 Python（已经写了骨架 `mx_decode.py`，含 `build_shittim_mx()`）；**响应方向也要逆向**（国服响应长什么样还没抓到）
- **风险**：低（不改任何现有组件）
- **评级**：**如果 passphrase 到手，这是最优路径**

### 路径 B：改 Shittim 支持国服信封

在 `GatewayController` 里加一个分支：读三个文本字段 → 解包 → 走同一套 handler。

- **前置**：同样需要 passphrase
- **工作量**：比 A 大（要改 .NET 代码、重编译、且 Shittim 是第三方源码，升级会冲突）
- **评级**：不如 A。**除非**以后要长期维护，才值得改到源码里

### 路径 C：绕过（不解密）

**思路**：既然客户端只关心「响应能不能被它解开并处理」，那我们可以不去理解它的请求 —— **只把请求原样吞掉，然后用我们构造的响应喂它**。

- 需要逆向的是**响应**格式（比请求简单得多，且响应通常是我们完全控制的明文 JSON + 同一套 StringCipher 加密）
- **但如果 response 也用同一个 passphrase 加密，还是绕不开钥匙**
- 除非 `encode: False` 时客户端接受明文响应 —— **这一点是可测的**：让服务端回一个明文 JSON，看客户端是报错还是能解析
- **工作量**：小（一个 nginx location + 一个 python 桩）
- **评级**：**性价比最高的试探** —— 一次实验就能判定「响应方向是否必须加密」

### 推荐顺序

```
1) 【立刻】路径 C 的判定实验：让服务端对 /api/account/auth 回一个明文 JSON，
          看客户端反应（能解析 -> 直接跳过解密，走路径 C）
2) 【一次采集】抓 2~3 份同协议的 packet，做差分（见 §6 实验 1），
          确认 salt/iv 是否每包随机（决定 §3.3 哪个布局成立）
3) 【离线爆破】用已知明文 314816420 / 61de1d1b… 刷 passphrase 字典
4) 【爆破失败才做】反汇编 StringCipher/XORCryptor 的静态构造器取常量
5) passphrase 到手后，走路径 A（转换器已写好骨架）
```

## 6. 决定性实验清单（给执行方）

### 实验 1：差分（判 salt/IV 是否随机）—— **成本最低、信息量最大的一个**

连点两次「点击任意区域进入游戏」，抓两份 `packet`：

| 观察 | 结论 |
|---|---|
| 前 16 字节**两份相同** | 无 salt，`payload` 头就是 IV → 用 `iv(16)+ct` 布局 |
| 前 32 字节**两份相同** | salt 和 IV 都固定 → 布局仍成立，但 key 可直接反推 |
| 前 32 字节**完全不同** | salt+IV 每包随机 → `salt(16)+iv(16)+ct` 布局确认，走已知明文攻击 |

**同时对比 `protocol` 字段**：两次是否相同？
- 相同 → `protocol` 是协议名的确定性函数（保长混淆或哈希）
- 不同 → `protocol` 是每包随机的东西（token/nonce），协议名只能在解密的 JSON 里

### 实验 2：明文响应试探（路径 C 的判定）

在 nginx 里把 `/api/account/auth` 直接回一个明文 JSON（比如 Shittim 的错误信封 `{"Protocol":-1,"ErrorCode":500,...}`），观察客户端：
- 报「服务器处理请求失败」→ 说明它在解密响应时失败（响应**必须**加密）
- 报别的文案 / 行为变化 → 说明它接受了明文，**路径 C 可行**

### 实验 3：请求体完整性检查

确认 `body_b64` 解出来的 multipart 里 `packet` 字段**没有被 WAF 或探针截断**（已知宝塔 WAF 会按长度启发式拦 POST，`report\29`）。

## 8. 诚实标注（没做到的）
