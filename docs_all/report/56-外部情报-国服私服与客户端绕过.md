## 0. 一句话结论

> **⚠️ 本文有第二轮补遗（§10），改写了三处结论。** 只读结论的话直接看 **§10.3（metadata 版本伪造）**、**§10.2（LocalizeConfig 结案）**、**§10.10（修订对照表）**。

**外部没有现成答案。** 截至本轮，全网没有找到任何一个能跑国服 `com.RoamingStar.BlueArchive` 的私服、一键端、改版 APK、Frida 脚本或 KernelSU 模块，也**没有任何人公开过国服 `/api/account/auth` 的成功响应**。

但本轮从外部带回 **4 条可直接用于推进的硬情报**（第 4 条见 §10.3，是第二轮加的、也是最重要的一条）：

1. `Account_Auth`(1002) 之后的**下一条协议是 `Account_LoginSync`(1019)，由客户端主动发**，不是等服务端推送 —— 这直接挑战本仓库既有的"等推送"假设（`report/48`）。
2. **`Account_Auth` 是免会话协议，`SessionKey` 是 `Account_CheckNexon`(1014)/`CheckYostar`(1009) 才发的** —— 国服首包若是 `Account_Auth`，说明它**根本没走 RSA / 发会话那一段**，这解释了为什么"补 SessionKey"无效。
3. Shittim 的 `ClientMetadataPatchService` 给出了 metadata 改公钥的**工业级做法**（AOB 定位 + 定长分块 + sidecar 还原 + 关开关必须主动还原）。
4. **【§10.3】看雪一篇 BA 逆向实录给出：`global-metadata.dat` 不是被加密，是 `version` 被伪造成 31（真实 il2cpp v27），且 metadata usage token 布局被魔改（`index` 要先右移 1 bit）。** 这与本仓库 `DEADENDS` D-34/D-35「表头混淆、methods 表 0 候选」**高度吻合**，并给出了 Il2CppDumper 的确切补丁与 `cpp2il` 兜底方案 —— **这可能是唯一能一次性消除"零反应"根因的路径。**

**为什么这条对国服 3.0.2 有价值（三条独立的、可复用的硬事实）：**

1. **国服资源目录是 `files/AssetBundls`（注意官方拼写就是少一个 e 的 `Bundls`）**，在 `Android/data/<pkg>/files/` 下。这与本仓库已知的 `files/Hosts`、`files/LocalizeConfig.txt` 同处一个目录。

### 3.2 【挑战既有假设】Auth 之后是 `Account_LoginSync`，由客户端发

- 原文位置：`docs/wiki/base/auth.md` §「当前流程」

**[实读]** 原文照抄（这是 headless SDK 的登录链路"当前流程"）：

> ## 当前流程

**[实读]** 同一文件对 `session` 的描述：

**这条对国服的意义（本报告最重要的一条推论）：**

本仓库 `report/48` 的核心假设是"客户端在等某个推送/某个字段"，`DEADENDS` D-45 也把"客户端只发 1 条协议就停住"当成一个需要解释的现象。但 headless SDK 显示：**在国际服，`Account_Auth` 之后的下一条是客户端主动发的 `Account_LoginSync`(1019)**，不需要服务端推送任何东西。

⇒ **两种可能，且都能被本仓库现有判据区分：**
- **（a）国服也是 Auth→LoginSync**：那"客户端不发第二条"就是**解析/字段层面的静默失败**，而不是"等推送"。`report/48` 的"等推送"假设应当削弱，`report/49` §5.2 那条"只改一处"的回退阶梯是正确方向。

## 5. 参考实现精读

### 5.1 【重点】Shittim `ClientMetadataPatchService.cs` 全文精读

- URL：<https://github.com/Neoexm/Shittim-Server/blob/main/Shittim-Server/Services/ClientMetadataPatchService.cs>
- **[实测]** 文件 18,931 字符，435 行，本轮全文取回并逐段读过。

**它到底在做什么（一句话）**：把客户端 `global-metadata.dat` 里**内嵌的官方 gateway RSA 公钥**，原地替换成私服自己的公钥。因为客户端用那把公钥对网关握手做 RSA 加密，服务端解不开就进不去。

**[实读]** 类头注释原文（关键句逐字照抄）：

> // The key is three separate string literals in the metadata rather than one run, and the split lands wherever the build's literal packing put it: 272/272/255 for the RSA-4096 key, and 150/150/150 for the RSA-2048 one it replaced.
> private static readonly int[] ChunkLengths = [272, 272, 255];
> private const int ChunkCount = 3;

> // The official Nexon gateway RSA-4096 public key, exactly as it is embedded inside the client's global-metadata.dat.
> // **The client RSA-encrypts the 50001 gateway handshake with this key**, so swapping in the private server's own key is what lets the gateway decode the handshake. Ours has to be 4096-bit as well: the chunks are fixed-size holes in `fieldAndParameterDefaultValueData`, and a PEM of any other length cannot go into them without shifting the section and every offset past it.

> // The three byte runs are located by content (an AOB scan) rather than by fixed file offsets: **the offsets move every time the client is rebuilt, and build 439170 shifted all three by +0x49B0.**
> // Writing at a stale offset corrupts whatever IL2CPP metadata now lives there and **hangs the client at "Unpacking game resources"**. A scan also fails safe: a chunk that cannot be found means no write at all.

**[实读]** 关掉开关时的行为（这条设计思路值得抄）：

> if (!IsEnabled())
> {
>     // Turning the patch off is how someone goes back to the official client, so it has to mean putting the key back rather than merely not patching again. A `global-metadata.dat` left carrying our gateway key **hangs the client on "Unpacking game resources"** with nothing on screen to say why, and the usual guess is to verify the files through Steam.
>     RestoreMetadata();
> }

**[实读]** 定位算法的 fail-safe（`TryLocateUnique`）：

> // Finds the single occurrence of pattern in data. **Returns false if absent or ambiguous (found more than once)** so the caller can fail safe instead of patching the wrong location.

**[实读]** 状态文件与还原（`RestoreMetadata`）：

> // 若当前字节不等于"已打过"的镜像 → `logger.LogWarning("Client metadata did not match the active patch state. Leaving it unchanged")` → 直接 return，不写
> // 否则写回 `originalChunks`，并删除 sidecar

**[实读]** 关键常量与环境变量：

> `SHITTIM_AUTO_PATCH_METADATA`（bool，覆盖配置）
> `SHITTIM_CLIENT_METADATA_PATH`（metadata 路径）
> `SHITTIM_GATEWAY_RSA_PUBLIC_KEY` / `..._PATH` / `SHITTIM_GATEWAY_RSA_PRIVATE_KEY` / `..._PATH`
> 配置项：`ServerConfiguration.EnableGateway && ServerConfiguration.AutoPatchClientMetadata`、`ClientMetadataPath`、`GatewayRsaPublicKeyPem`、`GatewayRsaPublicKeyPath`、`GatewayRsaPrivateKeyPath`
> sidecar：`<metadata>.shittim_patch.json`，结构 `{ MetadataPath, Chunks:[{ Offset, Original(base64), Patched(base64) }] }`
> 默认路径：`SteamGameLocator.FindGameFile("BlueArchive_Data/il2cpp_data/Metadata/global-metadata.dat")`

**对国服 3.0.2 的适配性：要改造，但思路和坑位全部适用。**

| 要素 | 国际服（Shittim 做法） | 国服 3.0.2 要怎么改 |
|---|---|---|
| 目标文件 | `global-metadata.dat` | 同名，但国服**表头被混淆**（magic `0x12724394` ≠ `0xFAB11BAF`，`report/24:245`、D-34）——**AOB 扫描不受影响**（它只按字节内容找，不解析结构）⇒ **这一步在国服反而更好用**，因为本仓库解析不了表头，但能扫字节 |
| 定位方式 | AOB 按内容扫，唯一命中才写 | **直接照抄**。国服每次 APK 更新偏移也会变，绝不能硬编码偏移 |
| 分块长度 | `[272,272,255]`（PEM 690 B，RSA-4096） | **必须先实测国服自己的分块长度**。做法：从国服 `global-metadata.dat` 里搜 `-----BEGIN PUBLIC KEY-----` 的**各段**，量出每段长度。若国服也是三段，长度很可能同样是 690（因为官方也用 4096-bit），但**不能假设**——若国服 PEM 是 2048-bit，长度是 450（`150/150/150`） |
| 写入位置 | `fieldAndParameterDefaultValueData` 段内的定长"洞" | 同段，但**长度必须严格相等**，否则后面所有偏移全错位 |
| 失败后果 | 客户端卡 `Unpacking game resources` | **国服等价现象未知，但极可能是"卡加载/闪退无日志"**。⇒ 这条解释了本仓库一类"无日志静默卡死"的可能成因，值得对照 `DEADENDS` 里那几条"无弹窗无日志"的记录 |
| 回滚 | sidecar 记录 Original/Patched/Offset；关开关**主动还原** | **强烈建议照抄**。本仓库 `report/30` 做过"网关 RSA 公钥定位与替换"，但**没有"状态化还原"机制**——一旦写错或换版本，无法回到官方字节，只能重装 |
| 安全阀 | `TryLocateUnique`：命中 0 次或 >1 次都**不写** | **强烈建议照抄**。这是"宁可不改也不要写坏"的硬纪律 |

**[实测]** 与本仓库既有工作的关系：`report/30`（网关 RSA 公钥定位与替换）已经做了同一件事的**一次性版本**。本文件补的是**工程化外壳**（状态、还原、fail-safe、环境变量、默认路径）。**这是本轮对"已有工作"最有价值的增量。**

**一个必须指出的疑点（也是最有用的疑点）：**
注释明确说这把公钥用于 **`50001 gateway handshake`**。而 headless SDK 的协议表显示：

- `Account_PassCheck`(1007) 的 **Request** 带 `ClientGeneratedKey` / `ClientGeneratedIV`，**Response** 回 `EncryptedKey` / `SignedKey` / `EncryptedIV` / `SignedIV`；
- `Account_CheckNexon`(1014) 的 Request 同样带 `ClientGeneratedKey` / `ClientGeneratedIV`，Response 在四件套之外还多一个 `SessionKey`；
- `Account_CheckYostar`(1009) 的 Response 也有 `EncryptedKey`/`SignedKey`/`EncryptedIV`/`SignedIV`（本仓库 `report/28:885` 另记它也在解密 `ClientGeneratedKey/IV`）。

⇒ **带这套"客户端生成 key/IV → 服务端 RSA 包 + 签名回传"的，只有 1007 / 1009 / 1014 这三个"换会话密钥"的协议。**
而 **`Account_Auth`(1002) 的 Request/Response 里一个 `*Key` / `*IV` 字段都没有**（Request 是 17 个设备/版本字段，Response 是 21 个业务字段）。

⇒ **[推断] RSA 只在 1009/1014 这类"发会话"协议上用到。** 而本仓库已实测国服首包是 `Account_Auth`(1002)（`report/33:96`）。**如果国服客户端首包直接是 `Account_Auth`，它根本没有走到 RSA 那一段。** 那么"改 metadata 里的 RSA 公钥"对国服的首包**可能是完全无效的**——这值得用一次低成本实验来判：把公钥改回官方值，看客户端行为**有没有任何变化**。若毫无变化 ⇒ 证实"国服首包不经过 RSA"，可把 `report/30` 这条路降级。

### 6.1 `report/48` 的"等推送"假设应当削弱

**依据**：§5.1 最后那段。Shittim 注释说 RSA 公钥用于 `50001 gateway handshake`；headless 协议表显示只有 1007/1009/1014 带 `ClientGeneratedKey/IV`；国服首包是 `Account_Auth`(1002)。

**动作**：把 metadata 里的网关 RSA 公钥**改回官方原值**，冷启动一次，比对行为（第二条请求数 / 弹窗 / 截图）。**若与"换成我们的公钥"完全一致** ⇒ 证实国服首包不经过 RSA，`report/30` 这条路可以降级/关闭，省掉后续所有在这上面的投入。

**成本**：一次冷启动 + 一次截图判读。**这是本轮性价比最高的一个实验。**

### 6.3 `report/49` 的定稿现在有了外部交叉验证

**依据**：§3.1 的 21 字段表与 `report/49` 的 20 属性逐条比对，14 个字段名一字不差吻合，5 个国服特有字段（`DailyRecordDBs`/`OptionDB`/`AccountLimitedFlashSaleDBs`/`Desc`/`FunctionClose`）外部没有但不冲突，5 个国际服独有字段（`AttendanceBookRewards` 等）与 `report/41` 的"国服 0 命中"一致。

**动作**：在 `report/49` 顶部把结论等级从"[推断] 类型是推断"升级一句：**"字段名与集合与 headless-bluearchive/SDK 公开 DTO 独立交叉验证一致（`docs/protocols/Account.md`）"**。

**成本**：零。

### 6.4 `report/30` 缺的"状态化还原"应当补上

**依据**：§5.1 的 sidecar + `RestoreMetadata` + `TryLocateUnique` 三重设计。Shittim 明确写：metadata 里留着"我们的公钥"会让客户端**卡在 `Unpacking game resources` 且屏幕无任何提示**。

**动作**：本仓库现在的公钥替换若是"一次性写死"，应补三件：① 写前把原始字节存到 `<metadata>.ba_patch.json`；② 定位时"命中 0 次或 >1 次都不写"；③ 提供一键还原。

**成本**：小。但**能避免一次"改不回来只能重装 2 GB"的事故**——`work/ba/audit/ba-pitfalls.md` 里已经记过清空 `/data/data/<pkg>` 会导致永久卡启动的教训。

### 7.2 最接近的方案是什么、差在哪

**最接近的三条，按"差多少"排序：**

**① headless-bluearchive/SDK —— 差"一个 region + 一套信封"**
- 它有的：`Account_Auth` 完整 DTO、协议号表、登录链路顺序（`Queuing_GetTicket → CheckNexon → ProofToken → Auth → LoginSync`）、`Account_LoginSync` 聚合体全表、`region_config.py` 这套干净的 region/profile 结构。
- 它差的：**没有国服 region**（5 个区全是 `nxm-*-bagl.nexon.com`）；**没有国服信封**（`multipart protocol/encode/packet` + 包尾明文 key 这套它完全不涉及）；`SessionKey` / `AttendanceBookRewards` 等国服不存在的字段反而在里面。
- **差在哪一句话**：它把国际服的**协议语义层**做完了，但**传输层和区服**这两块完全没有国服。而本仓库恰好相反——**传输层已破解（`report/35`），协议语义层在自研**。
- ⇒ **互补性极高，但合不起来。** 能拿的是 DTO 字段表和流程顺序（已拿，见 §3）。

**② Xuoos/AnimeGamesProxy —— 差"一个 game 条目"**
- 它有的：Xposed 层重定向到私服 + 禁用反作弊的**成熟框架**（240★，2026-07 在更）；`agp_config.xml` 静默配置；LSPatch/NPatch 无 root 路径；已给明日方舟做"仅国服"、给原神做 RSA Patch。
- 它差的：**碧蓝档案只做了日服&国际服**。
- **差在哪一句话**：一个明确会做国服、明确会做反作弊绕过的模块作者，**在 BA 上跳过了国服**。这要么说明国服 BA 的重定向点被 ACE 守住，要么说明国服的登录链存在某种"不做完服务端就没法动"的东西。**这是本报告最值得警惕的一条信号。**

**③ Neoexm/Shittim-Server 的 `ClientMetadataPatchService` —— 差"一次参数实测"**
- 它有的：metadata 改公钥的**完整工程做法**（AOB 定位、定长分块、唯一命中才写、sidecar 还原、关开关主动还原、环境变量/配置项）。

- **差在哪一句话**：工程外壳可以直接抄，**但要先证明这个洞在国服是通的**。

### ⭐ 命中点 1：`global-metadata.dat` 不是"被加密"，是**版本号被伪造**

本仓库 `DEADENDS` D-34 / D-35 的结论是「国服 metadata 表头被混淆，Il2CppDumper 首步即废，magic `0x12724394` ≠ `0xFAB11BAF`，32 秒 stride×phase 扫 methods 表 0 个候选」。

**[亲验]** 还给了绕过自动搜索的补丁与两个强制地址：

> `Il2CppDumper/Config.cs` 增加 `ForceCodeRegistration` / `ForceMetadataRegistration`
> 在 `PlusSearch` 前直接 `il2Cpp.Init(cr, mr)`
> - `ForceCodeRegistration = "ee1c1a0"`
> - `ForceMetadataRegistration = "f410418"`
> 求解思路：**MetadataRegistration** 找 `typeDefinitionsSizesCount`/`typesCount` 且每个指针字段都挂 `R_AARCH64_RELATIVE`；**CodeRegistration** 用 `codeGenModulesCount == imageCount`（本样本 108=0x6c）锁定 `(count, ptr)`，再往前数 13 个 8 字节即结构体起点

### ⭐ 命中点 2：metadata usage token 布局被魔改

**[亲验]** 原文（反编译 `sub_63E2AA0` 后剥出的核心）：

```c
// 最低位为0：已解析真实指针，直接返回
if ((token & 1) == 0)
    return token;

// 最低位为1：待解析token
kind  = (token >> 29) & 0x7;
index = (token >> 1)  & 0x0FFFFFFF;   // ← 先右移掉 bit0
```

> 可得与原版 il2cpp 的显著差异：**最低位被单独拿去当状态标志（标记是否已解析），index 得先右移掉这一位再取 28 位。套通用公式时这个 flag 混进了 index**，自然要么越界、要么解出无关字符串。
> 原版公式是 `kind = token >> 29; index = token & 0x1FFFFFFF;`

**这条能直接解释 D-34 里"stride×phase 扫 0 候选"**：`index` 只差一个右移，但所有索引整体错位 1 bit ⇒ 扫全表必然全空。

### 10.4 API 服务器地址到底在哪：`GameMainConfig` → `ServerInfoDataUrl`

上一节回答"key 里没有 API 地址"，这一节回答"那它在哪"。

**[亲验]** 看雪原文：

> `GameMainConfig` 大小为 914B，是**密文**。
> 其中的 TextAsset `GameMainConfig` …… 使用上面的脚本 `CreateKey('GameMainConfig')`，可以非常轻松的成功解密

> 资源根 `{root}` 则来自**登录 dispatcher 下发**的 `ServerInfoData.ConnectionGroups[].AddressablesCatalogUrlRoot`

**[亲验]** 明文→密文的验证（这条能给我们一个**自检手段**）：

> 直接看密文字节，可以发现**奇数字节呈现严格周期 8**：`23 06 72 57 23 06 72 57 ...`
> 这正好符合"UTF-16LE 明文的奇数字节多为 0，再被 8 字节 key 循环异或"的特征。同时 `06`、`57` 都小于 `0x80`，也和前面 `MersenneTwister.Next()` 会右移一位的特征吻合。

**⇒ 对国服的意义（三条）：**

1. **API 服务器地址不在任何文本配置文件里，而在 APK 内一个 914 B 的加密 TextAsset `GameMainConfig` 里**（字段名 `ServerInfoDataUrl`）。⇒ 以后想找"国服的 dispatcher URL"，**不要去翻 `LocalizeConfig.txt` / `Hosts` / `shared_prefs`，去解 `GameMainConfig`**。
2. **但我们已经不需要这个值了**——`report/31` 已从真实响应里拿到 `gsqc`/`state-api` 全套 URL。**这条的价值是"机制解释"，不是"要取新情报"。**
3. **`ConnectionGroups[]` + `OverrideConnectionGroups{}` 这个结构，就是 `files/Hosts`**。对照 `DEADENDS` D-09 记的 `Hosts` 结构：`u32 ver | u32 count | loop{u8 hostlen, host, u32=1, u8 urllen, url(带 scheme+端口), u64, u8 flag}` —— `host` = `ConnectionGroups[].Host`，`url` = `AddressablesCatalogUrlRoot`，`u32=1` 极可能是 `ConnectionGroup` 的启用/优先级位，`u64` = `OverrideConnectionGroups` 的版本键（如 `"1.69"` 这种版本串的哈希/时间）。

**⇒ 这条给了 `DEADENDS` D-10「Hosts 能写进去但不被选中」一个新的、具体的技术假设：**
`OverrideConnectionGroups` 是一个 **`Dictionary<string, ...>`，键是"版本串"**。我们改 `url` 但没改键 ⇒ 客户端拿**当前客户端版本**去查这个字典，查不到就**回落官方默认**。
**可检验预测**：`Hosts` 里那个 `u64` 字段很可能就是**版本键的编码**，必须改成"当前版本能命中的值"，而不是随便加 0x100000（D-12 干过的事）。
这是本轮对 `Hosts` 死路给出的**第一个有指向性的假设**。

### 10.5 表格/资源解密：一套可直接跑的算法（国服大概率同构）

本仓库 `report/04` 记「大厅数据灌入每一条都要 Excel 数据」。看雪这篇把**表包的解密链条全给了**。

**[亲验]** 原文链条（四层）：

1. **资源根**来自 dispatcher 的 `AddressablesCatalogUrlRoot`（= `ResUrls`）
2. `TableBundles` 是 **SharpZipLib 的带口令 ZIP**：`zipStream.Password = TableService.CreatePassword(bundleName, 20)`
3. `MediaResources` 同机制
4. `catalog_Android.zip` **不带口令**（普通 zip）
5. 表包内 `.bytes` 还有**第二层 XOR**：`TableEncryptionService.XOR(name, bytes)`

**[亲验]** 口令算法（ISIL 逐条推出）：

> `TableService.CreatePassword(key, length=20)`：
> `seed = xxHash32(UTF8(key))` → `mt = MersenneTwister(seed)` → `raw = mt.NextBytes(15)` → `Base64(raw)` = 20 字符
> `MersenneTwister.Next()` 不是直接 `genrand_int32()`，而是 `(genrand_int32() >> 1) & 0x7FFFFFFF`
> `NextBytes(len)` 每 4 字节调一次 `Next()`，`BitConverter.GetBytes` 按小端写入

**[亲验]** 作者给了**端到端验证**：

> 按真实运行名 `Excel.zip` 计算口令：`CreatePassword("Excel.zip") = /wy5f3hIGGXLOIUDS9DZ`
> 依旧成功解密。
> （`https://prod-clientpatch.bluearchiveyostar.com/r92_.../TableBundles/Excel.zip` → 200 / 18,209,833 B / `local header flags = 0x0009` ⇒ `flags & 1` ⇒ 加密 zip）

**⇒ 这套算法可直接用于国服，前提只有一个：国服的表包口令算法是否相同。**
判据很简单：`local header flags & 0x0001` 为 1 就是加密 zip；用 `CreatePassword("<bundle>.zip")` 试开，**开得开就说明同构**。

**[建议]** 把下面的实现落到 `work/` 下，拿**国服** `TableBundles/Excel.zip` 试一次。这是把 `report/04` 的"缺 Excel 数据"从"要手搓"变成"能直接解出"的关键，而且**完全离线、不碰手机**：

```python
# xxHash32(seed=0) + MT19937，用于 BA 表包口令与表内 XOR
import base64, struct
P1,P2,P3,P4,P5 = 2654435761,2246822519,3266489917,668265263,374761393
M=0xFFFFFFFF
def _rl(x,r): x&=M; return ((x<<r)|(x>>(32-r)))&M
def xxhash32(data, seed=0):
    n=len(data); i=0
    if n>=16:
        v1=(seed+P1+P2)&M; v2=(seed+P2)&M; v3=seed&M; v4=(seed-P1)&M
        def _round(v,k): return (_rl((v+(k*P2)&M)&M,13)*P1)&M
        while i<=n-16:
            v1=_round(v1,struct.unpack_from('<I',data,i)[0]); i+=4
            v2=_round(v2,struct.unpack_from('<I',data,i)[0]); i+=4
            v3=_round(v3,struct.unpack_from('<I',data,i)[0]); i+=4
            v4=_round(v4,struct.unpack_from('<I',data,i)[0]); i+=4
        h=(_rl(v1,1)+_rl(v2,7)+_rl(v3,12)+_rl(v4,18))&M
    else:
        h=(seed+P5)&M
    h=(h+n)&M
    while i+4<=n:
        k=struct.unpack_from('<I',data,i)[0]; i+=4
        h=(_rl((h+k*P3)&M,17)*P4)&M
    while i<n:
        h=(_rl((h+data[i]*P5)&M,11)*P1)&M; i+=1
    h^=h>>15; h=(h*P2)&M; h^=h>>13; h=(h*P3)&M; h^=h>>16
    return h&M

class MT:
    def __init__(self, seed):
        self.mt=[0]*624; s=seed&M; self.mt[0]=s
        for i in range(1,624):
            self.mt[i]=(1812433253*(self.mt[i-1]^(self.mt[i-1]>>30))+i)&M
        self.idx=624
    def genrand_int32(self):
        if self.idx>=624:
            for i in range(624):
                y=(self.mt[i]&0x80000000)|(self.mt[(i+1)%624]&0x7fffffff)
                v=self.mt[(i+397)%624]^(y>>1)
                if y&1: v^=2567483615
                self.mt[i]=v&M
            self.idx=0
        y=self.mt[self.idx]; self.idx+=1
        y^=y>>11; y^=(y<<7)&2636928640; y^=(y<<15)&4022730752; y^=y>>18
        return y&M
    def Next(self): return (self.genrand_int32()>>1)&0x7FFFFFFF
    def NextBytes(self,length):
        out=bytearray(length); i=0
        while i<length:
            b=struct.pack('<I',self.Next())
            for j in range(4):
                if i+j<length: out[i+j]=b[j]
            i+=4
        return bytes(out)

def create_key(name):                          # 8 字节 key（GameMainConfig 解密用）
    return MT(xxhash32(name.encode())).NextBytes(8)
def create_password(key, length=20):           # zip 口令，20 字符
    return base64.b64encode(MT(xxhash32(key.encode())).NextBytes((length*3)//4)).decode()
def xor_bytes(name, data):                     # 表内第二层 XOR
    mt=MT(xxhash32(name.encode())); out=bytearray(data); k=0
    for i in range(len(out)):
        if i&3==0: k=mt.Next()
        out[i]^=(k>>((i&3)*8))&0xFF
    return bytes(out)
# 自检（看雪给出的真值）：create_password("Excel.zip") == "/wy5f3hIGGXLOIUDS9DZ"
```

### 10.6 ⭐ `niyaniya-lab/ba-sniff`：国际服"RSA 墙"结论，反证**国服的加密比国际服弱**

**[亲验]** 本仓库已有子代理落盘的文件：`_intel_ba_sniff_FINDINGS.md`（34,602 B），我 grep 过原文：

> L35–37：`The AES **session key** is delivered in Queuing_GetCryptoKeys as a 256-byte RSA-2048 ciphertext wrapped to Nexon's gateway public key. Only Nexon holds the private key → unrecoverable by observation. The clear 32-byte value in the ...`
> L244：`50000 Queuing_GetTicket` · `50001 Queuing_GetCryptoKeys` · `50002 Queuing_GetAuthTicket`

**这段话的价值不在它说了什么，而在它和国服的对比：**

| | 国际服（ba-sniff 实测） | 国服（本仓库实测） |
|---|---|---|
| 会话 key 下发 | **256 B 的 RSA-2048 密文**，只有 Nexon 有私钥 ⇒ **被动抓包不可解** | **包尾 32 B 明文 ASCII** ⇒ `report/35` 实测 **100% 命中** |
| 包体 | `XOR(0xD9)` + gzip | `[u32 len] + gzip`，**外层无 XOR** |

**⇒ 结论（这条应该写进 INDEX）：国服没有做 RSA 包裹，把会话 key 明文留在包里。**
三条推论：
1. **我们的协议解密是真正完整的**，不存在"还差一层没解"——国际服社区那句"只能上 Frida"对国服**不成立**。
2. **RSA 公钥（`report/30`）在国服大概率不参与会话建立** ⇒ 与 §6.2 的 P0 实验**相互印证**。现在有两条独立依据支持"把公钥改回官方值，看有没有变化"。
3. ba-sniff 特别警告"`GetCryptoKeys` 里那个**跨会话不变的明文 32 字节**是诱饵，解不开任何东西"。**⚠️ 我们应当自查**：我们那个"包尾 32 B key"是否**跨会话不变**？如果是，它也可能不是真 key（虽然 `report/35` 说解出已知明文，那就不是诱饵）。**这条只是提醒，不是质疑既有结论。**

**[子代]** ba-sniff 的 body 解码有 3 个变体（A: 整体 XOR→`[i32 len][gzip]`；B: 明文长度前缀→其余 XOR→gzip；C: 整体 XOR→gzip 无长度前缀），我们的国服格式 = **变体 C 去掉 XOR**。此说法我**未逐行复核**，仅作参考。

### 10.7 Shittim 在 PC 端到底改哪三个文件（补 §5.1 的空白）

**[子代]**（来自 `ba-sniff` 的 `restore-client.ps1` 文档，我未独立复核）Shittim 每次启动 patch Global/Steam 客户端**三个**文件：

1. `gamescale.core.dll` —— 改 **auth 端点**（官方认证地址 → localhost）
2. `global-metadata.dat` —— 改 **gateway RSA 公钥**
3. `ExcelDB.db` —— 静态数据表

前两个有 sidecar 可秒还原；**`ExcelDB.db` 无备份**，只能靠 Steam"验证文件完整性"恢复。半还原状态会被官服拒绝并报 **"Abnormal client"**。

**[亲验]** `KiyoEditz/Shittim-Server` 的一句原文（子代理引，我标为[子代]）：`automatically patch the client gateway RSA public key inside global-metadata.dat`。

**⇒ 对我们的意义**：这套 PC 三文件法**不要照抄**。国服有 `LocalizeConfig.txt`（资源侧零改包），且国服是 ARM64，改 metadata 要重签 APK，风险远高于 PC。
**§6.4 的建议（补 sidecar + 唯一命中才写 + 一键还原）现在有了更硬的依据：连 PC 端都会因为漏备份 `ExcelDB.db` 而只能靠"验证完整性"兜底。**

另：**[子代]** Shittim 的 `ExcelDB.db` 没有备份这一点，反过来印证 §10.5 —— **表数据是可解密的**（否则它不会直接 patch 一个明文 sqlite）。
