## 0. 结论（先行）

**Q1｜能不能静态改客户端让 state 请求走我们？**
**不能改"值"，但能改"出口"。** 全文件扫描证明 `state-api.bluearchive-cn.com` 不是任何形式的静态字面量
（ASCII / UTF-16 / 单字节 XOR 全 256 key / 周期 ≤8 的 XOR keystream / libil2cpp 全部 0 命中）。
客户端里唯一与游戏 API 有关的 URL 字面量是 **`http://test-ba.yostar.net:5210/api/state`**（3 份相同，JSON 数组，
`global-metadata.dat:0x0c172b`，XOR key `0xB5`）——它是"默认 connection group"的内嵌 JSON。
真正能静态定位的是**消费 URL 的唯一出口**：`ServerInfoConnectionGroupData.get_ApiUrl`（裸名 `0x129daf`，方法表名
`0x3d8df9`，紧挨着 `GameSessionManager.CreateSession` 与 `HttpGameSession.Init`），以及 `GameMain.GetDefaultConnectionGroup`
（`0x41c579`）、`GameMain.get_ServerInfo`。**结论：静态只能定位到类/方法，定位不到值 → 值只能运行时取或不解密（改连接层）。**

**Q2｜证书校验，静态绕过 vs 运行时绕过？**
两者都绕不开同一个前置：**要拿到 `CustomCertificateHandler.ValidateCertificate` 的代码地址**。
而本包的 `global-metadata.dat` 是**部分 XOR 混淆的**（见 §2），标准 Il2CppDumper 静态解析在本包上不可行
（header magic 被改成 `0x12724394`；12 种 stride×phase 扫描找不到 methods 表；`nameIndex` 的 u32 引用 0 命中）。
→ **"静态 patch"实际等于"运行期 dump 解密后的 metadata + 离线改文件"**；纯运行期 text patch 还要额外吃 i-cache 不刷新的亏。
**成本最低的是第三条：先不碰代码**——把我们的 CA 装进 tmpfs 的 `cacerts`（你已确认可写），再把 connect 重定向到我们的 TLS 服务端
（真证书、SAN 已覆盖），看握手是否直接通过。只有这一步失败，才做 `ValidateCertificate` 的 patch。

**Q3｜有没有不碰证书的第三条路？**
**有，而且证据支持。** 默认 connection group 的字面量就是 **`http://`**（不是 https），说明 `ApiUrl` 的消费端
**接受明文 http**；metadata 里没有任何"强制 https / scheme 校验 / pinning"的游戏侧证据（`StartsWith`/`UriSchemeHttps`
全部来自 BCL/TMP 库，不是游戏逻辑）。因此：只要能让客户端**用 http 的 URL**（改 URL 或改 Hosts），TLS 整层可以跳过；
而"改 URL"又回到 Q1 的同一个出口。**在拿到 URL 之前，最省事的是 CA + 重定向。**

**最推荐的一条路**：`系统 CA 安装 → connect 重定向到我们的 443 → 用真证书跑通 TLS → 观察 /api/state 是否命中`
（零二进制补丁、可回滚）；跑不通再走"dump metadata → patch `CustomCertificateHandler.ValidateCertificate`"。
第一条命令见 §6。

## 2. 先决事实：`global-metadata.dat` 是**部分 XOR 混淆**的

这一节决定了 Q1/Q2 的"静态可行性"，必须先钉死。

### 2.1 文件头被改写

| 项 | 值 | 证据 |
|---|---|---|
| 文件大小 | 38,426,024 B | `md3.py` |
| 标准 magic `0xFAB11BAF` | **全文件不存在** | `md2.py`（`find` 返回 -1） |
| 实际首 4 字节 | `94 43 72 12` → 被当作 magic `0x12724394` | `md2.py` |
| `version` 字段 | 解析成 `-325170408`（无意义） | 标准头布局解析 |
| 分块可打印率 | 0x000000–0x0b0000 ≈ **0.37（随机/加密）**；0x0f0000–0x7a0000 ≈ **0.82（文本）**；0x7c0000 以后 ≈ 0.5（二进制表） | `md5.py` 全文件 256 KB 图 |

### 2.2 字符串堆按"段"使用不同 XOR key（这是关键）

同一个名字会以两种形态出现，且**都能解出同一内容**：

| 名字 | 明文偏移 | XOR-0x66 偏移 |
|---|---|---|
| `CustomCertificateHandler` | `0x0041b7ef`（作为 `CustomCertificateHandler-ValidateCertificate0` 的一部分） | **`0x001522b3`** |
| `certificateData` | — | `0x001522cc` |
| `ValidateCertificate` | `0x0041b808`（同上，后缀形态） | `0x001522dc` |
| `<>iFixBaseProxy_ValidateCertificate` | — | `0x001522f2` |
| `GetDefaultConnectionGroup` | `0x0041c579`（后缀形态） | `0x001546f0` |
| `CryptAES` | `0x00259ba6` | — |
| `DecryptRJ256Api` | `0x00259c08` | — |
| `EncryptRJ256Api` | `0x00259be7` | — |

解码方法（可复算）：

```python
seg = bytes(b ^ 0x66 for b in d[0x152200:0x152260])
# -> 'e\x00defaultActivate\x00...\x00CustomCertificateHandler\x00certificateData\x00ValidateCertificate\x00<>iFixBaseProxy_ValidateCertificate\x00...'
```

→ **字符串堆不是单一明文**：至少存在 key=0x00 与 key=0x66 两类区段；字符串字面量区还有"每个字面量独立 key"
（例：`["http://test-ba.yostar.net:5210/api/state",…]` 用 `0xB5`；InputSystem 的 JSON 用 `0x1A`/`0x7C`）。
**任何静态解析器都必须先做这层解码，否则拿到的 nameIndex/表全是错的。**

### 2.3 表区没有标准结构（标准 Il2CppDumper 走不通的直接证据）

| 检验 | 结果 |
|---|---|
| `nameIndex` 反查：把已知名字的**文件偏移**当 u32 搜全文件 | `0x41b7ef` / `0x41c579` / `0x129d13` / `0x14f9a7` 全部 **0 命中**（`md8.py`） |
| methods 表结构扫描：**12 种 stride**（0x14…0x40）× 全部 phase，要求首字段 >0 且 <0x1800000（24 MB 堆也覆盖） | **0 个候选**（`md13.py`） |
| 表区 u32 分布（0x7c0000 起） | `<0x1800000` 占 39%、`<0x10000` 占 29%、max `0xffffffff` —— 均匀随机，不是索引数组 |

→ **静态从 metadata 反推 methodIndex 这条路，在当前文件上不可行。** 这直接决定 Q2 的答案形态。

## 3. Q1：客户端到底怎么决定网关地址

### 3.1 能静态确定的类结构（全部来自 metadata 名字堆）

**A. `GameMain`（22 个方法，`0x14f9a7` 是类型名）**

GameMain-InitApp0 / InitAppInTool0 / InitGameData0 / InitSDK0 / InitDataManagerInTool0
GameMain-GetDefaultConnectionGroup0      ← 取"默认连接组"

GameMain-SetEnviormentPath0 / get_PersistentDataPath0 / get_DataPath0 / get_StreamingAssetsPath0
GameMain-CoNetworkTimeSync0              ← 网络对时（说明 GatewaySession 已建立）
```

**B. `ServerInfoConnectionGroupData`（字段/属性，行号 28999–29030）**

```
AddressablesCatalogUrlRoot(s) / ApiUrls / ApiUrl / CallbackUrl / Msg

→ 这就是"服务器信息/连接组"的 DTO：**ApiUrl 是唯一被网络层消费的 base**（`ApiUrls` 是候选列表，`get_ApiUrl` 取当前项，
`ResetApiUrl` 在切服/失败时重置）。

**C. 网络层（同一张方法名表，行号 135735–135760）**

```
GameSessionManager-CreateSession / get_TIMEOUT / SendRequest / SendRequestApi
HttpGameSession-Init / Send / set_State / WaitForRequest

```
关键顺序证据：**`ServerInfoConnectionGroupData-get_ApiUrl0` 就夹在 `GameSessionManager-CreateSession0` 与
`HttpGameSession-Init0` 之间**（行 135739–135742）——即 `CreateSession → get_ApiUrl → HttpGameSession.Init` 是同一条链。

**D. `GameMain.get_ServerInfo` + `GetDefaultConnectionGroup`** → 说明"启动时先拿默认连接组，再用 ServerInfo 覆盖"。

### 3.2 唯一的游戏 API URL 字面量（实测）

```
global-metadata.dat @ 0x000c172b, XOR key = 0xB5
明文：["http://test-ba.yostar.net:5210/api/state","http://test-ba.yostar.net:5210/api/state","http://test-ba.yostar.net:5210/api/state"]
```

- 是 **JSON 数组字符串**（带 `["` 和 `","`），不是 C# `new[]{...}` 的 IL 常量 → 说明默认连接组是**反序列化一段内嵌 JSON**得到的。
- 注意它是 **`http://`**，不是 https（对 Q3 很重要）。
- `test-ba.yostar.net:5210` 是测试环境；生产值不在文件里。

### 3.3 负结果（"找不到明文"的量化）

| 搜索方式 | 范围 | `bluearchive-cn` | `state-api` | `gsqc-api` |
|---|---|---|---|---|
| ASCII 明文 | metadata + libil2cpp | 0 | 0 | 0 |
| UTF-16LE | metadata + libil2cpp | 0 | 0 | 0 |
| **单字节 XOR（全 256 key × 全位置）** | metadata | 0 | 0（仅 `test-ba` 命中） | 0 |
| **周期 ≤8 XOR keystream** | metadata | **0** | 0（命中均为 `test-ba` 的片段） | 0 |
| 同上 | libil2cpp.bin | **0** | 0 | 0 |

→ **生产 state 域名不是静态字面量**，这条已被四种方法独立证伪（`md11.py`、`md14.py`）。

### 3.4 加密层证据：`CryptAES`（Rijndael-256）

名字堆里 `CryptAES`（`0x259ba6`）紧邻：

```
generateKeyString / byteSrc / encrypt / decrypt / toEncryptData
EncryptRJ256Api / sEncryptedString / DecryptRJ256Api
FBENCRYPT_BLOCK_SIZE / cRandom / IVString
CryptAESOrigin: plainText / EncryptStringToBytes_Aes / Encrypt
```

并且 `MX-Core-Services-CryptAES-DecryptRJ256Api0` / `-decrypt0`（行 135753–135754）**就排在 HttpGameSession/HttpGameMessage
方法之后**。两种解释：
- (i) **报文加解密**（更像）：`generateKeyString` / `cRandom` / `IVString` 是会话级随机材料，典型用于请求/响应体加密；
- (ii) **配置/URL 解密**：`sEncryptedString` / `toEncryptData` 也可能是内嵌密文，启动时解出连接组。

无论是哪一种，都说明**客户端存在"运行时才出现的字符串"**，这解释了为什么全文件找不到 `state-api`。
与 `ba-protocol-full.md:141`「国服 gateway endpoint 由 `/api/state` 下发，不是硬编码」一致。
（**证据不足**：未取得密文/密钥对，无法本轮直接解出 URL；也无法证明 CryptAES 参与 URL 构造。）

### 3.4b 三种可能的"URL 来源模型"（按证据强度排序）

| 模型 | 支持证据 | 反证/缺口 | 强度 |
|---|---|---|---|
| **M1. 运行时解密/拼接**（CryptAES 或等价物） | 全文件 0 命中；`CryptAES` 就在网络层旁边 | 未找到密文/密钥 | **高** |
| **M2. 序列化在 Unity 资源里**（boot 场景 / ScriptableObject 的默认连接组） | 磁盘 metadata 里只有 test 环境的 JSON 数组；生产值缺失 | 你们的 assets 扫描 0 命中（但需确认覆盖了 level0/sharedassets/设备侧 11 GB 资源） | 中 |
| **M3. 来自上一次 state 响应的 Hosts 缓存** | `Hosts` 是 state 的写穿缓存（你已实测）；`ServerInfoConnectionGroupData` 字段与 state 响应同构 | 首次安装/清数据后仍能连官方（说明存在内置 bootstrap） | 中 |

> 三者可以同时成立：**内置 bootstrap（M1/M2）→ state 成功 → 写入 Hosts（M3）→ 下次优先用缓存**。
> 对"改客户端让请求走我们"来说，M1/M2 决定能不能静态改；M3 解释了为什么改 Hosts 不生效（它不是入口，只是缓存）。

### 3.5 Q1 明确回答

- **静态能不能定位"构造 state URL 的那段代码"？** → **不能定位到值**；能定位到**唯一的消费出口**
  `ServerInfoConnectionGroupData.get_ApiUrl`（`0x129daf` / 方法表名 `0x3d8df9`），以及 `GameMain.GetDefaultConnectionGroup`（`0x41c579`）。
- **为什么不能**：值不是字面量（§3.3 四重证伪），且可能经 `CryptAES` 运行时产生（§3.4）；再叠加 metadata 表区的 XOR 混淆（§2），
  静态连 methodIndex 都拿不到。
- **可执行的替代**：**不要解 URL**。要么改连接层（connect 重定向 + 真证书），要么运行时在 `get_ApiUrl` 返回处替换。
  这两条都不需要知道 URL 的构造方式。

## 4. Q2：证书校验——静态 vs 运行时

### 4.1 校验链证据（决定 patch 点）

| 证据 | 位置 | 含义 |
|---|---|---|
| `::Scripting::UnityEngine::Networking::CertificateHandlerProxy` | `libunity.so.txt` **L17664** | Unity 原生侧**回调托管 `CertificateHandler`** 的代理类 |
| `ValidateCertificateNative` | `libunity.so.txt` **L17681** | 原生方法名；即 `CertificateHandler.ValidateCertificate` 的 native 入口 |
| `External/Mbedtls/builds/library/ssl_msg.c` 等 107 条 `mbedtls*` | `libunity.so.txt` | TLS 栈是 **mbedtls（UnityTLS）**，在 libunity 里 |
| `javax/net/ssl/X509TrustManager` / `checkServerTrusted` | `libunity.so.txt` **L31594 / L31597** | Unity 还有**走 Android 平台 TrustManager** 的 JNI 路径 |
| `CustomCertificateHandler` + `certificateData` + `ValidateCertificate` + `<>iFixBaseProxy_ValidateCertificate` | metadata `0x1522b3/0x1522cc/0x1522dc/0x1522f2`（XOR 0x66） | 游戏自己**覆写**了 `protected override bool ValidateCertificate(byte[] certificateData)` |

→ **结论：只要游戏给 `UnityWebRequest.certificateHandler` 装了 `CustomCertificateHandler`，托管方法就是最终裁决者**；
把它 patch 成 `return true`（`mov w0,#1; ret` = `0x52800020, 0xD65F03C0`）即可放行任意证书。
但如果走的是 `X509TrustManager` 路径，则系统 CA 安装就足够——两条路互斥，需要一次判别实验（§5）。

补一条决定性事实：`libil2cpp.bin` 里有 **2,653 条 `Type::Method(...)` 形态的方法签名字符串**，但
**`CustomCertificateHandler` / `ValidateCertificate` 在 libil2cpp 里 0 命中**（`libil2cpp.so.txt` 全文检索）。
→ 托管方法的名字与地址**只在 metadata 里**，so 里没有可用的符号锚点。这就是为什么"静态 patch 证书校验"必须先解决 metadata。

### 4.2 三条路线的成本对比

| 路线 | 前置 | 持久性 | 主要风险 | 成本 |
|---|---|---|---|---|
| **A. 系统 CA 安装**（`/apex/com.android.conscrypt/cacerts` tmpfs rw） | 无（root 已有） | 重启前有效（tmpfs），可做开机脚本 | 客户端若不用系统信任库则无效（mbedtls 自带 CA / BestHTTP 自带 CA） | **最低，10 分钟** |
| **B. 静态改 libil2cpp**（patch `ValidateCertificate` 为 `mov w0,#1;ret`） | 必须先拿到 methodPointer（→ §4.4 dump） | **永久**（随 APK/文件替换） | metadata 混淆导致 Il2CppDumper 静态失败；iFix 代理可能覆盖原方法 | 中，1–2 小时 |
| **C. 运行时 text patch**（`/proc/pid/mem` 写 libil2cpp 代码页） | 同样要 methodPointer | **每次启动重打** | **i-cache 不刷新**（见 §4.3）、误写即崩、ACE 若校验内存则命中 | 中高，且最脆 |

### 4.3 运行时 text patch 在 Android 17 + KernelSU 下的可行性

**原理**：`/proc/<pid>/mem` 的写走 `access_remote_vm()` + `FOLL_FORCE`，**绕过 PTE 写权限**，
对 `r-xp` 的私有文件映射也能落盘（COW 到匿名页）；SELinux 侧只要 `u:r:ksu:s0` 对目标域有 `ptrace` 即可
（KernelSU 的 root 域通常是 permissive 或已 allow）。**所以"能不能写进去"基本没问题。**

**命令形态**（把 `ADDR` 换成 `maps 基址 + 文件偏移` 的十进制）：

```sh
pid=$(pidof com.RoamingStar.BlueArchive)
# 1) 找基址（libil2cpp 取 r-xp 00000000 那行，与上轮结论一致）
grep libil2cpp.so /proc/$pid/maps
# 2) 4 字节系数：mov w0,#1 ; ret
printf '\x20\x00\x80\x52\xc0\x03\x5f\xd6' > /data/local/tmp/cert.bin
# 3) 写（bs=1 很慢，建议 bs=4096 对齐页内偏移；这里 8 字节用 dd 直接写）
dd if=/data/local/tmp/cert.bin of=/proc/$pid/mem bs=1 seek=$ADDR count=8 conv=notrunc
# 4) 读回校验
dd if=/proc/$pid/mem bs=1 skip=$ADDR count=8 2>/dev/null | xxd
```

**四个必须知道的坑**：

1. **i-cache 不会刷新**。ARM64 上通过 `/proc/mem` 从另一个进程写代码页，目标进程没有任何 `__builtin___clear_cache`；
   如果该页已被执行过，CPU 可能继续跑旧指令。→ **必须在该方法第一次被调用前打**（`InitSDK` 之前），或接受"打不上"的概率。
2. **写错地址 = 立即 SIGSEGV/SIGILL**，没有回滚（先用 `/proc/mem` 读回 16 字节确认是函数序言再写）。
3. **不能整页读改写**（上轮已实测会导致进程死亡）；只做 8 字节单点写。
4. **Android 17 的 `hidepid`/`ptrace_scope`** 对 root 域不生效，但 `su` 与目标 uid 不同域时仍可能被 SELinux 拒；
   先用 `dd if=/proc/$pid/maps` 验证可读，可读一般就可写。

**判定**：写完后立即让客户端发起一次连接（或重启到登录页），若 TLS 通过 → 生效；若崩溃 → 地址错/时机不对。

### 4.4 运行期 dump 解密后的 metadata（Q2 的真正工作量）

前提（你已确认）：进程里 metadata 已解好、header 正常。工作量分 5 步：

| 步 | 做什么 | 判定 | 失败概率 |
|---|---|---|---|
| 1 | `pid=$(pidof …)`；`grep global-metadata /proc/$pid/maps` 找映射区间（通常是 `r--p`，38,426,024 B） | 能看到一段 `…/global-metadata.dat` 且长度 ≥ 38 MB | 低（若被 free，则转 2b） |
| 2a | 直接按区间 dump：`dd if=/proc/$pid/mem bs=65536 skip=$((ADDR/65536)) count=$((SIZE/65536)) of=/sdcard/md.bin` | 头部 4 字节 = `AF 1B B1 FA`，`version` ∈ {24,27,29,31} | 中（映射权限/SELinux） |
| 2b | 若映射不存在：在 **rw- 匿名段**里搜 magic `AF 1B B1 FA`（`/proc/$pid/mem` 顺序 `dd` + `grep -abo`） | 搜到唯一命中，向前取 0x100 字节当 header | 中 |
| 3 | 用 **Il2CppDumper**（Windows 侧）喂 `libil2cpp.so` + dump 出的 metadata，产 `script.json` / `dump.cs` | `script.json` 里出现 `CustomCertificateHandler$$ValidateCertificate` 且带 `Address` | **最高**（见下） |
| 4 | 地址换算文件偏移：该 so 的 `p_vaddr == p_offset`（全部 LOAD 都满足），`file_off = address` | `xxd -s $off` 看到函数序言 `stp x29,x30,…` | 低 |
| 5 | 离线改文件：`mov w0,#1; ret`；`cp` 覆盖 `/data/app/.../lib/arm64/libil2cpp.so` | 冷启动后自签证书被接受 | 低 |

**第 3 步为什么最可能失败**：
- Il2CppDumper 需要 **未被二次混淆** 的 metadata 表结构；本包磁盘版已确认被 XOR/改写（§2）。运行期 dump 的是
  il2cpp 自己解析后的**明文缓冲**，理论上正常；但如果这个缓冲是**分段解密后分散存放**（il2cpp 为省内存只保留部分段），
  dump 出来的头正常、表却对不上——此时只能改用"**在内存里按 magic 找 header + 按 header 里的 offset 分段取**"。
- 另一个风险：`iFix` 热更框架会给每个方法生成 `<>iFixBaseProxy_*` 代理；**真正被调用的是代理**，
  即使 patch 了原方法也可能不生效 → 需要在 `dump.cs` 里同时确认代理与原始方法谁被 vtable 引用。

### 4.5 最小可行方案（步骤级）

1. **先做零代码判别（10 分钟）**：装 CA + connect 重定向，用真证书跑一次 state 请求（§5.3）。→ 通了就结束。
2. 不通 → 运行期 dump metadata（§4.4 步 1–2），确认 header 正常。
3. Il2CppDumper 出 `script.json`，定位 `CustomCertificateHandler$$ValidateCertificate`（若失败，退回 `iFixBaseProxy` 版本）。
4. 离线把该函数改成 `mov w0,#1; ret`，`cp` 替换 libil2cpp。
5. 冷启动 + 证书实验复测。
6. （可选）同时 patch `CryptAES.DecryptRJ256Api` 的返回值，用于观察解密后的 URL（见 Q1 的运行时验证）。

## 5. Q3：不碰证书的第三条路

### 5.1 证据

| 命题 | 证据 | 强度 |
|---|---|---|
| `ApiUrl` 消费端接受 **http** | 默认连接组字面量是 `http://test-ba.yostar.net:5210/api/state`（`0xc172b`） | **强**（同一个 DTO 的同一个字段） |
| 没有"强制 https"的游戏逻辑 | metadata 里 `StartsWith`（5 处）全在 BCL/TMP 上下文；`UriSchemeHttps`/`HttpsUri` 是 .NET 标准名；无 `IsHttpAllowed`/`Insecure` 类游戏字段 | 中（负证据） |
| 客户端有 `SkipClientCredentials`/`ValidateCertificateRequest` 字样 | 位于 `0x603380` 区（XOR 0x66），上下文是 **BestHTTP** 的 TLS 类，不是游戏逻辑 | 中 |
| Unity 可能用系统 TrustManager | libunity 有 `javax/net/ssl/X509TrustManager`、`checkServerTrusted` | 中 |

### 5.2 三条"不碰证书"的路（按成本排序）

1. **系统 CA**（已有：`/apex/com.android.conscrypt/cacerts` 与 `/system/etc/security/cacerts` 都是 tmpfs rw）
   → 把我们的 CA 以 `<subject_hash>.0` 写进两处（cacerts 目录需同时更新 `cacerts.pem`? 视 Android 版本），**重启生效**。
   若客户端走 mbedtls 自带 CA 或 BestHTTP 自带 CA，此路无效（用 §5.3 判定）。
2. **连接重定向 + 真证书**：`connect` 改到我们服务器，SNI 仍是原域名，服务端出示我们 CA 签的 `*.bluearchive-cn.com` 叶子。
   这条路**不需要改客户端任何字节**（上一轮已验证 libunity 的 connect GOT 可外部写）。
3. **让 URL 变 http**：需要改 `get_ApiUrl` 的返回值或内嵌 JSON（Q1 的出口）；一旦成功，TLS 整层消失，
   连 CA 都不用装。

### 5.3 判定实验（一次就能定三条路的取舍）

```
1) 装 CA（tmpfs 两处 + 重启 zygote/系统）
2) 用 /proc/mem 把 libunity 的 connect GOT 指到我们的服务端（上轮偏移 0x13d95d8）
3) 服务端用真证书（SAN=state-api.bluearchive-cn.com）监听 443
4) 启动游戏，观察：
   - 握手成功 + /api/state 命中 → 走 CA 路线，Q2 不用做
   - 握手失败 alert certificate unknown → 客户端不用系统 CA → 查是 mbedtls 自带还是 CustomCertificateHandler（§4.5）
   - 握手成功但请求 4xx/无 SNI 匹配 → 证书 OK，问题在协议层
```
