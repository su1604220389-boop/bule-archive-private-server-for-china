## 0. 结论摘要（先看这 6 条）

1. **现役 `libil2cpp_patched.bin` 钩错了函数**。它把 libunity 的 `base+0x13d94d0` 改写成 `repl_host`，而
   `0x13d94d0` 是 **`gettimeofday`**；真正的 `getaddrinfo` 在 **`0x13d94d8`**。
   README 里「旧值 0x13d94d8 其实是 basename，正确值是 0x13d94d0」这句话是**错的**，错位一格（−8）。
   证据三重：① `.rela.plt` 符号表；② libunity 自带 PLT 反汇编（`unity_full.asm`，`gettimeofday@plt` 用 `#0x4d0`、
   `getaddrinfo@plt` 用 `#0x4d8`、`basename@plt` 用 `#0x4e0`）；③ 现役机器码里内嵌 `movz #0x94d0 / movk #0x13d`。
2. **现役文件的 connect 钩子根本没装**。`g20.S`（= `patch_hit2.py` 产物）只写了一个槽（作者以为的 getaddrinfo 槽，实为
   `gettimeofday`），`repl_conn` 保留为**死代码**（符号偏移 +0x374，无任何 `str` 引用）。
   这一族脚本在「装不装 connect」上反复横跳：`patch_hc`(11:15) 还带；`patch_dump`/`patch_noop`/`patch_ga`(11:17–11:25) 删了；
   `patch_min`/`patch_min2`(11:13/11:25) 又加回；最后的 `patch_hit`/`patch_hit2`(11:46/11:47) 再次删掉。
   **现役文件属于最后一次「删掉」的版本**——它是「命中探针」，不是「重定向版」。
3. **`libil2cpp` 自己从来不调用 `getaddrinfo`/`connect`**。全段 BL 扫描：`.text+il2cpp+.plt`（0x59b8000–0xf2c2410）
   共 3,465,919 条 BL，其中跳到 `getaddrinfo@plt(0xf2c1000)` = **0 条**、`connect@plt(0xf2c1060)` = **0 条**，
   而其它 65 个 PLT 桩共被调用 116,219 次。
   → 所以「改 libil2cpp 的 PLT/GOT 没反应」不是 `-fno-plt`，而是**这两个导入在本 so 里没有调用点**。
   §4.9 的结论方向对、归因错。
4. **libunity 侧确实在用**：`getaddrinfo@plt` 1 个调用点（0xb84014）、`connect@plt` 3 个（0xc036f8 / 0xcb4720 / 0xcf50c8），
   另有 1 处直接读 connect 的 GOT（0x454788，`-fno-plt` 风格）。改 GOT 能覆盖全部 4 个调用者，这条路成立。
5. **差分极小且干净**：`libil2cpp` 全文只有 **3 处**改动（960 字节）：PH2 的 filesz/memsz 各 +0x1000、
   `DT_INIT` 值 0x10496434→0xf2c2410、0xf2c2410 起 1111 字节桩代码。`libtprt` 只改了 4（或 12）字节，`final` 与 `orig` 完全一致。
6. **当前实验状态**：不是 E38（E38 是纯填充字节翻转、无注入），不是 E63（E63 是 dlopen/dlsym 链，alive=24049 s），
   也不是 E64（E64 是「GOT 改写 + 真指针持久化」，未做稳）。
   现役文件 = **v20「hit」探针**（`patch_hit2.py` 11:47:04 → `g20.o` 11:47:06 → `libil2cpp_patched.bin` 11:47:06），
   = DT_INIT + 直接 `str` 写 libunity GOT + tail-call libil2cpp PLT，无 dlopen/dlsym、无 RW 暂存、无 `/proc/self/mem`、无 connect。
   **11:47 之后没有任何运行证据**（`sdk.log` 止于 11:24:39，`relay.log` 只有 11:27 一条），所以这一版**大概率没上过机**。

## 2. 差分结果表

### 2.1 `libil2cpp.bin` → `libil2cpp_patched.bin`

全文件差异：**148 个区间 / 960 字节**。148 这个数字只是「洞内代码含大量 0x00、逐字节比较把连续代码打碎」的假象，
语义上只有 **3 簇**，且**不涉及 `.plt`、不涉及任何填充字节、不涉及 `.rela.plt`/GOT 初值/节头**：

| # | 文件偏移 | 原值 | 新值 | 大小 | 含义 |
|---|---|---|---|---|---|
| 1 | PH2 项（条目起 `0xb0`；改动落在 `p_filesz` 的 0xd1、`p_memsz` 的 0xd9） | `filesz=0x990a410` / `memsz=0x990a410` | `0x990b410` / `0x990b410` | 2 B | 把 RX LOAD 段（`off=va=0x59b8000`，flags=5）**向后扩 0x1000**。原段末尾正好是 `0xf2c2410`＝洞的起点；不扩这一段，洞里写的字节**不会被加载**（因为 `p_filesz` 结束了，那段属于文件空洞）。扩完 end_va=0xf2c3410 < 下一段 `0xf2c4000`，不重叠，`p_align=0x4000` 也仍然自洽。 |
| 2 | `0x0f2c2410 – 0x0f2c2866` | 全 0（文件空洞，落在 `.plt` 之后的同页尾部） | 1111 字节 AArch64 代码 + 2 个字符串（`example.com`、`/data/data/com.RoamingStar.BlueArchive/files/bainj.txt`） | 1111 B | 注入桩本体。**与 `cave/g20.o` 的 `.text` 1112 字节前缀完全一致（FULL MATCH）**，即现役文件就是 `patch_hit2.py` 生成的那一版。 |
| 3 | `0x0fa2fc48`（`.dynamic` 里 `DT_INIT` 项，值在 +8 = `0xfa2fc50`） | `0x10496434` | `0x0f2c2410` | 8 B | 把库的 `DT_INIT` 指向代码洞。原值 `0x10496434` 落在 PH10（`va=0x10494000, off=0x1024c000`，RX），反汇编是一段正常的 init（`stp x29,x30; bl …; adrp/ldr/br x2`）。 |

补充事实（决定成败的几条）：

- `DT_FLAGS = 0x8 (BIND_NOW)`，`FLAGS_1 = 0x1 (NOW)`，`PT_GNU_RELRO = [0xf2c4000, 0xfbb4000)`。
  → **`.got.plt`（0xfbaf660 起）整段落在 RELRO 里**。BIND_NOW 意味着运行时槽位里是**已经解析好的 libc 地址**，
  不是文件里的 `0xf2c0010`。作者 §4.10「libil2cpp 的 GA/CO 槽值 = 0xf2c0010（仍指 PLT0）→ 从未被调用」这条，
  **值 0xf2c0010 其实是文件内容**（RELRO 页/文件 r--p 映射）；我的 BL 统计另证「确实没调用点」，结论巧合正确、证据链是错的。
- 洞在 `0xf2c2410`，正好是 `.plt` 的结尾（`0xf2c0010 + 0x2400`）；同页前 0xbf0 字节还是 PLT 代码。
  扩段后 `0xf2c3000–0xf2c4000` 那 4 KB 仍是空洞，不影响。
- 没有改 `.rela.plt`、没有改任何 GOT 初值、没有改节头（`.plt` 的 size 仍是 0x2400）。**这是一次最小侵入式改法，ELF 层面是合法的。**

#### 2.1.1 洞内代码语义表（偏移相对 `0xf2c2410`，符号取自 `g20.o`）

| 偏移 | 符号 | 做什么 |
|---|---|---|
| +0x000 | `entry` | 保存 x19–x22/x29/x30（`stp …, [sp,#-0xa0]!`） |
| +0x00c–0x084 | — | 打点 `I`：`open(bainj.txt, 0x441)`→`write(1B)`→`close`，全部经 libil2cpp 自己的 PLT 桩（P_OPEN/P_WRITE/P_CLOSE） |
| +0x088 | — | `dl_iterate_phdr(cb, &slot)`（P_ITER = 0xf2c0030，PLT 第 1 项） |
| +0x0ac | — | `x21 = slot`；`cbz x21, Lout`（找不到 libunity 就静默跳过） |
| +0x0b0–0x12c | — | 打点 `B` |
| +0x130–0x14a | — | `x9 = x21 + 0x13d94d0`；`adr x10, repl_host`；**`str x10,[x9]`** ← **就是这条错了**（gettimeofday 槽） |
| +0x14c–0x1c4 | — | 打点 `D` |
| +0x1c8 | `Lout/LskD` | 恢复寄存器，`adr x9,blob0; sub x9,CAVE; add x9,0x10496434; br x9` → 跳回原 `DT_INIT` |
| +0x204 | `cb` | `dl_iterate_phdr` 回调：在 `dlpi_fname` 里线性找 `"libunity"`（8 字节逐字节比较 `0x6c 0x69 0x62 0x75 0x6e 0x69 0x74 0x79`），命中则把 `dlpi_addr` 写入 `*x2` |
| +0x2a0 | `repl_host` | 如果 `x0 >= 0x1000` 且前两字节是 `'g','s'` → `x0 = "example.com"`；打点 `R`；然后 tail-branch 到 `getaddrinfo@plt`（0xf2c1000）。**注意：只认 `gs` 前缀**，`state-api.*` 不命中 |
| +0x374 | `repl_conn` | 改写 AF_INET/AF_INET6 的 443 目标地址 → **死代码**，没有任何指令引用它（现役版已删 connect 安装） |
| +0x408/0x419/0x450–0x457 | `host`/`logpath`/`I B D R` | 字符串常量 |

**为什么 `repl_*` 敢 tail-call libil2cpp 的 PLT 桩**：被 hook 的是 **libunity** 的槽（0x13d94d0/0x13d95d8），
而 tail-call 的目标是 **libil2cpp** 的桩（0xf2c1000/0xf2c1060），它读的是 **libil2cpp 自己**的槽（0xfbafe60/0xfbafe90）。
两个槽不同 → 不会自递归。这是 v20 相对 v13（dlopen/dlsym）的实质进步。

### 2.2 `libtprt_orig.so` → `libtprt_patched*.so`

| 文件 | 差异区间 | 字节数 | 具体改动 | 含义 |
|---|---|---|---|---|
| `libtprt_patched.so` | 0x120fc4, 0x120fc7；0x1210bc, 0x1210bf | 4 | `b.eq +0x10`（0x54000080）→ `b +0x10`（0x14000004）×2 | 把两处「校验失败→自杀」的条件跳转改成**无条件跳过**。校验形态：`bl 0x11d028`（往栈上写 0x80 字节）→ `cmp w0, #0xc4c5f3f8` → 不等则 `bl 0x15e850` + `mov w1,#9` + `bl 0x15ec60`（形态上是 `kill(pid, 9)` 一类的自毁）。 |
| `libtprt_patched2.so` | 上面 4 处 + 0x121010–13、0x121108–10b | 12 | `csel x0, x19, xzr, eq`（0x9a9f0260）→ `mov x0, x19`（0xaa1303e0）×2 | 另把两处「按返回值选 x19 或 NULL」的 `csel` 改成**无条件返回 x19**，即强制「成功」。上下文是 `mov w1,#0x1000; mov w2,#5; bl 0x15ec70`（mmap 形态）后 `cmp w0,#0; csel`。 |
| `libtprt_final.so` | 0 | 0 | 与 `orig` **逐字节相同**（sha256 都是 `47064882…`） | 明确回滚件。 |

**为什么放弃**（证据链）：

1. `libtprt` 是 ACE/TP 的核心（导出 `JNI_OnLoad`、`g_tprt_pfn_array`、`g_tprt_ori_array`、`tp_syscall_imp`），
   在 `attachBaseContextShell` 阶段最先加载，**早于 Unity 和 libil2cpp**；`audit/ba-airisdk.md:185` 实测「改任意字节 → kill(SIGBUS)」。
2. 脚本改的是「ACE 自己的校验点」，但 ACE 的 hash pin 不在这两个点上——改校验点不解决「文件被改」这个事实。
3. `:GP6/:GP7` 是独立进程（`ba-pitfalls.md` §4.3 的调用栈可证），一个进程里的 patch 管不到另一个进程的复核。
4. 产物结局：`patched`/`patched2` 都没被任何后续脚本引用，`final` 是原样回滚 → **实证放弃**。

> 顺带一条：`cf2c2410.S` / `cf2c2600.S` 这两个手写桩的布局（`.globl s1` @0xf2c2410、`.globl s2` @0xf2c2600）明显是为
> 「把 `.rela.plt` 的 addend 指向固定地址」那套方案准备的（见 §3 的 v14），但 `patch_reloc2.py` 里实际用的是编译产物偏移，没有用这两个 .S。

### 2.3 `libmain` 三件套

| 文件 | 大小 | 与原厂差异 | 含义 |
|---|---|---|---|
| `lib/arm64-v8a/libmain.orig.so` | 18,608 | —（基线；sha256 `e2a12641…`） | 原厂 |
| `lib/arm64-v8a/libmain.so` | 66,569 | 结构级：多一个 `LOAD(off=0x10000, va=0x10000, filesz=0x408)`、phnum 8→9；`DT_NEEDED` 增加 **`libgm.so`** | **重编版**：让 loader 额外拉我们的 `lib/lib/arm64-v8a/libgm.so`（该 so 的字符串是 `gm_ctor`/`gm_ping`/`gm_loaded.txt`，是个打点/探针 so）。属于「加新 so」路线。 |
| `libmain_patched.so` | 18,608 | 3 处 8 字节：`0x59d` 起 `"log.so"`→`"dg.so"`（即 `.dynstr` 里 `liblog.so`→`libdg.so`）；`0x3f38` 处 1 字节 `00→01`；`0x3f40` 处 1 字节 `00→72` | **依赖注入版**：把 `.dynamic` 末尾的 `DT_NULL` 槽改写成 `DT_NEEDED`（tag=1、val=0x72→`.dynstr` 里的 `libdg.so`），于是 NEEDED 变成 `libdg, libm, libdl, libc, libdg`（重复一次，无害但丑陋）。意图是让 loader 先加载 `libdg.so`（我们的 hook 库）。 |
| `fix/lib/arm64-v8a/libmain.so` | 18,608 | **0 字节差异**（与原厂完全一致） | 恢复件：证明这条路已回滚。 |

**结论**：libmain 的两条路线（重编 + NEEDED 注入）都被 ACE 掐死。证据：`ba-pitfalls.md` §一.2
「绝对不要往 APK 里加新 .so，也不要改 libmain.so 的 DT_NEEDED → 无日志闪退（ACE 直接杀进程）」；
`ba-gateway-host.md` §5.2b「`libairisgcore.so` 整库替换 → SIGBUS」。`fix/` 目录本身就是回滚物证。

## 6. 四个核心问题

### Q1. 从「文件被替换」到「钩子跑起来」，最小可行步骤是什么？脚本里哪一步缺了/错了？

**最小可行步骤（按顺序，缺一不可）**

1. **准备好 patched 文件**（在当前 Windows 侧无法重新编译，因为本机没有 aarch64 clang；只能直接用现成的
   `libil2cpp_patched.bin`，或者按 §8 第 1 步重建）。
2. **保住备份**：设备上 `/data/local/tmp/orig_inst.so`（270,927,056 B）已有（§4.9 记录），先校验大小/sha。
3. **原位覆盖**（不要 `mv`，不要动 APK，不要改 NEEDED）：
   ```sh
   su -c 'cp /data/local/tmp/libil2cpp_patched.bin /data/app/~~*/com.RoamingStar.BlueArchive-*/lib/arm64/libil2cpp.so'
   ```
   `cp` 是截断写同一 inode → SELinux context / owner 不变；`mv` 会换 inode，context 可能变。
4. **清 ACE 记账**（可选，但建议）：删 `files/{ace_shell_di.dat, shell_cache, ano_tmp}`（§4.2），否则历史判定可能连坐。
5. **强停 → 冷启动**（手动点图标，别用 monkey，避免小窗被杀，§4.4b）。
6. **判定钩子跑起来**：`/data/data/com.RoamingStar.BlueArchive/files/bainj.txt` 出现 `I`（DT_INIT 进入）
   → `B`（拿到 libunity 基址）→ `D`（GOT 写完）。现役版本写的是**单字节**、无换行，且 `open` 带 `O_APPEND`（flags=0x441），
   所以**首次运行**内容应是 `IBD`（若主机名命中还会多一个 `R`），之后每次启动会继续往后追加。

**脚本里「错」的一步**

- `patch_hit2.py`/`patch_min2.py` 的 `U_GA = 0x13d94d0` → **这是 `gettimeofday`**。
  正确值是 `0x13d94d8`。现役洞里的机器码是 `movz x9,#0x94d0; movk x9,#0x13d`，实锤。
- 后果：`gettimeofday` 被替换成 `repl_host`，而 `repl_host` 做的是「按 getaddrinfo 语义改 x0 再 tail-call getaddrinfo」。
  libunity 里 `gettimeofday@plt` 有 1 个调用点（0xc0b67c），一旦走到：
  `gettimeofday(tv, tz)` → 变成 `getaddrinfo(tv, tz, 垃圾x2, 垃圾x3)` → 返回 EAI_*，**且不填 timeval**。
  时间基准被破坏 → TLS 超时 / 心跳异常。**这正好解释「E64 从被拒绝变成超时」**（推断，但与现象高度吻合）。
- 另外 `patch_hc.py` 把 `0xEC871A78` 改成 `0x87EC/0x781A` 也是错的：前者 LE 字节是 `78 1A 87 EC` = <SERVER_IP>（正确），
  后者是 `EC 87 1A 78` = 236.135.26.120（反了）。幸好这版没进现役文件。

**脚本里「缺」的步骤**

| 缺什么 | 后果 | 补法 |
|---|---|---|
| 安装后的**回读校验** | 不知道写没写进去（现役只有 `D` 打点） | v13 `patch_direct` / v16 有；v20 删了。应恢复：写完 `ldr` 回来和 `repl_host` 地址比对，打 `1`/`0` |
| **connect 安装** | 现役根本没有 connect 钩子 | 加 `str repl_conn, [base+0x13d95d8]` |
| 主机名过滤含 `state` | 只认 `gs` 前缀，`state-api.*` 不命中 | 改成「`gs` 或 `sta`」双前缀，或干脆无条件（`any` 版） |
| 写前确认目标页可写 | 若 RELRO 生效会直接 SIGSEGV | 见 §8 第 3 步（先 maps 判定） |
| 幂等/来源断言 | 对已 patched 的 SRC 再跑一次会二次注入 | 断言 `DT_INIT != CAVE`、洞内全 0 |
| Windows 侧可复现 | 脚本硬编码 `/root/bapatch`，依赖设备上的 clang | 见 §8 第 1 步 |

**一句话**：链路本身（PT_LOAD 扩 0x1000 → 洞内写桩 → `DT_INIT` 改指向 → 桩里 tail-call libil2cpp PLT）
在 ELF 层面是**正确且已跑通**的（`I/B/D` 出现过）；**唯一错的是 libunity 的槽位常量**，缺的是 connect 那一步。

### Q2. 做一个**持久化**的 connect 改写（目标 → `127.0.0.1:PORT`，AF_INET + AF_INET6），现在差什么？

**先明确「持久化」的两层含义**：① 文件补丁本身跨启动持久（已具备）；② 钩子在**进程生命周期内**
对所有线程、所有调用点稳定生效，且能安全拿到「真函数」继续调用（**这一层现在有硬缺口**）。

**缺口清单（按重要性排序）**

1. **槽位常量**：`connect = 0x13d95d8`（已三重验证）；`getaddrinfo = 0x13d94d8`（不是 0x13d94d0）。
2. **「真函数指针」必须与「被 hook 的槽」分离**。三种做法：
   - (a) **tail-call libil2cpp 的 PLT 桩**（现役 v20 的做法）：`br 0xf2c1060`。
     它读的是 libil2cpp 自己的槽 `0xfbafe90`，**与被 hook 的 libunity 槽不同** → 不会自递归。**推荐**，代价最小。
   - (b) DT_INIT 里先 `ldr x9,[base+0x13d95d8]` 把原值存到可写内存，再覆盖。
     注意：`libil2cpp` 的 `.data` 段 `memsz(0x8ddd58) > filesz(0x6974f8)`，尾部有 **约 2.28 MiB 的零填充 BSS**
     （`0x1024b4f8 – 0x10491d58`），是天然的可写暂存区。
     但「`base+0x10300000` 没映射」这条作者结论**可疑**：`0x10300000 < 0x10491d58`，静态上是在 PH4 的 memsz 内的，应当已映射。
     建议先复核，不要沿用「不可写」的判断。
   - (c) 改 `.rela.plt` 为 RELATIVE（v14 思路，见下）。
3. **`127.0.0.1:PORT` 的字节布局**（现在只改 IP、不改端口、且 IP 是 <SERVER_IP>）：
   - AF_INET（`sa_family=2`；buf 布局 `family[2] port[2] addr[4]`，`sin_port/sin_addr` 都是网络序）：
     ```asm
     ; 端口：写 [x1+2]，w11 = htons(PORT) = ((PORT&0xFF)<<8)|(PORT>>8)
     movz w11, #<PORT 的 htons 结果>      ; 例：PORT=8080 -> 0x1F90
     strh w11, [x1, #2]
     ; 地址：写 [x1+4]，0x0100007F 的 LE 字节是 7F 00 00 01 = 127.0.0.1
     movz w11, #0x007F
     movk w11, #0x0100, lsl #16
     str  w11, [x1, #4]
     ```
   - AF_INET6（`sin6_addr` 在 +8，共 16 字节）：`::ffff:127.0.0.1`
     → `[x1+8]` 8 字节清零（`str xzr,[x1,#8]`），`[x1+16]` 写 8 字节
     `0x0100007F_FFFF0000`（LE 展开为 `00 00 FF FF 7F 00 00 01`，正好是 `::ffff:127.0.0.1`）：
     ```asm
     str  xzr, [x1, #8]
     movz x11, #0x0000
     movk x11, #0xFFFF, lsl #16
     movk x11, #0x007F, lsl #32
     movk x11, #0x0100, lsl #48
     str  x11, [x1, #16]
     ```
     核对：现役 `g20.S` 写的是 `0xEC871A78_FFFF0000`（LE `00 00 FF FF 78 1A 87 EC` = `::ffff:<SERVER_IP>`，
     这个 **IPv6 编码本身是对的**），换成本机只要把高 32 位从 `0xEC871A78` 换成 `0x0100007F`、并补上 `[x1+2]` 的端口写即可。
   - **端口**：现役完全没改（443 原样）。要改成 `PORT` 必须写 `[x1+2]`（2 字节，网络序）。
4. **只对 443 生效的守卫要保留**（否则会把 DNS 的 `connect` 到 53、或者其它服务也改掉）。
   现役判定是 `[x1+2]==0x01 && [x1+3]==0xBB`（443 的 0x01BB）——可以，但建议同时打印命中日志。
5. **线程安全**：GOT 写入是 8 字节对齐单次 `str`，ARM64 上原子；DT_INIT 阶段单线程。`repl_conn` 在任意线程跑，
   **不能调用非线程安全函数**（现役 `repl_conn` 纯寄存器操作，OK；如果要打点就必须加锁或用 `write` 系统调用）。
6. **LR/x29/x30**：`repl_conn` 是 tail-branch（`br`），LR 不动，无需保存；
   若改成 `blr`/`bl` 调用（例如要打点），必须先 `stp x29,x30,[sp,#-N]!` 并在返回前恢复。
   现役 `repl_host` 保存了 x29/x30 却没用（冗余，无害）。
7. **TLS 缺口（最容易被忽略）**：把 `connect` 改到 `127.0.0.1:PORT` 后，客户端仍然用**原域名做 SNI/证书校验**。
   除非 ① 你的服务端能出示该域名的受信证书（不可能），或 ② 证书校验被绕过（Q3），或 ③ 客户端走明文 HTTP，
   否则握手必失败。**这不是注入层能解决的，是 Q2 的真正终点。**
8. **可观测性**：现在只有 `I/B/D/R` 四个单字节。建议每步写一行（含 `base`、槽位地址、真指针、命中次数），
   否则「超时」这种软失败无法定位。
9. **持久化的运维面**：游戏更新/重装会换 `lib/arm64` 路径与 UID（§4.3b），补丁要重做；ACE 记账要清。

**更好的第三条路（建议评估）**：修 v14 的 `.rela.plt` → RELATIVE 方案。
它是**唯一不需要运行时可写页**的安装方式（loader 在重定位阶段替我们写 GOT），且天然持久。
失败证据是 SIGABRT，但脚本本身结构是对的（`r_info=(0<<32)|1027`、`addend=CAVE+off`）。
两个待查点：① bionic 是否允许 `.rela.plt` 里出现非 JUMP_SLOT（可先在一台可控设备上改一个无关符号做 A/B）；
② 是否被 ACE 的完整性检查 abort（抓 logcat 里 `linker`/`DEBUG` 行即可分辨）。

### Q3. 能不能在 libil2cpp 里定位并 patch 掉证书校验（`CertificateHandler.ValidateCertificate` 或等价物）？

**能，但不是「静态一把梭」，要分两步。**

**(a) 先确认目标存在——证据充分。**

- `audit/ba-apk/out/metadata-strings.txt` 里明确有：
  ```
  CertificateHandler
  get_CertificateHandler / set_CertificateHandler
  <CertificateHandler>k__BackingField
  CustomCertificateHandler-ValidateCertificate0      ← 关键
  ```
  `CustomCertificateHandler-ValidateCertificate0` 是**方法名**（这套元数据的方法名被改写成 `类型-方法名N` 形式），
  说明游戏自己定义了 `CustomCertificateHandler` 并**覆写**了 `ValidateCertificate`。
- `libil2cpp.bin` 里还有 `UnityEngine.Networking.CertificateHandler::Create(...)` / `::Release()` 两个 icall 名
  （`audit/ba-apk/out/strings/libil2cpp.so.txt`），说明走的是 Unity 的 `UnityWebRequest` + CertificateHandler 路径。
- 另有 BestHTTP/BouncyCastle 的整套 `X509*` 符号（metadata 字符串），所以**还可能存在第二条 TLS 栈**，
  `ValidateCertificate` 未必是唯一入口——需要先确认调用链（见 (c)）。

**(b) 静态定位：目前**做不到**，卡在两处硬事实。**

1. `libil2cpp.bin` 的 `.dynsym` 共 2660 项（2352 defined / 308 undef），**defined 里 `il2cpp_*` 一个都没有**。
   → 没有 `il2cpp_class_from_name` / `il2cpp_class_get_method_from_name` / `il2cpp_domain_get` 这类公开 API，
   不能「按名字」在运行期解析。
2. `global-metadata.dat`（`work/ba/audit/ba-work/x/assets/bin/Data/Managed/Metadata/global-metadata.dat`，38,426,024 B）
   **头部不是合法 IL2CPP 元数据**：
   - 文件里**找不到** `0xAF 0x1B 0xB1 0xFA`（sanity magic），首 16 字节是 `94 43 72 12 18 4b 9e ec 66 67 66 66 a6 62 65 66`；
   - 按标准头解析出来的 `version = -325170408`（无意义）、`methodsOffset=0x66ed4a72`（远超文件长）；
   - 但**字符串堆是明文**：`CustomCertificateHandler-ValidateCertificate0` @ `0x41b7ef`、`mscorlib` @ `0x62a879`、
     `UnityEngine.Networking` @ `0x6ed1d4`；熵分布 4.7–6.8（不是全加密）。
   → 结论：**头部（可能还有若干段）被加密，运行期必然被解密**。静态拿不到 `methods` 表 → 拿不到 methodIndex。

因此「静态三步」中的第 2 步（methodIndex）就断了，后面的 `Il2CppCodeRegistration.methodPointers[methodIndex]` 无从谈起。

3. **方法指针表本身可以「粗定位」，但没有意义**：`.data.rel.ro`（`0xf2c4000–0xfa2fa78`）里可以扫出连续的 8 字节数组，
   元素全部落在 `0x59b8000–0xf2c2410`（代码区）——那就是 `methodPointers` 一类表。
   但没有 metadata 的 `methodIndex`，你**无法知道哪一项是 `ValidateCertificate`**，只能靠「函数体是不是 `mov w0,#1; ret`」去猜，
   而返回常量的函数成百上千。→ 所以必须先拿到 metadata，表才有用。

**(c) 三条可行路径（按性价比排序）**

1. **运行期 dump 解密后的 metadata，再静态 patch 文件**（推荐）：
   - 时机：il2cpp 初始化完成之后（`DT_INIT` 之后、第一次联网之前）。
   - 手段：root 从 `/proc/pid/mem` 按 maps 里的 `global-metadata.dat` 映射整段 dump（38 MB，一次搞定），
     或 hook `il2cpp::vm::MetadataCache::Load`（需要先找到它，难度更高）。
   - 拿到明文后按标准头解析 → 找到 `CustomCertificateHandler` 的 `ValidateCertificate` → 得 `methodIndex`；
     同一份 dump 里还能直接读到 **`Il2CppCodeRegistration`/`Il2CppCodeGenModule`**（在 `.data.rel.ro`），
     `methodPointers[methodIndex]` 就是函数地址；减去 libil2cpp 基址 → **文件偏移**。
   - 然后**静态改文件**（libil2cpp 可改，E38 已验证不受 ACE hash pin 限制）：
     把函数入口 4+4 字节改成 `mov w0,#1`（`0x52800020`）+ `ret`（`0xD65F03C0`），
     或者把 `methodPointers` 表里那一项改成我们自己的 trampoline（表在 RELRO，需要 `/proc/mem` 或直接改文件）。
2. **不定位函数，直接让 TLS 不校验**：如果游戏用的是 Unity 的 `CertificateHandler`，可以在 Java 侧
   `UnityPlayer`/`UnityWebRequest` 上换 handler（需要 Java hook，且本作 Xposed API 是混淆替身，`ba-pitfalls.md` §4.6.7 已证不可用）——**不推荐**。
3. **先验证「证书校验到底挡不挡路」再决定要不要做**：把 connect 改到 `127.0.0.1:PORT` 起一个自签 TLS 服务端，
   看客户端是「握手失败（证书）」还是「HTTP 层被拒」。如果游戏网关其实允许明文 HTTP（README 说后续走明文），
   那 Q3 可能根本不需要做。**这是最省事的判定实验。**

**顺带纠正一个可能的误解**：`libil2cpp` 里 `CertificateHandler::Create/Release` 这两个字符串是 **icall 名**，
不是 `ValidateCertificate` 的地址线索；`ValidateCertificate` 是**托管方法**，它只存在于 metadata 的 method 表里，
静态 so 里不会出现它的名字。所以「在 libil2cpp.bin 里 grep 到 ValidateCertificate」这条路是走不通的（实测 grep 无命中）。

### Q4. 不改 libunity、不改 libil2cpp，只靠 root 从 `/proc/pid/mem` 改 libunity 的 connect GOT——工程可靠性如何？

**技术上成立，作者 §4.10 已实测「写入后读回一致」。作为研究手段可靠度高；作为交付方案可靠性中等。**

**成立的理由（本次静态证据支持）**

- libunity 的 `connect` 确实被使用：`connect@plt` 3 个调用点 + 1 处直接读 GOT（0x454788）。
  改 GOT 能覆盖全部 4 个调用者（直接读 GOT 的那种也覆盖）。
- `/proc/pid/mem` 的写走 `access_remote_vm`/`FOLL_FORCE`，**绕过 PTE 写权限**：
  即使该页因 `PT_GNU_RELRO` 被 mprotect 成只读，也能写进去（这点比 in-process `str` 强）。
  而 **in-process `str` 是否可行，取决于本机到底有没有对该库执行 RELRO**——见下面「必须实测的一件事」。

**必须实测的一件事（现在证据自相矛盾）**

- 静态事实：libunity `DT_FLAGS=BIND_NOW`、`FLAGS_1=NOW`、`PT_GNU_RELRO=[0x1390f48, 0x13dc000)`，
  而 `.got`（`0x13d94d0/0x13d95d8`）**正好在 RELRO 区间内** → 按 bionic 正常行为，装载后该页应为 **`r--p`**。
- 作者记录：「libunity 的 GOT 页是 rw-p，可以直接 str 写」。
- 两者矛盾。判定方法（一条命令）：
  ```sh
  grep libunity.so /proc/$PID/maps
  # 看 0x1390f48 所在那一行的权限：r--p = RELRO 生效（in-process str 必崩）；rw-p = 未生效
  ```
  若确认 `r--p`，则 v20 的 `str` 会在 `DT_INIT` 里直接 SIGSEGV，**必须改走 `/proc/pid/mem` 或 `.rela.plt` RELATIVE**。

**可靠性评估（作为方案）**

| 维度 | 评价 |
|---|---|
| 成功率 | 高（流程简单：找基址 → 写 8 字节 → 读回校验） |
| 前置条件 | **必须 root**；SELinux 需 permissive 或允许 ptrace 同域；Android 14+ 对跨进程写更严 |
| 时序窗口 | 宽裕：libunity 在启动早期加载，而网关 connect 发生在登录之后（秒级到十秒级），有足够时间打补丁 |
| 持久性 | **只在本次进程内有效**；每次启动都要重打 → 需要常驻守护（Magisk service / 轮询脚本） |
| 版本脆弱性 | 高：偏移 `0x13d95d8` 随版本变；必须每次重新解析 `.rela.plt`（不要硬编码） |
| 风险 | 写错地址 → 进程立即死；整页「读-改-写」被作者实测证明会「直接导致进程死亡」（他归因于懒绑定槽被回滚；在 BIND_NOW 下更可能是 RELRO/并发写问题）→ **只做单 8 字节写** |
| 可回滚 | 好：不改任何文件，重启即恢复 |
| 可观测 | 好：外部随时可以读回验证 |
| ACE 影响 | 低（文件没变；但 ACE 若校验内存中的 GOT 就会命中——目前无证据表明它校验 GOT） |

**结论**：**先做研究/验证手段**（改完立刻能确认「钩子是否真的生效、connect 是否被改到」），
确认整条链路（含 TLS）通了以后，再决定要不要落成「文件补丁 + DT_INIT」的持久方案。
如果最终交付必须「无 root + 单 APK」，那这条路只能当调试器用。

## 8. 若要继续这条线：按顺序要做的 N 步（每步给判定）

> 原则：**先把「洞 + 触发点」这条已验证的资产固定住，只动槽位常量和 repl 逻辑；每一步都有可判定的成功标志。**

**第 1 步｜把构建搬到可复现的环境**
写一个纯 Python 的「字节级」补丁脚本（不依赖 clang）：直接读 `cave/g20.o` 的 `.text`（或把洞内 1111 字节当常量 blob），
只做 `PH2 += 0x1000`、`DT_INIT = 0xf2c2410`、写洞。脚本要断言 SRC 的 `DT_INIT != CAVE` 且洞区全 0。
**判定**：对原厂 `libil2cpp.bin` 跑一遍，输出只出现预期的 3 簇改动（PH2 / DT_INIT / 洞），
且 `readelf -l` 显示 PH2 `filesz=0x990b410`、`readelf -d` 显示 `INIT=0xf2c2410`。

**第 2 步｜改对槽位常量**
把 `U_GA` 改成 `0x13d94d8`（`movz #0x94d8 / movk #0x13d`）。
**判定**：反汇编洞内 +0x130 处是 `movz x9,#0x94d8; movk x9,#0x13d`；
把 `grep -n "0x94d" g20.S` 的输出与 `.rela.plt` 对照一致。

**第 3 步｜先判定「能不能 in-process 写」**
上机后 `grep libunity.so /proc/$PID/maps`，看 RELRO 页权限。
- 若 `rw-p` → 继续 v20 的 `str` 路线；
- 若 `r--p` → **改用 `/proc/pid/mem`（Q4）或 `.rela.plt` RELATIVE（v14 修正版）**。
**判定**：能明确写进 `bainj.txt` 一行「RELRO=ro/rw」。

**第 4 步｜加回读校验**
写完 GOT 后 `ldr x11,[x9]`，与 `adr x10,repl_host` 比较，相等打 `1`、不等打 `0`。
**判定**：`bainj.txt` 出现 `...1`；故意写错槽位时应出现 `0`（自测）。

**第 5 步｜加回 connect 钩子（先只改 IP，不改端口）**
`str repl_conn, [base+0x13d95d8]`；`repl_conn` 保留 AF_INET/AF_INET6 判断，先写 `127.0.0.1`（`0x0100007F`）。
**判定**：用 `ss -tnp`/服务端日志看到有到 127.0.0.1 的连接尝试；`bainj.txt` 出现 `C`（加连线日志）。

**第 6 步｜改端口到 `PORT`**
AF_INET：`strh` 写 `[x1+2]`；AF_INET6：`[x1+2]` 同样处理。守卫仍只对原 443 生效。
**判定**：本地 `nc -l PORT` 收到连接；客户端 `getpeername` 显示 `127.0.0.1:PORT`。

**第 7 步｜验证「真函数」没被破坏**
给 `repl_conn` 加计数/日志（写到 `bainj.txt`，用 `open(O_APPEND)`），确认每次 connect 只走一次 repl、
不会无限递归（若误 tail-call 到被 hook 的同一个槽会死循环）。
**判定**：连续 100 次 connect，日志条数 = 100，进程不卡死。

**第 8 步｜TLS 判定实验（决定 Q3 要不要做）**
本地起 TLS 服务端（用 `c.pem/k.pem`），看客户端是「握手失败」还是「HTTP 层被拒」。
**判定**：抓到 `alert certificate unknown` → 必须做 Q3；能完成握手 → 直接进第 10 步。

**第 9 步｜（若第 8 步失败）证书校验绕过**
按 Q3(c)1：dump 解密后的 metadata → 找 `CustomCertificateHandler.ValidateCertificate` → 静态改文件为
`mov w0,#1; ret`。
**判定**：改完后同一实验能完成 TLS 握手；`il2cpp` 侧无崩溃。
