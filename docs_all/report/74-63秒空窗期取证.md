## §2 各数据源原始片段

### §2.0 先确认时间语义（否则会误判 20 秒）

`/www/server/nginx/conf/nginx.conf:8` 原文：

```nginx
log_format tcp_format '$time_local|$remote_addr|$protocol|$status|$bytes_sent|$bytes_received|$session_time|$upstream_addr|$upstream_bytes_sent|$upstream_bytes_received|$upstream_connect_time|sni=$ssl_preread_server_name';
```

所以字段依次是：**时间 | 客户端IP | 协议 | 状态 | 发给客户端字节 | 从客户端收到字节 | 会话时长 | 上游 | 上游发 | 上游收 | 上游连接耗时 | SNI**

- `$time_local` 由 stream 模块在**会话关闭时**求值 ⇒ 该时间是**连接结束时间**，不是开始时间。
- `$session_time` = 整个会话持续秒数。

**独立验证（防止把 06:07:01 误认为"新连接"）**：
若 `$time_local` 是"开始时间"，则 06:06:37/39/41 这 3 个 HTTP 请求必须挂在 `06:07:01` 这个"开始于 06:07:01"的连接上——**时间倒流，不可能**；
而客户端在 06:05:17 之后、06:06:37 之前没有任何其他 gsqc 连接。故 `$time_local` 只能是**结束时间**，
该连接建于 `06:07:01 − 24.350 = 06:06:36.65`，正好早于首个请求 `06:06:37` 约 350ms（TCP+TLS 握手耗时），完全自洽。

### §2.4 ★ 字节闭环证明：那条连接里除了 3 个已知请求，一个字节都没有多

这是整份报告最硬的一条证据。找 `05:46:32` 那条会话作对照标定 —— 它也是同一客户端、同样的 auth→nickname→getinfo 三连：

| 会话 | 结束时间 | session_time | 建连时间 | bytes_received (客户端→服务器) | bytes_sent (服务器→客户端) | 该连接上的 HTTP 请求 |
|---|---|---|---|---|---|---|
| A（标定） | 05:46:32 | 26.751s | 05:46:05.25 | **4327** | **4915** | 05:46:06 auth(1817) + 05:46:10 nickname(1244) + 05:46:12 getinfo(740) |
| B（**空窗前**） | 06:07:01 | 24.350s | 06:06:36.65 | **4327** | **5343** | 06:06:37 auth(1817) + 06:06:39 nickname(1244) + 06:06:41 getinfo(740) |

```
reqlen 求和：1817 + 1244 + 740 = 3801  （两次完全相同）
bytes_received：A = 4327，B = 4327     → TLS 握手开销 4327 − 3801 = 526，两次完全一致

bytes_sent 差：5343 − 4915 = 428
getinfo 响应差：620 − 192 = 428        ← ★ 精确相等
```

**结论**：B 这条连接里传输的字节量，被完全解释为「TLS 握手 526 + 那 3 个请求」；
`bytes_sent` 的差额又恰好等于两次 getinfo 响应体的差额（`05:46:12` 那次只回了 192 字节，本次回了 620 字节）。
**数学上没有任何余量可以容纳第 4 个请求。** 客户端在这条连接上真的一个字节都没多发。

同时该连接的时间线：

```
06:06:36.650  建连
06:06:41.002  最后一个响应(620B) 完成
   ……       闲置，零字节
06:07:01.000  连接关闭     ← 闲置 19.998 秒
```

**「最后一次响应之后精确闲置 20.000 秒再拆连」这个行为在 5 次会话上完全一致**：

```
05:38:29  20.361s 会话，末请求 05:38:09  → 闲置 20.0s
05:39:05  35.850s 会话，末请求 05:38:45  → 闲置 20.0s
05:40:48  20.751s 会话，末请求 05:40:27  → 闲置 20.0s
05:46:32  26.751s 会话，末请求 05:46:12  → 闲置 20.0s
06:07:01  24.350s 会话，末请求 06:06:41  → 闲置 20.0s
```

> 该 20 秒**不是** nginx 的配置：stream 层 `proxy_timeout 600s`（`ba_sni.conf:34`），
> HTTP 层 `keepalive_timeout 60`（`nginx.conf:39`）。
> 20.000s 这个整齐值最可能来自 bridge 后端 `127.0.0.1:9098` 或客户端自身的 keep-alive 超时；
> **日志无法区分是谁先发的 FIN，此处不臆断。**
> 但可以确定一个工程事实：**客户端每次拿到响应后，只有 20 秒的有效复用窗口。**

### §2.5 06:07:58 那条 gsqc 记录 = 本地 curl 测试，不是客户端

必须单独说明，否则会被误读成"客户端 06:07:58 又通了"：

```
14/Nov/2026:06:07:58 +0800|127.0.0.1|TCP|200|4362|1694|0.107|127.0.0.1:8443|...|sni=gsqc-api.bluearchive-cn.com
```

四条判别特征，全部指向"人手打的 curl / 重放"，而非游戏客户端：

1. **来源 IP = `127.0.0.1`**（服务器本机）。真实客户端是 `117.147.55.174`。
2. **`boundary=----TENTEST`**（"TENTEST" = 测试）。客户端只会用 `BestHTTP_HTTPMultiPartForm_XXXXXXXX`。
   同款 `----TENTEST` 在 `05:39:43` 的 callname 上出现过，是该机器既有的手工测试特征。
3. **`acc="*/*"`、`ae="-"`**（无 gzip）。客户端恒为 `ae="gzip"`。
4. **`headers` 里没有 `REQUEST-ID`、没有 `APP-VER` / `PLATFORM-ID` / `CHANNEL-ID` / `RESOURCE-VER` / `TABLE-VER`。**
   真实客户端的 3 个请求每个都带一整套，`REQUEST-ID` 是各自的 UUID。

`api_all_requests.log` 中 06:07:58 那条的原始 headers 可对照（注意字段缺失）：

```json
"headers": {"Host": "gsqc-api.bluearchive-cn.com", "Content-Length": "859", "Accept": "*/*",
 "Content-Type": "multipart/form-data; boundary=----TENTEST", "User-Agent": "BestHTTP/2 v2.4.0"}
```

## §4 这份证据能推出什么 / 不能推出什么

### 能确定（服务器侧硬证据）

1. 服务器全程健康：`nginx` 在 `0.0.0.0:443` 与 `127.0.0.1:8443` 双监听正常（`ss -lntp` 已核）。

3. 该 620 字节确实**完整发出**了（`bytes_sent` 核算已闭环，见 §2.4）。
4. 客户端**在线**且链路健康（TapSDK 60s 心跳一秒未漏，adjust / yostar 通道同期正常）。
5. 客户端在 06:07:01 之后、06:07:44 之前，**零字节发往我方 API**。
6. **20 秒 keep-alive 拆连**是我方一个稳定、可复现的既有行为（5 次样本全一致）。

### 不能确定（需要客户端侧数据，而本次被禁止触碰手机）

1. **弹窗到底对应哪一次失败的请求。** 服务器看到的是"没有请求"，所以失败发生在客户端内部。
   两个符合算术的候选（**均为推测，无证据**）：
   - 弹窗时刻 `06:07:44` − `60s` = `06:06:44`，正好紧接 620 字节响应之后约 3 秒。
     若客户端在 06:06:44 发起下一个请求并挂 60 秒超时，正好在 06:07:44 报错。
     **但这与"零字节到达"矛盾**——除非该请求因连接池/复用问题**根本没写出去**（Unity BestHTTP 典型的 pool-wait 超时）。
   - 拆连时刻 `06:07:01` + `43s`，非整数，不优先采信。
2. **客户端是否把 `gsqc-api` 解析/重定向到了别的 IP。** 若客户端在 06:07 之后改走真实 Yostar 服务器，
   服务器侧**必然看不到**，且真实服务器返回的内容客户端解不开，同样会报"同步账号信息错误"。
   这是**唯一无法用服务器日志排除的替代解释**。判别方法在手机侧（抓包 / hosts / DNS 缓存），本次约束下不做。
3. 20 秒拆连究竟是 bridge 还是客户端先发的 FIN —— `tcp-access.log` 不记录 FIN 方向。

### 给下一步的建议（不改动服务器）

1. 既然 06:07:01 的连接是被**20 秒闲置**拆掉的，而弹窗在 43 秒后才出现，
   优先怀疑**客户端复用了一条已被拆掉的 keep-alive 连接**：写进去的字节进了死 socket，
   既没到达服务器（`bytes_received` 已证明），也会阻塞到超时。
   → 检查客户端 BestHTTP 连接池复用策略 / keep-alive 超时设置（应 < 20s，或响应后显式禁用复用）。
2. 若要抓"客户端到底有没有尝试"，只能用手机侧手段（本次明令禁止），服务器侧已到证据边界。
3. `api_probe.out` 目前是 0 字节且被截断过，`access.log` 已停写 —— 若还需长期取证，
   建议先把 bridge 的 stderr 真正落盘（属改动配置，需另行授权，本次未做）。
