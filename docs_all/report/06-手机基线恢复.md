## 3. 结论：客户端为什么起不来（按证据强度排序）

1. **【强】直接死因：`libil2cpp.so` 被写成 0 字节。** bionic 在 `dlopen` 时 `fstat(fd).st_size==0`，报 `file offset for the library "libil2cpp.so" >= file size: 0 >= 0`；`libmain.so` 自己的 `dlopen` 是 `ok`，随后 `UnityPlayer.loadNative` → `JNI FatalError` → 进程 abort（`reason=1 EXIT_SELF status=13`、无 tombstone）。文件补齐（270927056 B、sha 6e2edf5a）后**同一 APK、同一路径、同一套桩**立刻可跑 40s+，这是最强的因果证据。
2. **【强】不是 zip-direct / 对齐 / Defl:N 问题。** `maps` 显示 9~10 个 segment 全部来自 `/data/app/.../lib/arm64/libil2cpp.so`（inode 1882202 / 1909677 与被替换文件一致），不是 `base.apk`。报告 07 的 open question 到此可以关掉。
3. **【强】101404 = AiriSDK 初始化网络失败，不是"资源初始化失败"。** `assets/SDKConfigSettings.json` 的 `sdk_url` 是 `http://127.0.0.1:8080`；手机 8080 无监听时 SDK 立刻 `onFail {"code":101404,"R_MSG":"网络异常?请重新连接"}`，弹窗文案是 SDK 的失败页。**只要 8080 有可用中转，SDK 段立刻通**（本次已验证到 quick-login 200）。
4. **【强】当前真正的墙：游戏网关鉴权。** 已进入标题画面，`state-api` / `gsqc-api` 解析并连接官方 CDN，随后弹「认证服务器拒绝了请求」。这是 token 层面的拒绝（我们 SDK 是私服签发的，官方网关不认），与客户端完整性无关。
5. **【强】`/system/etc/hosts` 覆盖无效。** 三个变体（shell ns bind、netd ns bind、DNS 缓存文件）都试过：解析始终返回官方 IP；解析实际由 netd + Clash tun 完成。
6. **【中】`Hosts` 缓存是"候选列表"，不是"连接目标"。** 客户端会读、会保留我们的条目（u32 计数 1→2），但在官方 state 成功时仍用官方候选；u64 调大不改变行为；单 IP 阻断会被 CDN 轮换绕过。**能否让它"官方失败时回落我们的候选"，目前没有拿到正面证据。**

### 7.6 改为"单条兜底 DNAT"（当前的最终形态）
逐条补 IP 是打地鼠；改为对**游戏 uid 的全部 443 出站**做兜底：
```
# 旧 38 条逐条 DNAT 全部删除（已存档 /sdcard/ba_nat_38_*.txt）
iptables -t nat -I OUTPUT 1 -p tcp -m owner --uid-owner 10576 --dport 443 \
         ! -d <SERVER_IP> -j DNAT --to-destination <SERVER_IP>:443
iptables -t nat -S OUTPUT →
  -A OUTPUT ! -d <SERVER_IP>/32 -p tcp -m owner --uid-owner 10576 -m tcp --dport 443 -j DNAT --to-destination <SERVER_IP>:443
iptables -t nat -L OUTPUT -n -v → 34 包 / 2040 B 命中
ip6tables -L OUTPUT -n -v → REJECT 计数 27 包
```
**两个坑（记录）**：
1. iptables 取反必须写 `! -d <SERVER_IP>`；写成 `-d ! <SERVER_IP>` 会报 `Bad argument`（rc=2）。c100/c101 两轮因此 **DNAT=0**，那两轮的 `ss` 数据作废。
2. **`ss` 显示的是 DNAT 前的原始 peer**（nat OUTPUT 只改报文目的地址，不改 socket），所以"ss 里只剩 <SERVER_IP>"在原理上做不到；判断"流量是否全到我们"只能用 **DNAT 计数器** + 服务端日志。

**本轮结果**：34 条连接全部被导到 `<SERVER_IP>:443`，屏幕仍「请确认网络连接状态后重试。」（`/sdcard/blanket3_012209.png`）
⇒ 在"流量 100% 到我们"的干净条件下仍失败，问题确证在 **TLS/证书校验层**；下一步由服务端 pcap 定性（alert `access_denied` → 硬 pinning → frida-il2cpp-bridge；出现 okhttp 请求 → 协议层适配）。

### 7.7 ★ 根因：客户端建 TLS 时**不发 SNI**（方法论教训，必须记录）

服务端用同一配置做对照：
```
带 -servername gsqc-api → ServerFlight 2601 字节（落到 ba_mitm，拿到 CN=*.bluearchive-cn.com）
不带 SNI               → ServerFlight 1355 字节（落到 0.default，拿到 CN=default 自签证书）
我们上一轮 pcap 的服务端 flight = 1352 字节 ≈ 1355
```
**⇒ 客户端一直落在 nginx 的 `0.default` 块，拿到的是 `CN=default` 自签证书 —— 我们准备的叶子/链/CA 它从来没见过。**
这一条同时解释了：三处 CA 全装上没用、链补到 3 张没变化、`ba_mitm.log` 里 `okhttp` 计数恒为 0、error.log 无握手失败（因为握手在 `0.default` 块里失败了，是另一个 vhost）。

**修复（服务端）**：给 `ba_mitm` 加 `listen 443 ssl default_server;` → 无 SNI 的连接也落到该块，拿到 `CN=*.bluearchive-cn.com`（SAN 覆盖 `gsqc-api`）。

**方法论教训（写给档案）**：
1. **之前所有 TLS 结论（包括 `access_denied` 的定性）都是在"客户端落在默认块、拿的是 `CN=default`"的前提下得出的，全部需要重估**——它们证明的只是"客户端不接受 CN=default"，而不是"客户端 pin 了我们的证书"。
2. 正确的排查顺序应是：**第一次拿到 pcap 就先比对 `ClientHello` 有无 SNI、`ServerFlight` 字节数是否与对照一致**，而不是先花时间装 CA / 补证书链。
3. 同理，`ba_mitm.error.log` 为空不代表"握手成功"（客户端主动 alert + FIN 时 nginx 不记 error），必须结合 pcap 判读。

**下一轮（等服务端 reload 后执行）的判据**：
- 屏幕进大厅 / 不再报网络错 → 通；
- 仍报错但 pcap 里 `ServerFlight ≈ 2601 B` → 至少证明它终于拿到我们的证书，再看 alert；
- pcap 里出现 `okhttp` 请求 → TLS 已过，转协议层适配。
