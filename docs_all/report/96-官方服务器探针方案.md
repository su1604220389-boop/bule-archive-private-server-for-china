### 1.2 没找到什么（必须写清楚）

| # | 缺口 | 证据 / 说明 |
|---|---|---|
| 1 | **`Authorization.Sign` 无法生成** | 见 §1.3。签名器是 `AiriSgClient.sign(byte[],int)` 的 native 实现，只在 `lib\arm64-v8a\libairisgcore.so`（2,658,312 B）里；**APK 没有 x86/x86_64 变体**（`work\ba\audit\ba-apk\lib\` 下只有 `arm64-v8a` 一个 ABI 目录）。 |

### 1.3 关键实测：`Sign` 是被真校验的（这一节是本报告最重要的证据）

我用探针向 `https://sdk-api.yostar.cn/user/detail`（POST，只读）连发 4 次，让**服务端自己把 Authorization 的 schema 一层层报出来**：

| 次 | 发送内容 | 真服响应（原文） | 读出来的事实 |
|---|---|---|---|
| 1 | 不带 `Authorization` | `{"Code":100400,"Msg":"参数有误:Authorization不能为空","Data":{}}`（72 B） | Authorization 是**必需**头，缺了直接 400 |
| 2 | Head 里 `UID` 按字符串发 `"1013178778"` | `…app.Authorization.Head: app.Head.UID: readUint64: unexpected character…`（348 B） | `Head.UID` 的类型是 **uint64**（必须发数字） |
| 3 | `Sign` 为空串 `""` | `…Key: 'Authorization.Sign' Error:Field validation for 'Sign' failed on the 'required' tag`（163 B） | `Sign` 是 **required** 字段 |
| 4 | `Sign` 给 256 字节全 0 的假签名 | `{"Code":100400,"Msg":"参数有误:Sign有误","Data":{}}`（57 B） | **签名被密码学校验**，不是"有值就过" |

⇒ 结论 **[实测]**：`Authorization = {"Head":{…},"Sign":"<base64 RSA-2048-SHA256>"}`，`Sign` 用服务器公钥验签，**伪造不可能**。原串里的 `app.Authorization` / `app.Head` 是 Go 包名，说明 SDK 服务端是 Go 写的，结构体走 go-playground/validator 校验。

### 1.4 一个必须纠正的混淆：`/auth/v1/*` 不是国服实际调用的路径

`report/27` 从 `classes2.dex` 的路径字面量表里列出了 `/auth/v1/login-by-token`、`/auth/v1/login-by-authorization-code`、`/account/v1/profile` 等 **20 条**。这些**确实存在于 dex**，但：

* **[实测]** `work\ba\bapatch\sdk.log` 里真客户端 **一次都没有**打过 `/auth/v1/*`，全部是 `/user/login`、`/user/quick-login`、`/user/detail`；
* `SdkConst.Uri`（国服自己在用的常量表）里也**没有** `/auth/v1/*`，只有 `/user/*`、`/common/*`、`/health-game/*`、`/heartbeat/*`。

⇒ 判断：`/auth/v1/*` 属于 **Airi 聚合 SDK 的国际版 / 通用版路径**，国服走的是 `SdkConst.Uri` 那一套 `/user/*`。**做国服探针请照 `SdkConst.Uri` 写，别照 `report/27` 的路径表写。**（这条纠正不影响 `report/27` 的其余结论。）

### 3.6 一个必须记下来的工程坑：本机 Python 的证书链

第一次跑 `--state` 时四条全部 `SSLCertVerificationError`：

```
state-api: [SSL: CERTIFICATE_VERIFY_FAILED] unable to get local issuer certificate
gsqc-api : [SSL: CERTIFICATE_VERIFY_FAILED] self-signed certificate in certificate chain
```

但同一台机的 `curl.exe` 和 Git 自带 `openssl s_client` 都能 `Verification: OK`。原因是 **Python 的 Windows 默认 store 缺 RapidSSL/DigiCert 中间证书**，而 Git 的 `ca-bundle.crt`（229,042 B）里有。

**探针的处理**：`_make_ssl_context()` 在 `ssl.create_default_context()` 之上**追加加载**候选 CA（`SSL_CERT_FILE` → `C:\Program Files\Git\mingw64\etc\ssl\certs\ca-bundle.crt` → Git usr 路径 → 同目录 `ca-bundle.crt`），**不关闭校验**。加载后两个域名都 `VERIFY OK`，产物里每条都记 `tls` / `tls_verified`。
`--insecure` 只在 CA 全试完仍失败时由人显式打开，且会把 `tls_verified=false` 写进 capture —— **默认绝不降级。**

## 4. §4 登录流程设计（短信 → token → auth）

### 4.1 三条路径，以及各自的当前状态

```
路径 A（推荐，今天就能跑）
  [已有] Data.User.Token（真服签发，40 hex）
      └─→ POST gsqc-api /api/account/auth   ← 当前 500（维护）
           └─→ /api/account/loginsync → /api/academy/getinfo → …
```

### 4.5 如果一定要打通路径 B（把签名补上）

按性价比排序，三条都是纯离线工作（不需要手机）：

| # | 做法 | 工作量 | 风险 |
|---|---|---|---|
| B1 | **从 `libairisgcore.so` 提取 RSA 私钥**：ARM64 反汇编 `JNI_OnLoad` → 找到喂给 `d2i_PrivateKey_bio` 的那段 buffer → 还原混淆（大概率是 base64+XOR 或 AES 解一段常量）→ 拿到 PEM | 中（一次逆向） | 低（纯离线） |

## 5. §5 风险与边界

### 5.1 频率与风控（探针已内建）

| 措施 | 实现 |
|---|---|
| 最小间隔 | `--sleep 1.0`（默认），`Recorder.pace()` 保证两次网络调用之间 ≥1s |
| 超时 | `--timeout 30` |
| 单次动作的请求数上限 | `--probe-gateway` 5 个、`--walk` 2~5 个、`--state` 4 个，全部写死在代码里，**不做循环重试、不做爆破** |
| 本次实际用量 | 约 **40 次**请求（含 3 次矩阵复跑），全部只读/无副作用，间隔 ≥1s，跨 25 分钟 |
| 触发停止条件 | 出现 429 / 403 就应停手（当前未出现；500 是业务侧，不是限流） |

### 5.2 账号安全（**写操作默认禁用**）

* `Account_Nickname(1001)` / `Account_CallName(1010)` 会**真的改账号昵称/读音**。探针默认**跳过**，必须同时给 `--nickname <名> --allow-mutating` 才会发。
* `--send-sms` / `--login` / `--sdk-detail` **默认 dry-run**，只打印将要发出的完整 wire（URL/头/body），不发。
* 真发短信需要 `--yes-really-send`，且本任务约束是**没有明确号码绝不发**。

### 5.3 凭据暴露面

本次报告与产物里出现了这些真实值，**建议按 secret 管理**：

| 值 | 在哪 | 风险 |
|---|---|---|
| `e026a35f6cf3f15f547988475a994e0fe738a808` | `sdk_resp/user_detail.json`、`report/27:265`、本文件 §3/§4 | 游戏 Token；若仍有效，可被他人冒用 |
| `177****1532` / `**仙` / `330*********06062*` | `sdk_resp/user_detail.json` | 已脱敏的手机号/实名校验信息 |
| `SLS.AccessKeyID/Secret` | `sdk_resp/common_config.json` | 阿里云日志服务 AK（官方下发给客户端的，本来就是暴露的） |
| `Taptap.ClientID/ClientToken` | 同上 | TapTap 客户端凭据 |

**注意**：本次所有请求都从**本机 IP** 发出，而 `DeviceUniqueId`/`DeviceModel` 是用户真机的值。**IP 与设备指纹不一致本身就是风控特征**，真服若做「异地登录」判定，可能触发二次验证或冻结。这也是为什么 §5.1 要限速、且建议**只用一条 token 做只读 auth**，不要在真服上做任何写操作。

### 5.4 结论边界（不要用超）

1. 「500 + 0 字节」是**当前时刻的观测**，不代表永久；开服后必须重测。
2. 「签名必须有效」是**实测**；但「签名原文的拼法」未知（是 `JSON(Head)` 的 SHA256？还是别的），要靠 §4.5 的逆向才能定。
3. `state` 的 676 B 与 `report/31` 逐字节一致 ⇒ **说明 `report/31` 的数据至今仍然有效**，可以直接当我们私服 `/api/state` 的黄金样本。
4. 本次**没有**任何真服登录链响应 —— **`captures_official/` 里 `resp_bytes=0` 的那几条就是证据，没有伪造**。

### 6.2 拿到 24000 响应后怎么用（这是整条链的关键缺口）

现状 **[实测]**：`report/67:161-164` 指出 `work/ba/proto/dto_schema.json` 里**没有任何 `Academy_*` DTO**，`dto_schema_academy.json`（28,427 B）是后来补的、来源不明。真服 24000 的响应正是**唯一权威**。

用法：

```
① 真服响应 → 明文 JSON（探针自动落 resp_plain）
② 与我们的构造做结构化 diff：
   python work\ba\server\diff_vs_official.py \
       captures_official\<真服24000>.json  work\ba\proto\dto_schema_academy.json \
       --label-a 真服 --label-b 我们的构造
③ 三类差异分别处理：
   - 只在真服有  → 我们缺字段，按路径补进 response_factory.py / protocol_router.py
   - 类型差异    → DTO 定义错了（int vs str / 对象 vs 数组），改 schema
   - 值差异      → 业务默认值不对（如 ServerId / Level / 时间格式）
④ 修完把我们的包再存一份 JSON，反向 diff 一次（A/B 对调），直到「两者结构一致」
```

**为什么这一步值得**：`report/67` 的 D1 显示客户端拿到只有 `{"Protocol":24000}` 的 192 B 假包后 **8 秒**弹「同步账号信息时发生错误」。真服 24000 一旦拿到，我们就有了「客户端期待的完整形状」，这比继续盲改 `Account_LoginSync(1019)` 收益高得多（`report/67` 的优先级判断：**24000 > 1019**）。

### 6.3 `diff_vs_official.py` 的能力（已实测）

对同一份文件自比 → `✔ 两者结构一致`（退出码 0）；对一份人造副本（删 1 键、加 1 键、改 1 类型、缩 1 数组、改 1 值）→ 五类差异全部命中（退出码 1）：

```
扁平键：A=12  B=11   差异：仅A=1  仅B=1  类型=1  值=1  数组长度=1

【只在 真服 有】1 条
  - IsOpenPreDownload
【只在 我们构造 有】1 条
  + ExtraField
【类型差异】1 条
  ! ResourceVersion     str("202611051844")  vs  int(202611051844)
【数组长度差异】1 条
  ~ AddressablesCatalogUrlRoots   A=3  B=2
【值差异】1 条
  ≠ State
    A = 1
    B = 0
```

特性：直接吃探针产物（自动从 `resp_plain`/`resp_inner` 取载荷）、`--pick req|resp` 选层、`--ignore 'ServerTimeTicks|MxToken'` 忽略易变字段、`--json` 机读输出、`--max-items` 控量。
