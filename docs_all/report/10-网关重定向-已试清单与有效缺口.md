## 0. 本轮叠加的新事实（档案里没有；下文一律记为 N1–N7）

| 编号 | 事实 | 对档案的杀伤点 |
|---|---|---|
| N1 | `files/Hosts` 二进制格式已解出：`u32 version=1 \| u32 count \| loop{ u8 hostlen, host, u32=1, u8 urllen, url(带 scheme+端口), u64, u8 flag=1 }`；166 B / 2 条样本 | 当年写的 `127.0.0.1:9443` 是**裸串**，不是这个结构 |
| N2 | 条目数 = 官方 `/api/state` 的 `Servers[]` 条数（2 条）→ 它是 `Servers` 的落盘缓存 | 与 `api-probe.md:22`「`ApiUrl/GatewayUrl` 由 `ServerInfoConnectionGroupData` 提供」互为印证 |
| N3 | `/system/etc/hosts` 的 bind-mount 对 app **无效**：app 解析走系统 DNS 服务（pid 1937，logcat tag `DNS_CACHE`），它在**另一个 mount namespace** | 直接判死档案里「游戏用 HTTPDNS，不走系统解析」的解释（`ba-pitfalls.md:179`） |
| N4 | 我方 nginx 对 `*.bluearchive-cn.com` 用的是**自签证书**（`/root/bapatch/c.pem` 那套） | 任何「域名解析到我们 IP」的方案都先死在 TLS 上，与路由无关 |
| N5 | `sdk_url=http://127.0.0.1:8080`（裸 http）能用；手机侧靠本地中转接到 `https://example.com/sdk`（该域名**真证书**，公网 200） | 证明**明文 HTTP 在本 app 内是被允许的**（与 `ba-sdk-protocol.md:10-11` 静态结论一致） |
| N6 | `example.com` 已配 `location ^~ /` → `proxy_pass http://127.0.0.1:5000;`（**完整路径透传**），`/api/Queuing/Ping` 公网 200 | 提供一个「真证书 + 全路径透传」的落地端点，而档案里全部实验都指向自签的 9443/9444 |
| **N7** | **真机 164→79 B 改写实验（lead 本轮实测）**：写入单条 `host=gsqc-api.bluearchive-cn.com` / `url=https://example.com/api/`（79 B，sha256 `65781f31…`），启动客户端 → 客户端**读懂了**，把文件重写成 **128 B**：`count` 1→**2**，**我们那条 URL 原样保留**，再**追加**官方 `https://gsqc-api.bluearchive-cn.com:443` | **推翻**档案结论「`Hosts` 只是记录/展示，不决定连接目标」。它被解析成**候选列表**，写入的条目**会被保留**，只是没被选中去连接 |

> N7 是本文最重的一条：它把一整类「Hosts 路线已死」的判断整体作废（详见 §3.1）。

## 2. 三个最贵的「无效实验」（结论已被下文取代）

### 2.1 `files/Hosts` 被判"只是记录/展示"——错的

- **原文**：`ba-pitfalls.md:128`「`files/Hosts` **不决定连接目标**（只做记录/展示）」；`ba-gateway-host.md:32`「本轮实测证明：**`Hosts` 只被读写，不决定连接目标**」；`ba-pitfalls.md:158` 把它列入「已废弃/不可用」。
- **缺陷**：写入格式与真实结构不符（裸 `127.0.0.1:9443` vs `hostlen+host+u32+urllen+url(带 scheme)+u64+flag`，N1）。格式坏 → 整条被丢弃 → `0 连接`，与「不被使用」**不可区分**。
- **反证**：`api-probe.md:14` 早已记录过 89 B 文件的真实形态（含完整带 scheme 的 URL 与长度前缀），只是没被拿去当写入模板。按 N1 算：`8 + (1+27+4+1+39+8+1) = 89` —— **89 B 恰好就是"1 条记录的同一格式"**。也就是说，档案里那份样本与 N1 的结构**完全同构**，当年只是没认出来。
- **现状**：见 §3.1，已被 N7 实测推翻。

### 2.2 `/system/etc/hosts` 被判"游戏用 HTTPDNS"——错的

- **原文**：`ba-pitfalls.md:179`「本机 `/system/etc/hosts` 覆盖官方域名 ❌ 无效（游戏用 HTTPDNS，不走系统解析）」。
- **缺陷**：没有任何「解析到底走了哪条路」的独立观测就下了归因。若当年 hook 过 `getaddrinfo`（C2）并看到"有时能拦到"，其实已经说明**存在系统解析路径**，与 HTTPDNS 结论自相矛盾，但没被追。
- **真正的因**：N3——app 的解析由**系统 DNS 服务 pid 1937**（logcat `DNS_CACHE`）完成，它处于**另一个 mount namespace**，shell 侧 `mount --bind` 覆盖不到。
- **影响**：一条**手段错误**的失败被写成了**机制结论**，直接关掉了整个 DNS 层面。

### 2.3 E64「超时」被当成"路径已改但实现有阻塞"——信号不可解释

- **原文**：`ba-pitfalls.md:184`「E64 表现从「被官方拒绝」变成「**超时**」，说明路径已改但实现仍有阻塞」。
- **缺陷**：超时至少有四种成因——目标地址写错（C4/C14 的 `adr`/基址 bug 当时未修净）、端口不通、TCP 通但无人应答、**TLS 握手挂在自签证书**（N4）。**没有一次「TCP 是否到达我们服务器」的旁证**（如 `ss -tn`/nginx access log），这个信号没有判别力。
- **连带**：E64 之后「现役版本」锚点仍写 E42（`ba-pitfalls.md:155`），说明这条实验的产物**从未被纳入可交付链**。

### 2.4（补充）证书环节先挂、却被记成路由没生效的两处

- **A3**：`ResUrls` → `https://127.0.0.1:9444/prodm39`，9444 起 python ssl（自签）。就算客户端采纳了，TLS 也会失败；而观测指标是 `cdn.log` 里"有没有请求"——请求到不了 nginx 日志，就永远读不到"TLS 失败"这层。
- **B4**：`tlsproxy.py` 9443 → 5000，同样是自签。A1/A2 的 `0 连接` 即便成立，也只证明"没建 TCP"，一旦格式修好、TCP 建起来，**下一个死的就是证书**，而当年没有任何一份文档讨论过这一层。

## 3. 被新事实推翻 / 改写的旧结论

### 3.1 ★ `files/Hosts` 的定位：从"记录/展示"改写为「候选列表（Servers[] 落盘缓存），写入条目会被保留」

**这条已不再是"未验证的猜测"，而是实测事实（N7）。**

| 项 | 旧结论 | 新结论（实测） |
|---|---|---|
| 文件性质 | 只做记录/展示，不决定连接目标（`ba-pitfalls.md:128`、`ba-gateway-host.md:32`） | **`Servers[]` 的落盘缓存，被解析成候选列表**；条目数变化（1→2）与我们写入的那条 URL 被原样保留，证明解析器读懂了它 |
| 写入有效性 | 写入 `127.0.0.1:9443` → 无效 | 写入**正确格式**（host + 完整带 scheme 的 URL）→ **被保留为候选** |
| 失败原因 | 归因为"文件不被使用" | 归因为 **(a) 当年写入格式不对**（裸串，非 `hostlen+host+u32+urllen+url+u64+flag`）；**(b) 联网状态下官方 `/api/state` 成功后会把官方条目追加进来并可能优先**（N7 实测：客户端把我们那条保留、再**追加**官方 `https://gsqc-api.bluearchive-cn.com:443`） |
| 尚未解决 | — | **"为什么没被选中去连接"**：可能是 u64 时间戳比官方旧，或 state 刷新后官方条目排到前面。这是当前唯一未闭合的问题 |

配套旁证：N2 的「条目数 = `Servers[]` 条数」与 `api-probe.md:22`「`ApiUrl/GatewayUrl` 由 `ServerInfoConnectionGroupData` 提供」一致；A5 的 `/api/state` 命中 0 只否定 `gameUrl`，不否定"`/api/state` 是候选来源"。

## 4. 在「新事实」约束下，从未被有效证伪的路

> 排序口径：**实现成本（低→高）/ 成功率（高→低）/ 需要改动的东西（少→多）** 綜合。每行给一句理由。
> 前提约束（必须同时满足，否则任何一条都不成立）：**先摘掉 7890 代理**（B1）、**别用自签证书对 `*.bluearchive-cn.com`**（N4）。

| 序 | 路 | 实现成本 | 成功率 | 需改动什么 | 为什么它"从没被有效证伪" |
|---|---|---|---|---|---|
| ① | **正确格式重写 `files/Hosts`，并让它"被选中"**（调 u64 / 只留我们一条 / 让官方条目追加不进来） | **极低**（1 个文件，约 100 B；已有 79 B 成功样本） | **高**（解析侧已证成立，只剩优先级） | 1 个文件（+ 可能加一条到 `state-api` 的阻断） | N7 只证明了"条目被保留"，**没证明"被选中"**；当年的 `0 连接` 是格式坏导致的，不是"不被使用"。这是当前**唯一**已被推进到"可解析"的一步 |
| ② | **同上，但 `url` 用明文 http**（`http://<IP>:<PORT>`，不带 scheme 的 https） | **极低** | **高**（若客户端遵守 scheme） | 1 个文件 | `cleartextTrafficPermitted=true` 已被 `sdk_url=http://127.0.0.1:8080` **实跑验证**（N5、`ba-sdk-protocol.md:10-11`），但**从来没有一次**把明文 scheme 写进 `Hosts` 的 url 字段——当年写的是 `https://127.0.0.1:9443`，直接撞上自签证书（N4）。这条把证书整层删掉了 |
| ③ | **DNS 层：`nsenter` 进 netd（pid 1937）的 mount namespace 改 `/etc/hosts`，或改完重启 netd** | 低–中 | 中高 | netd 的挂载视图 + 重启 netd（或改 `/system/etc/hosts` 后让 netd 重读） | N3 把旧失败的真因定位到 mount ns，但**没有人在 netd 的 namespace 里试过一次**。旧实验只在 shell 的 ns 里 bind-mount，属于打错靶 |
| ④ | **iptables DNAT（`nat` 表，`OUTPUT`+`PREROUTING`，最好带 `--uid-owner`）+ 系统 CA 注入** | 中–高 | 中 | iptables 规则 + 系统证书库（`/system/etc/security/cacerts`）+ 重启 | 旧「不生效」只有一句结论、零方法（B2）；而"系统证书"被**交付约束**提前否决、从未测试（D1）。现在有 `u:r:ksu:s0`（N6），两条前置都具备了 |
| ⑤ | **libunity `connect` GOT 写入（修正后的正确做法）** | 高 | 中（机制上应成立） | 注入桩（修 `adr`→局部标签、基址取 `r-xp 00000000`、单槽 `str` 写、不整页回写） | 当年那次"未证实"的根因已被自己写清（`adr`=0 + 基址取错，`ba-pitfalls.md:214-215`、`:243`），并给出「GOT 页 `rw-p`，可直接 `str` 写，不需要 mprotect」——**但从没按修正版跑过一次**。§4.10 还实测出 libunity 的 `connect` GOT **确实已被解析到 libc**（`0x74df8c9028`），即这条是"活的" |
| ⑥ | **libil2cpp `connect` PLT hook 改目标 IP，做到稳定** | 高 | 中 | 注入桩 + 区分 v4/v6（`ba-pitfalls.md:178`） | 这是档案里**唯一**「确实把连接改到目标 IP」的成功实验（C3），E63 存活 `24049`（C8）。E64 的"超时"信号不可解释（§2.3），所以"这条路能不能稳定"其实**没被真正测过** |
| ⑦ | **拦截 `/api/state` 那一条请求**（控制候选列表的来源） | 中 | 高（但依赖 ③/④ 任一先通） | 同上任何一条 DNS/IP 层手段 | A5 只证明 `gameUrl` 不参与登录，**没有**测"`/api/state` 的响应体被改后会怎样"。而 N2/N7 已把 `Hosts` = `Servers[]` 缓存这条链钉住，理论收益最大的一击是打它的上游 |

**不在此列（已被有效证伪）**：`LocalizeConfig.ResUrls` 劫持 CDN（与 API 无关）、`gameUrl`/`TechSDKUnityBridge` 改址（A5 命中 0）、libunity 4 字节证书补丁（ACE SIGBUS）、`.rela.plt` 改重定位类型（SIGABRT）、`dl_iterate_phdr` 全模块遍历（实现缺陷已定位）、`GET_SIGNATURES`/`TrustManager` hook 改 native 流量（只影响 SDK 的 Java 请求）。

## 5. 判读时最容易踩的四个坑（都在档案里出现过）

| # | 坑 | 档案表现 | 出处 |
|---|---|---|---|
| 1 | **把"没连上"和"连上了但握手失败"混为一谈** | 观测指标只有"端口连接数 / access log 有请求"，自签证书导致的 TLS 失败在指标上是不可见的 | A1/A2（`0 连接`）、B4、§2.4 |
| 2 | **把"格式不合法被丢弃"当成"该文件不被使用"** | 裸串写入 vs 二进制结构（N1） | A1/A2/A7 |
| 3 | **在没有隔离变量的情况下给机制下归因** | "无效（游戏用 HTTPDNS）"、"DNAT 不生效"、"只做记录/展示" | A4、B2、A1 |
| 4 | **路径/协议形态不匹配，导过去也连不上** | 官方是 `/api/{实体}/{动作}`（`ba-pentest.md:726-740`，18 条已实测），而 Shittim 是**单入口** `POST /api/gateway`（`ba-protocol-full.md:12`） | `ba-pentest.md §三十六` vs `ba-protocol-full.md §一` |

> 第 4 条单独提出来：`example.com` 的 `location ^~ /` 是**完整路径透传**（N6），所以客户端请求什么路径，Shittim 就收到什么路径。档案里**从未验证过** Shittim 能否应答客户端的真实路径形态——这是"导过去了但回 404/500"的现成雷。
