| 环节 | 现状 | 后果 |

### 1.3 调用关系（谁在什么顺序上被调）

```
客户端 SDK 登录      :8080  ──(卡密校验/签发 token)──┐
客户端 网关 CONNECT  :8443  ──(剥 CONNECT)──► :9443 ─┤
                                                      ├──► :5000  Shittim
宝塔 443 SNI A（*.bluearchive-cn.com）──────────────────┤
宝塔 443 SNI B（example.com 根）──────────────────┤
宝塔 443 /sdk/ ──► :8080（云端 sdkcard.py，pm2 `ba_sdk`）
```

两种部署形态并存、且互斥于 8080：

- **形态 1（设备本机）**：客户端 `sdk_url = http://127.0.0.1:8080` → PRoot 里的 `sdkcard.py`。
  这是 `ba-pitfalls.md:156` 记录的现役形态（「设备每次重启后要手动拉起」）。
- **形态 2（云端）**：`relay8080.py` 占 8080 → 云端 `example.com/sdk/` → 云端 8080 的 `sdkcard.py`
  （`README:43` 说「云端卡密 SDK（pm2 `ba_sdk`）已完成」、`add_sdk_loc.py` 注释写 `pm2: ba_sdk, 127.0.0.1:8080`）。
- 二者同时只可能有一个活着；`relay.log` 只有 1 条记录（`POST /common/config -> 200 (7837 B)`），说明形态 2 只做过一次连通性验证。

### 1.4 拓扑层面的三个硬缺口

1. **`ba_mitm.conf` 无自动化部署**：其他所有 nginx 改动都有脚本，只有这份 443 SNI 分流是手工放置；重装面板/换机即丢失。验证：`ls /www/server/panel/vhost/nginx/ | grep ba_mitm`。
2. **SNI 分流的证书是自签**（`srv.crt`），客户端不认（详见 §6 R01）。
3. **`/api/state` 也会被分流进 5000**，但 Shittim 侧没有该端点的实现证据（详见 §4 第 3 步）。

### 2.2 它是怎么「进」Shittim 的

三层动作，缺一不可：

1. **合并**：`merge_excel.py` 扫 `/sdcard/Download/tb`，逐个判 `head.startswith(b"SQLite format 3")`（非 SQLite 直接跳过），`ATTACH` 后把每张 `table`/`view` 用 `CREATE TABLE main.X AS SELECT * FROM s.X` 搬进主库；已存在则 `INSERT OR IGNORE`。
   产物：`/root/bapatch/data/ExcelDB_full.db` —— **13 张表 / 52 MB**（`ba-data-layer.md:23`、`merge_excel.py:3-4,29-56`）。
2. **禁止服务端自己下载覆盖**：`UseCustomExcel=true` + `DownloadExcelTables=false`
   （`ba-pitfalls.md:37` 明确：「服务端会自动下载/覆盖 `Resources/Dumped/ExcelDB.db`，放进去的明文库被替换成加密库」）。
3. **flatbuffer 表放子目录**：`.bytes` 表必须落 `Resources/Dumped/Excel/`，放根目录不生效（`ba-pitfalls.md:38`，表项 13）。

> 注意：合出来的只有 **13 表**，而 160 MB 分片里有 **398 表** —— 差额是 `merge_excel.py:38` 只搬 `table`/`view` 且同名冲突时 `INSERT OR IGNORE`/跳过视图，加上分片里大量 `*DBSchema` 是**表结构声明**而非数据。所以「398 表」不等于「398 张有数据的玩法表」。

**两处配置矛盾，必须记一笔：**

- **GC 堆上限低于文档要求**：四个脚本一律 `0x20000000`（512 MB），而两份文档的实测结论都写 `0x40000000`（1 GB）才够（`ba-pitfalls.md:39`：「`GC: Reserving 256 GiB ... failed` → `DOTNET_GCHeapHardLimit=0x40000000`」；`ba-data-layer.md:35` 同）。加载 160 MB ExcelDB + 资源缓存时 512 MB 有 OOM 风险。
- **配置源三重**：`appsettings.json`（`deploy2.sh` 改）→ `appsettings.Local.json`（`deploy3.sh:3-11` 写，四键齐全）→ 环境变量（`deploy3.sh:19-22` 导出，四键齐全）。三处同名键，.NET 的优先级是「环境变量 > Local > 主文件」，所以现值以环境变量为准。
  风险点：`deploy.sh` 与 `run_srv.sh` **都不导出这四个变量**。若用 `run_srv.sh` 拉起，靠的是仍在盘的 `appsettings.Local.json`（四键齐全，可用）；但若有人手工 `dotnet Shittim-Server.dll` 而本机 `appsettings.Local.json` 已被覆盖/删除，就会退回 `appsettings.json` 的旧值（`deploy2.sh` 曾把顶层同名键 `pop` 掉，`deploy2.sh:12-13`，此时顶层为缺省）。
  结论：**只能按 `deploy3.sh` 或 `run_srv.sh` 拉起**，且启动后必须核对 §7 B14 的 GC 值。

### 4.3 与 Shittim 原设计的一个结构性错配（重要）

Shittim 是 **Steam 版**私服，它的客户端补丁清单里有三条是为了「让客户端不查服务器列表」而存在的：

- `Metadata` patcher 往 `global-metadata.dat` 写 RSA 公钥 + region label
- `Gamescale IAS` 改登录 endpoint
- `Inface config` 改 endpoint 配置

> 出处：`ba-client-patching-shittim.md:16-23`、`ba-protocol-full.md:101-110`

也就是说：**Steam 路线根本不需要 `/api/state`，因为它的服务器地址是被 patcher 直接写进客户端的**。国服 Android 这条路是「`/api/state` 下发 `Servers`」（`ba-pentest.md:160`：「客户端连哪台服务器由这个响应决定」），**这是 Shittim 从没处理过的一条入口**。这是「进大厅」链条上最容易被忽略、也最确定会炸的一环。

## 6. 风险：「就算客户端连通也一定炸」的点

按登录时序排列。**R01-R05 任一未解决，都到不了大厅。**

| 编号 | 风险 | 为什么「一定炸」 | 证据 | 强度 |
|---|---|---|---|---|
| **R01** | **TLS 证书不被信任** | 客户端连 `CN=*.bluearchive-cn.com`（RapidSSL，公信 CA）；我们只能拿 `/root/bapatch/{c,k}.pem` 自签。系统信任链校验必失败，握手层即断。而「装系统 CA」需要 root，与「单 APK、零 root」交付冲突**已被明确否决** | `ba-pentest.md:27`、`tlsproxy.py:5-6`、`README:39`（「系统证书方案需要 root…已否决」） | 实测（证书事实）+ 文档（方案冲突） |

### 6.1 关于「客户端注入最后一步」的一个被低估的坑（文档自身矛盾）

`README:37` 记录：**正确 GOT 偏移是 `connect = 0x13d95d8`、`getaddrinfo = 0x13d94d0`；旧值 `0x13d94d8` 实际是 libc 的 `basename`**。
而 `ba-pitfalls.md:181` 又写「libunity 的 GOT 偏移：`getaddrinfo=0x13d94d8`、`connect=0x13d95d8`」——**同一份归档里两处对 `getaddrinfo` 给了不同值**（`0x13d94d0` vs `0x13d94d8`），且 README 明确说后者是错的（是 `basename`）。

→ **若后续人员按 `ba-pitfalls.md:181` 的值去写 GOT，会重走「写了没反应 / 崩在 strstr」的老路**。这是文档层面的炸弹，不是服务端问题，但会直接卡住「把流量导过去」这一步。**建议以 `README:37` 为准。**

## 9. 三条给 lead 的建议（按性价比排序）

1. **先花 30 分钟做 G08 + G04 + G03 三个探测**：这三个都是「一条命令」，但可能直接把 B03 从「小」降到 0、把 B06 从「大」降为「可跳过」、把 5100 从「未知」变成已知。**投入产出比最高。**
2. **B03/B05/B12/B13/B14 这批「服务器侧小改动」可以立刻并行做完**，不依赖客户端进展。做完后，一旦客户端连通，能至少确认「请求确实打到 5000 了、打到哪条路径、body 是什么形状」——这正是现在最缺的信息（`ba-pentest.md:97-103` 屡次强调缺一条真实业务包）。
3. **B01/B02 与 B06 的取舍要先拍板**：如果坚持「零 root、不装 CA」，则 B02 只能靠「改客户端跳过证书校验」，而这与 B15（ACE 记账）直接冲突；若接受「设备装 CA」，则 B02 变成「小」。**这是整个项目最大的前置决策，不是技术细节。**
