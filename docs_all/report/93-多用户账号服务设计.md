# 93 · 多用户账号服务设计（schema + 服务层 + 对接 + 迁移）

> 目标：把「Auth 请求 → 无条件返回同一个 `ServerId=10015354380` 的 AccountDB → 无条件签发同一个
> SessionKey」的单用户硬编码，换成**每个用户独立账号 / 独立进度 / 独立会话 / 持久化到数据库**。
>
> 本文所有结论分三档标注：**[实测]** = 本机跑过、有输出可复现；**[源码]** = 有 Shittim 源码/产物依据；
> **[推断]** = 只有间接证据，§5 逐条列出。**不许**把 [推断] 当 [实测] 用。

## §0 一页纸

### 0.1 结论

| 问题 | 答案 |
|---|---|
| 几张表 | **6 张**：`accounts` / `sessions` / `account_blobs` / `protocol_log` / `id_alloc` / `schema_meta` |
| 字段总数 | **53 列**（27 + 8 + 6 + 8 + 2 + 2） |
| 每用户状态怎么存 | 一个状态拆成 **1 行 + 21 个 JSON blob**，**41 个状态键**全覆盖（40 块进 blob，`account` 进列） |
| `server_id` 怎么发 | **从 `10000000000` 起**，`id_alloc` 表显式发号（不用 AUTO_INCREMENT），DDL 里再挂 `CHECK(server_id >= 10000000000)` 兜底 |
| 会话怎么发 | `uuid4()` → 36 字符小写 GUID，落 `sessions` 表，**30 天 TTL + 每账号默认只留 1 个活跃会话**（顶号） |
| 首登给什么 | Level=1 / Exp=0 / State=1 / **3 个 1 级学生** / **28 种货币**（信用点 100 万、AP 240、券类 3）/ 无道具无编队无通关 / 一间 1 级咖啡馆 |
| 时间怎么处理 | 一律**无时区 ISO** `2026-11-14T00:00:00`，只由 `to_iso()` 产出；库里空值存 NULL，出包时映射哨兵 |
| 自检 | `python account_service.py --selftest` → **20/20 通过，exit 0** |
| 最大未定项 | 客户端是否校验 `MxToken` 格式、`AccountState=1` 的语义、`EncryptedUID` 算法（§5） |

### 0.3 与既有四层的关系

```
① 路由层     protocol_map.json              （只读，别人的产物）
② 响应构造层  response_factory.py / build_response.py   ← 吃 state dict，不认识数据库
③ 数据层     **本文 + account_service.py + account_blobs**  ← 唯一写入方
④ 状态层     build_state_for() 输出的 41 键 state dict       ← ②③之间的唯一契约
```

核心设计原则：**②层只认 `state` dict，③层只产出 `state` dict**。两边不需要知道对方是数据库还是文件，
所以 `build_response.py`（旧）和 `response_factory.py`（新）能同时吃同一份数据（§3.1 实测两条路都通）。

## §1 数据库 schema

### 1.1 六张表一览

| 表 | 用途 | 主键 | 列数 | 行数量级 | 读写频率 |
|---|---|---|---|---|---|
| `accounts` | 一个玩家一行：身份 + AccountDB 22 字段 + 发号游标 | `server_id` | 27 | = 用户数（10²–10⁵） | 每次握手 1 读 + 1 写 |
| `sessions` | MxToken 会话 | `mx_token` | 8 | ≈ 用户数 × 1~3 | 每请求 1 读（+1 写） |
| `account_blobs` | 每用户子系统状态 | (`server_id`,`kind`) | 6 | = 用户数 × 21 | 每次业务协议 0~2 读、0~1 写 |
| `protocol_log` | 协议流水（可选） | `id` | 8 | 每请求 1 行 | 只追加 |
| `id_alloc` | BIGINT 发号器 | `name` | 2 | 单行 | 建号时 1 次事务内 CAS |
| `schema_meta` | 结构版本 / 常量锚点 | `k` | 2 | 3~10 行 | 启动时读 |

### 1.2 七个关键决策（每个都给「不这么做会怎样」）

| # | 决策 | 选择 | 理由 | 被否的备选 |
|---|---|---|---|---|
| **D1** | `server_id` 分配 | 从 **`10000000000`** 起自增，`id_alloc` 表显式发号 | 真账号实测 `10015354380`（≈1.0015e10）。同量级有两个硬好处：① 客户端把 `AccountServerId` 当 `ClientSaveData` 文件名前缀（实测 `10015354380ClientOption.save`），11 位数字长度一致；② 1e10 > 2³¹，**客户端若在某个子系统里把 long 截成 int32，我们和官方的截断行为完全一样**，不会在「小号」上暴露出官方从来没走过的分支 | ①`AUTO_INCREMENT=1`：和真账号差 4 个数量级，任何按位数/前缀的客户端逻辑都可能踩到「官方永不出现」的分支；②UUID/随机：客户端要 `long`，且可读性归零 |
| **D2** | 主身份键 | `dev_id`（`Account_Auth.DevId`），唯一键；`sdk_token` 只记录不鉴权 | Token 会轮换（SDK 重新登录就变），DUID 重装会变；DevId 是三者里最稳定的。**用 Token 当键 = 每次轮换生成一个新账号 + 进度全丢** | 用 Token 当键（错，见左）；用 `(DevId,DUID)` 复合键（重装就登不回去） |
| **D3** | 每用户状态存储 | **`account_blobs`：`server_id`+`kind`+`payload`(JSON)**，40 个状态块聚成 21 个 kind | 41 个状态块里 32 个只有 ≤4 个字段、且永远整块读写 → 开 32 张表意味着 32 套 DDL/迁移/代码，收益为零。聚成 21 个 = 「谁在写」的粒度，正好等于写入事务边界 | ①一子系统一表（太散，DDL 爆炸）；②一账号一行大 JSON（两个并发协议 load-modify-save 会互相覆盖；`Characters` 和 `Items` 同时写必丢一边） |
| **D4** | 会话生命周期 | **30 天 TTL** + `revoked` 标记 + **每账号默认 1 个活跃会话** | Shittim 的 `PurgeExpiredSessions` 有实现**零调用点** ⇒ 会话永不过期、重启靠 `sessions.json` 回灌。私服长期跑，永不过期的 token 等于永久凭据泄漏。30 天 = 休闲玩家不会掉线，泄漏的 token 也不会永久有效。「1 个活跃」对齐官方 `AddOrUpdate(UserId,…)` 的顶号语义 | ①永不过期（照抄 Shittim，安全性差）；②短 TTL（10 分钟）需要客户端有 refresh 机制——**客户端没有**，只能靠重新走 1002，会打断游戏 |
| **D5** | 时间字段 | 统一 `YYYY-MM-DDTHH:MM:SS` 文本，**只在 `to_iso()` 一处产出** | 协议 `DateTime` 是无时区语义；`str(datetime.now())` 会给 `2026-11-14 14:53:07.123456`（带空格+微秒），`isoformat()` 会带 `+00:00`，两种都被客户端 DateTime 解析挑食。产物要可 diff（`account_state.*.json` 用 `frozenTime` 固定值就是为了这个） | 存 `TIMESTAMP`/`epoch`：多一层时区换算，且出包还得转回文本 |
| **D6** | AccountDB 存储 | 22 字段**全部列化**进 `accounts` | AccountDB 在每次 `Account_Auth/1001/1017` 都要整份吐出去；列化后 `build_account_db_for()` 只需 1 次主键查询（无 blob 解析、无 JSON 拼装），且宝塔面板里能直接 `WHERE level>50` / `ORDER BY last_login_at` 看人 | 塞进 blob（每次握手多读一个 blob + 反序列化；面板里看不到人） |
| **D7** | 账号内实体 id | `accounts.next_entity_id` 单游标；号段 = `1_000_001 + (账号序号 % 1000) × 100_000` | `CharacterDB.ServerId` / `CafeDBId` / `ItemDB.ServerId` 都是「账号内唯一」的实体主键，值是 **7 位小数字**（官方 1000001 量级）。每账号从 **1000001** 起（= 已验证模板的取值），第 2 个用户从 1100001 起。**取模 1000** 是为了让 id 不超过 `1.0e8 < 2^31`：若直接用 `server_id` 序号做乘数，迁移那个 `10015354380` 会算出 `1.5e13` 的 13 位实体 id，任何客户端 int32 截断都会踩到官方永不走的分支。代价 = 跨账号唯一性以 1000 个账号为周期（**账号内唯一始终成立**，那才是协议要求的） | ①全表共享一个自增序列（id 会跑到百万级，且看不出归属）；②直接用 server_id 乘积（13 位，见左） |
| **D8** | 发号实现 | `id_alloc` 表 + `SELECT` 后 `UPDATE … WHERE next_id=?`（CAS）+ 重试 | AUTO_INCREMENT 的起始值只能靠 DDL 属性维护（改一次库丢一次）；SQLite 没有可移植等价物；而发号必须能**和「建账号+写 21 个 blob」同事务回滚** | AUTO_INCREMENT（见左） |

**另外 5 列（服务端自用，不进 AccountDB）**：

| 列 | 类型 | 为什么需要 |
|---|---|---|
| `device_unique_id` | VARCHAR(64) NULL | 32 位 hex 设备指纹。**不唯一**（一部手机可以有两个账号），只用于「换机了但 DevId 一样」这类怪事的排查线索 |
| `sdk_token` | VARCHAR(128) NULL | 最近一次见到的 SDK token（40 位 hex）。会轮换；`require_token_stable=1` 时才当作拒登依据 |
| `next_entity_id` | BIGINT | 账号内实体 id 发号游标（D7） |

| `login_count` | INT UNSIGNED | 累计 auth 次数。首登=1；用来区分「新建」和「回读」，也是 D7/迁移自检的观测点 |

索引：`uk_dev_id`（唯一，登录唯一入口）、`idx_device_unique_id`、`idx_publisher_account_id`、`idx_last_login_at`（"最近活跃"排序）、`idx_nickname`（面板里按名字搜人）。
约束：`CHECK (server_id >= 10000000000)` —— **把 D1 写进数据库**，任何从 1 开始的实现会当场写入失败（SQLite 的 `INTEGER PRIMARY KEY` 对 NULL 会自动编号成 1、2、3，这条 CHECK 正好把这个坑也堵上）。

### 1.4 `sessions`（8 列）

| 列 | 类型 | 说明 |
|---|---|---|
| `mx_token` | `CHAR(36) ascii_general_ci` **PK** | 36 字符小写 GUID。ascii + CI 排序规则 + 代码里统一 `lower()` ⇒ 等价于 Shittim 的 `StringComparison.OrdinalIgnoreCase` |
| `server_id` | BIGINT + FK(CASCADE) | 归属账号 |
| `issued_at` / `expires_at` | DATETIME | 签发 / 过期（`issued_at + ttl`） |
| `last_seen` | DATETIME NULL | 每次 `resolve_session()` 成功时刷新（滑动活跃度） |
| `revoked` | TINYINT(1) | 1=已撤销（`Account_InvalidateToken(1016)` 或顶号） |
| `client_ip` | VARCHAR(45) NULL | 签发来源（IPv6 够用） |
| `note` | VARCHAR(255) NULL | 如 `proto/1002`，排障时知道是哪个协议发的 |

为什么 `mx_token` 是主键而不是 `server_id`：同一账号可以有 N 行（历史会话 + 被别人顶掉的），查询入口却永远只有 token 一个。

### 1.5 `account_blobs`（6 列）+ 21 个 kind

| 列 | 类型 | 说明 |
|---|---|---|
| `server_id` + `kind` | BIGINT + VARCHAR(32) **复合 PK** | kind 见下表 |
| `payload` | LONGTEXT（MySQL）/ TEXT（SQLite） | **JSON 对象**：`{状态块名: 值}` |
| `revision` | BIGINT | 每次写 +1；`save_blob(expected_revision=N)` 用它做乐观锁 |
| `updated_at` | DATETIME | 最后写入时间 |
| `updated_by` | VARCHAR(64) | 写入方（协议名/`bootstrap`/`import:xxx`），追责用 |

### 1.6 另外三张表

**`protocol_log`（8 列）**：`id` / `server_id` / `protocol` / `started_at`(毫秒) / `duration_ms` / `resp_bytes` / `status` / `note`。
**故意不做外键、故意不存请求响应正文**：日志在热路径上，不想为了写日志去校验账号存在；正文里有 SessionKey/Token，落盘等于把凭据写进日志。

**`id_alloc`（2 列）**：`name` / `next_id`。当前只有 `('server_id', 10000000000)` 一行，留扩展位。

**`schema_meta`（2 列）**：`k` / `v`，存 `schema_version=1`、`server_id_base=10000000000`。服务启动读版本号，低于自己支持的版本**报错而不是带着半个结构跑**。

### 1.8 SQLite ↔ MySQL 方言差异（代码里逐处处理）

| 项 | MySQL | SQLite | 代码处理 |
|---|---|---|---|
| 自增 | `AUTO_INCREMENT` | `INTEGER PRIMARY KEY`（rowid 别名） | 只有 `protocol_log.id` 用；其余全部显式发号（D8） |
| 整数/时间类型 | `BIGINT` / `DATETIME` | `INTEGER` / `TEXT` | 时间统一存 ISO 文本，读出来 `to_iso()` 兼容 str 与 datetime |
| 占位符 | `%s` | `?` | SQL 只写 `?`，`_adapt()` 在 mysql 下替换 |
| Upsert | `ON DUPLICATE KEY UPDATE` | `ON CONFLICT … DO UPDATE SET … = excluded.…` | `_upsert_blob()` 两分支 |
| 严格类型 | 默认严格模式 | 需 `STRICT` 表（3.37+） | SQLite DDL 全表 `STRICT`，把「往 INTEGER 塞 TEXT」提前到写入时报错 |
| 外键 | 默认开 | 默认关 | 连接时 `PRAGMA foreign_keys=ON` |
| 并发 | InnoDB 行锁 | WAL + `BEGIN IMMEDIATE` | `transaction()` 按方言选 BEGIN 形态 |
| `COMMENT` / `ENGINE` | 支持 | 不支持 | 只在 MySQL DDL 里写注释 |

## §2 服务层（`work/ba/server/account_service.py`）

### 2.1 依赖与形态

- **纯标准库**：`sqlite3` / `uuid` / `json` / `hashlib` / `base64` / `datetime`。MySQL 模式需 `pip install pymysql`（可选）。
- 一个 `AccountService` 实例管一个库；**连接是 thread-local**（多线程网关每个线程一条连接、WAL 允许并发读），写操作走显式事务。
- 模块级还有 7 个同名函数（`identify` / `get_or_create_account` / …）委托给默认实例，`configure(db_path=…)` 换实例。

### 2.2 对外契约

| 函数 | 输入 | 输出 | 异常/边界 |
|---|---|---|---|
| `identify(req)` | `dict` / JSON `str` / `bytes`（已解密的请求明文） | `Identity(dev_id, device_unique_id, token, publisher_account_id, dev_id_source, protocol, counter, raw)` | `AuthRejected`：既无 `DevId` 又无 `DeviceUniqueId`（没有稳定身份就**拒绝建号**，否则每次 token 轮换都变新号） |
| `get_or_create_account(identity, record_login=True)` | `Identity` | `Account`（27 字段 dataclass） | 并发首登靠 `UNIQUE(dev_id)` 兜底：插入失败→回查→继续；`require_token_stable=1` 且 token 变了→`AuthRejected` |
| `issue_session_key(account, client_ip=None, note=None, ttl_seconds=None)` | `Account` | `SessionKey(account_server_id, mx_token)`，`.to_dict()` = `{"AccountServerId":…,"MxToken":"…"}` | 同账号超出 `max_active_sessions` 时把旧的置 `revoked=1` |
| `resolve_session(mx_token, touch=None)` | 任意 | `Account` 或 `None` | 大小写不敏感、容忍首尾空格；`revoked`/过期/不存在 → `None`（**不抛异常**，网关按「未登录」处理） |
| `load_blob(server_id, kind)` | int, str | `dict` 或 `None` | 未知 kind → `ValueError`（防拼错产生垃圾桶） |
| `save_blob(server_id, kind, payload, expected_revision=None, updated_by=None)` | int, str, dict | 新 `revision` | `expected_revision` 不符 → `BlobConflict`；payload 里出现该 kind 不允许的键 → `ValueError` |
| `build_account_db_for(account)` | `Account` | 22 键 dict（顺序 = schema 顺序） | 纯函数，不查库 |

配套（不是契约但也公开）：`build_state_for()` / `bootstrap_state()` / `import_state()` / `create_account_at()`（按指定 `server_id` 建号，迁移用）/ `alloc_entity_ids()` / `update_account()` / `record_login()` / `revoke_session()` / `revoke_all_sessions()` / `list_sessions()` / `log_protocol()` / `stats()` / `delete_account()` / `wipe()` / `get_account()` / `get_account_by_dev_id()` / `list_accounts()` / `blob_kinds()`。

### 2.4 `server_id` 分配（D1 的落地细节）

```python
# account_service.py::_alloc_server_id
for _ in range(50):
    SELECT next_id FROM id_alloc WHERE name='server_id'   (+ FOR UPDATE on MySQL)
    nxt = max(next_id, config.server_id_base)
    UPDATE id_alloc SET next_id = next_id + 1 WHERE name='server_id' AND next_id = ?
    if rowcount == 1: return nxt
```

- **在哪发**：`_create_account()` 的同一个事务里（`BEGIN IMMEDIATE` / InnoDB 事务）。失败就整个回滚，号码一起回退，不会留空洞语义（空洞无害但会让「下一个号」不可解释）。
- **并发**：读→改是 CAS（`WHERE next_id = 读到的值`），冲突就重读，最多 50 次。SQLite 侧 `BEGIN IMMEDIATE` 直接先拿写锁，MySQL 侧 `SELECT … FOR UPDATE` 锁行。
- **可配置**：`Config.server_id_base` / 环境变量 `BA_SERVER_ID_BASE` / CLI `--server-id-base`。数据库侧还有 `CHECK (server_id >= 10000000000)` 兜底 —— **改了基数低于 1e10 就必须连 CHECK 一起改**，这是故意的摩擦。
- **为什么不是「查 MAX+1」**：删号会让 MAX 回退，两个已删号的区间会重用，出现「老客户端拿着旧 server_id 正好登进新账号」的鬼故事。`id_alloc` 只增不减。

### 2.5 实体 id 分配（D7）

```python
ordinal    = server_id - server_id_base
band       = ordinal % 1000                                    # ENTITY_ID_BANDS
next_entity = entity_id_base + band * entity_id_stride         # 1000001 + band×100000
alloc_entity_ids(server_id, n)   # 事务内 SELECT next_entity_id → UPDATE next_entity_id += n
```

实测数字：

| 账号 | `server_id` | 学生 ServerId | 咖啡馆 CafeDBId | `next_entity_id` |
|---|---|---|---|---|
| 第 1 个（band 0） | 10000000000 | 1000001 / 1000002 / 1000003 | 1000004 | 1000005 |
| 第 2 个（band 1） | 10000000001 | 1100001 / 1100002 / 1100003 | 1100004 | 1100005 |
| 迁移的历史号（band 380） | **10015354380** | 1000001…（**导入时保留原值**） | 1（保留） | **39000005** |

- 首登时 `bootstrap_state()` 吃掉 4 个 id（3 学生 + 1 咖啡馆），**必须**立刻把游标写回 `accounts.next_entity_id`（`_create_account` 里的 `UPDATE`），否则第一次 `alloc_entity_ids` 会撞到学生身上 —— 自检第 14 步专门盯这个。
- `> 2^31` 会直接抛 `AccountServiceError`（防止有人把 `entity_id_stride` 配得太肥而静默产出 10 位 id）。
- 迁移已有状态时（`import_state`）**不重排**学生 id，而是扫出已用的最大 id 把游标推过去（§4.2 实测 `max_entity_id_seen=1000003`）。

### 2.8 时间策略（D5）

| 场景 | 做法 |
|---|---|
| 产出 | 只有 `to_iso()` 能产出时间串：`datetime` → `YYYY-MM-DDTHH:MM:SS`（去 tz、去微秒）；`str` → `normalize_iso()` 归一 |
| 读入 | 库里可能是 `str`（SQLite）或 `datetime`（pymysql），`to_iso()` 两者都吃 |
| 「现在」 | `now_naive()` = `datetime.now()` 无 tz。自检/可复现时用 `--frozen-now 2026-11-14T12:00:00` 固定 |
| 客户端看到的时钟 | 不走这些字段，走 `ServerTimeTicks`（由 `state._meta.frozenTime` 换算）。**线上必须传 now**，否则客户端时钟/倒计时冻住（§3.7 陷阱 1） |
| 哨兵 | `BirthDay` 未设置 → `1970-01-01T00:00:00`；其余可空字段 → `null` |

### 2.9 会话策略（D4）

| 项 | 选择 | 理由 |
|---|---|---|
| 格式 | `str(uuid.uuid4()).lower()` = 36 字符带连字符小写 | 与 Shittim `Guid.NewGuid().ToString()` 同形态；客户端只存不解析（§5-1），但保持官方形态零风险 |
| TTL | 30 天（`BA_SESSION_TTL` 可调） | 见 D4 |
| 顶号 | `max_active_sessions=1`（默认）→ 新会话签发时把同账号其它活跃会话置 `revoked=1` | 对齐官方 `AddOrUpdate(UserId, …)`「一个用户一个 session」；调成 0 = 不限（手机+平板同时玩） |
| 校验 | 3 条件：`mx_token` 命中 → `revoked=0` → `expires_at > now` | 与 Shittim `GetAuthenticatedUser` 的 3 条等价，多一条过期（它没有） |
| 大小写 | 写前 `lower()`、查前 `lower()` | 等价 `OrdinalIgnoreCase` |
| 撤销 | `revoke_session(token)` / `revoke_all_sessions(server_id)` | 供 `Account_InvalidateToken(1016)` 调用 |
| 刷新 | `resolve_session()` 成功时写 `last_seen` | 活跃度可观测；`touch_session_on_resolve=False` 可关（高频时可省一次写） |

### 2.10 鉴权边界（必须说清）

**这套东西的身份校验强度 = 「知道 DevId 就能登这个号」。**

- `Token` 我们**无法验证**：验证要向 Nexon/Yostar SDK 发请求，而本任务的硬约束是不连网/不连服务器。所以 `sdk_token` 只是「记录 + 变化告警」，不是凭据。
- `MxToken` 是**会话标识**而不是强凭据（36 字符 GUID，泄露即可冒用）。
- 可选加固（已实现，默认关）：`require_token_stable=1` —— 已记录过 token 的账号，来一个不同的 token 就 `AuthRejected`。
- 未来要做真鉴权，只有两条路：① 引入自己的密码/PIN 列 + 客户端侧无法配合（客户端没有输入框）⇒ 实际只能 ② 白名单（`accounts` 加 `enabled` 列或独立 `allowlist` 表），以及 ③ 把 `device_unique_id` 首次绑定后要求一致。
- 本设计的定位：**局域网/朋友间私服够用**；公网开放前必须补白名单（§6 P1）。

### 2.11 blob 读写与乐观锁

```python
payload = load_blob(sid, 'items')                       # {'items': [...], 'expiryItems': [...]}
rev     = load_blob_with_meta(sid,'items')['revision']  # 1
save_blob(sid, 'items', new_payload, expected_revision=rev)   # → 2；别人先改过则 BlobConflict
```

- **kind 白名单**：`save_blob` 拒绝未知 kind、拒绝 payload 里出现该 kind 不允许的键 —— 防止「`items` 里塞了个 `character`」这种静默数据污染。
- **revision**：`save_blob` 无 `expected_revision` 时是盲写（`revision+1`）；给了就变 CAS。
- **读**：`load_blob` 返回 `None`（没有该行）或 `dict`；`build_state_for(strict=True)` 才会把「缺 kind」当错误，默认用模板兜底（老账号升级友好）。

## §3 与响应构造层对接

### 3.1 数据流

**可以直接用骨架（与账号无关）：** 24000 段（战斗/静态表）、`Account_GetTutorial(1005)` 这类尚未建模的进度位、以及所有「返回静态 Excel 数据」的协议。判据很简单：**这个响应里有没有 `AccountId` / `ServerId` / `AccountServerId` 之一**——有就必须定制。

### 3.3 `SessionKey` + `AccountId` 必须单独处理

三个事实叠在一起：

1. `SessionKey` 只属于 `BasePacket`，而我们 schema 的 v1 把 `ResponsePacket` 当根 ⇒ **整层缺失**（`report/76 §2.5` 已论证）。
2. `AccountId` **不是字段**，是 `BasePacket` 的计算属性 `SessionKey?.AccountServerId ?? 0` ⇒ 任何「按字段表生成」的生成器都产不出它。
3. `build_response.Schema.fields()` 只沿 base 链走**一层**：即使换成 `dto_schema_full_v2.json`（`BasePacket` 存在），`SessionKey/OSType` 也不会被展开 ⇒ **v1/v2 都得补**（本机两条都实测过：34 键，补后 36 键）。

```python
def inject_session(packet, session_key):        # example_auth_flow.py
    packet = dict(packet); packet.pop('OSType', None)   # OSType 是请求侧字段
    want = session_key.to_dict()                        # {'AccountServerId':N,'MxToken':'…'}
    if packet.get('SessionKey') == want and packet.get('AccountId') == session_key.account_server_id:
        return packet                                    # 引擎已发对（factory）→ 幂等返回
    packet['SessionKey'] = want
    packet['AccountId'] = session_key.account_server_id
    return packet
```

**反向也要做**：非账号握手协议（1017 等）**不能**带这两个键 —— 官方 `ShouldEchoSessionKey` 白名单只有
`CheckNexon / Auth / ProofToken_*`，其余响应是「两个键都不存在」（不是 null）。示例里显式 pop（§3.7 陷阱 3）。

### 3.5 写回协议（请求里的值必须落库）

| 协议 | 请求字段 | 落库 | 备注 |
|---|---|---|---|

**不做写回会怎样**：客户端改名成功、界面显示新名，但下次 1002 拿回旧名 → 玩家会认为"改名没生效/被回档"。

### 3.6 性能（本机实测，SQLite / 200 账号 / 4 200 blob / 2.0 MB 库）

| 操作 | SQL 次数 | 实测 |
|---|---|---|
| 建账号（含 21 个 blob，一个事务） | 1 SELECT + (1 SELECT + 1 UPDATE + 1 INSERT + 21 upsert) | **0.74 ms** |
| `build_state_for()`（41 键） | 1 SELECT(accounts) + 1 SELECT(21 行 blob) | **0.22 ms** |
| `resolve_session()` | 1 SELECT(join) + 1 UPDATE(last_seen) | **0.08 ms** |
| `load_blob()` | 1 SELECT | **0.01 ms** |
| 一次 1002 全流程 | 上面 ①②③④ + 1 INSERT(日志) | **≈ 1 ms 量级** |

> 单写者（SQLite `BEGIN IMMEDIATE`）的写吞吐是天花板；并发读走 WAL 不受影响。
> 换 MySQL/InnoDB 后行锁更细，但会有网络往返，量级取决于链路，**未实测**（§5-11）。

可以省的：`build_state_for()` 现在一次取全部 21 块（登录同步要全量）；如果只想发 `Character_List(2000)`，
直接 `load_blob(sid,'characters')` 就够，不要走 `build_state_for()`。

### 3.7 陷阱清单（都会真的炸）

1. **`_meta.frozenTime` 必须是 now**。`account_state.*.json` 里固定成 `2026-11-14T00:00:00` 是为了产物可 diff；线上照抄会让 `ServerTimeTicks` 冻结 ⇒ 客户端时钟、倒计时、任务刷新全乱。`build_state_for()` 默认写 `now_iso()`，**不要**手工传 `frozen_time`。
2. **1017 子回包的 `ServerTimeTicks` 要是 0**。`build_response.build_login_sync()` 已经这么做了（Shittim 实测），自己拼的时候别忘了。
3. **非握手协议不要带 `SessionKey/AccountId`**。带 `null` 和"键不存在"在客户端是两种不同的反序列化路径。
4. **`validate()` 要在注入 SessionKey 之前跑**。`build_response.validate()` 会把 `SessionKey/AccountId` 判成"多余键"（schema 里没有）。
5. **同一份数据只能有一个写入方**。如果网关自己改了响应里的 `Nickname` 却没 `update_account()`，下次登录就"回档"（§3.5）。
6. **`update_account()` 之后必须重读**。它返回新 `Account`，但调用方手里的旧对象不会自动更新；`build_state_for()` 默认 `refresh=True` 就是为了兜住这个（自检第 19 步就是踩过这个坑才加的）。
7. **不要用 `str(datetime)` 直接出包**。见 D5。

## §4 迁移与兼容

### 4.1 现有硬编码 `ServerId=10015354380` 怎么处理

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A. 直接弃用 | 删掉硬编码，所有人新号从 10000000000 起 | 最干净 | 客户端本地存档按 `AccountServerId` 命名（`10015354380ClientOption.save` …），换号 = 本地设置/选项全部"重置"（服务器进度在库里，不丢） | 只有确认没人在玩这个号才可 |
| B. 原值入册 | `create_account_at(identity, 10015354380)` → 这个真号作为**库里的一行**存在 | 存档前缀对得上；后续用户从 10015354381 起 | 需要发号器跳过这个号（已实现 `_bump_allocator`） | **推荐** |
| C. 状态导入 | 再叠一步 `--import-state` 把现有 `account_state.seeded.json` 灌进去 | 学生/货币/进度原样保留 | 依赖状态文件是最新的 | **推荐（B+C）** |

**推荐组合 = B + C**：一条命令 `--import-state ... --dev-id <当前设备> --force-server-id 10015354380`。
**代码里不再出现这个数字**是本节的核心目标 —— 它只是库里的一行，之后所有用户（包括它）都走同一条
`get_or_create_account` 路径。

> 注意：`10015354380 = 1.0015e10 > 1e10` ✓ 天然满足 `CHECK(server_id >= 10000000000)`。
> 如果你要迁移的号比 1e10 小（例如早期测试的 `1`），`_create_account` 会直接拒绝并提示：
> 必须先改 `server_id_base` 并把 DDL 里的 CHECK 一起 DROP 掉（这是故意的摩擦，见 D1）。

### 4.4 宝塔面板里怎么管

**建库**：宝塔 → 数据库 → 添加数据库（字符集 `utf8mb4`，排序 `utf8mb4_general_ci`）→ 选中库 → 导入 → 上传 `schema_mysql.sql`。
（服务层自己建也行：`python account_service.py --init-db --dialect mysql --db ba_accounts`，需要库已存在 + `pip install pymysql`。）

**面板里会出现的 6 张表**：

| 表 | 面板里能直接干的事 |
|---|---|
| `accounts` | **看人**：`server_id`/`dev_id`/`nickname`/`level`/`last_login_at` 都在列里，可按等级排序、按昵称搜 |
| `sessions` | 看谁在线（`revoked=0 AND expires_at>now()`）、踢人（把 `revoked` 改成 1） |
| `account_blobs` | 改某个人的状态（**先备份该行**；`payload` 是 JSON，面板的"编辑"能直接改，但建议用 `--dump-state` 改完再导回） |
| `protocol_log` | 「某人 1002 报错」「1017 最近变慢」 |
| `id_alloc` | 看下一个可发的 `server_id`。**不要手工调小**（会撞已发号） |
| `schema_meta` | 看结构版本 |

**常用查询**：

```sql
-- 最近登录的 20 个人
SELECT server_id, nickname, level, last_login_at FROM accounts ORDER BY last_login_at DESC LIMIT 20;
-- 谁在线
SELECT a.server_id, a.nickname, s.issued_at, s.last_seen FROM sessions s
 JOIN accounts a ON a.server_id = s.server_id
 WHERE s.revoked = 0 AND s.expires_at > NOW();
-- 踢掉某人所有会话
UPDATE sessions SET revoked = 1 WHERE server_id = 10000000000 AND revoked = 0;
-- 某人的学生数（JSON 里数一下）
SELECT JSON_LENGTH(payload->'$.characters') AS students FROM account_blobs
 WHERE server_id = 10000000000 AND kind = 'characters';   -- MySQL 5.7+/8.0
-- 某协议最近 100 次耗时
SELECT started_at, duration_ms, resp_bytes, status FROM protocol_log
 WHERE protocol = 1017 ORDER BY id DESC LIMIT 100;
```

**备份**：宝塔 → 数据库 → 备份（计划任务每天一次）。逻辑备份时 `account_blobs.payload` 是文本，`mysqldump` 完全可读；
**增量技巧**：只导最近改过的块（`WHERE updated_at > 昨天`），因为 `account_blobs` 有 `idx_account_blobs_updated_at`。

**权限**：给面板建一个只读账号查数据，服务层用另一个只有 `SELECT/INSERT/UPDATE/DELETE`（无 `DROP/ALTER`）的账号；DDL 用管理员账号单独跑。**别**让服务账号有 `DROP` 权限——一个参数写错就能把 21 万行 blob 清空。

## §5 诚实标注：哪些是实测，哪些是推断

| # | 事项 | 状态 | 依据 / 残留风险 |
|---|---|---|---|
| 1 | **客户端会不会校验 `MxToken` 格式** | **[推断]** 不校验 | 依据：`report/76 §1.4` 源码显示客户端只是"存在本地→每条请求原样回填"，服务端 `GetAuthenticatedUser` 只做 `OrdinalIgnoreCase` 字符串比较。**但客户端 IL2CPP 侧没有反编译证据**。我们的选择（严格 36 字符小写)是"即使它校验也过"的安全选择 |
| 2 | `AccountState=1` 的含义 | **[推断]** | 枚举数值含义未解（`report/68 G3`：metadata 的 `fieldDefaultValues` 段仍加密）。沿用 `account_state.json` 里客户端已接受过的 1，且 `build_response --protocol 1002` 一直跑通 |
| 3 | 3 个初始学生的 `UniqueId` 存在于 `CharacterExcel` | **[推断]** | `ids.json.students` 里确有 10010/10000/10001（278 条真实 id），但**本地没有 CharacterExcel 表**，无法离线证明这 3 行存在。若客户端在"找不到 excel 行"处中断，改 `account_template.json` 的 `characters` 段即可（不影响代码） |
| 4 | `cafe.CafeId/CafeRank = 1` | **[推断]** | seeded 用的假设值，需与 CafeExcel 对齐（`report/68 G5`） |
| 5 | `friendCode` 的格式 | **[推断]** 只对齐长度 8 | 模板是 `"BASERVER"`（8 位）。官方真实格式（是否校验字符集/校验位）未知。我们用 base32 去掉了易混字符 `0/1/8/9` |
| 6 | `auth.EncryptedUID` 是每账号还是全服 | **[未知]** | 27 字符串，算法未知。当前**全服同值**（存在 `auth` blob 里，将来只要改行数据）。若客户端拿它做反作弊/防重放校验会出问题——没有证据表明它会 |
| 7 | `SessionKey` 在国服由 `Account_Auth` **签发**（而非回显） | **[推断]** | `report/76 §1.3` 已论证：国服无 CheckNexon（客户端 5 个协议里没有 1009/1014），请求里 `SessionKey:null` ⇒ 只剩"签发"一个自洽解 |
| 8 | `PublisherAccountId == DevId` | **[推断]** | 只有一次抓包（`314816420` 两边相同）。代码里"有 `PublisherAccountId` 就用它，否则若 DevId 是纯数字就用 DevId"，两边都能自洽 |
| 9 | `AccountDB.DevId` 该发什么形态 | **[推断]** | 发 `dev_id` 原值。若 `DevId` 缺失、我们用 `duid:<hash>` 合成身份键，则 AccountDB.DevId 会是 `duid:...` 形态（官方是数字串）。客户端目前只在 Account_Auth 请求里带自己的 DevId，不读响应里的这个字段——但**未证**。真机验证一次即可确定 |
| 10 | 会话 TTL 30 天 | **[本设计自定]** | 官方无此概念（Shittim 永不过期）。30 天是我们加的，属于行为差异不是兼容问题 |
| 11 | MySQL 侧**未实跑** | **[未验证]** | 本机没有 MySQL 服务、没有 `mysql` CLI、没有 `pymysql`。DDL 是按方言手写的，SQLite 侧 24 条语句全绿；MySQL 特有语法（`AUTO_INCREMENT=`、`JSON_LENGTH`、注释）未执行过。**首次导入宝塔后用 `--init-db` + `--stats` 复核** |
| 12 | `Token` 无法验证 | **[事实]** | 需要联 SDK 服务器，本任务禁止联网。故 `sdk_token` 不是凭据（§2.10） |
| 13 | `RetentionDays` / `VIPLevel` / `UnReadMailCount` 的业务含义 | **[未知]** | 只保证类型（`int?`）和值域与模板一致（1/0/0），语义未解 |
| 14 | 并发压测 | **[未做]** | 并发首登的 `UNIQUE` 冲突回查路径有代码但未做多线程压测；SQLite 侧 `BEGIN IMMEDIATE` 是串行写，QPS 上限取决于单写者（本机未测，只测了单线程延迟：§3.6） |
