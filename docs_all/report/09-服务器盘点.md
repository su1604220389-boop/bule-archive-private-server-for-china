## 6. A / B / C 三问回答

### A. 让「客户端能登录 + 拿到网关地址」最少要起哪几个进程

**三个（其中一个已在跑）**，且**没有依赖顺序上的强耦合**，只有端口先后：

| # | 进程 | 端口 | 作用 | 启动前置 |
|---|---|---|---|---|
| 1 | **nginx** | 80/443 | 443 SNI 分流（`*.bluearchive-cn.com→5000`）+ `/sdk/→8080` | ✅ **已在运行** |
| 2 | **`sdkcard.py`** | `127.0.0.1:8080` | SDK 登录第一跳：`/common/config`→`/user/quick-login`→拿 `Data.User.Token` | 无（纯 python3 标准库） |
| 3 | **Shittim**（单进程） | `0.0.0.0:5000`（API）+ `0.0.0.0:5100`（Gateway） | `/api/gateway` 协议分发、连接组下发 | `DOTNET_root`、`DOTNET_gcServer=0`、GC 堆上限、5000/5100 空 |

**建议启动顺序**：`nginx 确认 → sdkcard.py → Shittim`
理由：客户端发起序是「先 SDK 登录拿 token，再找游戏服务器」；nginx 只做转发，无状态。

**不需要起的**（本机已没有这些文件）：`tlsproxy.py`(9443)、`connectproxy.py`(8443)、`cdnproxy.py`(9444)。TLS 终止已由 nginx 承担。

**关键澄清（源码实证）**：5000 与 5100 **由同一个进程、同一张路由表**服务。
`CLI/GameServer.cs:160-174`：
```csharp
options.Listen(IPAddress.Any, apiPort);          // 5000
if (gatewayPort != apiPort) options.Listen(IPAddress.Any, gatewayPort);  // 5100
```
`Program.cs` 只有 `MapControllers`，没有按端口分流。
→ **`POST /api/gateway` 在 5000 和 5100 上都通**；两端口只是给客户端「ApiUrl / GatewayUrl」用的两个门牌号。
→ 另：代码会在 `../../certs/selfsigned_cert.pem` 存在时**额外监听 443**；该文件不存在 → 日志 `HTTPS on port 443 disabled (no certificate)`，443 由 nginx 独占，**不冲突**。

### C. `/api/state` 有没有实现

**没有。源码级确认，不是"没找到"。**

### 9.6 关于 D02（连接组地址）的源码级结论 —— 比预想更麻烦

`Configuration/Config.cs` 的三段逻辑把公开地址这条路堵死了：

```csharp
// :237  两个地址都是从 HostAddress + 端口拼的
private static string GetApiUrl() => $"http://{HostAddress}:{HostPort}/api/";
// :242
private static string GetGatewayUrl() => EnableGateway ? $"http://{HostAddress}:{GatewayPort}/api/" : "";

// :111-117  Save() 时强制把地址钉回 loopback
private static void ApplyLocalhostAddress() { HostAddress = LocalhostAddress; ... }

// :199-201  只要任何一个组的 URL 非空 → 整份配置重建为官方默认
if (connectionGroups.Any(HasConfiguredConnectionUrl)) return CreateServerInfoConfig();
```

因此：
- ❌ 手改 `ServerInfoConfig.json` 里的 URL → 被 `ApplyGatewayMode` **重置**
- ❌ 改 `Config.json` 的 `HostAddress` → 被 `Save()` 的 `ApplyLocalhostAddress()` **钉回 127.0.0.1**
- ❌ 改成公网 IP 也没用：**5000 端口被安全组挡着**（§9.4），而放行端口属于禁止项
- ✅ **唯一不碰源码、不碰防火墙的做法：在 nginx 侧改写响应体**。本机 nginx 编译带
  `--with-http_sub_module` **且** `--add-module=…/ngx_http_substitutions_filter_module`，可直接：

```nginx
# ba_mitm.conf 内的 server 块中
location /com.nexon.bluearchive {
    proxy_pass http://127.0.0.1:5000;
    proxy_set_header Host $host;
    sub_filter 'http://127.0.0.1:5000/api/' 'https://gsqc-api.bluearchive-cn.com/api/';
    sub_filter 'http://127.0.0.1:5100/api/' 'https://gsqc-api.bluearchive-cn.com/api/';
    sub_filter_once off;
    sub_filter_types text/plain application/json;
}
```
（`ba_mitm.conf` 现在没有 `location /` 之外的分支，加这一段不影响既有转发。）

同理，**将来若走 `/api/state` 方案，`Servers` 里直接写死 `https://gsqc-api.bluearchive-cn.com/api/` 即可，不受上述限制。**

> 理由：连接组 URL 是 loopback 这件事，只有在「客户端已经打到我们服务器」之后才会暴露；现在第一层（客户端解析官方域名 + 官方 IP）都还没通，先解决第二层没有意义。

### 11.3 两个 SNI 是不是同一个 `location`？—— **是，已用配置 + 运行时双重证明**

**证明一（配置层）**：`nginx -T` 展开后，`state-api` 与 `gsqc-api` **在同一个 server 块里**：

```
nginx -T 展开行号：
 390:  server_name gs-api.bluearchive-cn.com gsqc-api.bluearchive-cn.com state-api.bluearchive-cn.com
                  *.bluearchive-cn.com bluearchive-cn.com;
 395:  access_log /www/wwwlogs/ba_mitm.log;

```

一个 `server_name` 指令列出全部域名 → nginx 按 SNI 命中**同一个 server 块** → 共用同一张 location 表。

`add_header Cache-Control "no-store";` **只写在 `location = /api/state` 里**，`location /` 没有。
所以响应头里有没有 `Cache-Control` 就是「命中哪个 location」的判别器：

| 请求 | HTTP | `content-type` | `cache-control` | 判定 |
|---|---|---|---|---|
| `gsqc-api…/api/state` | 200 | `application/json` | **`no-store`** | ✅ 命中 `location = /api/state` |
| `state-api…/api/state` | 200 | `application/json` | **`no-store`** | ✅ 命中 `location = /api/state` |
| `gsqc-api…/api/gateway`（对照） | 200 | 空 | **无** | ✅ 落回 `location /` → 5000（Shittim） |

→ **结论：两个 SNI 命中的是同一个 `location = /api/state`，不是巧合。**
（注意 `ba_mitm.conf` 里**只有** `location /` 和 `location = /api/state` 两个 location，没有 `^~ /`；

### 11.6 登录取证采集器（**已常驻运行**）

**位置**：`/root/ba_watch/watch.sh`　**输出**：`/tmp/ba_watch.log`　**启动方式**：`setsid nohup`（不占 shell，SSH 断开不影响）

脚本内容（与 Lead 给的单行版本等价，但补了两处必要修正）：

```sh
#!/bin/sh
# BA 登录取证采集器：同时盯 bluearchive 系(ba_mitm.log) 与 example.com(example.com.log)
PAT='"(GET|POST) /(sdk/)?(common/config|user/(quick-login|login|detail)|api/state)'
tail -F -n0 /www/wwwlogs/ba_mitm.log 2>/dev/null \
  | grep --line-buffered -E "$PAT" \
  | while IFS= read -r l; do echo "$(date +%H:%M:%S) [mitm] $l"; done &
tail -F -n0 /www/wwwlogs/example.com.log 2>/dev/null \
  | grep --line-buffered -E "$PAT" \
  | while IFS= read -r l; do echo "$(date +%H:%M:%S) [xlcx] $l"; done &
wait
```

**相对 Lead 原命令的两处修正（都是必须的）：**

| # | 原命令 | 问题 | 修正 |
|---|---|---|---|
| 1 | 只 `tail -F /www/wwwlogs/ba_mitm.log` | 那 278 条探测**一条都不在这个日志里**（实测该 IP 在 ba_mitm.log 命中 **0**）；`/common/config` 也走 `example.com` → 会**整条链漏采** | **同时 tail 两个日志**，用 `[mitm]` / `[xlcx]` 前缀区分来源 |
| 2 | `tail -F`（默认 `-n10`） | 启动时会**回放最后 10 行历史**，混进采集结果造成误判 | 改用 **`tail -F -n0`**，只收启动之后的新行 |

另外：`grep` 模式从 `/common/config` 放宽为 `/?(sdk/)?(common/config|…)`，因为客户端若 `sdk_url=https://example.com/sdk`，
实际路径是 **`POST /sdk/common/config`**（nginx `location /sdk/` 剥前缀后才是 `sdkcard.py` 的 `/common/config`）——**这个 `/sdk/` 前缀不能漏**。

**已验证工作**：启动后故意打两条 `/api/state`（一条走 `gsqc-api` SNI、一条走 `example.com`），
`/tmp/ba_watch.log` 立刻收到两行且前缀正确：

```
00:40:19 [mitm] 127.0.0.1 - - [14/Nov/2026:00:40:19 +0800] "GET /api/state HTTP/2.0" 200 178 "-" "curl/7.81.0"
00:40:19 [xlcx] 127.0.0.1 - - [14/Nov/2026:00:40:19 +0800] "GET /api/state HTTP/2.0" 200 178 "-" "curl/7.81.0"
```

**日常查询（随时问随时给）：**

```bash
tail -40 /tmp/ba_watch.log                      # 最近 40 条
wc -l /tmp/ba_watch.log                         # 总量
grep -c 'common/config' /tmp/ba_watch.log       # 第一跳是否出现
grep -c 'quick-login'  /tmp/ba_watch.log        # 卡密链是否打通
grep -v '^.*\[mitm\] 127.0.0.1' /tmp/ba_watch.log | grep -v '<SERVER_IP>'   # 剔除自测，只看外部
```

**基线（用于判断"有没有新的"）**：手机最后一次请求是 `14/Nov 00:39:17`，采集器从 `00:40` 起计。
此后 `/tmp/ba_watch.log` 里出现**非 `127.0.0.1` / 非 `<SERVER_IP>`** 的行，就是手机的新流量。

**停止方式**：`pkill -f /root/ba_watch/watch.sh`（两个 `tail` 子进程会随之退出）。
