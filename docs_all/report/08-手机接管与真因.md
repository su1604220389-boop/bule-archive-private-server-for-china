## 2. 解出来了：`Hosts` 文件的二进制格式

```

6773...6f6d          (25 B)      "gs-api.bluearchive-cn.com"
01 00 00 00                      u32  ?        = 1

6874...3433          (37 B)      "https://gs-api.bluearchive-cn.com:443"
10 3b 97 d8 3e 41 df 48          u64  opaque   (LE = 0x48df413ed8973b10)
01                               u8   flag     = 1
```

**为什么这很重要**：文件里正好 **2 条**，而官方 `state-api/api/state` 的响应里 `Servers` 正好是 **2 条**：

```json
{"Servers":["https://gsqc-api.bluearchive-cn.com/api/","https://gs-api.bluearchive-cn.com/api/"],
 "State":1,"Msg":"服务器维护中，请耐心等待开服！"}
```

→ **`Hosts` 就是 `Servers` 的落盘缓存**（高度一致的强证据，标「推断」但证据很硬）。
→ 旧实验「写单条 `127.0.0.1:9443`」之所以无效，是因为：① 格式根本不是 `host:port`，而是 `host` + **完整带 scheme 的 URL** + u32 + u64 + flag 的结构体；② 联网启动时 state 会先请求成功并覆盖它。
→ 因此正确的实验必须是：**按这个结构写 + 让 state 请求失败（飞行模式）**。

### 3.2 进程在自杀循环

`dumpsys activity exit-info` 里 `reason=1 (EXIT_SELF) status=13`，`am_proc_died` 事件按 0.3 秒一个节奏连续出现（pid 31368 → 31429 → 31477 → … → 32344 → …）。**无 tombstone**（不是 SIGSEGV/SIGBUS，所以也不是 ACE 的 `SIGBUS status=7`）。

### 3.3 另一条佐证：`libmain.so` 自己是好的

```
D/nativeloader: Load .../lib/arm64/libmain.so using class loader ns clns-9 (caller=base.apk!classes2.dex): ok
```

只有 `libil2cpp.so` 挂。

### 3.4 时间线：是 **19:47 那次原位替换**把它搞坏的

| 时间 | 事件 |
|---|---|
| 18:38:51 | 客户端安装（当前这份 base.apk，2,126,786,978 B） |
| 19:12–19:13 | 连续产生 `tombstone_20/21`（那批是注入实验的 SIGSEGV，属于另一类故障） |
| **19:47** | `libil2cpp.so` 被 root 原位替换成「g20 探针」构建 |
| 19:57 | exit-info 开始出现 0.3 秒一次的 `EXIT_SELF status=13` 自杀循环 |
| 23:xx | 归档时 `bainj.txt` 已有 5976 B 的 `IBDIBD…` —— 那是**更早**（E63 时期）能启动时留下的，不是 g20 的 |

→ 结论：**g20 这一版从来没有真正跑起来过**（与 `report/02-注入链审计.md` 里「11:47 之后无任何运行日志，这版大概率没上机」的判断一致，现在被真机证据坐实）。
→ **工程后果**：自 19:57 起，所有「改了没效果 / 超时 / 不稳定」的观察都可能只是这个加载失败，不是链路结论。

### 3.5 为什么 `dlopen` 会给出 `0 >= 0`

`0 >= 0` 说明加载器拿到的 `file_offset` 和 `file_size` **都是 0**。可能来源：
- zip-direct 路径（`ANDROID_DLEXT_USE_ZIP_FILE`）：`FindEntry` 拿到 `offset=0 / uncompressed_length=0`；
- 或 `fstat` 出来是 0 字节的 fd。

已确认的事实：APK 里 `lib/arm64-v8a/libil2cpp.so` 是 **Defl:N（压缩）**、解压 270,927,056 B、CRC `bec312c0`；磁盘上同名文件也是 270,927,056 B。
**待验证**（交给 `report/07-dlopen报错考证.md`）：Unity 的 `loadNative` 到底走 `System.loadLibrary` 还是 zip fd，以及 `extractNativeLibs=true` + Defl:N 的组合在 Android 14 上是否仍会走 zip-direct。
**可直接用于判定的观测点**：`logcat` 里 `nativeloader: Load ... using class loader ns clns-N` 这一行，以及抓到活进程后的 `/proc/<pid>/maps` 里 libil2cpp 的映射来源路径。

### 新增的 4 个硬结论（推翻/升级了旧判断）
1. **/api/state 从未实现**（nginx 443 全链路 404）——这是国服客户端**第一个**请求，Steam 版 Shittim 走的是 com.nexon.bluearchivesteam/server_config/<ver>_Live.json，完全是另一套。
