## 1. 目标形态

### 1.1 一句话

> **bridge 变成"全协议终结器"：任何路径 + 任何国服信封进来 → 统一解成明文 JSON → 按协议名决定「自己造」还是「问 Shittim」→ 统一按一个可切换的函数封装回客户端。**

```
                    ┌──────────────────────── bridge (127.0.0.1:9097) ───────────────────────┐
客户端                │                                                                        │
POST /api/<任意>  ───▶│ ① parse_cn_envelope(body)      → {protocol_field, encode, packet_b64}  │
multipart:            │ ② decode_cn_packet(packet_b64) → {jsondict, key, iv, fragment}          │
  protocol=<b32>      │ ③ name = b32→name 反查                                                  │
  encode=True         │ ④ sess = ensure_session(DevId, Token)   ← 从明文里取，不再硬编码        │
  packet=<b64>        │ ⑤ 路由：L0 自造 / L1 问 Shittim / L2 透传                                │
                      │ ⑥ shittim_json = post_gateway(...)                                      │
                      │ ⑦ body = encode_cn_response(name, obj)   ← 唯一可切换的出口             │
                      └────────────────────────────────────────────────────────────────────────┘
                                                          │
                                          ┌───────────────┴───────────────┐
                                          ▼                               ▼
                                 L0：不调 Shittim                L1/L2：POST /api/gateway
                                 (自造响应)                       multipart 字段 mx = build_mx(json)
                                                                  Shittim 回 {"protocol","packet"}
```

### 1.2 入方向：国服信封 → 明文 JSON

**已经全部实现好了，不要重写。** `report\_tmp\mx_crypto\cn_cipher.py` 是已验证模块（`report\35` §八，`--selftest` 通过）：

| 步骤 | 现成函数 | 行号 | 做过什么 |
|---|---|---|---|
| 1 | `cn_cipher.b32(s)` | `cn_cipher.py:40-41` | 补 `=` 后 base32 解码 |
| 2 | `cn_cipher.unwrap_packet(packet_b64)` | `:48-60` | base64 → `[u32 LE 声明长度]` + `gzip` → 内层字节 |
| 3 | `cn_cipher.split_inner(inner)` | `:63-67` | `[iv:16][ct:...][key:32]`，**长度可变**（样本恰 432） |
| 4 | `cn_cipher.decrypt_inner(inner)` | `:82-88` | AES-256-CBC 解密 + PKCS7 去填充 → `(fragment, iv, key)` |
| 5 | `cn_cipher.decode_packet(packet_b64, protocol_field)` | `:91-104` | 一条龙 → `{fragment, json, iv, key, inner_len, frag_len}` |

**关键细节（`cn_cipher.py:97-102`）**：完整 JSON 是**拼出来**的，因为 `{"Protocol":"<名字>"` 这一段在密文之外：

```python
full = json.loads('{"Protocol":"%s"' % name + text)
```

⇒ 通用化改造（本方案唯一需要动的解析逻辑）：`decode_packet` 目前 `PROTOCOL_MAP` 只有 `Account_Auth` 一条（`:35-37`）。通配转发要把它换成 bridge 现成的 `b32md5` 反查（`cn_bridge_v5.py:42-43, 45-63`）——**反向映射**（名字→token）已经能算，正向只要 `{b32md5(n): n}` 建表就行。

**两个必须处理的边界**（`[推断]`，依据是客户端 JSON 的构造方式）：

| 情况 | fragment 长什么样 | 拼法 |
|---|---|---|
| 有参数 | `,"DevId":...,"Hash":123}`（以 `,` 开头、以 `}` 结尾） | `'{"Protocol":"X"' + frag` |
| 无参数（如 `NetworkTime_Sync`，其 Request 类是空类 `NetworkProtocol.cs:5609-5612`） | 可能空串 / `"}"` / 无内层 | 三路兜底：空前缀 → `{"Protocol":"X"}`；否则试拼接；再不行用 `json.loads` 失败则落 L2 |
| `encode=False` | packet **没加密**（原文） | 先试 `json.loads(base64decode(packet))` 或直接 `json.loads(packet)`，成功就不再解密 |

### 1.3 ★ 一个本方案要新增的设计点：会话身份从请求里取，不再硬编码

**现状**：`cn_bridge_v5.py:21-23` 把 `UID=314816420` / `TOKEN=61de1d1b…` 写死。

**通配转发必须改**：`[实测]` 国服 `Account_Auth` 的明文里有 `"DevId":"314816420"` 和 `"Token":"61de1d1b…"`（`report\35:55`），两者正好等于我们 SDK 下发的 `User.ID` / `User.Token`。

而 `[实测]` 国服 metadata 里 **`SessionKey` 全文 0 命中**（`report\41:173-175`）⇒ **国服客户端不会回传 Shittim 的会话**，它在每个请求里带的是 `DevId`/`Token`。

⇒ **架构结论（`[推断]`，但落地成本极低）**：bridge 是**唯一的会话持有者**——

```python
dev_id = obj.get("DevId")     # 例 "314816420"
token  = obj.get("Token")     # 例 "61de1d1b…"
enter_ticket = base64(f"{dev_id}/{token}")      # = CheckYostar/CheckNexon 的 EnterTicket
```

这有三重收益：① 多账号天然支持（不再全员映射到 314816420）；② `ensure_session()` 的缓存键应该改成 `dev_id`；③ `Account_CheckYostar` / `Queuing_GetAuthTicket` 要用的 `(uid, token)` 全从这一处取，不再有第二份常量。

> ⚠ 若某协议明文里**没有** `DevId`/`Token`（例如后续请求可能只在首包带），必须**回落**到最近一次成功的 (dev_id, token) —— bridge 要进程级记住 `last_identity`。

### 1.4 出方向：明文 JSON，且**可切换**

**结论（有硬证据）**：`report\41` §9.A（`:340-361`）——在国服 `global-metadata.dat` 里：

| 符号 | 命中 |
|---|---|
| `PacketCryptManager.EncryptRequest`（请求加密入口） | 1 |
| `HttpGameMessage.DecodeResponse`（响应解码入口） | 2 |
| **`EncryptResponse` / `EncodeResponse` / `DecryptResponse` / `MakeResponse`** | **全 0** |

⇒ **客户端没有任何"生成加密响应"的代码，也不握有钥匙**（`aesKey` 只由 `Queuing_*` 的 RSA 换钥写入，而客户端从未发过 `Queuing_*`）。

⇒ **响应方向不需要加密，明文 JSON 是唯一自洽的形态。** 这与 `report\34` §六（`DecryptOrReturnOriginal`）一致，也与 D-44 ③④"明文 3740 B 与加密 4491 B 行为完全一致"一致。

**但外层"信封形状"仍未定**（`report\41` §9.B/§9.C 的 L1/L2/L6 就是在测这个）。所以本方案把它做成**一个函数 + 一个常量**：

```python
# cn_bridge_v5.py 模块级，唯一开关（等 lead 的信封实验出结论后只改这一行）
CN_RESP_MODE = 'plain-lower'      # plain-lower | plain-upper | two-segment | cn-wrapped
```

| mode | body | 对应 41 号哪一枪 |
|---|---|---|
| `plain-lower`（**当前默认/基线**） | `{"protocol":"X","packet":"<JSON 字符串>"}` | L0 |
| `plain-upper` | `{"Protocol":"X","Packet":"<同一份>","Encode":false}` | L2 |
| `two-segment` | `text/plain`，body = `<26 字符 base32 token>` + `\n` + `<packet JSON>` | L6 |
| `cn-wrapped` | `packet = base64([u32 len][gzip([iv16][ct][key32])])`，**key 复用当次请求那把** | L4 |

`cn-wrapped` 的实现**不需要新代码**：`cn_cipher.build_inner(fragment, key=req_key, iv=新随机)`（`:108-122`，签名已支持传 key）+ `wrap_packet`（`:125-128`）。

> L4 的合理性（`report\41:413` 的思路）：客户端在本次请求里把 key 明文附在包尾，服务端沿用同一把 ⇒ 客户端**无需额外换钥**即可解。这是唯一一个"不走 `Queuing_*` 也能成立的加密方案"，`[推断，未验证]`。

## 2. 关键未知（逐条标注证据等级）

### 2.1 Shittim 的 `/api/gateway` 收到的 `mx` 怎么构造？

**答：已完全确定，源码 + 实测 + 现成实现三路一致。**

`[源码实测]` 读取端（`GatewayController.cs:360-409` `DecodeGatewayPayload`）：

```
0     uint32  crc              reader.ReadUInt32()      :367
4     int32   typeConversion   reader.ReadInt32()       :368
8     uint8   keyLength        reader.ReadByte()        :369
9     uint8   ivLength         reader.ReadByte()        :370
10    byte[keyLength] headerKey                         :371
      byte[ivLength]  headerIv                          :372
      byte[...]       rawPayload                        :373
```
`rawPayload` 的三种可接受排布（`:462-493`）：`xor-length-prefix` / `clear-length-prefix` / `xor-no-length`，XOR 键 `{0xD9}`（`:107`），随后 GZip。

**最小可用构造（我们桥接已在用，且被 Shittim 正常处理）**：

```python
def build_mx(obj):                      # cn_bridge_v5.py:81-86 == cn_cipher.py:135-141
    payload = json.dumps(obj, ensure_ascii=False, separators=(',', ':')).encode()
    body = struct.pack('<I', len(payload)) + gzip.compress(payload)
    enc  = bytes(b ^ 0xD9 for b in body)
    return struct.pack('<I', 0) + struct.pack('<i', 0) + bytes([0, 0]) + enc
```
`crc=0`、`typeConversion=0`、`keyLen=0`、`ivLen=0` ⇒ **Shittim 走明文分支，响应也是明文**（`:514-517`）。

`[实测]` 这个构造已被证实可用：`report\35:116`「造出的 `.mx` 被 Shittim 正常处理，WireDump 写出了明文交换，拿到 `Account_Auth`=1002、`NetworkTime_Sync`=3 两个真协议号」。
`[实测]` POST 姿势必须 `multipart/form-data` + 字段名 `mx`（`DEADENDS.md:459-461`，`INDEX.md:117-118`）。

**`[未找到]`**：`HandlerManager` 的 `Dispatch` 是否会做二次校验（类不在快照）。**`[推断]`** 会调 `SessionKeyService.ValidateRequest`（否则 `_publicProtocols` 白名单毫无意义）。

### 2.2 响应侧的 `mx` 怎么生成？要不要原样透传？

**答：不需要生成任何 `mx`；Shittim 回的也不是 `mx`。**

`[源码实测]` Shittim 的响应是**一个 JSON 文档**（`GatewayController.cs:791-800`）：

```csharp
string json = JsonConvert.SerializeObject(packet, serverPacketSettings);   // {"protocol":"X","packet":"<JSON 字符串>"}
if (ShouldUseAes(crypto))                                                  // :795  keyLen=0 时恒 false
    json = Convert.ToBase64String(HybridCryptor.EncryptGatewayResponse(...));
Response.ContentType = "application/json; charset=utf-8";
await Response.WriteAsync(json);
```

⇒ **`mx` 只存在于入方向。** 出方向只有三种可能：① 明文 `{"protocol","packet"}`；② 整个信封 base64(AES)；③ 我们没有的结构。

**所以"要不要原样透传"的答案是：**

| 层 | 建议 | 理由 |
|---|---|---|
| 外层（HTTP body） | **必须由 bridge 重写**，不能原样透传 | Shittim 的 `packet` 是 **JSON 字符串**（二次编码），且外层 key 是小写 camelCase；国服是否吃这一套 = lead 正在测的那一维 |
| 内层（`packet` 里的 JSON 对象） | **原样透传** | 那是业务数据，bridge 不该改动任何一个字节（`report\42` §1.5：Auth 的响应内容只取决于账号，与请求无关） |

⇒ 实现上就是 `encode_cn_response(name, obj)` 里对 `obj` 只做 `json.dumps`，**不做任何字段增删**。

### 2.3 如果 Shittim 对某个协议**没有 handler**，返回什么？

**答：永远不是 404，而是 HTTP 200 + `Error` 信封。四种情形同一个出口。**

`[源码实测]` 四条路径：

| 情形 | 位置 | 出口 |
|---|---|---|
| 协议名**不在枚举**（`GetRequestType` 为 null） | `GatewayController.cs:207-213` | `CreateProtocolErrorResponse("Failed to handle protocol", ServerFailedToHandleRequest)` |
| 在枚举但**没 handler**（`IsImplemented` false） | `:223-230` | `CreateProtocolErrorResponse("Protocol not implemented (Server Error)", ServerFailedToHandleRequest)` |
| handler 抛异常 | `:296-303` | 同上，`ex.Message` |
| 会话无效（`UnauthorizedAccessException`） | `:287-295` | `CreateProtocolErrorResponse(ex.Message, WebAPIErrorCode.InvalidSession)` |

`CreateProtocolErrorResponse`（`:773-789`）**不设 StatusCode** ⇒ 仍是 **200**。

`[源码实测]` Error 信封的精确形状 —— `ErrorPacket`（`NetworkProtocol.cs:782-789`）：

```csharp
public class ErrorPacket : ResponsePacket
{
    public override Protocol Protocol { get => Protocol.Error; }      // -1
    [Newtonsoft.Json.JsonIgnore]
    public string? Reason { get; set; }                                // ★ 不上线！只进日志
    public WebAPIErrorCode ErrorCode { get; set; }
}
```

⇒ 客户端实际收到的是：

```json
{"protocol":"Error","packet":"{\"Protocol\":-1,\"ErrorCode\":500,\"ServerTimeTicks\":6393...}"}
```
错误码常量：`ServerFailedToHandleRequest = 500`（`ProtocolData.cs:687`）、`InvalidSession = 3`（`:654`）。

**`[实测]` 客户端看到 Error 信封会怎样**：`DEADENDS.md:379-380`（D-44 ①②）—— 与 404 **完全一样**，弹「服务器处理请求失败。将返回标题画面。」

### 2.4 由此得到的硬结论（它会改写你的 L2 设计）

> **"放行给 Shittim" 对未实现的协议 = 404 弹窗 → 换成 Error 弹窗。D-44 实测两者行为无差别。**
> **所以 L2 不能当兜底。** 详见 §3.3。

## 3. 分层策略

### 3.1 三级定义（按"离 Shittim 的距离"分）

| 级 | 名称 | 数据来源 | 何时用 | 代价 |
|---|---|---|---|---|
| **L0** | 自造响应 | bridge 自己（常量 + 请求回显） | ① 我们已完全掌握语义的协议（Queuing 家族、CheckYostar、Auth 的会话铸造）② **所有"不认识"的协议的兜底** | 字段可能不全；不需要 Shittim 活着 |
| **L1** | 翻译给 Shittim | `POST /api/gateway` + `mx`，拿真 handler 输出 | Shittim **有 handler** 且我们要真数据（`Account_Auth` / `Account_LoginSync` / `Character_List` / cafe / mission…）或要它算 crypto（`GetCryptoKeys` / `GetAuthTicket`） | 依赖 Shittim；需要注入 `SessionKey`（客户端不给） |
| **L2** | 原样透传 | `TARGET_BASE + 原路径` | **仅用于诊断**：想主动看"错误弹窗"长什么样，或想验证某路径在 Shittim 是否真的不存在 | **必然 404**（`report\44` §4），且实测等同 Error 弹窗 |

### 3.2 决策表（bridge 里的实际判据）

```
收到 name（协议名）后：

①  name in L0_ALWAYS            → L0   （Queuing_*、Account_CheckYostar）
②  name in L1_TABLE             → L1   （有 handler 且要真数据；见 §3.4 清单）
③  name 不在 Shittim 枚举里      → L0-fallback（自造最小空响应）  ← 不要走 L2
④  name 在枚举里但没有 handler   → L1 试一次；若回 Error 且 ErrorCode==500
                                   → 立刻改 L0-fallback（并缓存"此协议不可用"）
⑤  name 未知（连 base32 都反查不到）→ L0-fallback + 打 rec['unknown']=True
⑥  客户端主动 GET（如 Queuing/Ping）→ L2 透传（这是唯一能命中的转发）
```

`L0_ALWAYS` / `L1_TABLE` 建议做成**两份模块级 dict**，一行一个协议，便于灰度和回滚。

### 3.3 ★ 对你原话里"L2 完全透传当兜底"的修正（请拍板）

你的要求是：**"遇到不认识的协议时，至少别 404（404 会弹窗）"**。

`[实测]` **透传到 `/api/gateway` 也救不了**：

| 兜底方案 | 实测/源码结果 | 客户端表现 |
|---|---|---|
| L2-a：透传原路径 | 404（`report\44` §4） | 弹「服务器处理请求失败」（D-44①） |
| L2-b：透传到 `/api/gateway` | 200 + `Error` 信封（§2.3） | **同一个弹窗**（D-44②） |
| **L0-fallback：自造最小响应** | 200 + 合法 JSON | **无弹窗**（D-44③④ 全部无弹窗） |

⇒ **兜底只能用 L0-fallback。L2 保留，但只当"诊断开关"**（例如 `cn_bridge_mode.txt` 走 `forward`）。

**L0-fallback 的推荐形状**（最小、最不容易 NRE）：

```json

```
只回 `Protocol`，其余字段全 null ⇒ 序列化时被 `DefaultValueHandling.Ignore` 删掉（`GatewayController.cs:118` 注释）⇒ 客户端 DTO 全部落默认值。

### 4.3 `SessionKey` / ticket 与 `Account_Auth` 的关系

`[源码实测]` 三层事实：

1. **唯一真源是 `CheckYostar`/`CheckNexon`。** `AccountHandler.cs:943` `var sessionKey = await _sessionService.GenerateSession(publisherId);` → `:947` `response.SessionKey = sessionKey;`

3. **`Account_Auth2` 走 `AccountHandler.cs:813-822`，会 regenerate 一个新会话**（`:816` 附近）。`[推断]` 这解释了为什么官方 Auth2 也是"会话协议"之一（`GatewayController.cs:318-322`）。

⇒ **`DevId`/`Token` → `base64("{DevId}/{Token}")` 这一个串，同时喂给 Queuing_GetAuthTicket、CheckYostar、CheckNexon 三条链。**（`report\43` §3.1 的常量可直接复用。）

**对 bridge 的落地含义（重要）**：

### 5.2 核心代码骨架（`encode_cn_response`，对应 §1.4）

```python
def encode_cn_response(name, obj, req_key=None):
    """唯一出口。四模式由 CN_RESP_MODE 决定；改实验只改这一个常量。"""
    packet = json.dumps(obj, ensure_ascii=False, separators=(',', ':'))
    if CN_RESP_MODE == 'plain-lower':                  # L0 基线（当前行为）
        body = {"protocol": name, "packet": packet}
        return json.dumps(body, ensure_ascii=False, separators=(',', ':')).encode()
    if CN_RESP_MODE == 'plain-upper':                  # 41 §9.C L2
        body = {"Protocol": name, "Packet": packet, "Encode": False}
        return json.dumps(body, ensure_ascii=False, separators=(',', ':')).encode()
    if CN_RESP_MODE == 'two-segment':                  # 41 §9.C L6
        tok = base64.b32encode(hashlib.md5(name.encode('utf-16-le')).digest()).decode().rstrip('=')
        return (tok + '\n' + packet).encode()
    if CN_RESP_MODE == 'cn-wrapped':                   # 41 §9.C L4：复用请求那把 key
        # 客户端重建方式是 '{"Protocol":"<名字>"' + fragment，故 fragment 必须以 ',' 开头、'}' 结尾
        rest = {k: v for k, v in obj.items() if k != 'Protocol'}
        frag = (',' + json.dumps(rest, ensure_ascii=False, separators=(',', ':'))[1:]) if rest else '}'
        inner = cn_cipher.build_inner(frag, key=req_key)    # key 复用；iv 由函数随机生成
        return cn_cipher.wrap_packet(inner).encode()        # ★ wrap_packet 已含 base64，别再编一次
    raise ValueError('unknown CN_RESP_MODE: %r' % CN_RESP_MODE)
```

> 实现提示：① `cn_cipher.build_inner(fragment, key=None, iv=None)`（`cn_cipher.py:108-122`）的签名**本来就支持传 key**，所以"复用请求那把 key"不需要改模块；② `req_key` 从 §1.2 的 `decode_packet()` 返回值里直接拿（`cn_cipher.py:103` 的 `"key"` 字段是 **str**，要去 `.encode('ascii')` 再传给 `build_inner`）；③ `wrap_packet` 返回的**已经是 base64 字符串**（`cn_cipher.py:128` 末尾 `.decode()`），不要再 base64 一次。

## 8. 为什么不建议改 Shittim（顺带回答"改哪一层"）
