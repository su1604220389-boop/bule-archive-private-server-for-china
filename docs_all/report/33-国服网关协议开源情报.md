## 一、摘要（先说最重要的）

**1. `protocol = AHTQLQI65FWJGGGK4KL5AEF57A` 已经破解，可复现：**

```
protocol = BASE32( MD5( UTF-16LE(协议名) ) )   去掉 '=' 填充
token("Account_Auth") = AHTQLQI65FWJGGGK4KL5AEF57A   ✅ 逐字符吻合
```

**2. 国服 metadata 里那把网关 RSA 公钥，和国际服 `Account_CheckNexon` 用的公钥是同一把 —— DER 逐字节相同。**

```
CN metadata 公钥 DER  sha256 = bb8efc04c1b6278959cf2840e5e3c5894b47578bd88e493c31cb8c6217ef7036
headless SDK 内置公钥  sha256 = bb8efc04c1b6278959cf2840e5e3c5894b47578bd88e493c31cb8c6217ef7036   ← 完全相同
模数头部（两把一致） = 00 b6 04 b6 05 72 ca 22 b2 3c 38 52 19 8b 78 1e b1 54 0b 42 af 04 a7 06
```

**3. 没有任何公开项目实现过「国服」这套信封**，但国服信封是**国际服 MX 信封的简化变体**，算法层完全可复用。

## 三、Q2 — `protocol = AHTQLQI65FWJGGGK4KL5AEF57A` 是什么？（★ 已破解）

### 3.1 正确的解码不是 base64，是 **base32**

```
27 字符？不，是 26 字符 → base32 对 16 字节的编码长度恰好是 ceil(16*8/5) = 26
```
（之前按 base64 解出 19 字节是错的；base32 解出的是干净的 **16 字节**，这是哈希长度。）

```
base32decode("AHTQLQI65FWJGGGK4KL5AEF57A")
= 01 e7 05 c1 1e e9 6c 93 18 ca e2 97 d0 10 bd f8   (16 字节)
```

### 3.2 算法（实测复现）

```python
import hashlib, base64

def protocol_token(name: str) -> str:
    digest = hashlib.md5(name.encode("utf-16-le")).digest()   # ← 注意是 UTF-16LE，不是 UTF-8
    return base64.b32encode(digest).decode("ascii").rstrip("=")

assert protocol_token("Account_Auth") == "AHTQLQI65FWJGGGK4KL5AEF57A"   # ✅ 通过
```

**关键点：编码是 `utf-16-le`（C# 的 `Encoding.Unicode` / .NET 默认 string 编码），不是 UTF-8。**
这就是为什么用 UTF-8 试 MD5 会全部失败。

### 3.3 全部常见协议的 token（可直接用于识别抓包）

| 协议名 | token |
|---|---|
| `Account_Auth` | `AHTQLQI65FWJGGGK4KL5AEF57A` ← **我们抓到的那条** |

### 3.4 这条结论为什么重要

- **我们抓到的那条 `/api/account/auth` 就是 `Account_Auth`** —— 客户端点「进入游戏」后发的第一条业务协议，与「先登录再进大厅」的时序一致。
- **协议号可以随时从名字算出来**，不需要客户端里的映射表、也不需要反编译。
- 反过来说：**「协议名 → token」这个映射是公开算法，不是密钥**，意味着国服的协议标识层没有额外安全性。

## 四、Q3 — `encode` / `packet` 是什么算法？

### 4.1 国际服 MX 信封（headless-bluearchive `core/packet.py`，[实测源码]）

```
packet = [crc:u32 LE][converted:i32 LE][keyLen:u8][ivLen:u8][key][iv][payload]
payload = XOR( gzip_length_prefixed(request_bytes), 0xD9 )
request_bytes = JSON 明文，或（有会话密钥时）AES-128-CBC(JSON)
crc = CRC32(payload)，poly 0x04C11DB7，初值 0，无反射
converted = type_conversion(crc, protocol)   # 按 crc%99 选桶，再从桶表里取 encoded_int32
```

关键常量（`core/crypto.py`）：
```python
CRC_POLY = 0x04C11DB7
XOR_KEY  = 0xAFB7E3D9      # 低字节 0xD9
XOR_BYTE = 0xD9            # ← 与 Shittim 源码里的 RequestXorKey = {0xD9} 完全一致
```

`gzip_length_prefixed(data) = struct.pack("<i", len(data)) + gzip(data)`

### 4.2 国服实际信封（我们抓到的）对照

```
base64decode(packet) -> 459 字节
[0:4] = b0 01 00 00 = u32 LE = 432
[4:]  = 1f 8b 08 00 ... （gzip 魔数，且是"裸"的，没有 XOR）
gunzip -> 432 字节
```

**对照结论：国服的 `packet` = `gzip_length_prefixed(request_bytes)`，但**
1. **没有 10 字节头**（无 `crc` / `converted` / `keyLen` / `ivLen`）
2. **gzip 流没有做 `0xD9` XOR**（`1f 8b` 是裸 gzip 魔数）
3. **`request_bytes` 那 432 字节不是 JSON**（首字符不是 `{`），且 `432 = 27 × 16` —— **正好是 AES 块长的整数倍**

⇒ **国服形态 = `base64( gzip_length_prefixed( AES-128-CBC(JSON) ) )`**，与国际服 `encrypt_request=True` 那条分支同构，只是把最外层的 CRC/conv/XOR 去掉了。

### 4.3 `encode: True` 的含义

国际服 SDK 里没有 `encode` 这个字段（Shittim 也不用它）。
结合 4.2 的结构，**`encode: True` 最可能是「`packet` 里的请求体是 AES 加过密的」这个布尔开关**（即对应 `_should_encrypt_request()` 那个判断）。

> **推断（未实测）**：当 `encode` 为 false 时，那 432 字节应该就是明文 JSON。

### 4.4 AES 的密钥从哪来 —— **这是目前唯一的未知量**

国际服流程里，AES key/IV 是**客户端生成**、随请求以 `ClientGeneratedKey` / `ClientGeneratedIV` 两个字段发出去（可选用 RSA 包裹）。国服的 multipart 只有 `protocol` / `encode` / `packet` 三个字段，**没有 key/IV 字段**。

⇒ 国服的 AES 密钥必然是**确定的**（固定密钥，或从某个双方共知的值派生）。

**候选线索（来自我们自己的静态逆向，`report/11` §3.4）：**
```
global-metadata.dat 里有一簇符号：
  CryptAES: generateKeyString / byteSrc / encrypt / decrypt / toEncryptData
            EncryptRJ256Api / sEncryptedString / DecryptRJ256Api
            FBENCRYPT_BLOCK_SIZE / cRandom / IVString
  MX-Core-Services-CryptAES-DecryptRJ256Api0 / -decrypt0   ← 紧挨着 HttpGameSession/HttpGameMessage
```
`generateKeyString` / `cRandom` / `IVString` 这三个名字强烈暗示：**密钥是运行时"生成字符串"得到的，而生成规则是固定的**。`RJ256` 这个名字也值得注意（不是标准 AES 命名，可能是他们自己的叫法，或指 Rijndael-256 块）。

**另外一条已在手但没验证的线索**：metadata 里解出的那个唯一 API 字面量
```
["http://test-ba.yostar.net:5210/api/state", ...]   （XOR key 0xB5）
```

## 六、如果必须自己逆，最短路径（给执行人的具体建议）

### 6.1 第一优先：找那把固定的 AES key（16 字节）

按代价从低到高：

1. **在客户端里搜 `CryptAES` 附近的字符串常量**
   ```bash
   # metadata 里（C# 字面量在这，注意可能是 XOR 0x66 混淆过的区段）
   grep -aob 'generateKeyString' global-metadata.dat
   grep -aob 'CryptAES' global-metadata.dat
   # 在命中点前后各 4KB 里找 16 字节的可疑常量
   ```
   `report/11` 已给出 `CryptAES` 在 `0x259ba6` 附近。

2. **在 `libil2cpp.so` 里搜同样的符号 + 附近的 16 字节常量**
   （注意：ACE 加密了 `.text`，但 `.rodata` 一般是明文；`report/21` 已确认 `.dynstr` 可用）

3. **直接 hook**：如果有 Frida 能力，hook `CryptAES.decrypt` 的入参，把 key/IV 打出来。这是最快的路，且不受混淆影响。
   （注意 `report/18` 的结论：KSU + Android 15/16 上 Frida **spawn 模式会崩**，只能 attach；而 attach 赶不上早期 JNI 调用 —— 但这里要 hook 的是「点击进入游戏之后」的调用，**attach 完全来得及**。）

4. **把 16 字节 token 当密钥试一遍**（零成本）：`key = iv = 01e705c1...`、`key = 01e7..., iv = 0`、`key = md5(utf16le("Account_Auth"))` 等组合，直接拿抓到的 432 字节试 AES-CBC 解密，看首字节是不是 `{`。

### 6.2 第二优先：验证「第一条请求就是 `Account_Auth`」
已经可以由 3.2 的算法直接确认（token 对上了）。所以**不需要**再去猜协议号。

### 6.3 第三优先：确认 `encode` 的反面
如果能构造一个 `encode: False` 的请求（或让服务端返回某种状态使客户端降级），就能直接看到明文 JSON —— 但这需要在客户端侧，成本高。

## 七、可直接复用的代码（给服务端/转换器）

```python
import hashlib, base64, gzip, struct

XOR_BYTE = 0xD9
CRC_POLY = 0x04C11DB7

def protocol_token(name: str) -> str:
    return base64.b32encode(hashlib.md5(name.encode("utf-16-le")).digest()).decode().rstrip("=")

def crc32_ba(data: bytes) -> int:
    crc = 0
    for b in data:
        crc ^= (b << 24)
        for _ in range(8):
            crc = ((crc << 1) ^ CRC_POLY) & 0xFFFFFFFF if crc & 0x80000000 else (crc << 1) & 0xFFFFFFFF
    return crc

def xor_crypt(data: bytes, k: int = XOR_BYTE) -> bytes:
    return bytes(b ^ k for b in data)

def gzip_length_prefixed(data: bytes) -> bytes:
    return struct.pack("<i", len(data)) + gzip.compress(data, compresslevel=1, mtime=0)

def cn_packet_build(aes_ciphertext: bytes) -> str:
    """国服 packet 字段：base64( [u32 len][gzip] )，无 XOR、无 10 字节头"""
    return base64.b64encode(gzip_length_prefixed(aes_ciphertext)).decode()

def cn_packet_parse(packet_field: str) -> bytes:
    raw = base64.b64decode(packet_field)
    ln = struct.unpack_from("<i", raw, 0)[0]
    plain = gzip.decompress(raw[4:])
    assert len(plain) == ln, (len(plain), ln)
    return plain          # ← 这 432 字节就是 AES 密文（27 个块）

def shittim_mx_build(protocol: int, json_bytes: bytes, conv_fn=None) -> bytes:
    """把明文 JSON 封成 Shittim 能吃的 .mx（crc/conv/keyLen=0/ivLen=0）"""
    payload = xor_crypt(gzip_length_prefixed(json_bytes))
    crc = crc32_ba(payload)
    converted = conv_fn(crc, protocol) if conv_fn else 0
    return struct.pack("<I", crc) + struct.pack("<i", converted) + b"\x00\x00" + payload
```

> `conv_fn` 就是国际服的 `type_conversion(crc, protocol)`（`crc%99` 选桶 + 桶表查 `encoded_int32`）。Shittim 侧对它有一定容忍度（`DecodeGatewayPayload` 会尝试三种解包），但**协议分发依赖它**，所以正式桥接时必须实现。

## 九、诚实标注

- **Q2 是完全实测的**（算法 → token 逐字符吻合）。
- **RSA 公钥同一性是完全实测的**（DER 逐字节相同，sha256 一致）。
- **4.2 的国服信封结构是从「我们抓到的 459 字节 + 国际服 SDK 源码」推出来的**，其中「`request_bytes` 是 AES-128-CBC」是**强推断**（依据：432=27×16、非 JSON、国际服同字段在 `encrypt_request=True` 时就是 AES 输出），**未用真实密钥验证**。
- **`encode: True` 的语义是推断**。
- **AES 密钥来源未找到任何公开证据**；4.4 的 `CryptAES` 线索来自我们自己的静态逆向报告，不是本次检索到的公开资料。
- **没有找到任何公开项目做过国服**。所有「国服」向的检索组合均 0 命中。
