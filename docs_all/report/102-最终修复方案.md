## §0 一页结论

### 根因（已被三条独立证据锁定）

```
客户端发请求 n 时，HTTP 头的 REQUEST-ID  =  响应 n-1 的包体内 RequestId
108/108 条全部成立（第 1 条无该头）
```

**我们的 24000 响应里没有 `RequestId` 字段**（`dto_schema` 里该字段命中 0 次），
所以客户端拿到 24000 之后，**下一条请求的 REQUEST-ID 没有来源，于是不发**。

这不是"数据不对"，是**"派发没有完成"**。E 线逐字溯源证明：
1017 请求体的 9 个键里，**没有一条来自 24000 的响应**（SyncProtocols 是客户端常量、
SkillCutInOption 是本地设置、SessionKey/AccountId 来自 1002）。所以 24000 只要让客户端
"认为这一条完成了"，它就会立刻发 1017 —— 官方实测间隔 0.130 秒（HTTP 91ms + 解析 39ms）。

### 除此之外还有 6 处结构错误（都在 24000 里）

| # | 问题 | 官方 | 我们 |
|---|---|---|---|
| 1 | `RequestId` | 每一条都有 | **缺失** |
| 2 | `SessionKey` | 有 | **缺失**（被白名单挡掉） |
| 3 | `AcademyDB.AccountId` | 有 | **缺失** |
| 4 | `AcademyDB.ZoneVisitCharacterDBs` | `map<string,array>` 71 键 | **list `[]`** |
| 5 | `AcademyLocationDBs` | 9 条 | **`[]`** |
| 6 | 多发键 | 官方无 | `MissionProgressDBs` / `EventMissionProgressDBDict` / `BattlePassMissionProgressDBDict` / `StaticOpenConditions` |

### 还有一个必须先解决的运维问题

```
日志里 24000 的 gen_kind = 'min'
但仓库代码里已经没有 'min' 这个取值（已升级成 'min+base'）
⇒ 线上部署的 account_auth_probe.py 是旧版本，确切源码未找到
⇒ 在不先对齐版本的前提下，任何本地修复都可能白改
```

## §3 阶段 1：24000 结构修复（解锁 1017 的关键）

### 3.1 目标结构（spec 权威，红队与 E 线双重确认）

```json
{
  "Protocol": 24000,
  "SessionKey": {"AccountServerId": <server_id>, "MxToken": "<64 字符 base64>"},
  "ServerTimeTicks": <.NET ticks，100ns 自 0001-01-01>,
  "ServerNotification": 0,
  "RequestId": "<uuid4，与 HTTP 响应头 requestid 同值>",
  "AcademyDB": {
    "AccountId": <server_id>,
    "LastUpdate": "<ISO 无时区，毫秒>",
    "ZoneVisitCharacterDBs": { ... 71 个 zone key，value 是数组 ... },
    "ZoneScheduleGroupRecords": {}
  },
  "AcademyLocationDBs": [ ... N 条 {AccountId, LocationId, Rank, Exp} ... ]
}
```

**键序固定**：`Protocol, SessionKey, ServerTimeTicks, ServerNotification, RequestId, AcademyDB, AcademyLocationDBs`
（注意：1002 是唯一例外，它的 SessionKey 排在 RequestId 之后）

**inner 紧凑 JSON 参考值**：官方 11,685 B（wire 层 17,560 B）

### 3.2 71 个 zone key 不是抄的，是推出来的

```
AcademyZoneDBSchema.f1 = location
国服启用 9 个 location（AcademyLocationDBSchema 11 行去掉 14/18）
⇒ 8 + 7 + 8×7 = 71 个 zone
与官方实测的 71 个键【集合完全相等】
```

**这是一条可重复推导的规则，不是快照。** D 线据此生成，独立 PASS。

### 3.3 `ZoneVisitCharacterDBs` 每个 zone 给什么

D 线给了 4 条理由选择「全给空数组」，并留了 `--zone-scope account` 开关（严格状态驱动 → 8 个 zone 也 PASS）。

**建议采用「全空」**，理由：
- `LastInteractTime` 初值无依据
- 单 zone 上限 3 个角色，而新号只有 4 个角色，铺不满
- 官方样本里本来就出现过空数组（`"1": []`）
- 与 `ZoneScheduleGroupRecords: {}` 自洽

### 3.4 `AcademyLocationDBs` 给几条（**待上机验证**）

```
官方那个 32 级号：9 条，LocationId = [1,7,11,12,13,15,16,17,19]
                  Rank = [2,1,1,2,1,1,2,2,2]，Exp = [0×8, 200]
ExcelDB 全表：    11 条，缺的是 14(Trinity) 和 18(Shanhaijing)
B 线查不到"新号该有几条"的规则
```

**方案**：先按 `suggested_minimum` 给 1 条（`LocationId=1, Rank=1, Exp=0`）跑一次。
如果客户端因学院崩，改给 9 条（`Rank` 全 1、`Exp` 全 0）。**这是上机时第一个要观察的点。**

### 3.5 删除 4 个官方没有的键

`MissionProgressDBs` / `EventMissionProgressDBDict` / `BattlePassMissionProgressDBDict` / `StaticOpenConditions`

**注意**：`StaticOpenConditions` 在整个项目里被当成必填补了两天，**官方 109 条响应里 0 次出现**。
它是从 `report/36` 的手工假设一路传播进 schema 的伪字段。

### 3.6 补 `RequestId`（**这一步是解锁的关键**）

```
值：uuid4，且必须与 HTTP 响应头里的 requestid 同值
    （官方 outer requestid == inner RequestId，逐字节相同）
```

现有 `_cn_send_envelope` 是自己生成 rid、不回填 inner，**必须改成用 obj['RequestId']**。
`scripts\292_24000_official.py` 里的 `_academy_24000_send` 已经这么做了，可以照抄。

**同时要给所有协议补** —— 不只是 24000。1001 / 1010 / 90004 现在都没有。

### 3.7 回滚

```bash
python3 /www/wwwroot/bapatch/292_24000_official.py --rollback
# 或
cp -a /www/wwwroot/bapatch/tools/account_auth_probe.py.bak.<TS> \
      /www/wwwroot/bapatch/tools/account_auth_probe.py
```
