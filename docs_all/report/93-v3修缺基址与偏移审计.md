## §0 一句话结论

v2 的状态迁移（mmap 状态页 + 洞页只留 `g_state`）**在真机上完全成功**（M1=0、M2 有效、
B0/C0 都出来了），崩的只有一条指令：回放槽把原函数的 `bl 0x640aa3c` 换成
「取字面量 → `blr`」，而字面量里放的是**文件内偏移/RVA**，`blr` 于是飞到 `0x000000000640aa3c`。

v3 把它改成 **PC 相对的 `adrp + add + blr`**：

```
0xf2c24a0  90fb8a50   adrp x16, 0x640a000     ; 运行时 = base + 0x640a000
0xf2c24a4  9128f210   add  x16, x16, #0xa3c   ; 运行时 = base + 0x640aa3c
0xf2c24a8  d63f0200   blr  x16                ; ← 与原 BL 语义逐位等价
```

这样洞里**再无绝对地址字面量**，目标对任意 base 都成立（不依赖 `g_state`，即使 mprotect 失败
也不会崩）。另加两条诊断 `T0`（DT_INIT 打一次）/ `T1`（慢路径打前 3 次），把
`base / rva / base+rva` 三元组落到 probe.log，下一轮一眼可比。

`+0x200` 那个 C0 疑点：**三个成品（v1/v2/v2data）里都只编码 `0x10496434`，全文件不存在
`0x10496634`**，且 `0x10496634` 落在原厂 DT_INIT 函数体中间、无 prologue，真进去连
`ret` 都对不上栈 —— 但真机确实启动到了 1.9 秒才崩。所以这是「日志与成品不一致」，
不是 v2 的偏移算错；**保留原值 `0x10496434`，来源标记为未确定**（见 §3）。

## §1 崩溃根因（洞页字节 ↔ tombstone 逐项对应）

### 1.1 地址复算（全部用 probe.log 与 B0 的真实值）

probe.log（284 B，四行）：

```
M1 0000000000000000 00000072cb513000 0000000000000000 0000000000000000
M2 000000750e233000 0000000000000000 0000000000000000 0000000000000000
B0 00000072bc251000 000000000000007c 000000000f2c2410 00000072cb513000
C0 00000000063c3b50 00000000063c2ea8 0000000010496634 0000000000000000
```

| 量 | 值 | 推导 |
|---|---|---|
| `base`（B0#1） | `0x72BC251000` | libil2cpp 加载基址（页对齐，末三位 000） |
| `CAVE_VA`（B0#3） | `0x0F2C2410` | 洞的链接 VA，也是 RX 段 `p_filesz` 终点 |
| 洞运行时地址 | `0x72CB513410` | = base + CAVE_VA |
| 洞页 | `0x72CB513000` | = `align_down(cave,0x1000)`，**与 B0#4 完全一致** |
| 洞起点页内偏移 | `0x410` | `0x0F2C2410 − 0x0F2C2000` |
| `replay_slot` VA | `0x0F2C2498` | 洞内 `0x88`（v2 成品符号） |
| 回放槽越界跳板 | `0x0F2C24A0` | slot+8（第 3 条原指令位置） |
| 跳板运行时地址 | `0x72CB5134A0` | = base + 0x0F2C24A0 = 洞页 + `0x4A0` |
| `lr`（tombstone） | `0x72CB5134A8` | = 洞页 + `0x4A8` = `blr` 的下一条（`b +16`） |

### 1.2 tombstone 的 dump 与 v2 成品字节：逐字一致

tombstone_25 的洞页 dump（4 个字）与 `libil2cpp_hook_v2.bin` 同一偏移的字节**完全相同**：

| 页内偏移 | tombstone 字 | v2 成品同偏移 | 一致 | 含义 |
|---|---|---|---|---|
| `0x4A0` | `0x58000090` | `0x58000090` | ✔ | `ldr x16, #16` |
| `0x4A4` | `0xD63F0200` | `0xD63F0200` | ✔ | `blr x16` |
| `0x4A8` | `0x14000004` | `0x14000004` | ✔ | `b +16` ← **lr** |
| `0x4AC` | `0xD503201F` | `0xD503201F` | ✔ | `nop` |
| `0x4B0` | `0x0640AA3C` | `0x0640AA3C` | ✔ | **`.quad 0x640aa3c`（RVA）** |
| `0x4B8` | `0xB940DA60` | `0xB940DA60` | ✔ | `ldr w0,[x19,#0xd8]` |

（工具：`python tools/v3_audit.py`，见 §5.2 的 `[C]` 段。dump 里的字节序是"字值直写"，
例如 `3c aa 40 06 00 00 00 00` 就是 64 位值 `0x000000000640AA3C`。）

### 1.3 一处算术，两行日志

```
原厂触发器 0x63C77FC:
  63c77fc: a9bf7bf3  stp  x19,x30,[sp,#-0x10]!
  63c7800: aa0003f3  mov  x19,x0
  63c7804: 94010c8e  bl   0x640aa3c        ← imm26=0x10c8e，PC 相对：0x63c7804 + 0x43238
  63c7808: b940da60  ldr  w0,[x19,#0xd8]
```

- 原指令 **`bl 0x640aa3c` 是 PC 相对**，运行时目标必然是 `base + 0x640AA3C`。
- v2 回放槽把它重写成：

```
0f2c24a0: 58000090  ldr  x16, 0xf2c24b0      ; 从字面量池读
0f2c24a4: d63f0200  blr  x16                 ; → x16 = 0x0640AA3C
0f2c24a8: 14000004  b    0xf2c24b8           ; 跳过字面量
0f2c24ac: d503201f  nop
0f2c24b0: 0640aa3c  .quad 0x640aa3c          ; ← 文件内偏移，不是地址
```

- `x16 = 0x0640AA3C`，`blr x16` ⇒ `pc = 0x000000000640AA3C`。
- 该地址落在 `[anon:dalvik-main space]`（rw，不可执行）里，于是 **Instruction Abort**：
  `esr = 0x82000006`（EC=0x20 = Instruction abort from lower EL，DFSC=0x06 = translation
  fault），tombstone 记成 `SEGV_ACCERR code 2`；`fault addr = 0x640aa3c`、`pc = 0x640aa3c`，
  而 `lr = 0x72CB5134A8`（洞页内）——三条线同时对上同一条 `blr`。
- **正确目标**：`base + 0x640AA3C = 0x72BC251000 + 0x640AA3C = 0x72C265BA3C`。

### 1.4 为什么"只崩这一条"

- M1 第 1 值 `0`：`mprotect(洞页,RWX)` 成功；M2 第 1 值 `0x750E233000`：`mmap` 匿名 RW 页成功。
- B0/C0 都在，说明状态页初始化、`g_state` 发布、B0/C0 日志全走完了；洞页随后被改回 RX，
  后面没有任何洞页写（v2 的静态审计已证明），所以 v2 里"写洞页"这一整类崩溃已经消失。
- 触发器 stub（`0x63C77FC` 的 `adrp/add/br`）把控制流送进了洞（`lr` 在洞页内即证明），
  回放槽前两条指令（`stp`/`mov`）也执行了，**崩在第三条**。
- ⇒ v2 的机制（触发器 + 状态页 + 回放）已经过了"能跑"这一关，只差这 1 个 `+base`。

## §2 找到的具体 BLR（源码行 / 反汇编 / 修复前后）

### 2.1 这处 BLR 不在 `hook.S`，也不在 `logic.c` —— 在 **`build.py` 生成器里**

`hook.S` 里的回放槽是一块"占位 NOP"，真正的指令由 `build.py` 按原厂触发器前 4 条指令
**生成**后填进去：

```asm
; cave/hook.S:143-155
.Ltrig_replay:
    // ↓↓↓ build.py 把这块换成原函数前 4 条指令的「回放序列」↓↓↓
replay_slot:
    .inst   0x7e570001
    .rept   REPLAY_WORDS - 1
    .inst   0xd503201f
    .endr
replay_end:
```

`hook.S` 里所有 `br/blr` 只有两处，都是干净的（`hit_common` 的 `br x16` 取状态页里的
`orig[tag]`；`replay_end` 用 `adr + sub CAVE_VA + add TRIG_RSM`，PC 相对）。所以按
"`blr` 目标是从字面量加载、且没有加基址"这个特征去 `hook.S`/`logic.c` 里 grep 是**找不到**的
——**bug 在生成它的 `relocate_insn_expand()`**：

```python
# build.py（v2）：BL 越界 → 6 字跳板，把 RVA 当绝对地址
        # ldr x16,#16 ; blr x16 ; b +16 ; nop ; .quad tgt
        return [0x58000090, 0xD63F0200, 0x14000004, 0xD503201F,
                tgt & 0xFFFFFFFF, (tgt >> 32) & 0xFFFFFFFF]
```

`tgt` 是 `old_pc + imm26*4`（= `0x640AA3C`，链接期 VA/文件内偏移），洞里没有加载器、
没有重定位，写进字面量就是错的。v2 的 `build.py` 第 557 行那句自检
（`if lit != 0x640AA3C: die(...)`）**恰好把 bug 当成正确性断言**，所以静态检查全绿、真机崩。

### 2.2 修复前后（字节级）

| | v2（崩） | v3（修） |
|---|---|---|
| `0xF2C24A0` | `58000090` `ldr x16,#16` | `90fb8a50` `adrp x16, 0x640a000` |
| `0xF2C24A4` | `d63f0200` `blr x16` | `9128f210` `add x16,x16,#0xa3c` |
| `0xF2C24A8` | `14000004` `b +16` | `d63f0200` `blr x16` |
| `0xF2C24AC` | `d503201f` `nop` | `b940da60` `ldr w0,[x19,#0xd8]`（原第 4 条） |
| `0xF2C24B0` | `0640aa3c 00000000` 字面量 | `14000006` `b replay_end` |
| 运行时 `x16` | `0x0640AA3C`（RVA） | `base + 0x640AA3C` |

`adrp` 的立即数是 **−36536 页**（`0x640A000 − 0xF2C2000 = −0x8EB8000`，共 −36536 页），
在 ±2²⁰ 页（±4 GB）范围内，同一 `.so` 内永远够。运行时：

```
adrp : x16 = (base + 0xF2C2000) − 0x8EB8000 = base + 0x640A000
add  : x16 = base + 0x640A000 + 0xA3C        = base + 0x640AA3C   ✔
blr  : 目标 = base + 0x640AA3C = 0x72C265BA3C（base=0x72BC251000 时）
```

### 2.3 为什么用 `adrp+add` 而不是"从 `g_state` 取 base"

任务书说"复用 B0 里已有的基址"。**技术上 `adrp+add` 与 `add x16, g_state->base, #RVA`
的运行时结果完全相同**，但它有三个硬优势，所以选了它：

1. **不依赖状态页**。`g_state` 在 mprotect/mmap 失败时是 0，`ldr [g_state,#0x20]`
   会变成空指针解引用 —— 那会把 v2 承诺的"失败也不崩"直接打掉。`adrp` 是纯 PC 相对，
   状态页坏了、没发布、被 ACE 改了都无所谓。
2. **热路径零成本**。回放路径每个触发器调用都要走（触发器有 **413,726** 个调用点），
   从状态页取 base 要多 2 条 `ldr` + 一个 `cbz`；`adrp+add` 就 2 条算术，且比 v2 的
   6 字跳板还短 3 字。
3. **这个写法在本包里已经被真机证明过**：触发器 stub `0x63C77FC` 就是
   `adrp/add/br`（report 51/58 的设计），这次崩溃时 `lr` 在洞页里，说明这条 stub 确实
   把控制流送进来了。`replay_end` 的 `adr + sub + add + br` 同理。

> 如果 Lead 坚持要"从状态页取 base"的写法，改动只有一行：把 `veneer_pc_rel()` 换成
> `adrp g_state; ldr; ldr [x,#ST_BASE]; ldr literal rva; add; blr`（6 字）。
> 不推荐（见上面 3 条），但接口是现成的。

### 2.4 同一生成器里的 `B`（无条件跳转）也有同一个 bug

`relocate_insn_expand()` 里越界的 `B` 用的是 `ldr x16,#8 ; br x16 ; .quad tgt`（4 字）——
**同样的"RVA 当绝对地址"**。本触发器的 4 条指令里没有 `B`，所以真机没暴露，但 v3 一并改成
`adrp+add+br`（3 字）。这是"同类 bug 不止一处"的第一处（见 §4 表 A5）。

## §3 `+0x200` 疑点（C0 第 3 值）的调查结论

### 3.1 结论先给

**未确定来源；不是 v2 的偏移算错；保留原值 `0x10496434`。**

### 3.2 三条互相独立的证据都指向 `0x10496434`

**(1) 原厂 `.dynamic` 的 DT_INIT 就是 `0x10496434`**

```
PT_DYNAMIC @ 0xfa2f000 附近；DT_INIT 条目 @ 0xfa2fc48，d_val = 0x10496434
VA→文件偏移：0x10496434 在 PT_LOAD#10（p_vaddr=0x10494000, p_offset=0x1024c000）
             → 文件偏移 0x1024e434（**注意 VA≠offset**）
反汇编（0x10496434 是标准函数入口）：
  10496434: a9bf7bfd  stp x29,x30,[sp,#-16]!
  10496438: 910003fd  mov x29,sp
  1049643c: 97ffff16  bl  0x10496094
```

**(2) `logic.c` 的常量是 `0x0010496434`，`build.py` 还断言输入必须是它**

```c
#define ORIG_DT_INIT     0x0010496434UL   /* 原厂 DT_INIT（C++ 静态初始化） */
```

```python
DT_INIT_ORIG = 0x0010496434
if init_val != DT_INIT_ORIG: die("DT_INIT = %#x != 原厂 %#x …" % ...)
```

**(3) 成品机器码里，两条路径（尾调 + C0 日志）都只拼得出 `0x10496434`**

v2 的尾调：`0xf2c29c4 movz w22,#0x6434` + `0xf2c29ec movk w22,#0x1049` → `x22 = 0x10496434`，
后面 `0xf2c2b3c add x8,x19,x22 ; blr x8`；
v2 的 C0：`0xf2c2ac0 movz w5,#0x6434` + `0xf2c2ee0 movk w5,#0x1049` → `x5 = 0x10496434`（第 3 字段）。

v1 完全一样（`0xf2c29a8/0xf2c29b0` 与 `0xf2c2a64/0xf2c2a7c`），v2data 也一样
（`0xf2c2ab0/0xf2c2ab4`）。**三个成品的洞内都没有一条 `imm16 = 0x6634` 的指令**
（`tools/v3_scan_imm.py`，见 §5.2），三个文件里也没有 `0x0000000010496634` 这个 64 位值。

### 3.3 为什么"真机不可能真的跳到 +0x200"

这条是独立于日志的**逻辑反证**：`0x10496434 + 0x200 = 0x10496634` 落在原厂 DT_INIT **函数体中间**，
不是函数入口（没有 `stp x29,x30,[sp,#-16]!` / `mov x29,sp`）：

```
  10496634: 5280014c  mov  w12,#10
  10496638: 2a0b414a  orr  w10,w10,w11,lsl#16     ; w10/w11 是"上一段代码的残留"
  1049663c: 4a0c0129  eor  w9,w9,w12
  10496640: 2a096149  orr  w9,w10,w9,lsl#24
  10496644: 51434129  sub  w9,w9,#208,lsl#12
  10496648: 7138993f  cmp  w9,#3622               ; 像一段校验和比较
  1049664c: 540000e1  b.ne +28
  10496650: 52800029  mov  w9,#1
  10496654: 3911e909  strb w9,[x8,#1146]          ; ← x8 未初始化：野写
```

从中间进入：跳过 prologue ⇒ 函数尾部 `ldp x29,x30,[sp],#16; ret` 会弹一个不存在的栈帧
（x30 = 垃圾）⇒ 要么在 DT_INIT 里就炸，要么返回到野地址。而真机是**启动成功、到 1.9 秒
Unity 起来、托管方法开始调用**才崩在洞里的回放槽 —— 说明 DT_INIT 的尾调**正常返回了**，
它用的必然是 `base + 0x10496434`。

### 3.4 那 `+0x200` 到底是什么

诚实写：**未确定**。可能性按概率排：

1. **日志与成品不是同一份字节**（最可能）。probe.log 的 C0 是设备上跑的那份打出来的；
   如果那份不是 `AA833EAA…`（比如现场又重编过一次、或拷的是别的构建），C0 就会跟我们对不上。
   **验证方法**（下一轮顺手做）：设备上
   `adb shell su -c "sha256sum $LIB_PATH"`，与 `AA833EAA…604A4F` 对比。
2. 抄写/转录误差（0x10496**4**34 → 0x10496**6**34）。
3. 某个我这轮看不到的构建用了 `0x0010496634`（本仓库里搜不到任何来源）。

**处理**：保留 `0x10496434`（= 原厂 DT_INIT，且与"启动成功"这一现象自洽）。
**不做任何"顺手对齐"的改动**——真改成 `0x10496634` 反而必然崩在 DT_INIT。

### 3.5 顺带：其它硬编码 VA 常量的全面核对（"同类偏移错"排查）

用原厂 ELF 的段表 + `.dynsym` 逐个核（`tools/v3_audit.py` 的 `[B]` 段）：

| 常量 | 值 | 落在哪个段 | 可执行 | 判定 |
|---|---|---|---|---|
| `CAVE_VA` | `0x0F2C2410` | —（= RX 段 `p_filesz` 终点，段外） | 否 | ✔ 正确：洞首就是段终点，`build.py` 断言 |
| `TRIG_VA` | `0x063C77FC` | #2 `XR [0x59B8000,0xF2C2410)` | 是 | ✔ 在代码段内，且是函数入口（`stp x19,x30`） |
| 回放 BL 目标 | `0x0640AA3C` | #2 `XR` | 是 | ✔ 是合法 RVA；**但它是 RVA，不能当地址用**（v2 的 bug） |
| `ORIG_DT_INIT` | `0x10496434` | #10 `XR [0x10494000,0x10497370)` | 是 | ✔ 是函数入口；**该段 VA≠文件偏移**，只能按 VA→offset 换算 |
| `OFF_FOR_EACH` | `0x063C3B50` | #2 `XR` | 是 | ✔ 与 report 58 的 `il2cpp_class_for_each` 一致 |
| `OFF_GET_METHODS` | `0x063C2EA8` | #2 `XR` | 是 | ✔ 同上（report 58：桩体 `0x640B084`） |
| `OFF_METHOD_NAME` | `0x063C37BC` | #2 `XR` | 是 | ✔ = `OFF_GET_METHODS + 0x914`，与成品里编译器自己算的 `add x23,x21,#0x914` 互证 |
| `OFF_PARAM_COUNT` | `0x063C37CC` | #2 `XR` | 是 | ✔ = `OFF_GET_METHODS + 0x924`，成品里 `add x8,x9,#0x924` 互证 |
| `EXEC_LO` | `0x05000000` | #1 `R [0,0x59B4E54)` | **否** | ⚠ 偏松：真正的代码段起点是 `0x59B8000`。只用于 `install()` 的"像不像代码指针"下界，偏小=只放宽、不误判，**不改**（改了等于收紧行为，与本轮无关） |
| `EXEC_HI` | `0x104B3E90` | —（= 模块上界） | — | ✔ 恰好等于 `max(p_vaddr+p_memsz)`，是**不含末地址**的正确上界 |
| `MOD_MAX` | `0x11000000` | — | — | ✔ 比真实跨度 `0x104B3E90` 大，保守（只影响 `k >= base+MOD_MAX` 的拒绝范围） |

**没有任何一处存在 `+0x200` 型的固定偏移错误。** 唯一的"偏移类"问题就是 §2 的那个

### 5.5 新增的两条诊断（`T0` / `T1`）


- **T0**：`cave_main` 里，`M1` 之后立刻打，**早于任何一次触发器回放**，且不受
  mprotect/mmap 成败影响（`fd < 0` 时 `log4f` 自己会丢弃）。1 次。
- **T1**：`cave_on_trigger`（慢路径，约 1/256 次触发）开头打，**紧挨着回放之前**；
  只打前 3 次（`st->t1n < 3`），1/256 × 3 不会刷爆日志。
- 两者都经 `0xF2C2F30` 这个 2 指令 wrapper（`mov x6,#0; b log4f`）调用，第 4 字段恒 0。

## §7 若还崩，下一个怀疑点（按概率排序）

### 7.1 目标页 `0x640A000-0x640E000` 没解密 / 不可执行（最可能）

- 回放 BL 的目标 `0x640AA3C` 落在 report 58/91 标记的"疑似 ACE 加密页"
  （`0x640A000-0x640E000`），`il2cpp_class_get_methods` 的桩体 `0x640B084` 也在这一段。
- 若 tombstone 的 `pc == T0 第 3 值`（`base+0x640AA3C`）且 `esr` 仍是取指异常：
  **我们的寻址已经正确**，问题变成"这一页在那一刻不可取指/内容未解密"。
- 排查：
  1. 在慢路径里读 `*(u32*)(base+0x640AA3C)` 打一行（`P1`），看是否等于原厂文件里的字：
     `python -c` 读 `libil2cpp.bin` 偏移 `0x640AA3C` 即可对照；
  2. 若运行期内容 ≠ 文件内容 ⇒ 该页运行期被改写/加密，需要换触发器（BL 直方图 rank 2/3，
     且 BL 目标不在加密页）；
  3. 若 `mprotect` 显示该页 `r-x` 但取指仍 fault，考虑 ACE 用 `userfaultfd`/段保护；
     备选是把回放也改成"不调用原函数"的语义等价替代（风险大，另议）。

### 7.2 `install()` 写 MethodInfo 数据页

- 位置：`logic.c` 的 `install()`，v3 里写槽指令是 `0xF2C2E54 stur x8,[x10,#-8]`
  （v2 是 `0xF2C2D80`；v3 因布局位移 +0xD4，以 build 日志符号为准）。
- 已改成 `mprotect(page, PROT_RW=3)`（v1 的 `6` 是 W|X，已修），失败打 `!` 并跳过。
- 若 `!0` 的 `rc` 是负：看 errno；若 `rc=0` 仍崩：用 `/proc/self/mem` + `pwrite` 写槽。

### 7.3 il2cpp API 偏移 / ABI

- `C0` 的三个常量本轮已复核：`for_each=0x63C3B50`、`get_methods=0x63C2EA8`、
  `orig_init=0x10496434`（§3.5）。
- 若 `S` 有、`R` 无、崩在 `on_class`：先怀疑 `get_methods(klass,&iter)` 的签名/迭代器语义，
  或 `method_get_name` 返回的不是 `const char*`；可把 8192 上限降到 256 做二分。

### 7.4 `probe_str` 的野指针

- 现象：`A0` 已出，随后崩在 `probe_str`；`Q0` 的 argc 异常（=8）。
- 备选：`probe_str` 的 `length` 上限从 4096 降到 256；或只对 `tag==0 && argc==1` 探 `x1`。

### 7.5 状态页被 ACE 扫到

- 现象：M1/M2/B0 正常，过一段时间才崩，且 pc 不在我们的写指令上。
- 备选：状态页改为"借 libil2cpp `.bss` 空槽"，或发布后 `mprotect(状态页, PROT_READ)` 只在写时临时 RW。

### 7.6 一句话排查顺序

`M1`（页可写？）→ **`T0`（base/rva/target 自洽？）** → `M2`（状态页拿到？）→ `B0/C0`
（发布/武装？）→ `T1`（回放时刻 base 仍对？）→ `S/R`（扫描跑了？）→ `P/Q/A`（detour 命中？）。
**若新 tombstone 的 pc 等于 `T0` 第 2 值（`0x640aa3c`），先怀疑"装的不是 v3"，
不要怀疑修法。**
