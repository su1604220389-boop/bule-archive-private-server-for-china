## 2. 解码验证（三步，全部通过）

任务要求"先用 5004670 验证能解出…再用"。实测该 `Bytes` 容器并非任务描述的那种 8 字节对齐托管布局，而是**自定义前置偏移表容器**：

```
u32 payload_start (LE)   ← 0x2c (ShopRecruit) / 0x20 (LocalizeGachaShop)
u16[] field_offsets      ← N = (payload_start - 6) / 2 个，相对 payload_start
payload                  ← 字符串 = [u32 len(LE)][UTF-8][0x00][对齐到 4]
```

因此任务给的那套 `Id@0x10 / SalePeriodFrom@0x30` 偏移**对本文件不成立**（实测 0x10 处是偏移表内容，不是 Id）。我改用两条数据驱动的路径并做了交叉验证：

### 验证 1 — 日期串直取 + 全量回归（最强证据）

用正则 `\d{4}-\d{2}-\d{2} \d{2}:\d{2}:\d{2}` 从 532 个 blob 里直取日期串：

- 529 行各有 **恰好 2 个**日期串；`1`、`2`、`3` 三行为 **0 个**（无销售期）。
- 取 `min` 为 `From`、`max` 为 `To`，导出为 ISO 后**与线上 529 条配置逐字节比对**：

```
regenerated bytes: 40739    original bytes: 40739
BYTE-IDENTICAL: True
```

即：**用"日期串 + min/max + 空格换 T"重生成，能 1:1 复刻线上那 529 条 JSON（40739 字节完全相同）**。这同时确认了三件事：日期解析正确、`From/To` 语义正确、候选 JSON 的序列化格式（`json.dumps(..., ensure_ascii=False)`，无缩进、无换行、无 BOM、按 id 升序）正确。

### 4.4 那 3 个 `DUMMY` 页签到底是谁？

由于数据里没有 `DUMMY`，只能从"页签名解析失败"这个行为反推。窗口内恰好 **10** 个池覆盖当前时刻，而界面只显示 **4** 个页签，说明客户端对池子做了二次筛选。下面给出两条证据链。

#### 证据链 A（推荐，唯一能解释"第 1 个页签 = 5004670"）

- 若页签按 `DisplayOrder` 升序排列，且只取常规招募类（CT 5 / 6 / 19）：
  `5004670(10) → 5004680(20) → 5004690(30) → 5004700(40) → 5004710(50) → 5004660(60)`
- **第 1 个 = `5004670`（美咲·泳装）**，与用户观察**完全吻合**；
- 随后 3 个即 `5004680` / `5004690` / `5004700`。

补充旁证：`5004680` / `5004690` 的页签名串段本身就是**开发占位文案**——
`限定限时招募 1` / `限定限时2`（对应韩文 `限定限时1` / `限定限时2`），
而不是像 `5004670` 那样有可用的通用页签名。这类占位名在客户端侧最容易解析失败。
（`5004700`/`5004710`/`5004670` 的页签名同为通用 `限时招募`，三者无结构差异，故这一条只能算旁证。）

⇒ **最可能：3 个 `DUMMY` 页签 = `5004680` / `5004690` / `5004700`。**

#### 证据链 B（备选）

`ShopRecruit` 里**唯一 3 条**具备"模板/占位行"全部特征的，是 `1` / `2` / `3`：

| 特征 | `1` | `2` | `3` | 其余 529 行 |
|---|---|---|---|---|
| 在线上 529 条配置里 | ❌ 不在 | ❌ 不在 | ❌ 不在 | ✅ 在 |
| `SalePeriodFrom/To` | **空** | **空** | **空** | 有值 |
| 销售期串段（日期） | 无 | 无 | 无 | 有 |
| `CategoryType` | 11 | 11 | 32 | 5/6/19/22/23/24/35 |
| 页签名 | `限时招募` | `长期招募` | `长期招募`（源自 `튜토리얼 모집` 教学招募） | 池专属或通用 |
| 本地化串段数 | 8 | 8 | 8 | 多为 5 |

它们就是 `532 - 529 = 3` 的那 3 行，且是**唯一 3 条无销售期**的行。若客户端的时段过滤把"空销售期"当成"永久开放"，这 3 行就会额外渲染成页签，而服务端 529 条配置里没有它们的 `From/To`（下发的 `SalesStartDate/SalesEndDate` 为 `0001-01-01`），页签名/档期解析失败 → 回落成界面默认 `DUMMY`。

⇒ 这一条也能得到"3 个"，但**无法解释"第 1 个页签是 5004670"**（1/2/3 的 `DisplayOrder` 与 5004670 无此先后关系）。

**最终判断：以 A 为准（`5004680` / `5004690` / `5004700`），B 列为备选。** 二者都需要抓一次 UI 或客户端日志才能 100% 定案 —— 因为**字符串层面根本不存在 `DUMMY`**，只能靠渲染行为反推。

## 7. 风险与建议

### 7.1 核心风险：这份清单会把正在跑的泳装活动全部干掉

- 当前窗口内 10 个池里，**5 个真实限时/限定池全部无卡面图**：`5004670`(美咲·泳装)、`5004680`(纱织·泳装)、`5004690`(日和·泳装)、`5004700`(白子·泳装)、`5004710`(野宫·泳装)。
- 原因不是数据缺失的偶然，而是**本库对 `CategoryType` 5 / 19 / 24 从不导出 `GachaBannerPath`**（0/260、0/83、0/16）。
- 因此"必须有卡面图"这一条筛选条件，等价于"**只保留常驻 + 特殊商店，删掉所有限时/限定活动**"。用之前请确认这是不是想要的结果。

### 7.2 若目标是"页签不再显示 DUMMY"，正确做法不是删池子

按 §4 的分析，3 个 DUMMY 页签的成因是**页签名解析失败**，不是"池子不该存在"。建议按优先级：

1. **先补 `GachaBannerPath`**：给 CT 5/19/24 的池子填 `uis/00_images/banner/Event_Banner_*`（对齐 CT 6 的命名规律）。这一步同时解决"卡面图缺失"和"页签无内容"。
2. **检查 `CategoryType` 22/23/35 的两条哨兵 + 两条特殊商店**是否应该出现在常规页签序列里（`90000000` 起始时间 `2026-07-16` 已过 4 个月、`7000001` 起始 `2025-08-14` 已过 15 个月，都是"永久挂"）。
3. **`1`/`2`/`3` 三行**建议在客户端侧确认是否被当成永久池渲染；若会，需在客户端表里剔除，或给它们补 `SalePeriod`。
4. 抓一次 UI（或客户端 `LocalizeGachaShop` 查询日志）以把 §4.4 的 A/B 两案定案 —— 这是唯一能把"`DUMMY` 到底是哪 3 个 id"从推断变成证实的手段。

### 7.3 次要观察

- `IsLegacy` 全表 532 行为 `false`，该字段在本库里**没有信息量**，别拿它做筛选。
- `LocalizeGachaShop` 有 1235 行，但只有 532 个 id 能对上 `ShopRecruit`；剩 703 行是历史/别的服 id（如 `50000`、`69996`、`80100`），别误当"有本地化=可渲染"。
