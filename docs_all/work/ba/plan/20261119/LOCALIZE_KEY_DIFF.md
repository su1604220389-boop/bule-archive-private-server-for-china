### 1.2 判定

看 `LocalizeGachaShop` row0 的头 0x20 字节：

```
00000000  20 00 00 00 00 00 00 00  18 00 30 00 28 00 24 00
00000010  20 00 1c 00 18 00 14 00  10 00 0c 00 08 00 04 00
00000020  18 00 00 00 2c 00 00 00  30 00 00 00 a4 00 00 00
```

- `0x00 = 0x20` → **root table 在 0x20**（uoffset，不是「段长度」）。
- `0x08` 起是 vtable：`18 00`=vtable 长度 24、`30 00`=table 长度 48，随后 `0x28 0x24 0x20 0x1c 0x18 0x14 0x10 0x0c 0x08 0x04`共 (24-4)/2=**10 个字段偏移**，单调递减 —— 这是 FlatBuffers 的 vtable 指纹。
- `0x20`：`18 00 00 00` = soffset_t 24，回指 `0x20-0x18 = 0x08`，正好是上面的 vtable ✅
- 字段值是 `table + field_offset`，字符串是 `uoffset32 → u32 长度 + bytes + NUL`。
- 末尾 `01 00 00 00` = `GachaShopId`（第 0 字段，offset 0x28 → 0x20+0x28=0x48）。

> 结论：**不是**「u32 LE 长度 + UTF-8 若干段」。段落长度确实存在（每个字符串前 4 字节），但外面还套着 FlatBuffers 的 table/vtable 结构，而且**字段位置逐行不同**。

### 1.3 为什么「固定偏移布局」在这张表上必错

FlatBuffers 写入时**省略等于默认值的字段**，vtable 也随之自动截断，因此：

- 同一张表里，字段的绝对偏移**逐行变化**；
- 未设置的字段干脆不在 vtable 里（不是「填 0」）。

实测 `ShopRecruitDBSchema` row0（Id=1）的 vtable 只有 0x26 字节 → 13 个字段存在、4 个被省略（`IsLegacy`/`DisplayTag`/`LinkedRobbyBannerId`/`InfoCharacterId` 都是默认值）。

所以任务里给的「`Id`@0x10、`CategoryType`@0x18、`SalePeriodFrom`@0x30（16 字节 `DateTime?`）…」在这批 blob 上不成立 —— 0x10~0x2b 整段其实是 **vtable**：

```
  Id                         @0x10 bytes=44 00 3c 00 38 00 00 00 2c 00 28 00 24 00 00 00
  CategoryType               @0x18 bytes=2c 00 28 00 24 00 00 00 00 00 23 00 1c 00 18 00
  IsLegacy                   @0x1c bytes=24 00 00 00 00 00 23 00 1c 00 18 00 0c 00 04 00
```

读出来的是 vtable 条目（0x44/0x3c/0x38…），不是字段值。而且 `SalePeriodFrom` / `SalePeriodTo` 实际是 **string**（形如 `2023-08-10 15:59:59`），不是 16 字节 `DateTime?`。

### 1.4 正确的解析函数

权威 schema 不必猜：仓库里就有 FlatBuffers 官方生成的 C# 类 `work\ba\srv_src\Schale\FlatData\ShopRecruitExcel.cs` 与 `LocalizeGachaShopExcel.cs`（字段号 = `(__offset(N) - 4) / 2`）。
下面这段是脚本里的实现，可直接复用：

```python
def vtable(buf, tab):
    """table 头部的 i32 soffset 回指 vtable -> (vt, vlen, tlen)"""
    vt = tab - struct.unpack_from("<i", buf, tab)[0]
    vlen = struct.unpack_from("<H", buf, vt)[0]      # vtable 字节长
    tlen = struct.unpack_from("<H", buf, vt + 2)[0]  # table 字节长
    return vt, vlen, tlen


def fb_fields(buf):
    """-> {field_index: 该字段在 blob 里的绝对位置}"""
    tab = struct.unpack_from("<I", buf, 0)[0]        # root uoffset
    vt, vlen, tlen = vtable(buf, tab)
    out = {}
    for i in range((vlen - 4) // 2):
        off = struct.unpack_from("<H", buf, vt + 4 + 2 * i)[0]
        if off:                                      # 0 = 该字段未设置
            out[i] = tab + off
    return tab, out


def fb_string(buf, pos):
    """字段位置上是 uoffset32 -> u32 长度 + UTF-8 bytes + NUL"""
    tgt = pos + struct.unpack_from("<I", buf, pos)[0]
    n = struct.unpack_from("<I", buf, tgt)[0]
    return buf[tgt + 4: tgt + 4 + n].decode("utf-8")


# --- LocalizeGachaShopDBSchema ---
# 下面这张名字表来自 srv_src 的【通用多语言版】class（21 字段 / 5 语言）。
# 但国服这版实测只有 10 个字段（f0 + 5 组 Cn/Kr 配对，见 §2.2）：
# 奇数字段 f1/f3/f5/f7/f9 才是中文，偶数字段 f2/f4/f6/f8 是韩文。
# 下面的名字仅作占位标识，语义以字段号 + §2.2 为准。
def parse_localize_gacha_shop(blob):
    tab, fields = fb_fields(blob)
    d = {}
    for idx, name in enumerate(LOCGACHA_NAMES):
        if idx not in fields:
            d[name] = 0 if idx == 0 else None        # 未设置 = 默认值
        elif idx == 0:
            d[name] = struct.unpack_from("<q", blob, fields[0])[0]
        else:
            d[name] = fb_string(blob, fields[idx])
    return d


# --- ShopRecruitDBSchema ---
# f0=Id f1=CategoryType f2=IsLegacy f3=OneGachaGoodsId f4=TenGachaGoodsId
# f5=GoodsDevName f6=DisplayTag f7=DisplayOrder f8=GachaBannerPath
# f9=VideoId[] f10=LinkedRobbyBannerId f11=InfoCharacterId[]
# f12=SalePeriodVisible f13=SalePeriodFrom(str) f14=SalePeriodTo(str) ...
def parse_shop_recruit(blob):
    tab, f = fb_fields(blob)
    def i64(i, dv=0):   return struct.unpack_from("<q", blob, f[i])[0] if i in f else dv
    def i32v(i, dv=0):  return struct.unpack_from("<i", blob, f[i])[0] if i in f else dv
    def boo(i, dv=False): return bool(blob[f[i]]) if i in f else dv
    def s(i):           return fb_string(blob, f[i]) if i in f else None
    return dict(Id=i64(0), CategoryType=i32v(1), IsLegacy=boo(2),
                OneGachaGoodsId=i64(3), TenGachaGoodsId=i64(4),
                GoodsDevName=s(5), DisplayTag=i32v(6), DisplayOrder=i64(7),
                GachaBannerPath=s(8), LinkedRobbyBannerId=i64(10),
                SalePeriodVisible=boo(12), SalePeriodFrom=s(13),
                SalePeriodTo=s(14), RecruitCoinId=i64(15),
                RecruitSellectionShopId=i64(16), IsNewbie=boo(20),
                IsSelectRecruit=boo(21), DirectPayInvisibleTokenId=i64(22),
                SelectAbleGachaGroupId=i64(25), MaxSelectCharacterNum=i64(26))
```

### 5.2 判定：整数哈希，不是字符串名

| 证据 | 结果 |
|---|---|
| `Key` 列声明类型 | `INTEGER`（不是 `TEXT`） |

### 5.3 是不是某个字符串的 hash？逐算法验证

`LocalizeDB` 的好处是 **Key 和文本在同一行**，可以直接验证 `hash(text) == Key`。用全表 18451 条有文本的行跑 10 种算法：

| 算法 | 命中 / 18451 |
|---|---|
| `crc32` | 0 |
| `xxh32(seed=0)` | 0 |
| `xxh64(seed=0)&0xFFFFFFFF` | 0 |
| `xxh64(seed=0)>>32` | 0 |
| `murmur3_x86_32(seed=0)` | 0 |
| `fnv1a32` | 0 |
| `fnv1_32` | 0 |
| `fnv1a64&0xFFFFFFFF` | 0 |
| `djb2` | 0 |
| `sdbm` | 0 |

再取**纯 ASCII 文本**（341 条，这类译文与源文大概率逐字节相同）及其 `+NUL` 变体重跑：**全 0 命中**。

再做「候选名 → hash → 是否存在于 Key 集合」的成员测试，候选名覆盖 `GachaShop_<id>` / `<id>` / `LocalizeGachaShop_<id>` / `GachaShop<id>` / `LocalizeGachaShopExcel_<id>` × {5004670, 5004660, 7000001, 8000004, 90000000, 99999999}：

**全部 0 命中。**

1. `Key` 是 **32 位整数哈希**，不是 `GachaShop_5004670` 这类字符串名；
2. 它**不是**表内中文文本经 crc32 / xxh32 / xxh64 / murmur3 / fnv1a / djb2 / sdbm 得到的（0/18451）；
3. 也不是 `GachaShop_<id>` 这类名字经上述算法得到的（名字不存在于 Key 集合）；
4. 最可能的解释：`Key` 是**源语言（KR/JP）原文**的哈希，而国服表里只留了译文，所以原文不在库里、算不出来。这一点**只能证伪、不能证实**，本报告不把它当结论，只标注为「未验证」。

`DUMMY` 这种全大写占位串是典型的**开发期 fallback**。结合「表里查不到」这一点，最合理的解释是：**客户端/服务端在拿不到文案时回落到硬编码占位符，同时把「查不到」这件事染成红色 `No LocalizeKey` 提示**。换句话说，红字和 `DUMMY` 是**同一个失败的两面**，不是两个独立 bug。

### 6.6 第三个页签（`DUMMY`）最可能是什么

已知：`f1`（页签短名）在 **1235/1235 行全是非空**。所以只要这个页签的 `GachaShopId` 存在于 `LocalizeGachaShop`，页签名就一定有值、**不可能**显示成 `DUMMY`。

反过来推：`DUMMY` 的出现意味着客户端拿到的那个 `GachaShopId` **根本不在客户端的 `LocalizeGachaShop` 里**。结合你的架构，这只有两种可能：

| 可能 | 说明 | 怎么验证 |
|---|---|---|
| 服务端下发了表里没有的 id | BAServer 的招募配置里有客户端 ExcelDB 不认识的 `GachaShopId`（自造的、旧版的、或跨版本抄来的） | 抓客户端请求/服务端响应，把下发的 `GachaShopId` 与 `_tmp\localize_gachashop_ids.txt` 求差集 |
| 客户端拼错了 key 形态 | 不是整数 id，而是 `GachaShop_<id>` 之类的字符串 → 命中失败 | 在客户端 `LocalizeGachaShop` 查表点下断，看传进去的键是什么类型/什么值 |

**注意这跟任务最初的怀疑并不矛盾，而是同一件事的精确化**：「客户端查表的 key 跟我们以为的 id 不是同一个」——在**表这一侧**已被证伪（§4 差集为 0）；但在**服务端下发这一侧**仍然完全可能成立，而且它是唯一能解释 `DUMMY` 的假设。

> 另外两个页签也已定位：`7000001`（新手冲刺Ⅱ，🟢 开放，但 `f9` 档期槽为空）与 `8000004`（3★自选招募，🟢 开放，`f9` 有值）。如果红字只在「新手冲刺」页签出现，那 §8.2 第 2 条（档期槽空）立刻成立。

## 8. 这些数据说明了什么 / 下一步该查哪里

### 8.1 已被数据排除的假设

- ❌ **「客户端用的 key 和我们以为的 id 不是同一个」**：532 个 `ShopRecruit.Id` **100%** 命中 `LocalizeGachaShop`，方向 A 差集是空集。拿 `ShopRecruit.Id` 去查这张表**不可能 miss**。
- ❌ **「两张表是两套 id 空间」**：多出的 703 个是 5 位 legacy 号，不构成第二套体系（§4.3）。
- ❌ **「`LocalizeGachaShop` 里没有这条文案」**：`5004670` 等行 5 段文案齐全（§2.4），5 个 banner id 也都有完整行（§7）。
- ❌ **「`LocalizeGachaShop` 的行数和 `ShopRecruit` 对不上所以有问题」**：532 ⊂ 1235 是设计如此（历史行 + 当前行），不是数据损坏。

### 8.2 数据指出的可疑点（按可疑度排序）

1. **界面上那 3 个文案，没有一个能从这张表原样取到**（§6.5）：`DUMMY` 全库 0 处、`新手冲刺!!` 全库 0 处、只有 `3★自选招募` 命中。「查不到 → 回落占位串 + 染红提示」这个解释能同时对上 `DUMMY` 和红字，**是目前最自洽的一条**。
2. **档期槽 `f9` 只有 529/1235 行有值**（§2.2、§3.3）：其余 706 行 `f9` 是空的。如果客户端把「档期」当独立控件按 `f9` 取值，那么打开这些行时档期就会落空。已开放的行里也有 `f9` 为空的（见 §3.3 最后两列），可直接拿那几行去复现。
3. **`LocalizeDB.Key` 是 hash，拼串规则必须逐字节一致**（§5.3）：10 种算法 × 多种候选名 0 命中，说明「`GachaShop_<id>` 拼串再哈希」这条路在本库里走不通。若客户端走这条路径，任何前缀/大小写/分隔符差异都会全 miss。
4. **`LocalizeGachaShop` 的真实 schema 只有 10 字段**（§2.2）：`srv_src` 里那份 21 字段的 class 是通用多语言版，字段名整体错位。如果之前的排查按 `TabNameKr=韩文` 的假设写了代码，取到的会是错槽。

### 8.3 建议的下一步（都还没做，本报告只到此为止）

- **抓客户端 `LocalizeGachaShop` 的查表调用点，确认它读的是 f 几**。拿到槽位号后，用 §2.2 的填充率直接算出该槽的空值率，一眼就知道能不能解释红字。
- **确认 `DUMMY` 是代码常量还是服务端下发**。它在 160 MB 库里 0 命中，只可能来自这两处之一；如果是服务端下发，就直接查 BAServer 里 tab 配置的默认值。
- **拿「已开放但 `f9` 为空」的行去复现**（§3.3），看红字是否正好出现在档期位置。
- 若要验证 `LocalizeDB.Key` 算法：需要一份**源语言原文**与 Key 的对照。本库只留译文，信息不足，**这条不建议再投入**。
