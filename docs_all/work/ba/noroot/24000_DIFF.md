## 8 · Q1–Q5 逐条回答

### Q1 · 71 个 zone 的数组长度分布；客户端会要求某些 zone 必须有角色吗？

**官方实测**：`{0: 1, 1: 20, 2: 32, 3: 18}`，共 **138 个元素**，**只有 key `"1"` 是空数组**。
**我们**：71 个全空。

**判断：结构上绝对合法，不是反序列化障碍。** 理由三条：
1. 类型是 `Dictionary<string, List<T>>`，`[]` 对任何 `List<T>` 都合法（`report/70` §4 也这么认为）。
2. 官方自己在 key `"1"` 上就发了 `[]` ⇒ 空数组是服务端会真实产生的东西。
3. 我们一个元素都没有 ⇒ 元素类型从未被"暴露"，客户端连类型不匹配的机会都没有。

**但语义上是"空世界"**：官方这个 32 级号有 138 条"学生拜访某 zone"的记录，新号自然是 0。若客户端在学院界面里对"某个 zone 必须能找到角色"做非空断言，会崩 —— 这是 *可能但无证据*，按 **P1** 处理，不做 P0。

### Q2 · `AcademyLocationDBs` 9 条 vs 1 条，多严重？

**中等（P1），不是反序列化障碍**：数组长度差异不抛异常。
但两点必须说清：
1. **`AccountId: 0` 是任务书的误判**。`gen24000`/v2/v3 里同一变量 `aid` 同时写 `SessionKey.AccountServerId`、`AcademyDB.AccountId`、`AcademyLocationDBs[].AccountId`；三者**不可能**一个是账号号、一个是 0。真正会显示成 "AccountId 缺失/0" 的是**旧基线** `_baseline/account_auth_probe.py:798-808`，它发的行只有 3 键 `{LocationId,Rank,Exp}`（**没有 AccountId**）。⇒ 你看到的 `AccountId: 0` 那条样本来自 **v3 之前**的响应。
2. 官方 `Rank` 不是全 1（`[2, 1, 1, 2, 1, 1, 2, 2, 2]`），`Exp` 只有 19 号是 200。我们 `all9` 是 Rank 全 1、Exp 全 0。新号用全 1 是合理初值（`initial_state_rules q8`），**不算错**。

### Q3 · `MxToken` 36 vs 64 字符，客户端会校验长度吗？

**先在事实层面纠正：我们不是 36 字符。**
- 官方：64 字符 base64，解码 **48 B**。
- 我们（v3）：64 字符 base64，解码 **48 B**。
- 本地 12 份 24000 样本（`report\_tmp\t24000*.json` 等）**逐一检查，无一例是 36 字符 GUID**。
- 代码层面 `patch_24000_v3.py:_ba24000_pick_token`：请求体 `MxToken` > 会话 > `sha384→base64`，**三条分支都产出 64 字符**。

⇒ **"36 字符 GUID" 未找到任何证据，判定为过时结论**（很可能来自 v1/更早的 `uuid4()` 实现）。

若线上真的出现 36 字符，那必然是**另一个补丁**在跑。**一行验证**（看服务器日志的这三个字段）：
```
grep -o '"academy_token_len":[0-9]*\|"academy_token_is64":[a-z]*\|"academy_token_src":"[a-z]*"' /www/wwwroot/bapatch/logs/api_all_requests.log | tail -20
# 期望：len=64 / is64=true / src=request 或 session
# 若 src=generated 且 is64=false -> 才是你说的问题
```

至于"客户端会不会校验长度"：**无法从我们的数据判定**（没有客户端侧证据）。但 64 字符 base64 是本仓库所有证据的一致形态，**保持 64 即可**。

### Q4 · `ServerTimeTicks` 量级对不对？

**对。** 官方 `639304002548158993`（18 位），我们 `639304064280547870`（18 位），同为 .NET 100ns 纪元（0001-01-01）。

**但坐标系要盯**：官方 ticks 反算 = `2026-11-16T04:30:54.815899`，与同一文件 `meta.bj = 04:30:54.980` 对齐 ⇒ **官方 ticks 存的是本地墙钟 UTC+8，不是 UTC**。
⇒ 若线上是 **UTC 时区的容器**，`datetime.now()` 会给出 UTC，ticks 比官方约定**少 8 小时（288,000,000,000 个 tick）**。这是**可验证的 P1**：
```
python3 -c "import datetime;t=int((datetime.datetime.now()-datetime.datetime(1,1,1)).total_seconds())*10**7;print(t, datetime.datetime(1,1,1)+datetime.timedelta(microseconds=t//10))"
date -Is   # 两者应相差 < 2 秒；若差 8 小时 => 容器 TZ=UTC，需要 TZ=Asia/Shanghai
```

### Q5 · `LastUpdate` 格式对不对？

**格式对，精度有坑。** 官方 `2026-11-16T04:00:06.479`；我们 `2026-11-16T06:13:48.054`。
两者都是"ISO + 毫秒 + 无时区"，`按 yyyy-MM-ddTHH:mm:ss.fff` 都能解析。

**坑**：`gen24000.b24000_fmt_time` 会 `rstrip("0")` 裁掉尾零，⇒ 毫秒为 `xx0` 时输出 **2 位**小数（如 `2026-11-16T06:13:47.88`），为 `x00` 时 **1 位**，为 `000` 时**连小数点都没有**（`2026-11-16T06:13:48`）。实测 **10.0% 的请求**会落到非 3 位小数（900/1000 才是 3 位）。
若客户端用 `ParseExact(..., "yyyy-MM-ddTHH:mm:ss.fff")` 就会抛异常 ⇒ **偶发失败（10%）**，不是"每次都失败"，所以不是本次卡点，但**必须修**（P1）。
