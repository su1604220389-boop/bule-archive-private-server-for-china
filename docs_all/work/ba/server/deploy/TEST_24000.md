### 2.3 与官方抓包逐字节比对（最重要的一条）

```
$ python work\ba\server\deploy\gen24000.py --fidelity
fidelity         : BYTE-IDENTICAL  引擎 11685 B / 官方 11685 B
   外层 requestid == 内层 RequestId: YES
```

做法：把官方抓包里的 4 个动态值（AccountId / MxToken / RequestId / ServerTimeTicks）、
9 条 `AcademyLocationDBs`、276 条 zone 访问记录一起喂给引擎，输出**逐字节等于**官方 `packet`（11,685 B）。

⇒ **引擎的序列化（键序、紧凑分隔符、时间格式）与官方完全一致**。
我们产出的字节数如果和 11,685 不同，只可能是"数据不同"，不可能是"格式不同"。

### 2.4 时间口径（顺带查清了）

官方 109 条响应里所有时间字符串的小数位分布：

```
0 位 2656 条 / 1 位 6 条 / 2 位 135 条 / 3 位 3102 条 / 8 位 20 条 / 9 位 154 条
例：2026-08-01T03:53:25.6  2026-08-01T04:06:07.03  2026-11-16T04:30:59.14735832
```

尾零被裁掉（`.6`/`.03`/`.14735832`）⇒ 官方用的是 Go `RFC3339Nano` 风格。
`b24000_fmt_time(frac=3)` 正好复现这一行为：毫秒 3 位、尾零裁掉（`…06.479` / `…34.02`）。

`ServerTimeTicks` 口径：官方抓包 `639304002548158993` 换算 = `2026-11-16T04:30:54.815899`，
与同一份抓包 meta 的墙钟 `04:30:54.980` 对齐 ⇒ **单位 100ns、取服务器本地墙钟**（不是 UTC）。
所以引擎用 `datetime.now()` 算 ticks，`LastUpdate` 由同一 ticks 反推，两者天然同坐标系。

## §6 已知边界 / 上机要观察的点

### 6.1 inner 字节数 1040 ≠ 官方 11685（这是数据差，不是格式差）

| 组成 | 官方那个 32 级号 | 我们的新号 |
|---|---|---|
| `AcademyLocationDBs` | 9 条 | 1 条（可配置成 9 条 → 1511 B） |
| `ZoneVisitCharacterDBs` 值 | 276 条角色记录（140 个非空 zone） | 71 个空数组 `[]` |
| `SessionKey.MxToken` | 64 字符 | 64 字符 |
| **inner 合计** | **11,685 B** | **1,040 B**（all9 = 1,511 B） |

§2.3 的 fidelity 测试已经证明：**把官方数据喂进去，引擎输出逐字节等于 11,685 B**。
所以线上日志里看到 `academy_inner_bytes≈1040` 是**正常的**，不要按 11,685 去判"部署没生效"——
判生效请用 `gen_kind='academy-24000'` + `gen_v='v2'` + `academy_rid_match=True` + 顶层 7 键。

### 6.2 `AcademyLocationDBs` 给 1 条还是 9 条（**上机第一个要看的点**）

`initial_state_rules.q8`：Rank/Exp 初值 high 置信（`Rank=1, Exp=0`），**"新号该有几条"未找到规则**。
所以默认走 `suggested_minimum`（1 条 `1/1/0`），客户端若因学院崩 → 用配置文件切成 9 条（§6.4）。
两种形态本地都 PASS（1 条：1 WARN；9 条：0 WARN）。

### 6.3 `RequestId` 与 `MxToken` 的来源

* `RequestId`：默认每条新生成 `uuid4`（**官方行为**：两条 24000 抓包的 RequestId 各不相同）。
  另有排查开关 `request_id_mode: "echo"`，会把客户端请求头 `REQUEST-ID` 回显——**默认不要开**。
* `MxToken`：优先级 `请求体 → SESSION.session_key（CheckNexon 下发的 64 字符 base64） → 由账号派生`。
  注意 `work\ba\server\account_service.py` 自己签发的是 **36 字符 GUID** token；
  如果哪天 24000 拿到 36 字符 token，`academy_token_is64=False` 会记进日志（不报错、不改写）。
  24000 用的一直是客户端自己带过来的会话 token，所以线上应恒为 `True`。

### 6.4 可配置项（不需要重启 bridge）

`/www/wwwroot/bapatch/academy_24000_config.json`（按 mtime 热加载，坏文件只回默认值）：

```json
{ "locations": null,               // null = 1 条(1/1/0)；给数组则按数组（含 9 条 A/B）
  "zone_scope": "service",         // service=71 键(官方集合) / account=只给本账号地点(8 键, 会 WARN)
  "last_update": null,             // null = 用生成时刻；给字符串则固定
  "request_id_mode": "fresh",      // fresh=uuid4(官方) / echo=回显请求头(仅排查)
  "default_account_id": 0 }        // 请求和会话都取不到账号时的兜底（0=不编造）
```

`python patch_24000_v2.py --dump-config` 直接打印默认版和 9 条版。

### 6.5 与同目录其它补丁的关系（`deploy\` 是共享目录）

`deploy\` 下还有别的线在改同一个 bridge，已核对过**不冲突**：

| 别的补丁 | 与 24000 的关系 |
|---|---|
| `patch_simple.py` | 自测断言里明确写着"开关全开也不接管 3 / 8000 / 90004 / **24000** / 1017"⇒ 不会抢 24000 |
| `patch_requestid.py` | 改的是**通用信封**（`cn_wire.build_plaintext` 那一层，给所有协议补 inner RequestId）；不替换 `if num == 24000:` 分支 |

本补丁的 `_ba24000_send` 自己调 `cn_wire.wrap_response(..., rid=obj['RequestId'])`，
不依赖也不冲突于信封层的改造（两边都保证 outer==inner，不会重复插入）。
**唯一需要守的次序**：任何补丁只要替换了 `if num == 24000:` 分支，之后必须重跑
`patch_24000_v2.py --apply` + `--verify`（`--apply` 会把分支和托管块一起重新对齐，幂等）。

### 6.6 本次**没有**做的验证

* **没做 bridge 端到端**：本机没有 `cryptography`，`cn_wire` 导入失败 ⇒ 起不了 bridge。
  已用等价的 `exec` 沙箱验证了 build/发送/兜底三条路径（`外层rid==内层rid PASS`），
  其中 StubCnWire 的明文构造与 `cn_wire.build_plaintext` 逐字段一致；**真 AES 那一步要在服务器上跑 `--verify`**。
* **没连服务器**（按要求）。所以 §0 里"线上生效"的判定字段（`gen_kind`/`gen_v`/`academy_*`）需要部署后看日志确认。
* `zone_visit` 只留了接口（`b24000_build(..., zone_visit=...)`），没有账号状态来源——新号全空数组是 §3.3 的结论。

## §7 部署 / 回滚命令

