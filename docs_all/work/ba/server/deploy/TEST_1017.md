### §0.1 一处口径更正（任务描述 vs spec 实测）

任务描述里写「5 个信封字段 + 25 个具名子回包 + 5 个散字段」，但列出来的名字是 **26 个子回包 + 4 个散字段**。
以 `official_spec.json` 为准（`top_key_order` 35 项、`mandatory_top_keys` 35 项）：

```
5  信封         Protocol / SessionKey / ServerTimeTicks / ServerNotification / RequestId
26 具名子回包   CafeGetInfoResponse … MultiFloorRaidLoginResponse（ItemListResponse 是 null 槽）
 4 散字段       FriendCount / FriendCode / PickupFirstGetHistoryDBs / AccountLevelRewardIds
                （官方 DTO 把它们排在 StickerListResponse 之后、MultiFloorRaid* 前后，不是全在末尾）
```

5 + 26 + 4 = 35 ✔。**子回包是 26 个，散字段是 4 个。**

### §0.2 「492 B」的准确含义

任务里说的 492 B 是**最外层 wire 口径**（HTTP body），不是 inner JSON。三层实测：

| 层 | 旧实现 | 全新号（新实现） | 官方那条 |
|---|---|---|---|
| inner JSON（compact） | **216 B**（9 键） | 83,639 / 83,804 B | 167,287 B |
| outer 明文（`{"protocol","packet","requestid"}`） | 331 B | 93,142 / 93,307 B | 185,068 B |
| **wire = base64(AES-256-CBC(outer)+32B key)** | **492 B** | 124,248 / **124,460 B** | **246,808 B** |

`492 = 4*ceil((16*ceil(331/16)+32)/3)`，与 `account_auth_probe.py:696-702` 那个固定包完全对上；
`246,808` 正是官方抓包 `meta.resp_bytes`。两个数字都能用同一套算式复现，不是估计。

## §6 WARN 全量清单（逐条解释）

**先说结论**：83 / 89 / 309 条 WARN **全部是 `WARN` 类别**（`长度越界` / `空数组首见` / `可选键缺失`），
**FAIL 一律为 0**。它们的共同原因是同一件事：**官方那条样本是玩过的号，我们的 A/B 是新号/中期号，数据少**。

三类 WARN 的判定口径（来自 `spec_check.py`）：

| 类别 | spec_check 的判定 | 为什么合法 |
|---|---|---|
| `长度越界` | 数组/map 长度不在官方观测区间 `[len_min,len_max]` | 区间只有 **1 次观测**（`observations=1`），等于把"那个号的数据量"当成了区间 |
| `空数组首见` | `empty_observations==0` 而实际给了 `[]` | 官方样本里没出现过空数组——因为官方号有进度 |
| `可选键缺失` | `always=false` 的键未出现 | proto3 可选标量的 presence 语义；官方只在**部分**实例上有值 |

### 8.5 补丁为什么是"纯插入"

```
插入 A：模块级，紧跟 return cn_cipher.wrap_packet(inner), frag 之后、class Handler 之前
         cn_1017_mode() / _gen1017_import()
插入 B：紧接着 `        if num in (1019, 1017):` 之前
         1017 且 mode != legacy → 生成 35 键并 return
         其它情况（含异常）→ 什么都不做，落到**未改动**的旧分支
```

- **不删不改任何既有行** ⇒ 不存在"改坏 if/else 链"的风险；
- **旧分支原样保留** ⇒ `--legacy` 的行为精确等于今天线上；
- `--rollback` 只要删两段 marker 块 ⇒ 逐字节回到原文件（已用 sha256 验证）。

### 8.6 RequestId 闭合（这一条最容易被做错）

`_cn_send_envelope` 自己 `uuid4()` 生成 rid、**只写进外层明文、不回填 inner**（report102 §3.6 的老问题）。
本补丁**不走** `_cn_send_envelope`：

```
_rid = uuid4()
obj  = gen1017.build(..., request_id=_rid)      →  obj['RequestId'] == _rid
wire = cn_wire.wrap_response(name, obj, _rid)   →  外层明文 requestid == _rid
```

官方实测两边**逐字节相同**（`bef95b60-6b60-419a-8844-d81f61ca0e05` 同时出现在外层 `requestid`
和内层 `RequestId`），我们的做法与之一致。

> HTTP 响应头上本来就没有 `REQUEST-ID` 头（`_send` 只发 Content-Type / Content-Length /
> Cache-Control / Connection，对**所有**协议都是如此）；客户端是从响应体**内层** `RequestId`
> 取下一条请求的 `REQUEST-ID` 的。所以"内层 = 外层明文"就是需要满足的全部条件。
