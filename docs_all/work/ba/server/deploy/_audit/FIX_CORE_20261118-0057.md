### 1.1 改了什么

`Account_CheckNexon`（`AccountHandler.cs:90`）与 `Account_CheckYostar`（`:925`）原本是同一个结构：

```csharp
else if (user.NpToken != token)
{
    user.NpToken = token;          // 覆盖写，不拒绝

```

改成（两处完全一致）：

```diff
@@ AccountHandler.cs L89-95 @@
         else if (user.NpToken != token)
         {
+            // >>> BAPATCH-TOKENGATE v1 BEGIN >>>
+            // The ticket's second field used to be written through unconditionally, so anyone holding a publisherId
+            // could present an arbitrary token and take the account over. A stored token that differs is now a
+            // rejection; an EMPTY stored token still adopts whatever arrives first, because accounts created before
+            // this gate existed carry none and must not be locked out on their next login.
+            if (Config.Instance.ServerConfiguration.EnforceTicketToken && !string.IsNullOrEmpty(user.NpToken))
+                throw new UnauthorizedAccessException("ACCOUNT_TOKEN_MISMATCH");
+            // <<< BAPATCH-TOKENGATE v1 END <<<
             user.NpToken = token;
             await db.SaveChangesAsync();
         }
```

### 1.2 三个边界怎么处理的

| 边界 | 处理 | 依据 |
|---|---|---|
| **首次登录（无 NpToken）** | 走 `user == null` 建号分支，直接写入 token（**未改动**）；即便走到 else 分支，`string.IsNullOrEmpty(user.NpToken)` 为真 ⇒ 放行并采纳 | `AccountHandler.cs:68-89`（建号）、`:97`（空值豁免） |
| **老账号 NpToken 为空串**（历史数据） | 同上，视为"尚无 token"，采纳本次并落库 ⇒ **不会被锁死** | `:97` |
| **GM 操作（`!giveall` 等）** | 完全不经过 `CheckNexon`/`CheckYostar`；`command` 走 `WebConnection.AccountServerId` 直通。**零影响** | `ManagementController.cs:445`、`WebConnection.cs:31` |
| **管理端登录** | 管理端不经票据，直接 `GET/POST /api/admin/*`，与票据无关。**零影响** | `AdminAuthAttribute` |

### 1.3 开关

```csharp
// ServerConfig.cs:65
public bool EnforceTicketToken { get; set; } = true;      // 默认开
```
- **默认 `true`**（按要求"默认开"）。
- 误伤时：**改配置文件 `Config/config.json` 里 `EnforceTicketToken: false` 并重启**，无需重编译。
- 关掉后行为 = 改前的"覆盖写"，一行代码都不用回滚。

### 1.4 影响面（必须知道）

| 场景 | 改前 | 改后 |
|---|---|---|
| 同一设备重登（token 稳定） | 通过 | **通过**（`sha256(card\|device)` 确定性） |
| 首次登录 | 通过 | **通过** |
| **换设备/重绑卡密**（token 变化） | 静默覆盖，通过 | **抛 `ACCOUNT_TOKEN_MISMATCH`** ⇒ 客户端登录失败 |
| 伪造 publisherId 登录 | **成功（高危）** | **拒绝**（有 token 的账号） |
| `Account_CheckYostar` 路径 | 同上 | 同上（两处对称修改） |

> ⚠ **换设备是本修复唯一的"可能误伤"路径**。当前桥/卡密侧换设备会得到新 token，服务端会拒绝。
> 短期处置：`EnforceTicketToken=false` 或手工更新 `UserAccounts.NpToken`。
> 长期处置（属 proto-analyst/srv-ops 范围）：**卡密侧重绑设备时同步告知服务端**（或由桥在重绑后调一个受控的 token 重置入口）。

## 2. F2 · 会话过期（P2）

### 2.1 改了什么

`SessionKeyService.GetAuthenticatedUser` 原本只查"存在 + token 一致"：

```diff
@@ SessionKeyService.cs L168-172 @@
             if (!session.Token.ToString().Equals(sessionKey.MxToken, StringComparison.OrdinalIgnoreCase))
                 throw new UnauthorizedAccessException("Session token mismatch");
 
+            // >>> BAPATCH-SESSIONTTL v1 BEGIN >>>
+            // Nothing ever expired a session: PurgeExpiredSessions exists but is called from nowhere, so a token stayed
+            // valid until something displaced it. An idle session past the configured TTL is now treated exactly like a
+            // missing one - same exception text, same client behaviour - and dropped so the persisted sidecar cannot
+            // resurrect it on the next start. SessionTtlMinutes = 0 disables the check.
+            var ttlMinutes = Config.Instance.ServerConfiguration.SessionTtlMinutes;
+            if (ttlMinutes > 0 && session.LastActivity < DateTime.UtcNow.AddMinutes(-ttlMinutes))
+            {
+                _activeSessions.TryRemove(sessionKey.AccountServerId, out _);
+                PersistSessions();
+                throw new UnauthorizedAccessException("Session expired or invalid");
+            }
+            // <<< BAPATCH-SESSIONTTL v1 END <<<
+
             session.LastActivity = DateTime.UtcNow;
```

### 2.2 关键设计点

| 点 | 说明 |
|---|---|
| **"和不存在一致"** | 用的异常文本与"会话不存在"那行**完全一致**：`"Session expired or invalid"`（`:166` vs `:181`），客户端表现不变 |
| **判据是"空闲"不是"创建"** | 用 `LastActivity`（每次成功鉴权都会刷新，`:185`），不是 `CreatedAt`；长期在线玩家不会被踢 |
| **主动剔除** | `TryRemove` + `PersistSessions`，避免重启时 `LoadPersistedSessions` 把死会话从 `sessions.json` 复活 |
| **不挡正常流程** | `GenerateSession`（`:77-123`）**不经过** `GetAuthenticatedUser`，`Account_CheckNexon → Account_Auth → LoginSync` 全链路不受影响 |
| **默认值** | `SessionTtlMinutes = 10080`（7 天）。0 = 关闭 |
| **为何不担心首启误杀** | 会话只有"7 天没发过任何请求"才会失效；`sessions.json` 里的旧记录 `LastActivity` 若超 7 天，则客户端重登（桥会重铸），行为与"服务端重启后 session 失效"一致 |

### 2.3 影响面

| 场景 | 改前 | 改后 |
|---|---|---|
| 正常在线（有请求） | 有效 | **有效**（LastActivity 持续刷新） |
| 闲置超过 7 天 | 永久有效 | **失效 ⇒ 重登** |
| 服务端重启后 | 靠 `sessions.json` 恢复 | 恢复；但若记录已超 TTL，则判失效 |
| `BAPATCH-SESSION-REUSE`（同账号复用） | 一直复用 | 复用分支会刷新 `LastActivity`（`:94`），**不受影响** |
