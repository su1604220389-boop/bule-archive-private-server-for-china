## §3 官方 1240 条 vs 新号应该多少条

### 3.1 1240 条按 Category 路由（1240/1240 全部有归属）

| Category | 落到表 | 该表行数 | 官方 08 选中 | 选中率 |
|---|---|---:|---:|---:|
| 0 | `MissionDBSchema` (f1) | 240 | 72 | 30.0% |
| 1 | `MissionDBSchema` (f1) | 60 | 12 | 20.0% |
| 2 | `MissionDBSchema` (f1) | 35 | 11 | 31.4% |
| 3 | `MissionDBSchema` (f1) | 3,084 | 379 | 12.3% |
| 4 | `GuideMissionDBSchema` (f2) | 923 | 690 | 74.8% |
| 7 | `MiniGameMissionDBSchema` (f4) | 371 | 18 | 4.9% |
| 8 | `EventContentMissionDBSchema` (f4) | 2,282 | 56 | 2.5% |
| 9 | `MissionDBSchema` (f1) | 22 | 1 | 4.5% |
| 10 | `MissionDBSchema` (f1) | 3 | 1 | 33.3% |
| **合计** | | **7,153** | **1,240** | **17.3%** |

（`MissionDBSchema` 另有 cat0 240 + cat1 60 + cat2 35 + cat3 3084 + cat9 22 + cat10 3 = 3444；
`EventContentMissionDBSchema` 另有 f4=1 的 94 行、f4=11 的 8 行；`MiniGame` 另有 f4=6 的 31 行。
这些组合官方 8000 一次都没出现，`gen8000.py` 仍按所在表路由，避免目录里有条目落不到表。）

### 3.2 为什么 1240 不能由静态表推出来

1. **同一张表、同一个 Category 内只取了一部分**：cat3 有 3084 条只出 379（12.3%），cat9 有 22 条只出 **1** 条，cat10 有 3 条只出 **1** 条。
2. **取中的 id 是离散的**，不是简单阈值：476 条 MissionDB 散布在 40 个万位段（`1502..400012`），
   `60000..62011` 一段就占 154 条，`30002..30097` 占 72 条，没有单调整数关系。
3. **357/1240 带 `Complete:true`**，`StartDate` 有 **23 个不同时间戳** —— 这些是「一段时间里发生过的事」，不是「表里有什么」。
4. 与 B 线 `initial_state_rules.json` 的 `not_found` 一致：**「首日任务进度」查不到规则**。

### 3.3 新号的答案：`empty` = 0 条 / `seed` = 29 条

| profile | ProgressDBs | inner 字节 | 依据 |
|---|---:|---:|---|
| `empty` | **0** | **382** | 任务进度是玩家状态，新号没有进度。结构合法（spec 只 WARN，见 §6） |
| `seed`（**默认**） | **29** | **4,297** | 只给**时间驱动**的那一批（见下） |

`seed` 的 29 条构成：

```
Cat 1（日常） 15 条 : 1500..1514
Cat 2（周常） 12 条 : 2300..2309 + 2399 + 2400
Cat 9（每日突发）1 条 : 1606   ← 也就是 DailySuddenMissionInfo.Id
Cat 10（周期）  1 条 : 1701
```

**为什么只给这 29 条 —— 证据**：官方 08 里 Cat 1/2/9/10 被选中的 **25 条全部** 共享
`StartDate = 2026-11-16T04:00:06.215`，而同一次抓包的 `meta.bj = 04:30:56`。
⇒ 这批记录是**当日 04:00 日重置作业**创建的，与账号练度无关。
Cat 0/3/4/7/8（共 **1,215** 条）的 `StartDate` 分散在 **22** 个不同时间点，且**没有一个等于** `04:00:06.215`
⇒ 那是历史进度，新号不该有。（1240 条合计 23 个不同 `StartDate` = 22 + 1。）

**"29 vs 1240" 不是缺陷**：官方那个号是 **32 级、通关 357 条、有 372 条历史** 的号。
新号进度全空 ⇒ 回包必然远小于 183 KB，这是**正确**的（任务见「特别注意」第 3 条）。

**取舍**：默认 `seed` 而不是 `empty`，因为任务面板里日/周常本就恒有；
但两者都 PASS，可用 `--profile empty` 一键换成 0 条。

## §6 WARN 逐条解释

`spec_check` 只有两类输出：`FAIL`（结构不符）和 `WARN`（合法但超出 3 次观测的样本范围）。
本次 4 个渲染的 WARN 一共只用到 3 个类别：

### 6.1 `WARN [可选键缺失] ProgressDBs[i].Complete`（seed 29 条 / 849 39 条 / 10838 35 条）

```
always=false 未出现 (官方观测 357/1314 次有)
```

- **含义**：`ProgressDBs[]` 的 `Complete` 是 **proto3 可选 bool**。spec 标注 `always=false`（1,314 条元素里只 357 条有），
  `seen=357 / parent_instances=1314`。
- **为什么我们没有**：`Complete` 只在该任务**已通关**时才序列化。新号一条都没通关 ⇒ 一条都不带 `Complete`。这是 proto3 的 presence 语义，不是漏字段。
- **证据**：官方 `08` 自己就有 **883** 条这个 WARN；`10`/`11` 各 39/35 条，**是这三份文件的全部 WARN**。
- **要不要消掉**：不要。硬塞 `Complete:false` 会让 spec 报 `类型不符`（`Complete` 在官方样本里只出现过 `true`），
  而且违背「默认值不序列化」的 proto3 规则。

### 6.2 `WARN [长度越界] $ .ProgressDBs`（seed 1 条 / empty 1 条）

```
数组长度 29 不在观测范围 [35,1240]
数组长度  0 不在观测范围 [35,1240]
```

- **含义**：`len_min=35 / len_max=1240` 来自 3 次观测（35 / 39 / 1240），是**样本范围**，不是约束。
- **为什么越界**：新号只有 29 条（`seed`）或 0 条（`empty`）—— 3 次观测都来自同一个 32 级号，**从没覆盖过新号**。
- **结论**：合法。这正是 §3.3 说的「新号回包远小于 183 KB 是正常的」在 spec 层的表现。

### 6.3 `WARN [空数组首见] $ .ProgressDBs`（仅 `empty`，1 条）

```
官方样本中未出现空数组
```

- **含义**：`empty_observations=0` —— 3 次观测里 `ProgressDBs` 从没空过。
- **为什么空**：`--profile empty` 刻意给 0 条。
- **风险**：这是本方案里**唯一没有官方样本支撑**的形态。若上机后发现任务页异常，把它换成 `--profile seed`（29 条）即可；
  代码里已把两者都做成合法路径，`seed` 也不触发这条 WARN。
- **注意**：`MissionHistoryUniqueIds` / `ClearedOriginalMissionIds` 是 `[]` 时**不会**触发这条
  （`empty_observations=2`，官方 10/11 本来就是空数组）。

### 6.4 没有出现的 WARN

- `WARN [键名形态]`（map<int_str> 出现非数字键）：**0 条** —— `ProgressParameters` 的 key 全是数字串（`"0"` / `"849"` / `"8492301"` / `"10838"`）。
- `WARN [类型不符] ... spec=float, 实际=int`：**0 条** —— 8000 里没有 float 字段。

## §7 幂等与性能

任务要求：「8000 在大厅里会被反复调用（抓包里 3 次），服务端必须幂等且快」。

### 7.1 幂等的精确定义与实测

官方自己 3 次调用（04:30:56.292 / .839 / 04:30:57.167）里，`SessionKey` 完全相同，
`ServerTimeTicks` 与 `RequestId` 每次都不同，`ProgressDBs` 内容相同。**所以「幂等」在这里只能是：
除 `ServerTimeTicks` / `RequestId` 外逐字节相同。**

| 检查 | 结果 |
|---|---|
| 同 `--now` + 同 `--request-id` 跑两次 | **byte-identical = True**（三个变体全部） |
| 只改 `RequestId` | 差异键 = `['RequestId']`，**仅此一个** |
| 同一天不同时刻（04:30 / 23:59 / 次日 00:00） | `StartDate` 恒定 `2026-11-16T04:00:04.291`，inner 恒为 4,297 B |

关键设计：`StartDate` **不用 `now()`**，而是「当日 04:00 日重置点 + 账号派生常数毫秒」
（`sha256("ba8000:startdate:<id>")` 取 1~21 秒），所以同一天任意次调用都同值，且形态贴合官方 `04:00:06.215`。

### 7.2 性能

- 目录构建：7,153 行 × 一次 vtable 查表 → 实测 **< 0.2 s**（进程启动一次）。
- 之后每次请求是纯内存过滤：
  - 事件变体：`by_event[N]` 直接命中 + 一次切片 → O(k)，k=35/39。
  - 全量 `seed`：遍历 7,153 条比对区间 → 微秒级。
- 服务端部署形态（`patch_8000.py` 注入的 block）把目录预导出成 144 KB 的
  `8000_catalog.json`，**按 mtime 缓存**（文件不变就不重解析），每次请求只做一次列表推导。

### 8.4 独立开关文件（`8000_switch.json`）

与 bridge 同目录，**运行时按 mtime 热读**，改完立刻生效、不用重新打补丁也不用重启：

```json
{
 "_comment": "Mission_List(8000) 运行时开关。改 enabled 后立刻生效，无需重启。",
 "enabled": true,
 "profile": "seed",
 "reset_hour": 4,
 "daily_sudden_id": 1606,
 "max_progress": 5000
}
```

| 键 | 作用 |
|---|---|
| `enabled` | `false` ⇒ 分支不委托，落回 bridge 原有处理（最快的失灵开关） |
| `profile` | `seed`（29 条）/ `empty`（0 条） |
| `reset_hour` | 日重置小时，默认 4 |
| `daily_sudden_id` | `DailySuddenMissionInfo.Id`，默认 1606（3 份抓包恒为此值） |
| `max_progress` | 安全阀，单次回包上限条数（防目录异常产生巨包） |

### 8.5 本地演练记录（真实执行，目标 `%TEMP%\ba8000_fixture\`）

用一个合成的 bridge 副本（**不是真 bridge**，没有 `_bridge_ref` 参与）跑完整周期：

```
--dry-run   → 打印 unified diff（新增 block 247 行 + 分支 13 行），不写任何文件
--apply     → 备份 .bak.20261116_052406 / sha e3965147 → 44f6e34e / 分支 inserted
             目录 7153 条 written / 开关 written
--apply     → "目标已是最新，逐字节 no-op（不备份、不写）"        ← 幂等
--verify    → [1/6] 语法 OK  [2/6] block 行 16..262（247 行）  [3/6] 分支 272..284 委托=是
             [4/6] 目录 7153 条 格式 OK  [5/6] 开关 enabled=true
             [6/6] full/seed 29 · full/empty 0 · event 849 39 · event 10838 35
                   四个变体 spec_check 全 PASS
             verify: PASS   ← exit 0
--disable   → 开关变 enabled=false；再跑一次 → unchanged（幂等）
--rollback  → 依据"找到不含 managed block 的原件 .bak.20261116_052406"
             还原后仍有 block: 否（干净）；block 与分支都不在了
--apply     → 往返回来 sha 仍为 c8ab7d54（补丁输出确定）
BOM          → 目标文件原有 BOM 被保留（239,187,191）
```

> 演练中发现并修掉的两个真 bug（都已改）：
> ① 默认开关字典用 `json.dumps` 嵌进 Python 源码 → `NameError: name 'true' is not defined`（改用 `repr`）；
> ② `--rollback` 原来取「最新备份」= 上一个补丁版，会**回滚不干净**（改成往回找第一个不含 BEGIN 标记的原件）。
> 另外补了 BOM（`utf-8-sig`）处理，否则 Windows 上编辑过的 bridge 直接 `compile()` 会报 `U+FEFF`。
